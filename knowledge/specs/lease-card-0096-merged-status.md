# Спецификация: зафиксировать слияние устойчивого lease в карточке

## Цель и влияние на владельца

Текущая продуктовая задача является дубликатом уже влитой реализации: lease
длится 30 секунд, первый heartbeat планируется через 10 секунд, а sweeper
запускается каждые 5 секунд. Владельцу не нужно запускать повторную реализацию
или новый прогон продуктовой задачи. Нужна только точная карточка, чтобы статус
не создавал впечатления, что изменения всё ещё ожидают ручного слияния.

После документирования `CARD-0096` будет показывать, что работа уже в `main`,
и будет ссылаться на фактический implementation commit
`5f0ab88e825a32667431e041ade3d262fe23ff25`, а не на промежуточный коммит
прошлого процесса.

## Технический подход и реальные файлы

Продуктовый код уже реализован коммитом
`5f0ab88e825a32667431e041ade3d262fe23ff25` и находится в свежем `main`.
Он изменил `internal/worker/attempt_lifecycle.go`,
`internal/controlplane/state.go` и их регрессии, а также `ARCHITECTURE.md` и
`docs/worker.md`. Эта работа не меняет ни один из этих файлов.

Следующий небольшой документационный этап изменит только
`knowledge/cards/CARD-0096-batch-lease-expiry-resilience.md`:

- заменит `Status: Verified PASS — awaiting human merge.` на статус, прямо
  фиксирующий слияние в `main`;
- заменит обе ссылки на прежний implementation commit фактическим полным SHA
  `5f0ab88e825a32667431e041ade3d262fe23ff25`;
- удалит формулировку об ожидании ручного merge и действие по ручному слиянию;
- сохранит исторические результаты проверок и описание реализованного
  поведения без переинтерпретации продуктового решения.

Миграции, UI, API, настройки lease, heartbeat, sweeper и тесты исходников не
меняются. Эта спецификация и отдельная карточка описывают только передачу
документационной работы.

## Последовательный план

1. Сверить, что implementation commit присутствует в свежем `main` и содержит
   продуктовые изменения вне `knowledge/cards/`.
2. Открыть `CARD-0096` и заменить устаревшие статус и implementation commit
   ровно на подтверждённые значения.
3. Убрать только фразы `awaiting human merge` и следующий ручной merge; не
   менять LOG с доказательствами прежних этапов.
4. Проверить diff карточки на отсутствие продуктовых файлов и на единообразие
   полного SHA.

## Критерии приёмки

1. `CARD-0096` недвусмысленно говорит, что реализация влита в `main`; фразы
   `awaiting human merge` и указание на будущую ручную заливку отсутствуют.
2. Заголовочная строка и поле HEAD карточки содержат полный SHA
   `5f0ab88e825a32667431e041ade3d262fe23ff25` как implementation commit.
3. Изменён только `knowledge/cards/CARD-0096-batch-lease-expiry-resilience.md`;
   product code, UI и прежняя спецификация не затронуты.
4. Существующие сведения о 30-секундном lease, первом heartbeat через 10 секунд
   и sweep каждые 5 секунд остаются документально согласованными с реализацией.

## Тест-план

- Выполнить точечную документальную проверку, которая требует наличие полного
  implementation SHA, статуса слияния в `main` и отсутствие фразы `awaiting
  human merge` в `CARD-0096`.
- Проверить `git diff --check`.
- Продуктовые Go-тесты не запускать повторно: код уже в `main`, а задача не
  меняет исходники. В качестве исторического подтверждения сохраняются
  регрессии из карточки и реализационный коммит.

## Риски и решения

- Подмена фактического коммита промежуточным хешем исказит provenance. Решение:
  записывать только полный SHA уже влитого implementation commit.
- Редактирование исторического LOG может скрыть результаты прошлых этапов.
  Решение: менять лишь HEAD-поля и устаревшее следующее действие.
- Повторная реализация способна создать конфликт или регрессию. Решение:
  scope ограничен одной карточкой; любые файлы вне неё — причина остановить
  документационный этап.
