# Factory честно говорит, готов ли новый проект к работе

## Цель и влияние на пользователя

После добавления GitHub-репозитория владелец сразу видит честный вердикт: проект
уже проверен на одном из воркеров, может быть получен по требованию, но ещё не
проверен реальной работой, либо сейчас заблокирован. Factory больше не называет
новый проект «готовым» только потому, что здоровый воркер в принципе умеет
клонировать репозитории с GitHub.

Это позволяет владельцу отличить подтверждённую готовность от обещания первой
попытки и не запускать важную работу, ошибочно считая доступ к новому приватному
репозиторию уже проверенным.

## Технический подход

Сохранить действующий серверный контракт. `internal/controlplane/store.go`
обоснованно выставляет `routing_ready`, когда хотя бы один воркер проходит текущие
проверки маршрутизации: online/healthy, доступ к GitHub, поддержка managed
acquisition, свободный cache и retention. В ответе уже есть достаточные факты по
каждому воркеру: `ready`, `cached` и `advertised` из
`internal/protocol/types.go`. При этом для нового репозитория `ready=true` может
означать только наличие cache headroom; конкретный репозиторий ещё не был
получен, а `gh repo clone` выполняется позднее в подготовке первой попытки.

В `web/src/Repositories.tsx` ввести небольшую чистую классификацию отображаемого
состояния:

- `verified`: есть готовый воркер, у которого репозиторий `cached` или
  `advertised`;
- `unverified`: готового знакомого с репозиторием воркера нет, но хотя бы один
  воркер имеет `ready=true` и может попробовать managed acquisition;
- `blocked`: сервер не нашёл ни одного готового маршрута;
- `disabled`: маршрутизация репозитория выключена.

Баннер и строки воркеров должны использовать эту классификацию. Для `verified`
показать подтверждённую готовность; для `unverified` — что первый запуск ещё
проверит доступ и клонирование; для `blocked` оставить причины сервера; для
`disabled` сохранить нынешнее объяснение. Не менять `routing_ready`: это
маршрутизационный факт, а не доказательство успешного получения исходников.

Добавить отдельный `web/src/Repositories.test.tsx` для табличной проверки чистой
классификации и обновить интеграционные ожидания в `web/src/App.test.tsx`, чтобы
сценарий нового uncached-проекта не принимал возможность acquisition за готовый
проект. В `docs/local.md` пояснить различие между доступным маршрутом и
подтверждённой готовностью.

Изменений БД, миграций и HTTP API нет.

## План

1. Вынести в `web/src/Repositories.tsx` вычисление четырёх состояний из
   `enabled`, `routing_ready` и существующих worker facts.
2. Переписать заголовок и пояснение readiness-баннера так, чтобы подтверждённый,
   непроверенный, заблокированный и выключенный проекты не смешивались.
3. В строках воркеров заменить безусловное `Ready` для uncached/unadvertised
   кандидата на честную подпись возможности получить репозиторий.
4. Добавить модульные сценарии классификации и интеграционный сценарий сразу
   после добавления нового репозитория; сохранить проверки переключения routing.
5. Обновить локальную документацию о первой проверке доступа при подготовке
   задания.

## Критерии приёмки

1. Новый включённый репозиторий с подходящим, но ещё не знакомым с ним воркером
   не содержит утверждения «готов»: экран сообщает, что воркер может получить
   проект, а доступ и клонирование подтвердит первый запуск.
2. Если хотя бы один `ready`-воркер сообщает репозиторий как `cached` или
   `advertised`, экран однозначно сообщает, что проект проверен и готов к работе.
3. Если `routing_ready=false`, экран сообщает, что проект сейчас не готов, и
   сохраняет конкретные причины для каждого воркера из ответа сервера.
4. Выключенный репозиторий независимо от worker facts показывает, что routing
   выключен и новые задания отклоняются до включения.
5. Смешанный список воркеров не завышает готовность: непроверенный кандидат не
   увеличивает число подтверждённо готовых воркеров, а cached/advertised ready
   кандидат увеличивает.
6. Фоновое обновление readiness переводит экран из `unverified` в `verified`,
   когда воркер начинает сообщать репозиторий как cached, без перезагрузки
   страницы и без изменения API.

## План проверки

- Новый `web/src/Repositories.test.tsx`: все четыре состояния, приоритет
  `disabled`, смешанные worker facts и переход `unverified` → `verified`.
- `web/src/App.test.tsx`: добавление нового проекта показывает непроверенное
  состояние; существующий cached/advertised проект показывает подтверждённую
  готовность; toggle сохраняет `disabled`-состояние.
- Обязательная целевая команда: `npm --prefix web test -- --run
  src/Repositories.test.tsx src/App.test.tsx`.
- Перед сдачей реализации: `npm --prefix web run typecheck` и
  `git diff --check`. Полный набор остаётся единственным прогоном на Verify.

## Риски и решения

- Решение намеренно не проверяет GitHub по сети при добавлении проекта. Такая
  проба потребовала бы выбрать воркер, передавать новый результат через heartbeat
  и определять время жизни проверки; это отдельная функция, а не минимальная
  правка честности интерфейса.
- `cached`/`advertised` доказывает, что воркер знает checkout, но не гарантирует,
  что следующий `fetch` никогда не упадёт. Текст должен говорить о проверенной
  готовности Factory, а не обещать доступность внешнего GitHub.
- Альтернатива изменить значение `routing_ready` отклонена: это сломало бы
  on-demand маршрутизацию нового проекта, хотя воркер штатно умеет клонировать его
  при первой работе.
- Вне области: автоматическая тестовая задача после регистрации, хранение
  истории проверок, repository-specific permission probe и изменение формы
  создания проекта.
- Перед реализацией не требуется продуктового решения, если владелец согласен,
  что «проверен» означает cached/advertised на готовом воркере. Если требуется
  именно свежая сетевая проверка прав GitHub, область нужно расширить отдельной
  задачей.
