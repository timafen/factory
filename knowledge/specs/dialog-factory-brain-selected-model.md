# Экран «Диалог»: разговор с мозгом фабрики на выбранной модели

## Цель и влияние на пользователя

Владелец открывает `/dialog`, выбирает одну из моделей действующей `brain_chain`
и ведёт с ней многоходовый разговор, не покидая интерфейс Factory. В ответе
видно человеческое имя модели; ошибки лимита, таймаута и недоступного CLI не
стирают уже показанную переписку и допускают повторную отправку.

MVP не создаёт работу в pipeline и не хранит разговор после перезагрузки: это
оперативный разговор с мозгом фабрики, а не новый журнал задач.

## Технический подход

- Добавить в `internal/protocol/types.go` запрос с `model` и ограниченной
  последовательностью сообщений ролей `user`/`assistant`, а также ответ с
  текстом и словесно подписанной моделью. Голые внутренние ID в UI не выводить.
- Добавить `POST /api/v1/dialog/messages` в `internal/controlplane/http.go` и
  отдельный `internal/controlplane/dialog_http.go`. Обработчик читает актуальный
  `PilotConfigStore`, принимает модель только при точном совпадении с записью
  `brain_chain`, проверяет роли, непустой последний вопрос, число сообщений и
  общий размер, затем вызывает runner с серверным таймаутом. Произвольные CLI,
  аргументы и model от клиента в процесс не попадают.
- Runner получает выбранный `PilotBrain` и сериализованную историю. Для `codex`
  он повторяет действующий контракт `pilot/pilot.py`: `codex exec -m <model>
  --skip-git-repo-check -`; для `claude`: `claude -p <prompt> --output-format
  text` с `ANTHROPIC_MODEL`. Исполнение идёт в настроенном сервером каталоге и
  окружении, stdout ограничен; stderr не возвращается браузеру. Интерфейс runner
  внедряется в API, чтобы HTTP-тесты не запускали реальные модели.
- Добавить типы и вызов в `web/src/types.ts` и `web/src/api.ts`, экран
  `web/src/Dialog.tsx`, маршрут и пункт «Диалог» в `web/src/App.tsx`, стили в
  `web/src/styles.css`. Список моделей берётся из уже существующего
  `GET /api/v1/settings/pilot`; выбор по умолчанию — первая запись цепочки.
  `Dialog.tsx` хранит сообщения только в React state, блокирует повторную
  отправку на время запроса, поддерживает Enter/Shift+Enter и доступные labels.

Изменений БД и миграций нет. Потоковой выдачи, Markdown/HTML-рендеринга,
вложений, нескольких сохранённых чатов и автоматического fallback в MVP нет.

## План

1. Зафиксировать protocol-типы, лимиты и injectable runner для двух уже
   поддерживаемых CLI.
2. Реализовать и зарегистрировать endpoint, allowlist выбранной модели,
   таймауты и безопасное отображение ошибок.
3. Добавить API-типы, `/dialog`, навигацию и состояния загрузки/ошибки/повтора.
4. Добавить целевые Go- и Vitest-проверки, затем прогнать сборку и полный Go-набор.
5. На Implement/Verify обновлять `knowledge/cards/CARD-0034-dialog-factory-brain.md`.

## Критерии приёмки

1. На `/dialog` видны модели из текущей `brain_chain`; первая выбрана по
   умолчанию, другую можно выбрать до отправки вопроса.
2. Вопрос уходит именно выбранной настроенной модели, ответ добавляется в
   переписку с её словесной подписью, а следующий запрос содержит предыдущие
   реплики в исходном порядке.
3. Пустой вопрос не отправляется; во время ожидания нельзя создать два запроса.
4. Неизвестная модель, неверные роли и превышение лимитов отклоняются до запуска
   процесса; клиент не может подменить CLI или его аргументы.
5. Таймаут, пустой ответ или сбой CLI показаны по-русски; история и введённый
   вопрос сохраняются, после ошибки доступен повтор.
6. Обновление страницы начинает чистый разговор; задачи, карточки и pipeline не
   создаются и не изменяются.

## План тестирования

- `internal/controlplane/dialog_http_test.go`: выбранная модель и полная история
  доходят fake runner; неизвестная модель/роль/oversize не запускают runner;
  timeout и ошибка получают стабильные HTTP-коды без утечки stderr.
- `web/src/Dialog.test.tsx`: модели из настроек, выбор второй модели,
  многоходовая история, блокировка двойной отправки и retry после ошибки.
- Обязательные проверки реализации: целевой Go+Vitest тест ниже, `go test ./...`,
  `cd web && npx tsc -p tsconfig.app.json --noEmit && npx vite build`.

## Риски и решения

- Синхронный HTTP-запрос удерживает соединение до ответа модели. Для MVP выбран
  малый серверный таймаут; streaming/SSE требует отдельного контракта.
- Передача полной истории увеличивает prompt. Нужны серверные лимиты; обрезать
  историю молча нельзя.
- Control Plane получает право запускать два известных CLI. Реализация должна
  использовать массив аргументов, фиксированный cwd/env и allowlist из конфига,
  а не shell. Возможность произвольного `cli` в настройках здесь не расширяется.
- Нужно человеческое подтверждение продуктовой границы: переписка не переживает
  reload и запрос не использует fallback-цепочку. Персистентность и fallback —
  отдельный scope после MVP.
