# Экран «Автоматизация»: единый живой статус всех автоматик

## Цель и влияние на владельца

Владелец открывает один экран и видит все запущенные Фабрикой автоматики, включая
pilot/«мозг», release broker, службы выката и janitor. Для каждой записи понятны
название, источник, последняя попытка с объяснением результата, время обновления и
одно из русских состояний «живая», «стоит» или «сломана». Просроченный heartbeat,
проверка или запуск выделяются красным; отсутствие данных показывается явно, а не
выглядит как исправная автоматика.

## Технический подход и реальные файлы

Сделать на control-plane серверную projection `AutomationStatus`: она объединяет
durable пользовательские Automations из SQLite с read-only снимками внутренних
автоматик из существующих источников состояния pilot, brain chain, release broker,
deploy и janitor. Каждый источник обязан вернуть стабильный ключ, owner-facing
название, тип, `last_seen`, deadline/heartbeat, состояние, последний результат с
пояснением и диагностикой отсутствия данных. Нельзя считать отсутствие записи
успехом; stale определяется сервером по типу автоматики и возвращается отдельным
признаком просрочки.

Добавить отдельный API-ресурс, например `GET /api/v1/automation-status`, с полной
пагинацией и временем снимка. Не ломать существующие CRUD `/automations`; при
ошибке одного внутреннего источника отдавать его запись как «нет данных», сохраняя
остальные записи. Ответ не должен содержать служебные ID или сырые секреты.

Реальные точки интеграции текущего кода: `internal/controlplane/automations.go`
и `internal/controlplane/automations_http.go` (хранение и HTTP),
`internal/protocol/types.go` (контракт), `internal/controlplane/pilot_config.go`
и `internal/controlplane/pipeline_patrol.go` (pilot и патруль), а также существующие
источники release/deploy/janitor, которые нужно определить по их durable журналам
до реализации. UI находится в `web/src/Automations.tsx`, типы и запросы —
`web/src/types.ts` и `web/src/api.ts`; маршрут уже подключён в `web/src/App.tsx`.
Целевые проверки следует добавить в `internal/controlplane/automations_test.go`,
`web/src/App.test.tsx` и при необходимости отдельные fixture-тесты источников.

## Последовательный план

1. Инвентаризировать и назвать все внутренние источники и их heartbeat/result
   журналы; зафиксировать TTL для каждого типа.
2. Описать protocol-модель и серверный адаптер снимка с изоляцией ошибок источников.
3. Реализовать объединение с пользовательскими Automations, сортировку, пагинацию,
   перевод статусов и вычисление красной просрочки на сервере.
4. Подключить API и обновить экран: русские labels, источник, last result/message,
   `Обновлено`, stale-красный маркер и состояние «нет данных».
5. Добавить целевые Go/UI-тесты, проверить сборку web и ручной экран `/automations`.

## Критерии приёмки

- Один запрос и один экран показывают пользовательские и все внутренние автоматики:
  pilot, brain, release broker, deploy services и janitor; ни одна категория не
  исчезает при пагинации или временной ошибке другого источника.
- Для healthy/running, остановленного и ошибочного источника UI показывает ровно
  «живая», «стоит», «сломана»; неизвестное или отсутствующее состояние — «нет данных».
- Последний результат содержит человекочитаемое объяснение, а не только код,
  timestamp или внутренний идентификатор.
- Просроченный heartbeat/проверка/запуск имеет красную индикацию и доступное
  пояснение; свежий результат красным не помечается.
- Обновление экрана получает новый снимок без ручного reload; сбой одного источника
  не маскирует данные остальных и не превращается в «живая».
- Существующие CRUD, включение/выключение и детальная история Automations не
  регрессируют.

## Тест-план

- Go: fixture на каждый внутренний источник, смешанный snapshot, source timeout,
  отсутствующий журнал, stale threshold, перевод трёх русских состояний и полный
  последний result message; проверить сортировку и пагинацию API.
- UI: проверить все категории на одном экране, «нет данных», красную просрочку,
  понятный последний результат и обновление polling без потери фильтров.
- Обязательная проверка спецификации: `git diff --check origin/main...HEAD`.
- Дополнительно: `npm --prefix web run test -- --run App.test.tsx` и
  `npm --prefix web run typecheck`.

## Риски и решения

- Журналы внутренних служб имеют разные форматы и TTL: использовать адаптер на
  источник и явную метку `data_unavailable`, не общий эвристический parser.
- Частичное чтение журналов может дать старый результат: передавать `last_seen` и
  считать запись stale по серверному времени, с тестом на границе TTL.
- Много polling-источников может нагрузить control-plane: собирать снимок одним
  серверным циклом/кэшем с коротким TTL, не делать N+1 запросов из браузера.
- Русские подписи не должны менять машинные enum: хранить стабильные коды и
  локализовать только в projection/UI.
