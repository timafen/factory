# Спецификация: вопросы об административных правах сначала решает старшая модель

## Цель и влияние на владельца

Технический вопрос, для ответа на который требуется разрешённая административная
операция, не должен сразу останавливать работу и попадать владельцу. Старшая
модель сама выбирает и выполняет допустимое действие через существующий мост
`sudo -n /usr/local/bin/fx`, получает его результат и продолжает работу либо
формирует обоснованную эскалацию.

Владелец по-прежнему является единственным источником решения, когда операция
не предусмотрена `fx`, относится к production, секретам, тратам или
необратимому изменению. Нового канала произвольных root-команд не появляется:
модель не получает shell/root и не может обойти включённые владельцем права.

## Технический подход и реальные файлы

- `pilot/pilot.py`: `route_question()` сейчас вызывает `orchestrator_answer()`,
  но последний возвращает только `answer`/`wait`/`escalate`; `brain()` запускает
  CLI модели без механизма выполнения. Добавить ветку `admin_action`:
  старшая модель возвращает структурированное намерение (`scope`, `verb`,
  допустимый подвид и аргументы), Pilot валидирует его кодом и вызывает
  `_fixed_command()` с argv `sudo -n /usr/local/bin/fx ...`, без shell.
- `pilot/pilot.py`: описать в prompt точную политику: для безопасного staging
  можно просить только операции из `ops/fx`; `prod`, `factory`-release,
  секреты, расходы, удаление/восстановление и неизвестная операция всегда
  требуют `escalate`. После выполнения передать модели код возврата и
  сокращённый вывод для решения `answer`, `wait` или `escalate`; сам вывод не
  считать разрешением на следующую root-команду.
- `ops/fx`: не менять. Его root-owned список команд, разбор аргументов,
  `policy.json` и `access.json` остаются окончательной границей. Pilot дублирует
  лишь более узкий allowlist для намерений, чтобы не дать модели передать
  произвольные аргументы в уже безопасный посредник.
- `pilot/pilot.py`: сохранять в JSON вопроса признаки `authority: "admin"`,
  предложенное действие, результат (`executed`/`denied`/`failed`) и причину
  эскалации. Запись с `owner_only: true` создавать только после отказа модели
  либо запрещённого/неуспешного действия; auto-resolved запись остаётся с
  `answered_by: "orchestrator"` и проверяемым аудитом.
- `internal/controlplane/questions_http.go` и
  `internal/controlplane/questions_http_test.go`: список вопросов должен
  выдавать владельцу только действительно открытые owner-эскалации; техническая
  admin-попытка и её служебные детали не маскируются под владельческий вопрос.
- `pilot/test_pilot.py`: добавить изолированные регрессии маршрута и argv.

Узкий allowlist Pilot включает только безопасные staging-диагностики и
восстановимые исправления, уже реализованные в `ops/fx`: `status`, `health`,
`restart` с известным unit, `manage check`, `manage showmigrations`,
`manage collectstatic`, sandbox-поддействия только с обязательным `--dry-run`,
`env-names` и `release-info`. `manage migrate`, sandbox без `--dry-run`, любой
`--force`, `staging release`/`rollback`, любой `prod`, `factory`, `repo put`,
произвольный `manage` или нераспознанный аргумент не исполняется и передаётся
владельцу до запуска. Отказ `fx` из-за выключенного доступа — не повторять и
эскалировать с понятной причиной.

## Последовательный план

1. Ввести типизированный разбор и validation admin-намерения, формирующий
   исключительно фиксированный argv `fx`.
2. Расширить ответ старшей модели и её prompt: сначала самостоятельно
   диагностировать/исполнить разрешённый staging-action, затем оценить его
   результат; явно перечислить владелецкие границы.
3. Связать выполнение с `route_question()`: вести audit в вопросе, продолжать
   pipeline при решении модели и создавать owner-вопрос только для допустимого
   fallback.
4. Отфильтровать служебные admin-записи из owner-list API, сохранив настоящие
   открытые эскалации и обратную совместимость старых JSON без `authority`.
5. Добавить целевые unit/HTTP тесты и выполнить обязательную команду.

## Критерии приёмки

1. Вопрос о разрешённом staging-действии сначала получает старшая модель; при
   валидном `admin_action` Pilot вызывает только `sudo -n /usr/local/bin/fx` с
   кодовым argv, а не shell-командой от модели.
2. Успех действия и последующий ответ модели помечают вопрос решённым и
   возобновляют работу без карточки «Нужен твой ответ» у владельца.
3. `fx`-отказ, неизвестная операция и любой запретный scope/verb не выполняют
   повторных или произвольных команд; владельцу видна причина эскалации.
4. Продакшн, секреты, траты и необратимые действия всегда идут владельцу до
   исполнения, даже если модель сформировала JSON действия. В частности,
   `manage migrate`, sandbox без `--dry-run` и sandbox с `--force` не должны
   доходить до `_fixed_command`; `collectstatic` остаётся разрешённым.
5. Старые owner-вопросы и обычные auto-answer продолжают работать; API не
   выдаёт служебную admin-запись как ожидающую решения владельца.
6. Тест доказывает точный `sudo -n /usr/local/bin/fx staging ...` argv и
   отсутствие вызова для запрещённого входа.

## Тест-план

- В `pilot/test_pilot.py` замокать `_fixed_command` и `brain`: разрешённый
  `staging health` должен быть один раз вызван фиксированным argv, а результат
  должен привести к auto-resolve без `notify(... «Нужен твой ответ» ...)`.
- Проверить по одному отрицательному случаю для `prod`, `repo put`, неизвестного
  аргумента и выключенного доступа: `_fixed_command` не получает опасный argv,
  а JSON имеет `owner_only` и понятную `escalation_reason`.
- Проверить, что `manage migrate`, реальное создание sandbox-данных и `--force`
  эскалируются до `_fixed_command`, а `manage collectstatic` и sandbox
  `--dry-run` сохраняют точный фиксированный argv.
- Проверить повторный разбор после неудачи `fx`: результат первой операции
  передаётся модели, но второй action без нового route не выполняется.
- В `internal/controlplane/questions_http_test.go` создать открытый owner-вопрос
  и admin-аудит; `GET /api/v1/questions` возвращает только owner-вопрос.
- Новый тест
  `AdminQuestionRoutingTests.test_allowed_staging_health_is_resolved_by_orchestrator_before_owner`
  одним сценарием фиксирует главный контракт: старшая модель возвращает
  `admin_action`, Pilot ровно один раз вызывает фиксированный argv
  `sudo -n /usr/local/bin/fx staging health`, принимает итоговый ответ модели и
  не создаёт owner-only вопрос. До реализации этот тест обязан быть красным,
  после реализации указанная ниже обязательная команда завершается кодом 0.
  Отрицательные случаи и HTTP-фильтр остаются отдельными целевыми тестами;
  дополнительно выполнить их и `git diff --check`.

## Риски и решения

- Модель может попытаться подменить argv. Решение: JSON парсится в
  allowlist-структуру, аргументы проходят те же ограничения формата, а
  `subprocess` получает список аргументов без `shell=True`.
- Список Pilot и `ops/fx` может разойтись. Решение: `ops/fx` остаётся
  authoritative и final deny; Pilot разрешает только консервативное подмножество
  и имеет регрессию на каждый допустимый шаблон.
- Результат админ-действия может содержать чувствительные данные. Решение:
  автоматический allowlist не содержит `logs`, потому что произвольный журнал
  нельзя надёжно очистить от всех секретов; `env-names` оставляет только имена.
- Автоматический restart/release способен ухудшить среду. Решение: restart
  ограничен staging unit-ами, а любые release/rollback остаются owner-only;
  `fx` журналирует каждую попытку с worktree.
- Миграция либо создание/перезапись sandbox-данных могут быть необратимы.
  Решение: `manage migrate`, sandbox без `--dry-run` и любой `--force` удалены
  из автоматического allowlist; перед их запуском требуется решение владельца.
- Сбой `fx` не означает, что доступ можно открыть автоматически. Решение:
  `denied` фиксируется как terminal escalation, менять grants может только
  владелец через существующую политику.
