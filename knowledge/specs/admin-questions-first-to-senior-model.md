# Спецификация: административные вопросы сначала решает старшая модель

## Цель и влияние на владельца

Перенести в свежий `main` готовую поставку CARD-0116, не вливая накопленную
историю её ветки. После переноса безопасный технический вопрос о staging сначала
обрабатывает старшая модель через ограниченный посредник `fx`; владельцу остаются
только решения, которые действительно требуют его полномочий. Это сокращает
лишние остановки работы, не открывая модели доступ к произвольным root-командам.

Необратимые действия, production, секреты, расходы, `manage migrate`, sandbox
без `--dry-run` и любой `--force` по-прежнему эскалируются до запуска.

## Технический подход и реальные файлы

- `pilot/pilot.py` — добавить структурированное `admin_action` в ответ
  оркестратора, консервативно превратить его в фиксированный argv
  `sudo -n /usr/local/bin/fx staging ...`, записать аудит результата и повторно
  запросить решение модели. Запрещённый или неуспешный вызов создаёт
  owner-only эскалацию.
- `pilot/test_pilot.py` — закрепить точный argv разрешённого `staging health`,
  отсутствие owner-вопроса и отрицательные случаи до выполнения команды.
- `internal/controlplane/questions_http.go` — не показывать в списке вопросов
  владельца служебные записи `authority: "admin"`, если они не помечены
  `owner_only`.
- `internal/controlplane/questions_http_test.go` — проверить, что admin-аудит
  отфильтрован, а обычный открытый вопрос остаётся в ответе API.

`ops/fx` не меняется: его владелец-управляемая политика остаётся окончательной
границей. Pilot разрешает лишь более узкое подмножество и никогда не использует
shell для аргументов модели.

## Последовательный план

1. Перенести из коммита поставки только четыре продуктовых файла и целевые
   тесты, исключив независимые коммиты ветки.
2. Сопоставить admin-намерение с allowlist и сформировать argv без shell.
3. Связать успешный результат с повторным ответом старшей модели, а отказ — с
   понятной owner-only эскалацией и аудитом JSON.
4. Скрыть завершённый служебный admin-аудит из HTTP-списка владельца.
5. Запустить целевые Python- и Go-проверки и проверить состав diff относительно
   свежего `origin/main`.

## Критерии приёмки

1. Разрешённый `staging health` вызывается ровно один раз фиксированным argv
   `sudo -n /usr/local/bin/fx staging health` и после ответа модели не создаёт
   owner-only вопрос.
2. Запрещённые scope/verb и необратимые действия не вызывают `_fixed_command`;
   владельцу записывается причина эскалации.
3. `collectstatic` и sandbox только с `--dry-run` остаются в разрешённом
   подмножестве; `migrate`, sandbox без `--dry-run` и `--force` — нет.
4. API не возвращает служебный admin-аудит как вопрос владельца, но не скрывает
   настоящую owner-эскалацию.
5. Перенос ограничен четырьмя файлами реализации, двумя целевыми тестовыми
   файлами (в тех же путях) и документами CARD-0116.

## Тест-план

- `python3 -m unittest pilot.test_pilot.AdminQuestionRoutingTests` проверяет
  разрешённый маршрут, запреты, аудит и отсутствие уведомления владельцу.
- `go test ./internal/controlplane` проверяет HTTP-фильтр вместе с пакетом.
- `git diff --check` выявляет ошибки пробелов, а
  `git diff --name-only origin/main...HEAD` подтверждает минимальную область.

## Риски и решения

- Модель подменяет аргументы: JSON валидируется allowlist, а subprocess получает
  только список аргументов без `shell=True`.
- Политики Pilot и `fx` расходятся: `fx` остаётся последним запретом, Pilot
  допускает только более узкий список и имеет регрессии на границе.
- Вывод команды содержит чувствительные данные: журналы не входят в allowlist,
  а результат ограничивается перед повторной передачей модели.
- В перенос попадает история без отношения к CARD-0116: применять только
  подтверждённые файлы поставки и сверять diff с новой базой.
