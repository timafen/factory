# Спецификация публикует документы до передачи в разработку

## Цель и влияние на пользователя

Этап `Specification` должен передавать в `Implement + Test` не только текст
отчёта, но и опубликованный Git-артефакт. Сейчас общие инструкции одновременно
запрещают commit/push и требуют сохранить результат в ветке; из-за этого
спецификация и карточка остаются в retained worktree, а переход повторяется.

После изменения Specification по-прежнему не пишет продуктовый код, но обязана
сохранить документы в назначенной ветке, выполнить commit и push, сообщить
`BRANCH`, `HEAD` и `PUSHED`. Существующий stage gate передаст работу дальше
только после проверки непустого трёхточечного diff опубликованной ветки.

## Технический подход

Изменение ограничить данными workflow и регрессиями:

- добавить `migrations/023_specification_publishes_documents.sql` как новую
  immutable revision только для включённого workflow с title `Specification`;
- в ревизии явно запретить реализацию пользовательского/продуктового кода и
  изменение UI, а разрешить только спецификацию и отдельную карточку
  `knowledge/cards/CARD-0070-specification-publishes-documents.md`;
- обязать агента работать в назначенной ветке, не делать checkout другой ветки,
  проверить `git diff --name-only origin/main...HEAD`, закоммитить документы
  русским человеческим заголовком, выполнить `git push -u origin HEAD` и
  закончить отчёт точными строками `BRANCH:`, `HEAD:` (полный SHA) и
  `PUSHED: yes`;
- сохранить существующую проверку в `pilot/pilot.py`: `branch_candidates`,
  `pushed_branch` и `branch_report` должны выбрать ветку из origin и подтвердить
  непустой `main...branch` до создания `Implement + Test`. При отсутствии
  commit/push повторно создаётся Specification с понятной инструкцией; при
  недоступности GitHub переход ждёт новый цикл. Этот gate и лимит возврата не
  ослаблять.

Точный текст новой установленной инструкции должен быть таким (без
противоречивого запрета commit/push):

> Ты выполняешь только этап Specification. Не реализуй продуктовый код, не
> меняй UI и не исправляй исходники приложения. Подготовь спецификацию в
> `knowledge/specs/` и отдельную карточку
> `knowledge/cards/CARD-0070-specification-publishes-documents.md`; область
> должна содержать только документы, необходимые для этой спецификации.
> Работай в назначенной рабочей ветке и не переключай её. Перед сдачей
> выполни `git fetch origin main`, при необходимости `git rebase origin/main`,
> затем проверь `git diff --name-only origin/main...HEAD` — diff должен быть
> непустым и содержать только документы этой задачи. Обязательно выполни
> commit с русским человеческим заголовком и
> `git push -u origin HEAD`. Отчёт закончи отдельными строками:
> `BRANCH: <имя назначенной ветки>`, `HEAD: <полный SHA последнего коммита>` и
> `PUSHED: yes`. Без commit и push этап не считается завершённым.

Миграция должна быть идемпотентна механизмом `schema_migrations` и создавать
новую ревизию с детерминированным `id`/`request_key`, номером на единицу выше
текущей, затем атомарно переключать `workflows.current_revision_id`. Она не
должна переписывать историю и не должна менять отключённые workflow. Ревизия
должна быть доступна через обычный workflow API как текущая установленная
ревизия.

## План реализации

1. Добавить SQL-миграцию 023 с точным текстом инструкции выше, сохранив summary
   и title текущей Specification и переключив только включённый workflow.
2. В `internal/controlplane/store_test.go` добавить upgrade-тест: собрать
   legacy schema с прежней Specification revision, применить миграцию, проверить
   номер, `request_key`, current revision и полное точное содержимое
   instructions; отдельно убедиться, что disabled workflow не изменён.
3. В `pilot/test_pilot.py` добавить сквозной тест с установленной ревизией:
   успешный результат Specification с `BRANCH/HEAD/PUSHED` выбирает ветку,
   `branch_report` возвращает `есть` и хотя бы один файл, после чего создаётся
   ровно одна `Implement + Test` с этой веткой в context. Тест также должен
   подтвердить отсутствие ручного восстановления/дубликата.
4. Сохранить проверки отсутствующей или незапушенной ветки: они возвращают
   Specification с инструкцией commit/push, не создавая Implement; проверку
   временной ошибки GitHub оставить повторяемой без ложного возврата.

## Критерии приёмки

- После upgrade текущая ревизия workflow Specification — новая ревизия 023;
  её номер, request key и точный текст совпадают с ожидаемыми, а старые
  ревизии остаются в истории.
- Текст ревизии запрещает продуктовую реализацию, но не запрещает commit, push
  или создание документов; явно требует документы, `BRANCH`, полный `HEAD` и
  `PUSHED: yes`.
- При опубликованной ветке с непустым `origin/main...BRANCH` stage gate создаёт
  ровно одну задачу `Implement + Test`, передавая именно эту ветку.
- При отсутствии commit/push, имени ветки или непустом результате diff gate не
  запускает Implement и возвращает Specification с понятной инструкцией.
- Сбой GitHub оставляет переход для следующего цикла; retained worktree не
  становится источником повторных Implement-задач.
- Ворота Review/Verify, delivery gate и код приложения не изменяются.

## План тестирования

- `go test ./internal/controlplane -run 'Test.*Specification.*Migration'` —
  миграция и установленная ревизия.
- `python3 -m unittest -v pilot.test_pilot.SpecificationBranchHandoffTests` —
  опубликованная непустая ветка и безопасные возвраты.
- `git diff --check`.
- Один upgrade-тест должен применять миграцию к базе с прежними workflow
  данными, а не только проверять наличие строк в SQL.

## Риски и решения

- Точный текст миграции — часть API данных: изменение формулировок требует
  новой ревизии, а не редактирования старой.
- Универсальным доказательством артефакта остаётся непустой diff, потому что
  подключённые проекты могут хранить документы в разных каталогах; наличие
  `HEAD/PUSHED` в отчёте повышает наблюдаемость, но не заменяет GitHub-проверку.
- Не добавлять новый API, таблицу или gate для `Review/Verify`; это scope creep.
- Карточка создаётся агентом в назначенной ветке и должна быть отдельной; общий
  журнал `CARD-0030` и карточка `CARD-0069` не изменяются.
