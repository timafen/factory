# Спецификация: считать этап обработанным только после создания продолжения

## Цель и влияние на владельца

Завершённый этап конвейера не должен исчезать из обработки, пока Pilot не
подтвердил создание его продолжения. Сейчас `cycle()` добавляет ID исходной
задачи в `state["processed"]` сразу после чтения detail, хотя реальное создание
следующей задачи происходит значительно позже. Любая пауза, machine-gate,
отсутствующий worker/workflow, дубль, ошибка control plane или некорректный
ответ может оставить работу отмеченной без продолжения.

После изменения владелец получает надёжный автопереход: задача остаётся
доступна следующему циклу, пока следующий этап действительно не создан и не
вернул валидный task ID. Это устраняет молчаливое зависание без изменения
пользовательских вопросов, UI или API control plane.

## Технический подход и реальные файлы

Реализация ограничивается `pilot/pilot.py` и `pilot/test_pilot.py`.

- В `pilot.cycle()` убрать раннее добавление `tid` в `state["processed"]` около
  обработки terminal task. Ввести узкий внутренний путь подтверждения: он
  вызывается только после успешного `create_child_task()` и только если
  `created["task"]["id"]` — непустой корректный идентификатор.
- Если `create_child_task()` выбрасывает исключение, возвращает несловарь,
  не содержит `task` или не содержит валидный `task.id`, вызвать существующий
  `retry_terminal_task(conf, state, tid)` и не добавлять ID в `processed`.
  Следующий цикл повторяет тот же handoff с прежним request key; имеющаяся
  идемпотентность control plane не допускает второго child при повторе.
- Все отложенные ветви до создания continuation (`AREA WAIT`, отсутствующий
  worker/workflow, specification/review machine-gates, остановка работы,
  обнаруженный дубль, route question) не получают отметку `processed` только
  из-за прохода через terminal loop. Там, где ветвь уже вызывает
  `retry_terminal_task`, сохранить это поведение; для остальных явно выбрать
  повторную обработку или существующий отдельный terminal outcome.
- Намеренные конечные исходы не являются continuation: `work_lifecycle_block`
  и закрытие/дубликат, для которых уже доказано существование следующей или
  финальной работы, остаются отдельной семантикой. Реализация должна
  документировать и тестировать, что `CLOSE`/`DUPLICATE` отмечаются только
  после подтверждённого terminal outcome, а не по умолчанию из раннего cursor.
- Сохранить restart recovery, `terminal_cursor`, `terminal_retry_ids` и
  проверку `live_or_done_at()`: первая предотвращает повтор после рестарта,
  вторая — starvation, третья — дублирование уже созданного продолжения.

## Последовательный план

1. Зафиксировать контракт валидного результата `create_child_task` и добавить
   небольшой helper либо локальную проверку, которая отмечает исходный этап
   обработанным ровно один раз после подтверждённого child ID.
2. Перенести раннюю запись `processed` из terminal loop в успешный путь
   обычного handoff; аудитом всех `continue` подтвердить освобождение cursor
   для ожиданий, ошибок и machine-gate.
3. Явно сохранить завершение для закрытых жизненным циклом работ и для
   доказанного continuation/dedup outcome, не смешивая его с успешным create.
4. Добавить целевые регрессии на успех, исключение, неполный ответ, ожидание
   worker/workflow и повторный цикл; расширить restart/dedup сценарии при
   необходимости.
5. Запустить целевой набор и статическую проверку, затем полный
   `pilot.test_pilot` в Verify.

## Критерии приёмки

1. Успешный `create_child_task()` с непустым ID continuation добавляет ID
   исходного этапа в `state["processed"]` ровно один раз.
2. Исключение при создании, пустой/некорректный ответ, отсутствие worker или
   workflow, `AREA WAIT` и machine-gate WAIT не добавляют исходный ID в
   `processed`; следующий `cycle()` повторно рассматривает handoff.
3. Повтор после временной ошибки успешно создаёт continuation и затем отмечает
   исходный этап обработанным; повторный успешный цикл не создаёт дубль.
4. Рестарт после неуспешной попытки не теряет handoff, а рестарт после
   подтверждённого continuation сохраняет существующую дедупликацию.
5. Явно подтверждённые terminal outcomes (`CLOSE`/`DUPLICATE` и lifecycle
   block) сохраняют согласованное, отдельно протестированное cursor-поведение.
6. Не меняются API control plane, пользовательские вопросы, Verify/release
   lifecycle, выбор worker и UI.

## Риски и решения

- Внешнее создание и локальное сохранение state не образуют одну транзакцию.
  Решение: request key остаётся стабильным, а повторный create обязан
  возвращать тот же child; отметка делается только после валидного ответа.
- Проверка только на отсутствие исключения недостаточна: control plane может
  вернуть неполный payload. Решение: валидировать структуру и ID, иначе
  считать попытку retryable.
- Некоторые ветви сознательно не создают continuation. Решение: не объявлять
  их успешным handoff; сохранить явные terminal-outcome правила и покрыть их
  тестами, прежде чем фиксировать cursor.
- Снятие ранней отметки может увеличить число попыток. Решение: сохранить
  `terminal_cursor`, retry queue, `live_or_done_at()` и request-key
  идемпотентность, чтобы избежать starvation и дублей.
