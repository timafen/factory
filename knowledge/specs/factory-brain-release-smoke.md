# Спецификация: выкат проверяет ответ мозга до приёмки

## Goal and user impact

После обновления мозга выкат не будет считать успехом один лишь запущенный HTTP-
процесс. Он задаст мозгу один контрольный вопрос и примет новую версию только при
одном содержательном ответе. Ошибка модели, неверный JSON, пустой или неоднозначный
ответ приведут к возврату прежних файлов мозга, поэтому владелец не получит внешне
«зелёный», но фактически неработающий конвейер.

## Technical approach

Минимальное изменение остаётся внутри установщика мозга и его новой изолированной
shell-регрессии:

- В `ops/install-brain.sh` после успешных `systemctl is-active` и `/health` отправить
  ровно один фиксированный POST-запрос в `http://127.0.0.1:7338/suggest-answer`.
  Тело содержит один контрольный вопрос и нейтральные значения остальных полей
  действующего `SuggestIn` из `intake/app.py`; публичный API не меняется.
- Ответ считать успешным только при HTTP 200, корректном JSON-объекте с единственным
  верхнеуровневым полем `answer` и непустой строкой в нём. Так дымовая проверка
  проходит весь путь `suggest_answer` → `fable` → `pilot.brain`, а не только HTTP-
  готовность приёмника.
- Ограничить запрос тайм-аутом. Сетевая ошибка, тайм-аут, не-200, неверная форма или
  пустой ответ переводят существующий `ok` в отказ и используют уже имеющийся путь:
  восстановить `.prev`, перезапустить затронутые службы и выйти с кодом 7.
- Добавить `ops/test-install-brain.sh`: временные исходники, live-каталог и mock-
  команды проверяют ровно один запрос, успешную приёмку и откат для каждого класса
  плохого ответа без обращения к настоящей модели или systemd. Для тестируемости
  установщик получает переопределяемые окружением пути/URL с безопасными текущими
  значениями по умолчанию; это не выключатель smoke-проверки.

`ops/fx-factory-release` менять не требуется: он уже вызывает установщик и завершает
выпуск ошибкой при его ненулевом коде. Схемы данных и внешний HTTP-контракт не меняются.

## Plan

1. Сделать live-путь и локальный URL приёмника переопределяемыми в тестовой среде.
2. Добавить после проверки здоровья один POST к `/suggest-answer` и строгую проверку
   HTTP-кода и формы ответа.
3. Подключить любой отказ smoke-проверки к существующему откату файлов и служб.
4. Написать shell-регрессию успешного ответа, единственности запроса, тайм-аута,
   не-200, невалидного JSON, лишнего поля и пустого `answer`.
5. Запустить только новую целевую регрессию; полный набор оставить этапу Verify.

## Acceptance criteria

1. После изменения файлов мозга установщик задаёт через `/suggest-answer` ровно один
   контрольный вопрос и завершает установку только после одного непустого ответа.
2. Smoke-проверка действительно вызывает модель через действующий endpoint, а
   успешный `/health` сам по себе больше не достаточен.
3. Тайм-аут, транспортная ошибка, HTTP не 200, невалидный JSON, пустой ответ или
   дополнительные верхнеуровневые поля возвращают прежние изменённые файлы,
   перезапускают затронутые службы и завершают установщик кодом 7.
4. Если файлы мозга не изменились, сохраняется текущий быстрый выход без перезапуска
   и без платного smoke-запроса.
5. Внешний контракт `POST /suggest-answer` и поведение server/worker-отката не меняются.

## Test plan

- Новый `bash ops/test-install-brain.sh` проверяет успешный путь, ровно один POST и
  все перечисленные причины отката на mock-окружении.
- На Verify один раз выполнить `bash ops/test-install-brain.sh`, затем существующие
  `python3 -m unittest pilot/test_pilot.py` и `bash ops/test-fx-factory-release.sh`.
- Живую проверку настоящего модельного ответа выполнять только на staging при наличии
  установленного мозга; она не заменяет детерминированную shell-регрессию.

## Risks and decisions

- Smoke-запрос добавляет один модельный вызов и его задержку на каждый выкат, который
  действительно меняет мозг. Это осознанная цена проверки полезной функции вместо
  формального health-check.
- Строгий единственный ключ `answer` намеренно выявляет дрейф контракта. Изменение
  ответа endpoint потребует синхронного обновления smoke-проверки.
- Откатывается только мозг: `ops/fx-factory-release` устанавливает server и worker
  раньше и прямо сообщает, что они уже обновлены. Расширение атомарности на все три
  компонента — отдельная задача и здесь было бы scope creep.
- Перед реализацией нужно подтвердить лишь продуктовый выбор: допустим ли один
  реальный модельный вызов при каждом изменении мозга. Спецификация исходит из
  названия принятой задачи и считает его обязательным.
