# Спецификация: мозг конвейера на любой живой подписке

## Goal and user impact

Когда Claude Code или Codex возвращает признак исчерпанного лимита, решения
конвейера и голосовая постановка продолжаются на следующей живой подписке из
настроенной `brain_chain`. На следующем запросе исчерпанный провайдер не
получает новую заведомо безрезультатную попытку до снятия его блока. Владелец
видит тот же блок на уже существующих экранах «Доступы» и «Главное».

Первый инкремент сознательно ограничен надёжностью уже существующего fallback:
никакой новой модели, настройки, API или перераспределения задач не добавляется.

## Текущее поведение и причина

- `pilot/pilot.py:brain()` последовательно пробует `brain_chain`, пропускает
  провайдеров, для которых `limit_active()` возвращает `true`, и при rate-limit
  должен вызвать `note_limit()` перед переходом к следующему движку.
- `note_limit(conf, provider, evidence, resets_at="")` требует конфигурацию для
  уведомления. В ветке rate-limit `brain()` сейчас вызывает его без `conf`.
  Исключение ловится общим `except`, резервный движок всё же отвечает, но запись
  блока не создаётся. Следующий вызов вновь начинает с уже исчерпанной подписки.
- `pilot/pilot.py:stage_worker()` уже исключает заблокированного провайдера при
  назначении исполнителя этапа. `intake/app.py:fable()` уже использует этот же
  `brain()`. `web/src/Access.tsx` и `web/src/Overview.tsx` уже отображают
  `limits.json`; их менять не требуется.

## Technical approach

1. В ветке rate-limit `brain()` передаёт текущий `conf` в `note_limit()`, не
   меняя формат `limits.json`, порядок `brain_chain` или правила ручного
   отключения.
2. Добавить изолированный тест в `pilot/test_pilot.py` с двумя моделями:
   первая возвращает rate-limit, вторая — успешный ответ. Мок записи лимита
   проверяет `conf`, провайдера и текст ошибки и делает Codex заблокированным.
3. Тем же тестом вызвать `brain()` повторно и подтвердить, что ранее
   исчерпанный провайдер уже не запускается, а Claude отвечает сразу. Это
   отличает устойчивое переключение от однократного fallback.

### Affected modules/files

- `pilot/pilot.py` — один вызов `note_limit()` в `brain()`.
- `pilot/test_pilot.py` — регрессия rate-limit и повторного выбора живого
  провайдера.
- `knowledge/cards/CARD-0114-pilot-brain-provider-fallback.md` — карточка
  работы; её должен обновить Implement/Verify.

### Data and API changes

Нет. Используются существующие `brain_chain`, `limits.json`, `note_limit()` и
`BRAIN_STATE`. HTTP-контракты, SQLite и UI остаются совместимыми.

## Acceptance criteria

### Переключение мозга

- Если первый доступный элемент `brain_chain` завершился сообщением, подходящим
  под `LIMIT_SIGNS`, `brain()` записывает его провайдера как исчерпанного через
  существующий `note_limit(conf, provider, evidence)`.
- В том же вызове `brain()` возвращает первый непустой ответ следующего
  незаблокированного движка и сообщает этот движок вызывающему коду.
- В следующем вызове, пока сохранённый блок активен, исчерпанный провайдер не
  запускается; выбор начинается со следующей живой подписки.
- Ручное отключение и уже сохранённый формат лимитов работают как до изменения.

### Регрессия

- Новый тест не вызывает реальные CLI, сеть, `/opt/factory-data` или внешние
  подписки.
- Существующий тест голосового fallback сохраняет зелёный результат.

## Risks and decisions

- Решение не делает здоровой подписку при произвольной ошибке CLI: без
  доказательства лимита она остаётся доступной для следующей попытки. Это
  сохраняет текущую политику и не маскирует сбои окружения как исчерпание квоты.
- Проверка реального OAuth/usage API и предзаблокирование на 95% уже реализованы
  в `provider_limits_tick()` и не входят в этот маленький фикс.
- Более широкая перестройка маршрутизации стадий не нужна: `stage_worker()` уже
  читает тот же блок. Если нужна смена не только при лимите, а при любом сбое
  подписки, это отдельное решение о классификации ошибок и сроках повторов.
