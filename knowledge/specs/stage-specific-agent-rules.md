# Правила только для своих этапов

## Goal and user impact

Сократить повторяющийся контекст автоматических задач без ослабления ворот качества. Агент каждого этапа должен получать только относящиеся к нему требования: Specification — проверяемые обещания `ГОТОВО-КОГДА`, Review — правила измерения поставки трёхточечным diff. Остальные этапы больше не оплачивают токенами два неприменимых правила и не отвлекаются на них.

Текущее поведение: `pilot/pilot.py:create_task` добавляет весь литерал `AGENT_RULES` в `context` каждой задачи с префиксом `[auto]`. В общем литерале правила №4 и №6 описывают исключительно Specification и Review. Добавление защищено только проверкой маркера `ПРАВИЛА ДЛЯ АГЕНТА`; разделения по этапам нет.

## Technical approach

Самое малое связное изменение:

1. В `pilot/pilot.py` удалить из общего `AGENT_RULES` два уже перенесённых в инструкции этапов фрагмента: правило Specification о строках `ГОТОВО-КОГДА` и правило Review о `git diff origin/main...HEAD`, границах замечаний и строке `ПРЕДЛОЖЕНИЕ`.
2. Перенумеровать оставшиеся общие правила, не меняя их содержания и не менять механику `create_task`, лимит контекста или маркер защиты от повторной вставки.
3. В `pilot/test_pilot.py` добавить узкий тест области правил: общий блок не содержит двух этапных требований, но сохраняет универсальные требования и маркеры начала/конца. Это предотвращает обратное разрастание общего контекста.

Инструкции workflow хранятся как ревизии в таблице `workflow_revisions` и приходят в задачу по `workflow_revision_id`; исходного файла с их рабочим текстом в репозитории нет. Эта поставка не должна добавлять миграцию или новый источник истины для workflow. Предусловие реализации — принятые тексты Specification и Review уже содержат перенесённые требования; текущая инструкция Specification это подтверждает для `ГОТОВО-КОГДА`.

Данные, HTTP API и формат конфигурации не меняются.

## Plan

1. Зафиксировать действующие ревизии Specification и Review и убедиться, что в них присутствуют соответствующие правила; если Review не обновлён, остановить реализацию и сначала выпустить его новую ревизию штатным API workflow.
2. Добавить `AgentRulesScopeTests` в `pilot/test_pilot.py`; до изменения общего блока тест должен падать на обоих этапных фрагментах.
3. Удалить два этапных правила из `AGENT_RULES` в `pilot/pilot.py` и последовательно перенумеровать оставшиеся пункты.
4. Запустить новый целевой тест, затем существующие тесты пилота, затрагивающие создание задач и передачу контекста.
5. На Verify один раз выполнить полный проектный набор согласно правилам конвейера и подтвердить, что diff от точки ветвления содержит только обещанные файлы реализации и карточку/спецификацию.

## Acceptance criteria

1. Любая новая `[auto]`-задача по-прежнему получает общий блок правил ровно один раз.
2. Общий `AGENT_RULES` больше не содержит `ГОТОВО-КОГДА` и инструкции Review про `git diff origin/main...HEAD`/трёхточечное сравнение.
3. Универсальные правила о ветке, сдаче, финальном отчёте, человеческих заголовках, отдельных карточках, скорости и живой проверке остаются в общем блоке без смысловых изменений.
4. Specification продолжает требовать строки `ГОТОВО-КОГДА`, а Review — проверку поставки от точки ветвления, за счёт собственных ревизий workflow.
5. Новый тест падает на текущем состоянии и проходит после удаления двух дублей.

## Test plan

- Добавить `pilot.test_pilot.AgentRulesScopeTests`, проверяющий отсутствие двух этапных сигнатур и наличие универсальных сигнатур в `pilot.AGENT_RULES`.
- Целевая команда разработки: `python3 -m unittest pilot.test_pilot.AgentRulesScopeTests`.
- Регрессия области: `python3 -m unittest pilot.test_pilot`.
- Полный набор запускается ровно один раз на Verify командой, принятой в репозитории (`just test`).

## Risks and decisions

- Главный риск — удалить страховку из общего контекста до публикации обеих ревизий workflow. Реализация допустима только после чтения действующих Specification и Review; одной проверки репозитория для этого недостаточно.
- Тест репозитория может доказать состав общего блока, но не содержимое изменяемой вне Git ревизии workflow. Проверка этапных инструкций должна быть отдельным операционным доказательством Verify.
- Отвергнуто добавление текстов всех workflow в `pilot.py`: это создаст второй источник истины рядом с `workflow_revisions` и расширит задачу.
- Отвергнута динамическая фильтрация `AGENT_RULES` по названию этапа: требования уже доставляются штатными инструкциями workflow, поэтому фильтрация лишь сохранит дубли и усложнит код.
- Человеческого решения перед реализацией не требуется, если обе действующие ревизии уже содержат правила. Если правило Review отсутствует, нужна публикация его ревизии до изменения кода.
