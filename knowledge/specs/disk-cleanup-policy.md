# Политика ежедневной уборки диска после тестовых прогонов

## Цель и влияние на владельца

Тестовые прогоны за три дня заняли около 60 ГБ; текущий диск заполнен на 68%
(198 ГБ из 291 ГБ). Сейчас `factory-janitor` переносит только retained
worktree/attempt в карантин и удаляет старый карантин, но не управляет общим
`.cache` или историей выпусков. После реализации ежедневный запуск будет
освобождать предсказуемые, разрешённые владельцем категории, не трогая активные
прогоны и оставляя две точки отката выпусков. Перед первым безвозвратным
удалением владелец увидит точный список кандидатов в журнале.

## Технический подход и реальные файлы

Изменение ограничить операционным janitor-контуром, без UI и исходников
приложения:

- `ops/factory-janitor.sh`: добавить конфигурируемые корни общего кэша,
  браузерных данных, карантина и релизов; выполнять ежедневную фазу после
  безопасного освобождения worker. Общий `.cache` и `.cache/ms-playwright`
  удалять только после 3 суток неактивности; активные прогоны определять по
  текущим worker/attempt и исключать их пути. Карантин удалять после 7 суток.
  В `releases` сохранить `current` и два последних успешных выпуска, а старые
  удалять только после проверки, что они не являются текущим/предыдущим
  указателем и помечены успешными.
- Перед первым фактическим удалением каждой категории (или после изменения
  политики) выполнить один dry-run: записать категорию, абсолютный путь,
  размер, mtime, причину попадания и границу retention в
  `FACTORY_JANITOR_LOG`. До успешной записи кандидатов удаление запрещено;
  повторный запуск после журнала идемпотентен.
- `ops/test-factory-janitor.sh`: расширить изолированный fixture активным
  прогоном, старыми/свежими кандидатами, карантином и успешными/неуспешными
  релизами; проверить dry-run, исключения и границу количества выпусков.
- `ops/systemd/factory-janitor.service` и
  `ops/systemd/factory-janitor.timer`: добавить справочные unit-файлы с
  ежедневным запуском после загрузки, `Persistent=true`, ограниченными
  правами и без параллельных запусков. Если фактическая установка janitor
  выполняется вне репозитория, зафиксировать в документации оператора путь
  установки и переменные корней.

Вне области этой работы: изменение Overview/UI, удаление Git-истории,
очистка активных worktree/attempt, удаление неуспешного выпуска без явного
правила безопасности и изменение серверного API.

## Последовательный план

1. Вынести retention-параметры и корни в переменные окружения с безопасными
   значениями 3/7/2; проверить, что все пути абсолютны и не являются `/` или
   корнем рабочего каталога.
2. Снять снимок активных worker/attempt и построить белый список путей,
   которые нельзя удалять; при ошибке API перейти в fail-closed режим.
3. Реализовать общий отбор кандидатов по mtime и отдельные отборы для
   quarantine/cache/releases, не следуя symlink при удалении.
4. Добавить обязательный журнал dry-run перед первым удалением, атомарный
   маркер применённой политики и понятные строки результата/ошибки.
5. Подключить ежедневный systemd timer с lock/пропуском при уже работающем
   экземпляре.
6. Расширить shell-тесты, затем прогнать синтаксическую проверку и целевой
   тест; полный набор проекта оставить для отдельного этапа Verify.

## Критерии приёмки

1. Ежедневный timer запускает ровно один janitor; повторный параллельный запуск
   безопасно пропускается.
2. Файлы общего кэша и браузерных данных старше 3 суток удаляются только из
   разрешённых корней; файлы младше границы и пути активных прогонов остаются.
3. Объекты quarantine младше 7 суток остаются, старшие удаляются после
   успешного dry-run-журнала.
4. В `releases` остаются current и два последних успешных выпуска; текущий,
   предыдущий, неуспешный или активный выпуск не удаляется автоматически.
5. На чистом журнале первый запуск только фиксирует кандидатов и не удаляет
   их; следующий запуск удаляет ровно ранее зафиксированный набор либо заново
   фиксирует изменившийся набор.
6. Ошибка определения активных прогонов, чтения mtime, журнала или удаления
   не приводит к широкому `rm -rf`; ошибка видна в журнале и завершается
   ненулевым статусом/пропуском категории.
7. Существующее освобождение offline retained worktree и подтверждение API
   сохраняют прежнее поведение.

## План тестирования

В `ops/test-factory-janitor.sh` добавить сценарии: старые и свежие cache/
Playwright/quarantine; активный путь внутри cache; первый dry-run без удаления;
повтор с удалением; три успешных релиза плюс current/previous links;
неуспешный выпуск; отказ API/журнала; параллельный lock. Проверить отсутствие
удаления вне разрешённых корней и повторяемость запуска.

Обязательная проверка этапа:
`bash ops/test-factory-janitor.sh`

Дополнительно: `bash -n ops/factory-janitor.sh ops/test-factory-janitor.sh` и
`git diff --check`. Полный набор тестов не требуется на этапе Specification.

## Риски и решения

- Активный тест создаётся после снимка: держать lock на cleanup-фазу и повторно
  проверять активность перед каждым удалением; при сомнении пропускать файл.
- Неверный путь может привести к катастрофическому удалению: разрешать только
  заранее заданные абсолютные корни, запрещать symlink и пустые переменные,
  проверять `realpath`/родителя до `rm`.
- Удаление релиза может сломать rollback: опираться на валидированные current/
  previous ссылки и манифест успешной установки, сохранять два успешных
  поколения независимо от возраста.
- Первый журнал может заполнить диск или не записаться: сначала проверить
  доступное место и атомарно записать bounded manifest; при сбое не удалять.
- Разные часы и coarse mtime дают неверную границу: использовать epoch из
  `stat`, явную timezone-независимую границу и тесты ровно на 3/7 суток.
