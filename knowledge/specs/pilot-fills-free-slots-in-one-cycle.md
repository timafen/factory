# Спецификация: Pilot заполняет свободные слоты за один цикл

## Цель и влияние на владельца

Когда одновременно завершились несколько этапов, Pilot должен продолжить до
четырёх независимых работ за один цикл. Очередь не ждёт по одному циклу на
каждый handoff, пока здоровые подходящие исполнители и общий лимит параллельных
работ оставляют свободные слоты. Для владельца это сокращает задержку между
этапами без ручного перезапуска и без ослабления защиты от переполнения старой
историей.

## Технический подход и реальные файлы

- `pilot/pilot.py`: оставить `MAX_PARALLEL_WORKS = 4` и поднять ограничение
  рассмотренных терминальных задач за цикл до того же значения. Цикл по-прежнему
  берёт bounded history, применяет приоритет этапов и durable cursor, поэтому
  архивный хвост не превращается в неограниченный обход.
- `pilot/pilot.py`: после каждого успешного `create_task` немедленно добавлять
  локальный снимок созданной задачи в `_active_work_tasks` и
  `_host_load_tasks`. Следующие решения этого же цикла обязаны видеть уже занятый
  слот, даже если API ещё не вернул обновлённый список.
- `pilot/pilot.py`: для дочерней задачи восстанавливать `work_id` по
  `parent_task_id` из снимка цикла, если API create не вернул идентичность
  работы. Так две завершённые попытки одной работы не создадут две тяжёлые
  следующие стадии при пакетном заполнении слотов.
- `pilot/test_pilot.py`: закрепить заполнение четырёх свободных слотов одним
  вызовом `cycle`, предел четырёх решений при большем backlog, отсутствие дубля
  следующей стадии и продвижение cursor мимо отложенного handoff.

## Последовательный план

1. Связать лимит терминальных решений одного цикла с текущей вместимостью Pilot:
   по умолчанию рассматривать не более четырёх кандидатов.
2. Сохранить существующие фильтры терминальных задач, приоритет ближайших к
   доставке стадий и круговой cursor; ограничение применяется после фильтрации.
3. После успешного создания продолжения обновлять оба локальных capacity-снимка,
   чтобы следующий кандидат учитывал занятый слот без нового poll API.
4. При записи созданного продолжения наследовать durable `work_id` родителя и
   тем самым сохранить дедупликацию одной работы внутри пакетного цикла.
5. Добавить целевые регрессии на четыре независимых handoff, backlog больше
   вместимости, повторные терминальные попытки одной работы и capacity-deferred
   кандидата.

## Критерии приёмки

1. При четырёх завершённых независимых этапах, четырёх свободных слотах и
   совместимом worker один вызов `cycle` создаёт ровно четыре разные следующие
   стадии; дополнительный цикл для их создания не нужен.
2. При шести завершённых этапах и свободной capacity один цикл вызывает решение
   и создаёт продолжение только для первых четырёх, отмечает backlog и оставляет
   остальные следующему циклу.
3. Каждый успешный create сразу резервирует слот в снимке текущего цикла;
   суммарное число активных и вновь созданных работ не превышает действующий
   лимит параллельных работ.
4. Две завершённые попытки с одним `work_id` создают ровно одну тяжёлую следующую
   стадию, даже если ответ create не содержит `work_id`.
5. Отложенный из-за capacity handoff обновляет `terminal_cursor` и не мешает
   проверить следующий подходящий терминальный этап в том же цикле.
6. После создания handoff следующий poll остаётся быстрым с причиной `handoff`;
   после исчерпания backlog используется обычный active-интервал.

## Тест-план

- `AdaptivePollingTests.test_four_parallel_handoffs_create_each_next_stage_once`
  доказывает основной пользовательский сценарий: четыре продолжения за один
  цикл и отсутствие повторного handoff на следующем цикле.
- `AdaptivePollingTests.test_terminal_backlog_is_bounded_to_four_decisions_per_cycle`
  проверяет bounded pass и сохранение вызова refill без допуска новой Plan-работы.
- `AdaptivePollingTests.test_duplicate_terminal_attempts_start_one_heavy_next_stage`
  проверяет наследование идентичности и единственную следующую тяжёлую стадию.
- `AdaptivePollingTests.test_deferred_terminal_handoff_does_not_starve_next_terminal`
  проверяет справедливое продвижение cursor внутри одного цикла.
- Целевой обязательный прогон ниже должен завершиться с кодом 0; дополнительно
  перед сдачей реализации выполнить `git diff --check`.

## Риски и решения

- Пакетный обход может превысить capacity на устаревшем API-снимке — каждый
  успешный create синхронно резервирует слот в локальных снимках цикла.
- Несколько завершённых попыток одной работы могут породить дубли — дочерняя
  задача наследует durable `work_id` родителя до следующего API poll.
- Увеличенный batch может снова запустить полный архив — окно истории остаётся
  равным 200, а число рассмотренных за цикл ограничено четырьмя.
- Отложенная дорогая стадия может голодом блокировать остальные — cursor
  продвигается при рассмотрении, включая capacity-deferred результат.
- Конфигурация `max_terminal_tasks_per_cycle` сохраняет явное переопределение;
  значение нормализуется минимум до одного, чтобы ошибочный ноль не остановил
  очередь полностью.
