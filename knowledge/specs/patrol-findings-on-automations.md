# Патрули и их находки на экране «Автоматизации»

## Цель и влияние на владельца

Встроенные патрули Factory перестают выглядеть как продуктовые работы: их
активные, успешные и неуспешные запуски не попадают ни в разделы экрана
«Работа», ни в «Сделано». Владелец наблюдает каждый такой запуск там, где он
ожидаем — в истории соответствующей Automation, вместе с состоянием,
фактическим итогом попытки и явно сформулированной находкой.

Обычные пользовательские работы и пользовательские scheduled Automation
сохраняются без изменений. Если исполнитель не оставил результата, экран не
приписывает запуску проверку или находку, а честно показывает нейтральное
«Результат не оставлен».

## Технический подход и реальные файлы

### Устойчивая граница патруля и экрана «Работа»

Единственным правилом распознавания остаётся `classifyWork` из
`internal/controlplane/work_classification.go`: класс `patrol` получается
только у scheduled Automation, чьи сохранённые title или context содержат
канонический маркер `factory pipeline patrol`. Заголовок самой Task не
участвует в распознавании, поэтому пользовательская работа со словом Patrol и
обычная scheduled Automation не исчезнут.

`internal/protocol/types.go` расширит списочную проекцию `Task` необязательным
полем `work_class`. В `internal/controlplane/store.go` запрос `Tasks` получит
Automation-факты через связь occurrence → Automation → schedule trigger и
вычислит поле тем же `classifyWork`; детальный контракт Task и создание задач
не меняются. `internal/controlplane/store_test.go` зафиксирует классификацию
встроенного патруля и исключения для пользовательского заголовка, обычной
scheduled Automation и несвязанной продуктовой задачи.

`web/src/types.ts` примет поле, а `web/src/Work.tsx` отфильтрует
`work_class === "patrol"` до группировки в `build`. Поэтому один и тот же
инвариант действует для активных групп, архива и «Сделано», не зависит от
состояния запуска и не оставляет патрульную стадию внутри смешанной группы.
`web/src/Work.test.ts` проверит активный, успешный и failed/cancelled патруль,
а также сохранение обычных задач и Automation.

### Итог запуска на экране «Автоматизации»

Сохранённый источник результата уже существует: `attempts.result` и
`attempts.error`, которые `pilot/pilot.py::collect_automation_findings` читает
у завершённой Automation-задачи. Не вводить вторую таблицу и не извлекать
результат из diagnostic или заголовка.

`internal/protocol/types.go` добавит к `AutomationOccurrence` необязательную
проекцию последней попытки: её состояние, `result` и `error` без внутренних
идентификаторов. `internal/controlplane/automations.go` выберет ровно последнюю
попытку связанной Task по номеру попытки с детерминированной развязкой по
времени/ID; occurrence без Task или попытки останется валидным. Это сохранит
pagination: один occurrence по-прежнему даёт одну строку. Тесты в
`internal/controlplane/automations_test.go` покроют успешный result,
неуспешный error и отсутствие попытки/результата.

`web/src/Automations.tsx` покажет в каждой строке запуска три независимые
части: существующий badge фактического состояния, «Находка» для строк
`НАХОДКА: ...` из result и «Итог» для полного результата либо ошибки. Разбор
находок ограничивается построчным каноническим префиксом и не меняет исходный
итог. Если result и error пусты, выводится нейтральное «Результат не оставлен»;
успех состояния сам по себе не превращается в «проверку пройдена».
`web/src/Automations.test.tsx` проверит успешный, неуспешный и пустой запуск,
включая отсутствие выдуманной находки.

Ложная подпись `проверка пройдена` у успешной Task в `web/src/Work.tsx`
заменяется на фактическое `задача выполнена`; `web/src/Work.test.ts` фиксирует,
что успешное выполнение без verdict не называется проверкой. Формулировки
настоящего verdict (`final_pass`) остаются вне этого изменения.

## Последовательный план

1. Расширить wire-модели Task и AutomationOccurrence необязательными
   read-only полями, сохранив обратную совместимость JSON.
2. Присоединить к списку Tasks устойчивые Automation-факты и вычислять
   `work_class` только общей Go-классификацией; покрыть позитивный случай и
   исключения.
3. Проецировать последнюю попытку в occurrence без размножения строк и
   проверить result, error и пустое состояние на уровне Store/API.
4. Исключить только `patrol` до группировки Work, заменить ложную подпись и
   добавить регрессионные тесты всех разделов.
5. Отрисовать состояние, находки и итог каждого Automation-run; проверить
   successful, failed и empty fixtures, затем прогнать целевые Go и web-тесты.

## Критерии приёмки

- Scheduled Automation с каноническими признаками Factory Pipeline Patrol не
  видна на экране «Работа» ни при running/queued, ни при
  succeeded/failed/cancelled, включая «Сделано» и архив.
- Классификация использует связь с Automation, тип schedule и сохранённые
  Automation title/context; совпадение слова в Task title не скрывает
  пользовательскую работу.
- Обычная scheduled Automation, любая другая Automation-задача и продуктовая
  Task остаются на своих нынешних экранах и сохраняют действия.
- Каждый запуск на detail-экране Automation показывает фактическое состояние,
  полный итог последней попытки и каждую явно отмеченную `НАХОДКА:` строку.
- Failed-запуск показывает сохранённую ошибку как итог, а запуск без result и
  error — нейтральное «Результат не оставлен» без ложного успеха или находки.
- Повторы не создают дубликатов occurrence: показывается результат последней
  попытки, при этом retry badge продолжает работать по нынешнему контракту.
- Простое `succeeded` без принятого verdict нигде не подписано
  «проверка пройдена»; существующий настоящий `final_pass` не переименован.

## Тест-план

- `go test ./internal/controlplane -run
  'TestTasks.*WorkClass|TestAutomationOccurrence.*AttemptResult'` — устойчивая
  классификация, пользовательские исключения и проекция последней попытки.
- `cd web && npm test -- --run src/Work.test.ts src/Automations.test.tsx` — патрули отсутствуют во всех Work-состояниях,
  обычные задачи остаются, runs показывают success/failure/empty.
- `cd web && npm run typecheck && npm run lint && npm run build` — контракты и
  production-сборка после расширения DTO.
- На Verify открыть `/automations/<id>` у патруля с тремя типами запусков и
  `/work`: глазами сверить находку/итог/нейтральное состояние и отсутствие
  патрулей в рабочих разделах.

## Риски и решения

| Риск | Решение |
| --- | --- |
| Скрыть пользовательскую Automation из-за похожего названия Task | Не анализировать Task title; использовать только общую Go-классификацию и durable Automation/schedule facts. |
| JOIN попыток размножит occurrence и сломает cursor | Выбирать одну последнюю попытку коррелированным запросом/подзапросом с устойчивой сортировкой; тестировать число и порядок occurrence. |
| Большой result сделает список нечитаемым | Показывать итог в ограниченном сворачиваемом блоке, сохраняя полный текст доступным; не менять сохранённые данные. |
| Ошибка будет выдана за находку | Находка появляется только из отдельной строки с каноническим префиксом `НАХОДКА:`; error остаётся итогом failed-запуска. |
| Старые occurrence не имеют Task/attempt | Сохранить поля необязательными и показывать нейтральное состояние, не считать отсутствие данных успехом. |
| Новый `work_class` затронет иных клиентов Tasks API | Поле аддитивно; сервер не удаляет записи из API, фильтрация выполняется только экраном Work. |
