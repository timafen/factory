# Спецификация: параллельные работы получают разные номера карточек знаний

## Статус спецификации

Эта спецификация закрепляет контракт для уже перенесённого в `main` исправления
после конфликта: дальнейшие изменения не должны возвращать выбор номера в
локальный checkout или терять выданный `Card:` при повторной обработке этапа.
Исходная реализация находится в `pilot/pilot.py`, а её регрессии — в
`pilot/test_pilot.py`.

## Цель и влияние на пользователя

Несколько работ Factory могут одновременно дойти до `Implement + Test` от одной
версии `main`. Общее правило требует отдельную карточку знаний, но не выдаёт ей
номер. Поэтому исполнители независимо выбирают один и тот же «следующий»
`CARD-xxxx`; в итоге в репозитории появляются разные карточки с одинаковым
номером, а владельцу и экрану результатов трудно понять, какая из них относится
к какой поставке.

После изменения Пилот до запуска разработки закрепляет за каждой опубликованной
рабочей веткой один следующий свободный номер карточки и передаёт его во все
дальнейшие стадии. Параллельные ветки получают разные номера, повторная попытка
той же ветки — тот же номер. Исполнитель больше не выбирает номер по локальному
снимку репозитория, а создаёт карточку по выданному контракту.

## Технический подход

Изменение ограничивается оркестратором и его изолированными Python-тестами:

- В `pilot/pilot.py` добавить в сохраняемое состояние Пилота реестр резервов
  номера по паре «подключённый репозиторий + опубликованная рабочая ветка».
  Ключом служит именно ветка, а не заголовок: новая повторно открытая работа с
  тем же названием получает новую ветку и новую карточку, а повторная обработка
  одного этапа остаётся идемпотентной.
- При успешном переходе `Specification → Implement + Test`, после уже
  существующей проверки опубликованной непустой ветки, Пилот определяет
  наибольший числовой `CARD-<n>` в `knowledge/cards/` основой ветки и выбирает
  большее из него и локального счётчика резервов. Номер форматируется не менее
  чем четырьмя цифрами (`CARD-0070`). Резерв сразу сохраняется в `STATE_PATH`
  до создания следующей задачи; неуспешное создание задачи может оставить
  пропуск, но не может выдать номер второй работе.
- Добавить строку `Card: CARD-…` в контекст разработки и сохранять её при
  переходах Implement, Review и Verify, наряду с уже переносимой строкой
  `Branch:`. `AGENT_RULES` будет требовать создавать файл
  `knowledge/cards/<выданный Card>-<slug>.md` ровно с этим значением и прямо
  запретит искать «следующий» номер в файлах или выбирать его самостоятельно.
- Расширить существующую машинную проверку карточки перед Review: если в
  контексте есть `Card:`, среди файлов поставки должна быть карточка с этим
  префиксом. Проверка implementation commit остаётся прежней. У старых или
  вручную созданных работ без строки `Card:` новая проверка не применяется,
  чтобы не вернуть в работу уже начатые поставки.
- Если GitHub не дал прочитать список карточек для первого резерва, Пилот не
  угадывает номер: снимает завершённую Specification с `processed` и ждёт
  следующего цикла. Публичные HTTP API, формат карточек, интерфейс Cards и
  правила merge не меняются.

Центральный реестр выбран вместо инструкции «сначала посмотри origin/main»:
такая инструкция не устраняет гонку двух исполнителей. Отдельный общий файл в
репозитории также отклонён — он сам стал бы конфликтующей точкой параллельных
веток. Нумерация остаётся привычной числовой, поэтому `web/src/Summary.tsx`,
который уже распознаёт `CARD-\d{3,4}`, не требует изменения в этой поставке.

## План реализации

1. В `pilot/pilot.py` определить формат строки `Card:`, чтение числовых имён
   карточек и идемпотентную функцию резервирования номера в состоянии Пилота.
2. После успешных ворот сохранности Specification получить или восстановить
   резерв для выбранной ветки; при неопределённости GitHub отложить переход,
   а не создавать задачу Implement.
3. Сохранить реестр до вызова `create_task`, добавить `Card:` в новый context и
   переносить эту строку в каждый последующий handoff и возврат на доработку.
4. Дополнить общие правила исполнителя требованием использовать выданный номер
   и передать ожидаемый номер в `review_gate` /
   `implementation_commit_gate` для точной проверки карточки.
5. Добавить регрессии на два параллельных резерва, повтор того же резерва,
   перенос номера между стадиями, отказ неправильной карточки перед Review и
   безопасное ожидание при недоступном списке карточек.

## Критерии приёмки

1. Две опубликованные ветки одного репозитория, обработанные в одном цикле,
   получают разные `Card: CARD-…`; номера больше уже существующего максимума.
2. Повторная обработка той же ветки получает первоначально зарезервированный
   номер и не расходует следующий.
3. Созданная задача `Implement + Test` и её следующие Review/Verify получают
   один и тот же `Card:` в context; правило исполнителя предписывает имя
   карточки с этим префиксом.
4. Перед Review поставка с выданным `Card:` и карточкой другого номера
   возвращается на доработку; поставка с подходящей карточкой проходит этот
   новый аспект ворот и затем проверяется обычным implementation commit gate.
5. Ошибка чтения каталога карточек не создаёт Implement и не резервирует
   угаданный номер; завершённая Specification доступна для повторной проверки.
6. Работы без `Card:` из времени до выпуска не получают ложный возврат только
   из-за нового правила.

## План тестирования

В `pilot/test_pilot.py` добавить `CardNumberReservationTests` с подменённым
GitHub и временным состоянием. Основной сценарий должен сначала показать
сегодняшний дефект: две разные ветки без реестра получают один максимум + 1,
после реализации — разные последовательные номера и стабильный номер при retry.

Отдельные проверки должны подтвердить сохранение резерва до создания задачи,
передачу `Card:` через handoff, отказ несоответствующей карточки в Review и
отложенный переход при сбое получения каталога. Существующие
`SpecificationBranchHandoffTests` остаются регрессией для уже имеющейся проверки
ветки и выполняются вместе с новым классом.

Обязательная команда разработки:
`python3 -m unittest -v pilot.test_pilot.CardNumberReservationTests pilot.test_pilot.SpecificationBranchHandoffTests`.

## Риски и решения

- Счётчик может иметь пропуски, если задача создана не была после сохранения
  резерва. Это осознанная цена гарантии уникальности; непрерывная нумерация не
  является пользовательским контрактом.
- Реестр живёт в состоянии единственного Пилота. Параллельное ручное создание
  карточки вне Factory не резервирует номер; такая карточка будет учтена при
  следующем чтении максимума, но не входит в обещание этой автоматической
  поставки.
- Если когда-нибудь потребуется несколько активных экземпляров Пилота, реестр
  надо перенести в транзакционное хранилище control plane. Сейчас это расширило
  бы область без доказательств второго писателя.
- Не вводить UUID в имена карточек: это действительно устранило бы коллизию, но
  сломало бы понятную владельцу последовательную нумерацию и распознавание
  карточек в существующем экране результата.

## Карточка

`knowledge/cards/CARD-<номер, зарезервированный Пилотом>-parallel-knowledge-card-numbering.md`

Конкретный номер намеренно не выбирается на стадии Specification: его должен
атомарно зарезервировать Пилот перед Implement, иначе сама эта работа повторит
исправляемую гонку. Карточку создаст Implement после отдельного коммита кода,
чтобы её первая строка содержала существующий полный `Implementation commit`.
