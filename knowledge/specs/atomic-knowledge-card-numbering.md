# Атомарная нумерация карточек знаний

## Цель и влияние на пользователя

Две параллельные работы сейчас самостоятельно выбирают следующий номер файла
`knowledge/cards/CARD-NNNN-*.md`. Обе могут увидеть один и тот же максимум и
доставить разные карточки с одинаковым номером. В `main` уже есть исторические
группы дублей `CARD-0068` и `CARD-0069`, поэтому по номеру нельзя однозначно
найти знание о поставке.

После изменения Factory выделяет номер централизованно и атомарно до подготовки
ветки `Implement + Test`. Исполнитель получает в своём prompt единственный
разрешённый номер и выбирает только slug. Перед передачей в `Review` и `Verify`
машина дополнительно проверяет все карточки ветки: новая или изменённая карточка
не может разделять номер с другим `CARD-NNNN-*.md`, даже если slug отличается.
Исторические дубли, которых ветка не касается, остаются читаемыми и не
останавливают текущие поставки.

## Технический подход

Минимальная граница решения — control plane, worker prompt и существующие ворота
Пилота. Номера не резервируются GitHub-веткой или файлом в репозитории: такая
операция потребовала бы гонок push/force-push и не была бы общей точкой
сериализации для разных воркеров.

- В `migrations/023_knowledge_card_number_reservations.sql` создать таблицу
  резервирований с уникальным ключом `(repository_id, card_number)` и связью с
  задачей. Это является единственным авторитетом для параллельных задач Factory.
- В `internal/controlplane/store.go` при создании задачи workflow
  `Implement + Test` определить максимальный номер среди файлов
  `knowledge/cards/CARD-*.md` в `main` и уже выданных резервов, затем в той же
  SQLite-транзакции записать следующий номер. Чтение GitHub используется только
  для занятых исторических файлов; решение и запись номера сериализует БД.
  Повтор `request_key` возвращает прежнюю задачу и тот же резерв, не расходуя
  ещё один номер. Ручные задачи и стадии Triage/Specification/Review/Verify не
  получают новый номер.
- В `internal/protocol/types.go` добавить к `Claim` необязательный снимок
  резерва (число и сформированный префикс `CARD-%04d`). В
  `internal/controlplane/state.go` включать его в выдаваемый claim. В
  `internal/worker/attempt_lifecycle.go` добавлять перед workflow-инструкциями
  короткое доверенное правило: создать одну карточку только с этим номером и
  уникальным slug. Claim уже приходит до `prepareWorktree`/`addPreparedWorktree`,
  поэтому номер известен до создания ветки и запуска агента.
- В `pilot/pilot.py` вынести проверку номера карточки из `review_gate` в общий
  gate, вызываемый перед созданием как `Review`, так и `Verify`. Через GitHub API
  он читает весь каталог `knowledge/cards` именно в проверяемой ветке, извлекает
  номер регулярным выражением из каждого `CARD-<digits>(-<slug>)?.md` и сравнивает
  его как целое число (также ловит `CARD-70` против `CARD-0070`). Если номер
  карточки из diff ветки встречается более одного раза, gate возвращает работу с
  обоими путями. Сбой GitHub остаётся временно неблокирующим, как остальные
  пред-Review ворота.
- В `pilot/test_pilot.py` покрыть gate двумя вызовами перехода: перед Review и
  перед Verify. Проверка обязана сканировать полный список, а не только diff;
  при этом группа исторических дублей без изменённого номера пропускается. Если
  diff добавляет/переименовывает карточку в такую группу, поставка возвращается.

Изменений UI и публичных HTTP-маршрутов нет. Внутренний JSON claim расширяется
обратносуместимым необязательным полем: старый worker может получить claim без
использования номера, поэтому rollout требует обновить control plane и workers
одной поставкой; защитный gate всё равно не пропустит дубль.

## План реализации

1. Добавить миграцию резервов и Go-модель данных; выбрать следующий номер из
   опубликованных карточек и локальных резервов, записав его атомарно вместе с
   созданием задачи `Implement + Test`.
2. Передавать резерв в claim и включить его в prompt worker до подготовки
   worktree; обновить live revision workflow, чтобы исполнитель не выбирал
   номер по сканированию файлов.
3. Добавить конкурентный тест создания двух задач одной репозитории: оба
   резерва должны существовать и иметь разные последовательные номера; replay
   одного `request_key` возвращает исходный номер.
4. Добавить машинную проверку всех карточек проверяемой ветки и включить её в
   переходы к Review и Verify.
5. Добавить регрессии разных slug, неполного/полного написания номера,
   исторического неизменённого дубля и GitHub-ошибки; запустить целевые Go и
   Python проверки.

## Критерии приёмки

1. Два одновременных создания задач `Implement + Test` для одного репозитория
   получают разные номера; ни одна ветка агента не создаётся до выдачи своего
   reservation claim.
2. Повтор того же запроса не создаёт второй task или второй резерв. Резервы
   разных репозиториев независимы.
3. Новый номер больше максимума среди опубликованных `knowledge/cards/CARD-*.md`
   и уже выданных резервов; формат в prompt — минимум четыре цифры.
4. Worker получает номер до запуска агента и явно обязан использовать его в
   единственной карточке своей работы; slug остаётся свободным.
5. Перед Review и перед Verify карточки сканируются целиком. Добавление
   `CARD-0070-one.md`, когда уже есть `CARD-0070-other.md`, возвращает работу с
   понятной причиной; вариант `CARD-70-other.md` трактуется тем же номером.
6. Уже существующие дубли, не затронутые diff поставки, не блокируют её;
   автоматического переименования или удаления `CARD-0068`/`CARD-0069` нет.
7. Ошибка GitHub при инвентаризации карточек не выдаёт ложный PASS и не создаёт
   ложный возврат: gate сохраняет нынешнее неблокирующее ожидание/retry.

- В `pilot/test_pilot.py` добавить `KnowledgeCardNumberGateTests`: разные slug,

- На Implement запускать целевые команды ниже. На Verify один раз запускать

## Риски и решения

- Решение: БД control plane — атомарный источник резервов. GitHub не даёт
  транзакции на выбор имени файла, поэтому используется только для обнаружения
  уже занятых номеров. Внешняя ручная запись в Git между инвентаризацией и
  merge не может захватить резерв, но будет остановлена gate.
- Решение: исторические группы дублей пропускаются только если diff не меняет
  этот номер. Отклонить все найденные дубли сразу нельзя: это остановит каждую
  текущую поставку до отдельной миграции знаний, которая вне области.
- Решение: резервировать только workflow с существующим точным именем
  `Implement + Test`. Это сохраняет стадии Specification и Verify без лишних
  номеров; поддержка произвольных пользовательских workflow потребовала бы
  отдельного явного флага продукта и не входит в эту поставку.
- Риск rollout: старый worker не обязан понять новое поле claim. Обновление
  worker вместе с control plane обязательно, а Review/Verify gate служит
  страховкой до завершения rollout.
- Вне области: переименование исторических карточек, миграция их ссылок,
  UI для резерва и запрет ручных Git-поставок вне Factory.

## Карточка

`knowledge/cards/CARD-0070-atomic-knowledge-card-numbering.md` — ожидаемый
первый путь после текущего максимума. На стадии Specification карточка намеренно
не создаётся: её номер должен впервые подтвердить реализованный резерв. Если
параллельная работа займёт `0070` раньше, Implement обязан использовать выданный
резервом путь и обновить эту ссылку, а не создавать дубликат.
