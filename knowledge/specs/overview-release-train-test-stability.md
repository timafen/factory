# Тест поезда на Обзоре не зависит от часов машины

## Цель и влияние на владельца

Сделать сценарий `shows N+1 after the current train without inventing its start time`
детерминированным: он должен подтверждать отображение текущего поезда и состава
N+1 после применения ответа `/api/v1/dashboard`, а не зависеть от скорости машины,
реальных часов или случайного порядка завершения запросов. Владельцу это даёт
доверие к регрессии блока «Поезд выпуска»: десять повторных прогонов и полный
`Overview.test.ts` должны проходить одинаково.

Производственное поведение `Overview` не меняется. API dashboard, вычисление
`elapsed_seconds`, broker, очередь, хранилище и визуальная разметка вне scope.

## Технический подход и реальные файлы

`web/src/Overview.tsx` загружает `/api/v1/dashboard` внутри общего `Promise.all`,
а затем асинхронно записывает снимок в состояние. Регион «Поезд выпуска» может
появиться с текстом unavailable до того, как `release_train` применён. Поэтому
`web/src/Overview.test.ts` должен получать фиксированный mock dashboard и ожидать
внутри региона наблюдаемый текст `идёт 2 мин` через Testing Library async API.
Проверка N+1 и отсутствие «Следующая попытка» выполняются только после этого
ожидания; синхронные `getByText` для данных, приходящих из dashboard, в этот
сценарий не добавляются.

Использовать только mock `fetch` и данные с фиксированным `elapsed_seconds: 125`.
Не использовать `Date.now`, `new Date()` как источник ожидаемого значения,
fake timers, `setTimeout`, `sleep` или произвольные задержки. `waitFor` допустим
только для наблюдаемого DOM-условия, а не как таймер ожидания.

Файлы реализации:

- `web/src/Overview.test.ts` — единственный файл, который изменяется на этапе
  Implement + Test; тестовый mock должен возвращать dashboard только для
  `/api/v1/dashboard`, а tasks — для запроса списка задач.
- `web/src/Overview.tsx` — файл контекста и проверки отсутствия продуктовых
  изменений; менять его нельзя.

## Последовательный план

1. В тесте N+1 сохранить фиксированный dashboard fixture с running train,
   `elapsed_seconds: 125`, текущим и следующим пассажиром, без `retry_at`.
2. После `render` дождаться в том же регионе текста `идёт 2 мин` через
   `findByText` либо `waitFor` с callback-проверкой; затем проверить пассажира
   N+1 и отсутствие «Следующая попытка».
3. Убедиться, что ожидание не читает системное время и не вводит задержки или
   timers; не менять компонент, fixture API или production fetch flow.
4. Выполнить десять последовательных filtered-прогонов под нагрузкой, затем
   один полный прогон `Overview.test.ts`.

## Критерии приёмки

- Проблемный тест ждёт применения mock dashboard по видимому значению
  длительности текущего поезда и после этого проверяет N+1.
- В тесте нет реальных часов, fake timers, `sleep`, `setTimeout` и arbitrary
  delay; `elapsed_seconds` остаётся единственным источником ожидаемых «2 мин».
- Все десять последовательных filtered-прогонов завершаются кодом 0 без
  повторного запуска, а полный `web/src/Overview.test.ts` также завершается
  кодом 0.
- Тест подтверждает текущего пассажира, пассажира следующего состава и то,
  что неизвестный `retry_at` не превращается в ложную дату.
- `web/src/Overview.tsx` и прочие production/API-файлы отсутствуют в diff.

## Тест-план

- Целевой сценарий: отфильтровать по `without inventing`, выполнить десять
  последовательных запусков без параллелизма и без retry.
- Регрессия файла: один полный `npm test -- --run src/Overview.test.ts` после
  серии, включая состояния idle/waiting/running/succeeded/failed и остальные
  секции Обзора.
- Для каждого filtered-запуска mock dashboard должен завершить JSON-ответ,
  после чего проверка наблюдаемого текста доказывает отсутствие гонки загрузки.

## Риски и решения

- Ожидание только `region` может завершиться до применения dashboard state.
  Решение: ждать конкретный текст длительности внутри этого региона.
- Fake timers замаскируют, но не устранят гонку между fetch и React state.
  Решение: синхронизироваться с результатом mock API через DOM.
- Слишком широкое `waitFor` может скрыть регрессию или ждать не тот элемент.
  Решение: ограничить поиск `within(section)` и проверять фиксированный текст
  и N+1 в том же сценарии.
- Полный прогон может выявить независимую нестабильность других тестов.
  Решение: зафиксировать конкретный failing test и отделить его от этой
  test-only области; не менять production-код ради чужих ошибок.
