# Экран «Обзор»: свой блок «Продукт» на каждый проект

## Цель и влияние на пользователя

На «Обзоре» владелец видит не один жёстко названный блок торговой системы, а
отдельный блок «Продукт» для каждого зарегистрированного в Factory репозитория с
`enabled=true`. Порядок блоков совпадает с ответом каталога репозиториев. В каждом
блоке видны последнее изменение основной ветки и, когда для проекта настроен
провайдер, сведения о релизе и здоровье его сред. Проект без такой настройки не
исчезает: интерфейс прямо сообщает «Стенд не настроен» или «Сведения о выпуске
недоступны», не строя адрес или команды из имени репозитория.

## Технический подход

Сохранить один снимок `/api/v1/dashboard`: `internal/controlplane/dashboard_http.go`
по-прежнему только отдаёт JSON, а `pilot/pilot.py` собирает тяжёлые сведения раз в
пять минут. Вместо единственного поля `release` снимок получает массив `projects` в
том же порядке, что `GET /api/v1/repositories`, после фильтра `enabled=true`.
Каждый элемент содержит идентификатор и отображаемое имя репозитория, последний
коммит отслеживаемой основной ветки и массив сред с понятным статусом.

`pilot/pilot.py` получает явный конфигурационный реестр серверных провайдеров,
ключом которого служит нормализованный `remote_identity`. Провайдер задаёт только
разрешённые команды/среды, а не выводится из названия репозитория. В начальной
конфигурации фиксируются два существующих случая: торговая система использует
нынешние команды `fx staging|prod release-info` и `health`, а Factory —
`fx factory release-info` и `health` как единственную боевую среду. Неизвестный
или неполный провайдер не запускает shell-команды и возвращает явное отсутствие
настройки. Ошибка команды или отсутствие распознаваемого выпуска превращается в
«Сведения о выпуске недоступны» для соответствующей среды, не ломая другие
проекты.

Поскольку конфигурация пилота строго декодируется и редактируется через API,
добавить тип и в `internal/protocol/types.go`, валидацию/совместимое чтение в
`internal/controlplane/pilot_config.go`, образец в `pilot/config.example.json`, а
также тип и редактор в `web/src/types.ts` и `web/src/Settings.tsx`. Настройка
провайдера должна быть явной и сохраняться без потери; адреса, секреты и догадки о
стендах в UI не добавляются.

`web/src/Overview.tsx` заменяет одиночную секцию релиза списком блоков данных из
`projects`; визуальная логика состояния вынесена в небольшую чистую функцию, чтобы
тестировать пустой список, ненастроенный провайдер, недоступный выпуск и успешные
среды. Старый `release` удалить из клиентского контракта после перевода снимка,
так как он отражает только один продукт.

Затрагиваемые файлы реализации: `pilot/pilot.py`, `pilot/test_pilot.py`,
`pilot/config.example.json`, `internal/protocol/types.go`,
`internal/controlplane/pilot_config.go`, `internal/controlplane/pilot_config_test.go`,
`web/src/types.ts`, `web/src/Settings.tsx`, `web/src/Settings.test.tsx`,
`web/src/Overview.tsx`, `web/src/Overview.test.ts`.

## План

1. Описать и провалидировать конфигурационный реестр провайдеров сред; добавить в
   пример торговый и Factory-провайдеры и сохранить его в API настроек.
2. В `pilot.dashboard_slow()` получить каталог репозиториев, отфильтровать
   включённые и в его порядке собрать `projects`, беря последний коммит из
   отслеживаемой основной ветки локального рабочего каталога каждого проекта.
3. Выполнять release-info/health только через совпавший настроенный провайдер;
   нормализовать результат в статусы «настроен», «стенд не настроен» и «сведения о
   выпуске недоступны» без ложной деградации для других проектов.
4. Заменить на клиенте старый единичный `release` типом `projects` и отрисовать
   заголовок, последнее изменение и среды каждого проекта в полученном порядке.
5. Добавить серверные, конфигурационные и UI-регрессии для двух известных
   провайдеров и честных fallback-состояний.

## Критерии приёмки

1. Если API каталога возвращает включённые репозитории A, B и выключенный C,
   `/api/v1/dashboard` и «Обзор» содержат ровно A и B в этом порядке; C не показан.
2. Для каждого показанного проекта отображается тема последнего коммита его
   отслеживаемой основной ветки; отсутствие доступной локальной копии не подменяется
   данными другого репозитория и показывается как недоступное изменение.
3. Торговый провайдер показывает отдельные `Стейдж` и `Прод` с данными текущих
   команд `fx`; Factory показывает одну настроенную боевую среду с данными
   `fx factory release-info`/`health`.
4. Включённый репозиторий без провайдера остаётся на экране и ясно содержит
   «Стенд не настроен»; команды и адреса по его имени не угадываются.
5. Если настроенная команда выпуска/здоровья завершается ошибкой или не даёт
   пригодного результата, соответствующий блок сообщает «Сведения о выпуске
   недоступны» и не выдаёт состояние «не отвечает» как достоверный факт.
6. Изменённая настройка провайдера проходит строгую серверную схему, сохраняется
   через экран настроек и после чтения остаётся без потери полей.

## План проверки

- `pilot/test_pilot.py`: мокированный каталог, порядок enabled-репозиториев,
  раздельные команды торгового и Factory-провайдера, неизвестный провайдер и
  неудачный release-info.
- `internal/controlplane/pilot_config_test.go`: строгая схема и round-trip
  реестра провайдеров.
- `web/src/Overview.test.ts`: порядок блоков и все три понятных состояния;
  `web/src/Settings.test.tsx`: редактирование и сохранение провайдера.
- Обязательная целевая команда: `npm --prefix web test -- --run
  src/Overview.test.ts src/Settings.test.tsx && python3 -m unittest
  pilot.test_pilot && go test ./internal/controlplane -run 'PilotConfig'`.
- Дополнительно перед сдачей: `git diff --check`.

## Риски и решения

- Формат реестра (включая допустимые имена сред и команды) — новая настройка,
  требующая проверки безопасности: реализация не должна исполнять произвольные
  команды, введённые через веб-форму. Минимальный безопасный выбор — перечисление
  известных типов провайдеров с фиксированными командами; UI выбирает тип, а не
  принимает shell-текст. Это решение нужно подтвердить перед реализацией, если
  владелец ожидает произвольные провайдеры.
- Локальные рабочие копии не гарантированно содержат все включённые репозитории.
  Поэтому последняя правка — лучшая доступная информация, а не причина скрыть
  проект; получение коммита через сетевой Git API не входит в эту задачу.
- Не добавлять историю выпусков, ссылки на внешние стенды, управление выкладкой
  или автоматическое обнаружение окружений: это scope creep относительно обзора.
