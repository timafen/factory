# Спецификация: общий бюджет слотов соответствует мощности узла

## Цель и влияние на владельца

На одном восьмиядерном узле Factory одновременно подготавливает или выполняет
не более восьми задач суммарно во всех worker-службах. Добавление новой службы
или ошибочное `max_concurrent = 10` больше не увеличивает фактическую ёмкость
узла до 20, 30 и выше и не создаёт повторную перегрузку CPU.

`max_concurrent` сохраняет нынешний смысл локального верхнего предела отдельной
worker-службы. Дополнительно control plane выдаёт каждой новой попытке один слот
из общего бюджета узла. Бюджет настраивается один раз в server config и по
умолчанию равен числу логических CPU, которое видит процесс сервера; поэтому на
целевой машине значение без ручной настройки равно 8.

## Технический подход и реальные файлы

Сейчас `internal/worker/config.go` по умолчанию задаёт каждой службе
`max_concurrent = 10`, `internal/worker/manager.go` создаёт отдельный канал
`slots` такой ёмкости, а `internal/worker/claiming.go` резервирует только этот
локальный канал. Несколько процессов не разделяют канал. Control plane уже
является общей для всех локальных worker-служб точкой выдачи: в
`internal/controlplane/state.go` метод `Store.Claim` в одной SQLite-транзакции
проверяет `workers.capacity` и создаёт attempt с состоянием `preparing` и lease.

Реализация добавляет в `cmd/factory-server/config.go` положительное целое поле
`host_max_concurrent`. Если поле отсутствует, загрузчик подставляет
`runtime.NumCPU()`; явно заданные ноль и отрицательное значение отклоняются при
старте. `cmd/factory-server/main.go` передаёт разрешённое значение в новый
`controlplane.OpenWithOptions` и включает `host_max_concurrent` в структурный
событийный лог `server_started`. Обычный `controlplane.Open` остаётся
совместимым вспомогательным входом для recovery и существующих тестовых fixture,
а production server всегда открывает Store с разрешённым бюджетом.

`internal/controlplane/store.go` хранит неизменяемый для времени жизни процесса
`hostMaxConcurrent` в `Store`; изменение настройки применяется перезапуском
сервера. В `internal/controlplane/state.go` новый admission-check выполняется в
той же транзакции `Claim`, после обработки идемпотентного повтора существующего
request и проверки конкретного worker, но до выбора queued execution и вставки
attempt. Он считает по всем worker ID только attempts в `preparing`/`running` с
`lease_expires_at > server now`. При достижении бюджета claim штатно сохраняет
пустой результат, как при заполненном локальном `max_concurrent`, и не создаёт
attempt или supervisor.

SQLite уже открывается с `_txlock=immediate`, поэтому два одновременных claim,
увидевших последний свободный общий слот, сериализуются: только один успевает
вставить новый `preparing` attempt. `preparing` входит в общий счёт с момента
выдачи lease и закрывает разрыв до запуска runtime. Существующие terminal-пути
и lease expiry освобождают бюджет без нового счётчика или миграции. Supervisor
уже останавливается до последнего lease deadline, поэтому просроченная попытка
не продолжает работу после того, как перестала входить в server-time счёт.

Документация в `docs/worker.md` и `docs/local.md` объясняет два независимых
ограничения и пример server config:

```toml
# Необязательно; без поля равно числу логических CPU сервера.
host_max_concurrent = 8
```

Текущий контракт относится к одному loopback control plane и всем его
worker-службам на том же узле, что соответствует описанной в `docs/worker.md`
модели развёртывания. Удалённый fleet потребует явного host identity и отдельных
бюджетов и в эту работу не входит. UI, схема БД, wire-формат worker registration,
локальный диапазон `max_concurrent` 1–100 и pilot load admission не меняются.

## Последовательный план

1. Расширить server bootstrap config полем `host_max_concurrent`, подстановкой
   числа CPU для отсутствующего поля и fail-fast проверкой явных значений.
2. Добавить опции открытия Store, передать production-настройку из
   `factory-server` и записывать эффективный бюджет в `server_started`.
3. В транзакции `Claim` после идемпотентного replay поставить общий admission
   перед выбором задачи и созданием attempt, сохранив текущий локальный check.
4. Покрыть два worker, восьмой/девятый claim, конкурентную границу, terminal и
   lease expiry целевыми store-тестами; покрыть default/override/reject config.
5. Обновить операторскую документацию и выполнить обязательную целевую команду.

## Критерии приёмки

1. При двух здоровых worker-службах с `max_concurrent = 10` каждая и
   `host_max_concurrent = 8` первые восемь claim суммарно создают восемь
   `preparing` attempts, а девятый возвращается пустым и не создаёт строку
   attempt независимо от распределения задач между службами.
2. Два параллельных claim на восьмой свободный слот не превышают общий предел:
   успешен ровно один, второй пуст, а число непросроченных active attempts равно
   8. Повтор request уже выданной попытки возвращает ту же попытку и не
   блокируется самим заполненным бюджетом.
3. Завершение одной попытки в terminal-состояние разрешает следующий новый
   claim. Просроченный lease также перестаёт занимать общий слот; непросроченные
   `preparing` и `running` занимают по одному слоту каждый.
4. Локальный предел продолжает действовать: worker с `max_concurrent = 2` не
   получает третью попытку при свободном общем бюджете 8, а другой worker может
   использовать остальные общие слоты.
5. Без `host_max_concurrent` server использует `runtime.NumCPU()`; на узле с
   восемью видимыми CPU эффективный предел и поле лога равны 8. Положительный
   override применяется, явные `0` и отрицательные значения останавливают
   запуск с понятной ошибкой.
6. Понижение бюджета при перезапуске ниже числа уже живых lease не прерывает
   задачи, но ни один новый claim не выдаётся, пока active count не станет
   меньше нового предела.
7. `max_concurrent`, данные registration и страница отдельного worker продолжают
   показывать локальную ёмкость службы; общий лимит не подменяется суммой этих
   значений и подтверждается конфигурацией, стартовым логом и поведением claim.

## Тест-план

- `cmd/factory-server/main_test.go`: отсутствующее поле получает
  `runtime.NumCPU()`, override 8 сохраняется, явные 0 и -1 отклоняются, прежние
  `listen`/`database` и unknown-field проверки остаются зелёными.
- `internal/controlplane/store_test.go`: fixture с общим бюджетом 8, двумя
  worker capacity=10 и девятью совместимыми задачами; восемь claim успешны,
  девятый пуст, число active attempts не превышает 8.
- Там же: синхронизировать два goroutine на последнем слоте и проверить один
  новый attempt; повторить успешный request ID после заполнения бюджета.
- Там же: table-driven освобождение после `CompleteAttempt` и server-time lease
  expiry, а также независимое соблюдение worker capacity=2.
- Целевая команда ниже сначала проверяет, что новый regression общего предела
  действительно существует (обычный `go test -run` без найденных тестов ложно
  завершился бы успешно), а затем запускает его; отдельно выполнить
  `git diff --check`. До реализации команда красная из-за отсутствующего теста.

## Риски и решения

- **Гонка выдачи последнего слота.** Считать и вставлять attempt только внутри
  уже существующей immediate SQLite-транзакции; конкурентный тест фиксирует
  итоговый active count, а не порядок goroutine.
- **Устаревший `active_count`.** Общий admission не суммирует
  `workers.active_count`: источником остаются непросроченные строки attempts,
  как в реализованной сверке CARD-0085.
- **Потеря слота при подготовке.** `preparing` считается сразу после claim;
  terminal transition или lease expiry освобождает его существующим lifecycle.
- **Снижение лимита при живой работе.** Не завершать уже выданные lease и не
  скрывать превышение; fail closed только для новых claim до естественного
  drain, чтобы смена настройки не уничтожала работу владельца.
- **Смешение продуктовой метрики capacity=4 и ресурсов узла.** Не использовать
  `productCapacity` из `internal/controlplane/capacity.go`: это отдельная
  классификационная метрика, а новый бюджет ограничивает все worker attempts.
- **Будущие удалённые workers.** Пока server и workers loopback-only, один Store
  однозначно соответствует одному узлу. До снятия loopback-ограничения контракт
  расширяется host identity, а не молча применяет один бюджет ко всему fleet.
