# Полная карточка готовности нового проекта

## Цель и влияние на пользователя

Владелец сможет открыть «Обзор» и увидеть для каждого включённого managed-
репозитория одну карточку из девяти проверок: репозиторий, исполнители,
безопасный стенд, доступы, тесты, выпуск, откат, секреты и браузерный доступ.
Карточка даёт один из трёх детерминированных итогов — «Готов», «Требует
настройки» или «Заблокирован» — и показывает конкретные причины. Это заменяет
необходимость сопоставлять отдельные продуктовые блоки «Обзора» с экраном
маршрутизации репозитория.

Данные, которых нет или которые нельзя безопасно доказать, не становятся
успехом. Они остаются «Неизвестно» с причиной и ведут к «Требует настройки»;
production-write остаётся выключенным по умолчанию. Никакая карточка не
показывает значение секрета, произвольный вывод команд или возможность записи
в production.

## Технический подход

Расширить снимок `projects`, который `pilot/pilot.py` публикует в
`$FACTORY_DATA_HOME/pilot/dashboard.json` и который без вычислений на запрос
отдаёт `internal/controlplane/dashboard_http.go`. В `ProductProject` появится
`readiness` с упорядоченным массивом ровно из девяти объектов `{key, title,
state, reason}` и полем `verdict`. Ключи и порядок фиксированы:

1. `repository` — включённая регистрация из `GET /api/v1/repositories` и
   доступный точный локальный checkout через `_project_repo_dirs`; отсутствие
   checkout не подменяется другим каталогом.
2. `workers` — `routing_ready` и причины из существующего
   `GET /api/v1/repositories/{id}/readiness`, основанного на живых фактах
   `Store.ManagedRepositoryReadiness`.
3. `safe_environment` — только явно разрешённый non-production scope
   code-owned провайдера (`trade` → `staging`) и его `fx ... health`;
   у `factory` отдельного безопасного стенда сейчас нет, поэтому статус
   «Неизвестно», а не успех.
4. `access` — нормализованный ответ существующего `GET /api/v1/access`,
   учитывающий root-owned `/etc/factory-access/policy.json` и switchboard
   `pilot/access.json`. Для безопасного стенда нужен доступ `staging`; наличие
   `production-write` никогда не является условием успеха и при отсутствии
   остаётся ожидаемым безопасным значением.
5. `tests` — последний завершённый Verify того же `repository_id`, где
   сохранённый итог попытки начинается с `PASS`; пилот извлекает только
   итоговый статус и время из API задач/попыток, не публикуя отчёт. Если такого
   подтверждения нет, состояние «Неизвестно».
6. `release` — уже существующий только-для-чтения code-owned вызов
   `fx <scope> release-info` и распознанная метка выпуска из
   `_environment_snapshot`.
7. `rollback` — явная, code-owned декларация процедуры отката в каталоге
   провайдеров (`factory` → `fx factory rollback`; для `trade` — штатная
   процедура релизного провайдера). Это проверка наличия безопасно описанного
   пути, а не запуск отката. Последний наблюдённый факт отката берётся только
   из `pilot/release-events.jsonl` и показывается как причина, без логов.
8. `secrets` — фиксированная read-only команда `fx <safe scope> env-names`;
   достаточно непустого списка имён. В JSON/UI передаётся лишь состояние и
   число/имена, если они уже являются публичными именами переменных; значения,
   stderr и пути env-файлов не сохраняются и не отдаются.
9. `browser` — свежий безопасный маркер успешного `ops/test-browser-sandbox.sh`,
   который установщик `ops/install-server-browser.sh` пишет после smoke в
   `$FACTORY_DATA_HOME/pilot/browser-readiness.json`. Маркер содержит только
   `passed_at` и fingerprint поставленного браузера; отсутствующий, просроченный
   или ошибочный маркер даёт «Неизвестно»/«Заблокирован» без запуска браузера на
   каждом обновлении карточки.

Пилот опрашивает эти источники в уже существующей медленной пятиминутной части
снимка. Доступные команды остаются исключительно литеральными argv в коде;
тип `ProjectProvider` не получает поля shell-команды. Каталог `trade`/`factory`
становится единственным местом, где описаны разрешённые scope, release,
rollback и secret-name probes. Публичный API не получает значений секретов и
не добавляет write-операций.

Состояния одной проверки: `ready`, `needs_configuration`, `blocked`, `unknown`.
Порядок вердикта строго такой: если есть хотя бы один `blocked` —
«Заблокирован»; иначе, если все девять `ready` — «Готов»; иначе — «Требует
настройки». Причины сортируются в порядке девяти ключей, а не по времени или
порядку ответов. Ошибка чтения источника равна `unknown`, кроме наблюдаемого
отрицательного факта (например, нет готового worker или health вернул
неуспех), который равен `blocked`.

`web/src/Overview.tsx` получает чистую функцию нормализации/verdict и
отрисовывает карточку в существующем продуктовом блоке. Карточка всегда
показывает девять строк, итог, время снимка и причины; «Обзор» остаётся
отдельным экраном для визуальной проверки. Детальный экран
`web/src/Repositories.tsx` сохраняет нынешнюю диагностическую маршрутизацию и
не дублирует новый агрегат.

## План

1. Описать типы readiness в `internal/protocol/types.go`, клиентские типы в
   `web/src/Overview.tsx` и строгую совместимую схему провайдера в
   `internal/controlplane/pilot_config.go`; дополнить пример конфигурации.
2. В `pilot/pilot.py` ввести code-owned каталог probe-источников, чтение
   readiness API/access, безопасные parsers release/env-names/Verify и
   браузерного marker-файла; собрать девять строк для каждого включённого
   проекта в существующем порядке API.
3. Дополнить `ops/install-server-browser.sh` атомарной записью минимального
   browser marker только после успешного sandbox smoke; ошибка не создаёт
   успешный marker.
4. Реализовать чистую агрегацию и UI-карточку в `web/src/Overview.tsx`; явно
   показать причины, unknown и безопасное отсутствие production-write.
5. Добавить серверные, пилотные, UI и Playwright-регрессии для полного
   контракта и ссылки на «Обзор».

## Критерии приёмки

1. Каждый enabled-репозиторий на «Обзоре» содержит одну доступную по роли
   карточку с девятью строками в фиксированном порядке; disabled не появляется.
2. Ответ snapshots содержит те же девять ключей, состояния, итог и причины;
   перестановка ответов источников не меняет итог или порядок причин.
3. Неточный или недоступный источник не становится `ready`; UI явно показывает
   «Неизвестно» и причину.
4. `ready` возможен только когда все девять наблюдаемых проверок готовы;
   наблюдаемый отказ хотя бы одной даёт «Заблокирован», а нехватка факта без
   отказа — «Требует настройки».
5. Проверка безопасного стенда требует только разрешённый non-production scope;
   production-write по умолчанию выключен, не запрашивается и не нужен для
   «Готов».
6. Секретная проверка публикует только наличие/отсутствие (и допустимые имена),
   никогда значения, env-файлы, stderr или произвольный output.
7. Rollback не выполняется при сборе карточки; карточка отличает отсутствие
   описанной процедуры от последнего зафиксированного события отката.
8. Browser ready возможен лишь со свежим marker после sandbox smoke; отсутствие
   marker не объявляется успехом и не запускает Chromium при просмотре UI.
9. Компонентный и Playwright-тест проверяют видимую карточку, итог и причину на
   отдельном экране «Обзор».

## План проверки

- `pilot/test_pilot.py`: все девять источников, защищённая фильтрация secret
  output, freshness browser marker, fixed provider argv, unknown/blocked и
  таблица детерминированных вердиктов.
- `internal/controlplane/pilot_config_test.go` и
  `internal/controlplane/http_test.go`: строгая конфигурация провайдера,
  исходные readiness/access данные и сериализация dashboard-контракта.
- `ops/test-install-server-browser.sh`: marker появляется только после
  успешного sandbox smoke и не включает секретные данные.
- `web/src/Overview.test.ts`: девять строк, все три итога, причины и отсутствие
  ложного успеха. `web/e2e/control-plane.spec.ts`: страница «Обзор» отображает
  карточку и сохраняет screenshot результата.
- Обязательная целевая команда после реализации:
  `python3 -m unittest pilot.test_pilot && go test ./internal/controlplane -run 'PilotConfig|Dashboard|ManagedRepositoryReadiness' && npm --prefix web test -- --run src/Overview.test.ts && npm --prefix web run test:browser -- --grep 'shows project readiness card' && bash ops/test-install-server-browser.sh && git diff --check`.

## Риски и решения

- Сейчас нет durable project-specific записи о прошедшем Verify и нет browser
  marker. Реализация должна добавить минимальные, allowlisted факты; нельзя
  выдавать за доказательство свободный текст отчёта или лог выпуска.
- Для `factory` нет отдельного safe environment. Спецификация намеренно
  оставляет эту строку unknown, пока владелец не выберет безопасный стенд или
  явно не изменит политику; нельзя считать production безопасным по умолчанию.
- Значение «готов» для rollback — это наличие зафиксированной процедуры, не
  выполнение разрушительного действия. Альтернатива — пробный откат — отвергнута.
- Выполнение тестов при каждом цикле dashboard слишком дорого и может менять
  состояние. Поэтому используется последний успешный Verify с узким статусом;
  новый тест запуска карты только в CI/e2e.
- Не входят в работу: изменение cached/advertised маршрутизации, угадывание
  провайдеров/стендов, раскрытие секретов, запись в production, история релизов
  или управление выкладкой.
