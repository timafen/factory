# Спецификация: приёмка Factory десятью полными работами без ручного ремонта

## Цель и влияние на владельца

Доказать на безопасном внутреннем сервисе Factory ровно десять последовательных
полных работ, после каждой из которых есть разработка, проверка, слияние в `main`
и штатный `fx factory release`. Владелец должен видеть человеческий русский
статус, название релиза, единый итог, понятное следующее действие и длительность
без чтения логов, а диагностический отчёт — скопировать без секретов. Приёмка не
затрагивает торговую систему, production, её данные или секреты.

## Технический подход и реальные файлы

Текущая группировка работ и уже существующие русские статусы находятся в
`web/src/Work.tsx`; `web/src/format.ts` содержит длительность этапа, но её
английский формат и разрозненное время нужно заменить общими функциями. Badge
статусов и пустые/ошибочные состояния находятся в `web/src/ui.tsx`, detail и
итог — в `web/src/TaskDetail.tsx` и `web/src/Summary.tsx`. Overview с названиями
релизов и карточками окружений — `web/src/Overview.tsx`, этапная история —
`internal/controlplane/work_history_http.go` и `web/src/WorkHistory.test.tsx`.
Диагностические данные API определены в `internal/controlplane/provider_diagnostics.go`;
экранные сообщения и копирование нужно связать с `web/src/Automations.tsx` или
`web/src/Summary.tsx` после уточнения фактического payload. Маршрут и browser
приёмка — `web/e2e/control-plane.spec.ts`.

Единый view-model работы должен получать историю этапов, verdict, owner-question,
паузы/тупики, origin, release label и диагностический текст; отрендерить один
итоговый статус, блок «что случилось / дальше / участие владельца», русскую
хронологию с длительностью каждого этапа и всей работы. Секретоподобные поля,
токены, промпты и сырые `result/error` исключаются до помещения текста в буфер
обмена. Фильтр «Нужно решение владельца» обязан использовать тот же источник,
что и badge, а не отдельную эвристику.

Разрешённый порядок приёмки — ровно такой: (1) русские названия всех статусов;
(2) человеческие названия релизов; (3) единый непротиворечивый итог работы;
(4) понятное следующее действие остановленной работы; (5) фильтр «Нужно решение
владельца»; (6) русская хронология этапов; (7) длительность этапов и всей работы;
(8) понятные пустые состояния и ошибки; (9) копирование диагностического отчёта
без секретов; (10) автоматические проверки этих правил интерфейса. Следующая
работа стартует только после полного прохождения предыдущей через разработку,
проверку, merge в `main` и `fx factory release`.

## Последовательный план

1. Зафиксировать API/view-model и таблицу всех исходных состояний: queued,
   running, succeeded, failed, cancelled, owner pause, stuck, open question,
   empty и server error; добавить тестовые fixture без production данных.
2. Реализовать общий русский словарь статусов, релизов, этапов и ошибок, затем
   подключить его к badge, Work, Task detail, Overview и summary.
3. Устранить расхождения итогов и next action: приоритет открытого вопроса,
   паузы и тупика должен быть одинаковым в списке и detail; успешная стадия с
   отрицательным verdict не считается принятой.
4. Добавить фильтр владельца, хронологию и расчёт длительности по timestamps с
   безопасным отображением неизвестного/неполного времени.
5. Добавить empty/error states и копирование санитизированного diagnostics
   payload с подтверждением результата и fallback для недоступного Clipboard API.
6. Добавить unit/component проверки по каждому правилу и один именованный
   Playwright-сценарий. Запускать десять работ только по одной, после каждого
   результата фиксировать экран и release-проверку; ручной ремонт данных запрещён.

## Критерии приёмки

- На десяти последовательно принятых работах счётчик ровно 10; ни одна не
  требует ручного изменения состояния, базы, ветки или release-артефакта.
- Все видимые статусы, этапы, действия, ошибки и release labels русские и
  устойчивы к неизвестному backend-значению (показывается безопасное «Неизвестно»).
- В списке и detail один и тот же итог, owner-action и причина остановки; для
  вопроса показано действие ответа, для паузы — продолжение/настройки, для тупика
  — решение владельца, для принятой работы — завершение без ложного retry.
- Фильтр «Нужно решение владельца» показывает ровно открытые вопросы и тупики,
  не включает queued/no-worker и не расходится с секциями Work.
- Хронология отображает все фактически пройденные/пропущенные этапы по времени,
  длительность каждого этапа и lead time всей работы; незавершённый этап явно
  обозначен как текущий.
- Empty/error state объясняет, что делать дальше, имеет доступное действие
  повтора и не показывает raw error, секрет, токен, prompt или служебный URL.
- Копирование выдаёт только разрешённые поля диагностики, а автоматическая
  проверка доказывает отсутствие секретных значений в буфере.
- После каждой работы проверены целевые тесты, merge в `main` и `fx factory
  release`; десятый прогон дополнительно запускает полный UI gate.

## Тест-план

- `web/src/format.test.ts`: русский словарь, длительности, неизвестные значения
  и санитизация diagnostics.
- `web/src/Work.test.ts` и `web/src/WorkView.test.tsx`: десять состояний,
  единый итог, filter owner decision, pause/stuck next action и пустые/error UI.
- `web/src/WorkHistory.test.tsx`, `web/src/Overview.test.ts`,
  `web/src/App.test.tsx`: русская chronology/release label и доступные действия.
- `internal/controlplane/work_history_http_test.go` и
  `internal/controlplane/provider_diagnostics_test.go`: контракт безопасной
  истории/diagnostic payload без сырых секретных полей.
- `web/e2e/control-plane.spec.ts`: один последовательный browser-сценарий,
  видимый на экране, с десятью fixture-работами и assertions по всем правилам;
  отдельный запуск должен завершаться кодом 0.

## Риски и решения

- Старые payload могут не иметь timestamps, release label или verdict: не
  додумывать, а показывать «Нет данных» и сохранять исходное состояние.
- История может быть неполной из-за pagination: backend возвращает явный
  cursor/границу, UI не объявляет отсутствующий этап пропущенным без доказательства.
- Clipboard API и browser automation могут быть недоступны: fallback-кнопка
  показывает текст в доступном readonly блоке, но не копирует секреты.
- Соседние карточки CARD-0084—0089 не являются этой работой. Удалённая ветка
  предыдущей triage-работы не существует, поэтому перенос не выполнен; исходной
  точкой остаётся свежий удалённый `main`.
- Любой сбой торгового проекта, production, данных или секретов — немедленная
  остановка приёмки и отдельный отчёт, без попытки ремонта.
