# Спецификация: одноразово развести исторические дубли номеров карточек

## Цель и влияние на владельца

В `knowledge/cards/` один и тот же номер сейчас обозначает несколько разных
работ: например, `CARD-0047` имеют пять независимых карточек. На экране Cards
и в отчётах Пилота имя карточки выглядит как её устойчивый идентификатор, но
повтор номера делает ссылку, поиск и устное обсуждение неоднозначными. Уже
выпущенный механизм резервирования предотвращает новые коллизии, однако не
исправляет исторический каталог.

После одноразовой миграции каждый файл карточки на `main` будет иметь
единственный номер `CARD-NNNN`. Владелец сможет назвать номер карточки без
уточнения slug, а переходы по ссылкам в спецификациях, миграциях и карточках
останутся рабочими. Содержимое, статусы, implementation commit и история Git
не переписываются; меняются только пути и текстовые ссылки на них.

## Технический подход и реальные файлы

- Добавить одноразовую проверяемую утилиту
  `scripts/renumber_historical_cards.py`. Она читает дерево
  `knowledge/cards/`, группирует имена по префиксу `CARD-NNNN`, оставляет
  каноническим лексикографически первый путь в каждой группе, а каждому
  остальному пути выдаёт следующий свободный номер после максимального
  номера дерева. Соответствие old-path → new-path выводится в детерминированном
  порядке и применяется только после явного флага `--apply`; режим без флага
  не пишет файлы.
- В той же утилите заменить только точные вхождения старого пути
  `knowledge/cards/CARD-NNNN-<slug>.md` во всех отслеживаемых текстовых
  файлах репозитория. Голый `CARD-NNNN` не переписывать: это историческая
  метка в отчётах, а не однозначная ссылка. После замены проверить, что все
  ссылки на путь существуют, а номера итоговых файлов уникальны.
- Добавить `scripts/test_renumber_historical_cards.py` с временным деревом:
  две группы дублей, ссылки в `.md`/`.py`, dry-run, повторный запуск и отказ
  при конфликтующем назначении. Тест не использует настоящий каталог и не
  изменяет историю Git.
- Запустить утилиту с `--apply` ровно один раз и закоммитить только
  переименования карточек и обновлённые точные ссылки в `knowledge/`,
  `migrations/` и тестовых fixtures, если они действительно ссылаются на
  переименованный путь. Перед коммитом сверить вывод dry-run с манифестом
  миграции в карточке работы.
- Не менять `pilot/pilot.py`, `pilot/test_pilot.py`, API Cards или React UI:
  они уже работают с полным путём и механизм `reserved_card_number` должен
  продолжать выдавать номера после максимума уже очищенного каталога.

Фактический снимок `origin/main` содержит 23 дублирующихся номера:
`0030, 0034, 0036, 0037, 0038, 0039, 0041, 0043, 0045, 0047, 0048, 0051,
0052, 0055, 0057, 0058, 0059, 0060, 0067, 0068, 0069, 0083, 0089`.
Уникальными должны стать все 68 файлов этого набора; канонические 23 остаются
на месте, а 45 остальных получают новые номера. Значения выбираются утилитой
из свежего дерева непосредственно перед применением, поэтому параллельно
появившаяся карточка не будет случайно перезаписана.

## Последовательный план

1. Реализовать dry-run и `--apply` в `scripts/renumber_historical_cards.py`;
   запретить запись вне корня репозитория и отказать, если целевой путь уже
   занят.
2. Описать в тестах детерминированный выбор канонического пути, выделение
   свободных номеров, точную замену путей, идемпотентность и безопасный
   dry-run.
3. На свежем `origin/main` сохранить вывод dry-run как таблицу old-path →
   new-path в `knowledge/cards/CARD-0108-historical-card-number-deduplication.md`.
4. Выполнить `--apply`, проверить уникальность номеров и отсутствие ссылок на
   старые пути, затем вручную просмотреть список переименований и ссылок.
5. Запустить целевой тест и `git diff --check`; отдельным быстрым вызовом
   `python3 -m unittest -v pilot.test_pilot.CardNumberReservationTests`
   доказать, что будущая выдача номеров не регрессировала.

## Критерии приёмки

1. В `knowledge/cards/` нет двух файлов с одинаковым числовым префиксом
   `CARD-NNNN`.
2. Каждая прежняя карточка существует ровно в одном новом или прежнем пути;
   содержимое её тела не теряет status, implementation commit и журнал.
3. Все отслеживаемые точные ссылки на переименованные пути указывают на
   существующий файл; ни одна строка с одним лишь историческим `CARD-NNNN` не
   меняется из-за миграции.
4. Повторный dry-run после применения сообщает об отсутствии дублей и не
   предлагает изменений.
5. Новые карточки по-прежнему получают номер через существующий резерв Пилота,
   а не через миграционную утилиту.

## Тест-план

`python3 -m unittest -v scripts.test_renumber_historical_cards` создаёт
временный каталог с конфликтами, подтверждает план без записи, применение,
замену только полных путей, уникальные назначения и нулевой второй запуск.

После применения дополнительно выполнить:

`find knowledge/cards -maxdepth 1 -type f -name 'CARD-*.md' -printf '%f\\n' | sed -E 's/^(CARD-[0-9]+).*/\\1/' | sort | uniq -d | test ! -s /dev/stdin`

Эта команда завершается с кодом 0 только когда в каталоге не осталось
повторяющихся номеров. Регрессия резервирования запускается отдельной
целевой командой из плана; полный набор проекта для одноразового переименования
не требуется.

## Риски и решения

- Новая карточка может появиться между dry-run и `--apply`. Утилита повторно
  читает каталог перед записью и отказывается при занятом назначении; запуск
  выполняется после `git fetch origin main` и rebase.
- Замена голых номеров могла бы исказить исторические отчёты и ссылки на
  старые поставки. Поэтому заменяются только полные пути, а номер внутри
  заголовка карточки меняется осознанно вместе с её именем.
- Массовое переименование создаст большой, но чисто документальный diff.
  Генерируемый детерминированный план в карточке и dry-run позволяют review
  сверить каждую пару до записи.
- Изменение runtime-резервирования одновременно с миграцией увеличит риск
  регрессии. Оно вне области: текущие `CardNumberReservationTests` служат
  предохранительной проверкой существующего поведения.

## Карточка работы

`knowledge/cards/CARD-0108-historical-card-number-deduplication.md` —
отдельная карточка этой поставки. Номер проверен как свободный в свежем
`origin/main` и опубликованных ветках на момент Specification; он не заменяет
и не обновляет общие журналы.
