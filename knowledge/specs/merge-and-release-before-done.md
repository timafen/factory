# Работа считается готовой после слияния и выпуска

## Цель и влияние на пользователя

Сейчас успешный `Verify` отмечается финальным PASS и владелец получает
«Задача выполнена» сразу после `gh_merge`. Выпуск запускается отдельно в фоне,
поэтому в промежутке между merge и его результатом эпик может перейти к
следующей подзадаче, а экран «Работа» — назвать работу принятой. При ошибке
выпуска это создаёт ложное обещание готового результата.

После изменения работа станет готовой только по двум сохранённым фактам:
ветка успешно влита и штатный post-merge выпуск завершился с кодом `0`.
Пока выпуск выполняется или повторяется после release-lock, UI честно покажет
ожидание слияния и выпуска. Ошибочный выпуск не закроет работу и даст владельцу
явное уведомление о необходимости вмешательства. Сам Pilot по-прежнему не
ожидает процесс выпуска синхронно и продолжает вести другие конвейеры.

## Технический подход

Минимальное изменение остаётся в текущей модели Pilot и не добавляет HTTP API,
миграции или новые внешние команды.

- В `pilot/pilot.py` успешный merge продолжит писаться в `MERGES_PATH`, но
  `mark_final(..., True)` и уведомление «Задача выполнена» переносятся на
  обработку успешного завершения выпуска в `poll_post_merge_deploys`.
- В состоянии `post_merge_deploys` либо в соседнем сохраняемом разделе
  `state.json` появятся ожидания поставки, привязанные к Verify task id,
  названию работы, репозиторию, цели выпуска и минимальному поколению release.
  Если новый merge застал уже идущий выпуск, ожидание относится к
  коалесцированному следующему поколению, а не к потенциально старому процессу.
- После `rc=0` polling создаёт отдельный durable receipt выпуска, отмечает
  только связанные ожидания как поставленные, вызывает `mark_final(..., True)`
  и единожды уведомляет владельца. Повторный polling или рестарт не должны
  создать второе уведомление, receipt или финальный PASS.
- `rc=8` остаётся штатным ожиданием внешней блокировки: ожидания сохраняются и
  переходят на повтор. Любой другой ненулевой результат фиксируется как
  неуспешная поставка, не выставляет финальный PASS и уведомляет владельца
  один раз на поколение. Автоматически объявлять работу законченной или
  перепривязывать её к неизвестному следующему выпуску нельзя.
- `merge_receipt` и восстановление эпиков будут использовать receipt именно
  успешной поставки, а не один лишь merge journal. Это не позволит следующей
  подзадаче стартовать после чистки истории до завершения выпуска.
- В `recent_done_block` запись получает статус «готово» только при receipt
  поставки; запись с одним merge остаётся честным прогрессом. В `web/src/Work.tsx`
  успешный терминальный `Verify` без `final_pass` получает отдельный статус
  «Ожидает слияния и выпуска», а не общий `completed → работа завершена`.

Формат команд выпуска и правила выбора Factory/staging-репозитория не меняются:
их уже изолирует `deploy_after_merge`. Успешный выход штатной allowlisted-команды
считается подтверждением выпуска; отдельная проверка URL не добавляется, потому
что она уже входит в её контракт и дублирование создало бы второй источник истины.

## План реализации

1. Описать сохраняемую запись ожидания поставки и receipt успешной поставки;
   добавить помощники чтения/записи, дедупликации и поиска receipt по task id и
   поколению.
2. В ветке успешного `Verify` записывать merge-факт и регистрировать ожидание
   выпуска до старта/коалесцирования процесса; не ставить финальный PASS и не
   отправлять успешное уведомление.
3. В `poll_post_merge_deploys` закрывать ожидания только после `rc=0` нужного
   поколения; при `rc=8` сохранять их через retry, при иной ошибке оставлять
   работу незавершённой и выдавать дедуплицированную тревогу.
4. Перевести восстановление эпиков и «Сделано недавно» с merge receipt на
   receipt поставки, сохранив обратную совместимость чтения старого merge
   журнала лишь как факт слияния, но не как факт готовности.
5. Обновить построитель статуса в `web/src/Work.tsx`, чтобы завершённый
   `Verify` без delivery PASS не попадал в «Done»; добавить тест интерфейса.
6. Добавить изолированные регрессии Pilot для успешного выпуска, lock/retry,
   ошибки выпуска, коалесцирования и рестарта; затем прогнать целевые Python
   и UI-тесты.

## Критерии приёмки

1. После PASS Verify и успешного merge до `rc=0` выпуска отсутствует
   `final_pass: true`, не отправляется «Задача выполнена», эпик не переходит к
   следующей подзадаче и экран работы показывает ожидание поставки.
2. `rc=0` поколения, которое покрывает merge, единожды создаёт delivery receipt,
   ставит `final_pass: true`, завершает связанную подзадачу и отправляет
   владельцу итоговое уведомление с существующим TRY/доказательством.
3. Если merge произошёл во время занятого выпуска, работа ожидает именно
   коалесцированный последующий выпуск; успех старого поколения её не закрывает.
4. `rc=8` сохраняет ожидание через рестарт и retry; работа не считается
   готовой до успешного завершения повторного поколения.
5. Ненулевой код, кроме `8`, не создаёт delivery receipt и не ставит
   `final_pass`; владельцу приходит одна понятная тревога, а повторный polling
   не дублирует её.
6. После рестарта Pilot сохраняет связь ожидания с работой и не теряет либо не
   дублирует успех, ошибку, уведомление и receipt.
7. Обычная отдельная успешно завершённая задача без pipeline по-прежнему
   остаётся в Done; меняется только terminal Verify автоматического конвейера.

## План тестирования

В `pilot/test_pilot.py` добавить класс, например
`PostMergeDeliveryCompletionTests`, с временными `STATE_PATH`, release status
files, verdicts, merge/delivery receipts и подменёнными `notify`/`Popen`.
Сценарии проверяют состояние до release, точное поколение коалесцированного
выпуска, `rc=0`, `rc=8`, обычную ошибку и restart/deduplication. Существующие
`PostMergeDeployTest` и `EpicCompletionReceiptTests` обновить так, чтобы они
доказывали сохранение ожиданий и запрет завершения по одному merge.

Ключевая новая регрессия должна сначала быть красной: создать в
`PostMergeDeliveryCompletionTests` сценарий успешного merge до завершения
release и утверждать, что `final_pass` отсутствует. Затем этот же сценарий
должен стать зелёным только после `rc=0` связанного поколения, когда появляется
delivery receipt и ровно один итоговый PASS. Так команда ниже проверяет саму
причину задачи, а не только наличие нового кода.

В `web/src/Work.test.ts` добавить terminal Verify без `final_pass` и проверить
пользовательский статус ожидания, а также сохранить текущую проверку standalone
success в Done. Целевые команды:

```sh
python3 -m unittest -v pilot.test_pilot.PostMergeDeployTest pilot.test_pilot.PostMergeDeliveryCompletionTests pilot.test_pilot.EpicCompletionReceiptTests
cd web && npm test -- --run src/Work.test.ts
```

## Риски и решения

- Решение: ожидание связывается с поколением выпуска, а не только с целью
  (`deploy_factory_cmd`/`deploy_staging_cmd`). Иначе уже запущенный процесс
  мог бы ошибочно закрыть работу, которая влилась позже.
- Решение: `rc=8` — ожидание, прочие ненулевые коды — незавершённая поставка с
  тревогой. Бесконечно повторять потенциально опасный выпуск без решения
  владельца отклонено.
- Решение: Pilot не блокируется на `wait()`. Асинхронное polling сохраняет
  текущую пропускную способность конвейеров.
- Риск: старая запись `MERGES_PATH` не содержит поколения или delivery receipt.
  Её нельзя ретроспективно считать выпуском; для уже завершённых исторических
  работ сохраняется прежнее отображение, новые работы используют новый receipt.
- Scope creep: не менять release broker, настройки проектов, API Overview и
  расчёт метрик. Метрика `merge_release_wait` остаётся merge-интервалом до
  отдельной согласованной задачи по аналитике.
- До реализации одобрение человека не требуется: поведение следует прямому
  требованию задачи, а выбранный контракт не меняет внешние команды выпуска.
