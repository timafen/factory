# Завершение подзадач эпика переживает очистку истории

## Цель и влияние на пользователя

После очистки истории задач уже завершённая подзадача эпика должна оставаться
завершённой. Владелец не увидит повторный запуск следующей зависимой работы и не
получит ложное завершение новой попытки от старой одноимённой задачи.

## Технический подход

В `pilot/pilot.py` расширить сохраняемое состояние подзадачи в файле эпика
durable-квитанцией: `completed_at`, `completion_source` и
`completion_receipt`. `advance_epics()` записывает её, когда финальный этап
успешен с `final_ok(..., strict=True)`, либо когда после исчезновения задач
найдена точная запись в `MERGES_PATH`. Для завершённой подзадачи отсутствие
строк в текущем API-снимке не меняет статус `done`.

Поиск merge-квитанции должен сопоставлять только точное базовое имя и запись не
старше `started_at` текущего поколения. Если у `done`-подзадачи появляется
новая работа того же имени (включая `failed` и `stuck`), вернуть её в `running`
и сохранить временную границу нового поколения. После очистки истории старая
merge-запись не сможет завершить этот перезапуск.

Очередь не меняет существующие правила: `hold_reason` удерживает зависимый
хвост, а `parallel_ok` позволяет независимой подзадаче стартовать рядом с
последовательной. Форматы HTTP API и UI не изменяются. Область реализации:
`pilot/pilot.py` и `pilot/test_pilot.py`.

## План реализации

1. Добавить помощники чтения и проверки merge-квитанции, включая разбор старого
   локального и нового UTC времени.
2. При завершении подзадачи сохранять источник, квитанцию и время завершения в
   JSON эпика.
3. В `advance_epics()` не переоткрывать `done` из-за пустой истории, но
   распознавать новое поколение и обновлять его `started_at`/`task_id`.
4. Добавить изолированные регрессии для очистки истории, точного имени,
   временной границы, перезапусков и правил очереди.

## Критерии приёмки

1. Успешная финальная задача переводит подзадачу в `done` и сохраняет квитанцию;
   следующий цикл с пустым списком задач сохраняет всё состояние без изменений.
2. Running-подзадача без задач завершается по merge-журналу только при точном
   имени и записи, созданной не раньше её `started_at`.
3. Старая merge-запись не завершает новую попытку после `running`, `failed` или
   `stuck`, даже когда запись о новой попытке уже очищена из истории API.
4. Подзадача с `hold_reason` не запускает зависящую следующую подзадачу;
   `parallel_ok` по-прежнему стартует независимо в пределах лимита.
5. Изменение не меняет API, UI и формат существующих эпиков без новых полей.

## План тестирования

Добавить `EpicCompletionReceiptTests` в `pilot/test_pilot.py` с временными
`EPIC_DIR` и `MERGES_PATH`. Проверить сохранение квитанции после очистки,
точное совпадение имени, отсечение старого merge, границы перезапуска для
`failed`/`stuck`, а также `hold_reason` и `parallel_ok`.

Обязательная целевая проверка: `python3 -m unittest
pilot.test_pilot.EpicCompletionReceiptTests`. Перед передачей реализации также
прогнать весь модуль: `python3 -m unittest pilot.test_pilot`.

## Риски и решения

- Решение: квитанция хранится внутри эпика, а не в истории API, потому что
  очистка истории является штатным процессом и не должна менять факт приёмки.
- Решение: достаточно точного имени и времени старта; связывание по одному
  `task_id` не пережило бы очистку истории, а неточное совпадение способно
  закрыть другую работу.
- Риск: старые merge-записи без корректной даты не считаются доказательством;
  это безопаснее ложного завершения и оставляет подзадачу running до свежего
  подтверждения.
- Вне области: изменение хранения истории задач, экран эпиков, API и общая
  переработка планировщика.
