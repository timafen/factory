# Спецификация: архив неактуальных регистраций исполнителей

## Цель и влияние на владельца

Владелец должен видеть на `/workers` фактический текущий парк, а не все
когда-либо зарегистрированные машины. Сейчас старые offline-регистрации остаются
в ответе API и попадают в единый список и в сводку, поэтому «Registered» не
отвечает на практический вопрос о доступном парке.

После изменения экран показывает только регистрации с heartbeat моложе семи
суток как текущий парк. Старые записи не теряются: они доступны в свёрнутом
архиве и по-прежнему открывают профиль исполнителя. Сводка даёт владельцу
раздельные числа `Current`, `Online`, `Available slots` и `Archived`; доступная
ёмкость не завышается историческими регистрациями.

Это только представление в web-клиенте. Удаление регистраций, изменение
маршрутизации задач, серверная фильтрация и изменение правила online не входят
в работу.

## Технический подход и реальные файлы

### Существующий контракт

`internal/controlplane/store.go` в `Store.Workers` выбирает все строки
`workers` и сортирует их по `registered_at, id`; SQL не ограничен свежим
heartbeat. Это полезный полный API-контракт и он остаётся без изменений.
`scanWorker` в том же файле вычисляет `Worker.Online` на серверном времени по
`protocol.WorkerOnlineWindow`, который сейчас равен 30 секундам в
`internal/protocol/types.go`. Клиент использует уже полученное поле `online` и
не пересчитывает его.

`web/src/api.ts` отдаёт этот ответ как `Worker[]`, а
`web/src/Workers.tsx` сейчас называет его `registered`, выводит единым списком
и считает сводку по всему массиву. Именно здесь будет сделано разделение; API,
`Worker` type, маршруты `/workers` и `/workers/{id}` не меняются.

### Разделение и сводка

В `web/src/Workers.tsx` добавить небольшую чистую функцию/константу для окна
архива: семь раз по 24 часа в миллисекундах. За один render снять единый `now`,
вычислить `cutoff = now - 7d` и сохранить относительный порядок API внутри двух
массивов.

- Текущий парк: `Date.parse(worker.last_heartbeat) > cutoff`.
- Архив: timestamp ровно на границе либо старше (`<= cutoff`). Некорректный
  timestamp также уходит в архив, чтобы сомнительная запись не влияла на
  оперативную ёмкость.
- Новый heartbeat при следующем polling-ответе автоматически возвращает
  исполнителя в текущий парк; никакой миграции и записи в API для этого нет.

Числа сводки считаются только от текущего массива: `Current` — его длина,
`Online` — количество с серверным `online=true`, `Available slots` — сумма
`max(capacity - active_count, 0)` только для current + online + healthy,
`Archived` — длина архивного массива. Offline worker моложе семи суток остаётся
в текущем списке, но не добавляет online или capacity.

### Представление и доступность

При действительно пустом ответе API (`workers.length === 0`) остаётся текущий
`No workers registered` empty state. Когда ответ непустой, но все записи
архивные, экран показывает сводку с `Current 0`, отдельное понятное состояние
«нет текущих исполнителей» и счётчик `Archived`; это не должно выглядеть как
отсутствие регистраций.

Архив по умолчанию скрыт. При `Archived > 0` рядом с текущим списком есть
кнопка `Show archived (N)`; повторное нажатие меняет её на `Hide archived (N)`.
Кнопка имеет корректный `aria-expanded` и связывается с раскрываемой областью.
После раскрытия архив использует те же заголовки и строки, что текущий список;
нажатие на любую архивную строку передаёт прежний ID в `onWorker` и открывает
существующий профиль. Если архив пуст, дополнительная кнопка и пустой блок не
рисуются.

В `web/src/styles.css` сводка станет сеткой из четырёх ячеек на широком экране.
На ширине до 760px она перестраивается в две колонки с `minmax(0, 1fr)` и
корректными внутренними границами. Заголовок архива и раскрытый список не
добавляют min-width шире контейнера; действующее компактное представление
`.worker-row` на ширине до 980px сохраняется. Это исключает горизонтальный
overflow и на 390px, и на планшете.

Реализационные файлы: `web/src/Workers.tsx`, новый
`web/src/Workers.test.tsx`, `web/src/styles.css` и
`web/e2e/control-plane.spec.ts` для проверки узкой компоновки. Файлы control
plane, protocol и API-клиент не изменяются.

## Критерии приёмки

| Сценарий | Проверяемый результат |
| --- | --- |
| Граница архива | Worker с `last_heartbeat` ровно `now - 7d` находится в `Archived`; запись на одну миллисекунду новее остаётся `Current`. |
| Возврат в парк | После нового heartbeat та же запись появляется в current на следующем ответе, без изменения API или базы. |
| Сводка | Показывает `Current`, `Online`, `Available slots`, `Archived`; online и slots учитывают только current, а slots — только healthy online. |
| Offline, но свежий | Offline worker моложе семи суток виден в current; его online остаётся серверным значением и capacity не добавляется. |
| Пустые состояния | Пустой API показывает `No workers registered`; непустой all-archived ответ показывает сводку, `Current 0` и доступный архив. |
| Архив | До нажатия архивные строки не рендерятся; кнопка показывает точный счётчик, меняет `aria-expanded`, а строка после раскрытия открывает профиль. |
| Компоновка | На 390px и 800px summary/списки не выходят за ширину `main`; мобильная строка исполнителя сохраняет действующий компактный вид. |
| Границы системы | `/api/v1/workers` по-прежнему возвращает все регистрации; 30-секундное серверное вычисление `online`, API-типы и маршруты профилей не меняются. |

## Тест-план

В новом `web/src/Workers.test.tsx` рендерить `WorkersView` с фиксированным
временем. Табличные fixtures должны покрыть fresh online healthy worker, fresh
offline worker, unhealthy worker, worker ровно на границе и старую архивную
запись. Проверить разделение, четыре значения summary и исключение архивных
строк из доступных slots.

Отдельные tests проверяют all-archived против пустого ответа, исходно скрытый
архив, смену подписи/`aria-expanded`, точный счётчик и вызов `onWorker` по
архивной строке. Rerender с новым heartbeat доказывает возврат записи в current.
В случае некорректной даты test фиксирует fail-closed помещение в архив.

В `web/e2e/control-plane.spec.ts` расширить существующий сценарий narrow
layouts: на `/workers` при 390px проверить, что `main.scrollWidth <=
main.clientWidth`, и сохранить existing screenshot. Это покрывает четыре
summary-card без зависимости от живого семидневного ожидания.

Целевые команды реализации:

- `cd web && npm test -- Workers.test.tsx`
- `cd web && npm run lint`
- `cd web && npm run typecheck`
- `cd web && npm run build`
- `cd web && npx playwright test e2e/control-plane.spec.ts --grep "supports narrow grouped layouts"`

## Риски и решения

- Клиентские часы могут отличаться от server time. Решение: семь суток — только
  UX-граница отображения, а online и routing остаются server authoritative;
  один `now` на render не даёт одной записи попасть в обе группы на границе.
- ISO timestamp может быть повреждён. Решение: `NaN` не попадает в current и
  не увеличивает capacity; API-контракт продолжает ожидать RFC3339 от Go.
- Четвёртая карточка сводки может переполнить мобильный экран. Решение:
  двухколоночная `minmax(0, 1fr)` сетка и browser assertion фактической ширины.
- Дублирование разметки current/archive способно разойтись. Решение: один
  общий renderer таблицы/строки и один `onWorker` callback для обеих групп.
- Архив могут принять за удаление worker. Решение: явные `Archived` count,
  доступная кнопка и сохранённый переход в профиль; база и API не фильтруются.
