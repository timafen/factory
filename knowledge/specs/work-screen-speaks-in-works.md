# Экран «Работа» говорит на языке работ, а не задач

## Цель и влияние на владельца

Экран должен давать владельцу одну карточку на одну работу и называть разные
виды ожидания по их смыслу. Сейчас `web/src/Work.tsx` объединяет этапы по
очищенному тексту заголовка: две независимые работы с одинаковым названием
сливаются, хотя task API уже возвращает устойчивый `work_id`. Одновременно
надписи «В очереди Factory», «Ждёт следующий этап» и колонка задач «В очереди»
используют одно слово для трёх разных состояний.

После изменения существующие задачи одного `work_id` образуют одну историю, а
одинаково названные, но разные работы остаются раздельными. Владелец видит,
ожидает ли текущий этап свободного исполнителя, готовит ли Factory следующий
этап или отдельная задача ещё не начала выполнение. Работы без единой задачи
не показываются: отдельного серверного реестра таких работ в этой работе нет.

## Технический подход и реальные файлы

В `web/src/types.ts` добавить в `Task` необязательный `work_id?: string` в
соответствии с уже действующим `internal/protocol/types.go` (`WorkID`, JSON
`work_id,omitempty`). Сервер, миграции и HTTP-маршруты не меняются.

В `web/src/Work.tsx` дать `Group` устойчивый `id`. `build()` выбирает ключ как
непустой `task.work_id`, а для legacy-задачи без provenance — как разобранный
`base` заголовка. Отображаемое имя остаётся `base`; оно не является identity.
Метаданные `works`, `statuses` и `promises` сначала читаются по group id, а для
legacy-ответа — по `base`. React `key`, состояние раскрытия и локальные
индикаторы возобновления используют group id, поэтому одинаковые подписи не
связывают состояние карточек. Публичный `onResume` продолжает получать
человекочитаемый `base`, поскольку контракт resume сейчас адресует работу по
названию; менять этот API вне области задачи.

Три смысла ожидания развести так:

- статус live-задачи `queued`: «Ждёт исполнителя»;
- успешный промежуточный этап до handoff: «Factory готовит следующий этап»;
- раздел работ: «Ожидают исполнителя», подсказка «Текущий этап ещё не начат»;
- в переключаемой доске этапов техническое состояние задачи остаётся явно
  названным «Задачи: ожидают запуска», а пустое состояние — «Таких задач нет».

Заголовок основного экрана заменить с «Работа агентов» на «Работа», а пункт
основной навигации `Work` в `web/src/App.tsx` — на «Работа». Служебный пункт
`Workers` назвать «Исполнители», чтобы экран работ не воспринимался как
мониторинг агентов. Маршруты и поведение навигации остаются прежними.

В `web/src/Work.test.ts` проверить identity и статусы чистой функции. В
`web/src/WorkView.test.tsx` проверить две одновременно видимые карточки с
одинаковым названием и разными `work_id`, независимое раскрытие и новые
владелец-ориентированные формулировки. В `web/src/App.test.tsx` закрепить русские
названия двух пунктов навигации.

## Последовательный план

1. Расширить web-тип `Task` полем `work_id`, не меняя server contract.
2. Добавить group id и перевести группировку, lookup сопутствующих данных и
   UI-state карточек на `work_id` с title fallback только для legacy-задач.
3. Заменить заголовок экрана, подписи навигации и четыре формулировки ожидания,
   не меняя вычисление состояний.
4. Добавить unit-регрессию для одинаковых названий и component-регрессию для
   независимых карточек; обновить существующие ожидания текстов.
5. Запустить целевые web-тесты, typecheck и `git diff --check`.

## Критерии приёмки

1. Все загруженные существующие задачи с одним непустым `work_id` показаны в
   одной карточке работы независимо от текста stage-заголовков.
2. Две существующие задачи с одинаковым отображаемым названием и разными
   `work_id` показаны двумя карточками; раскрытие одной не раскрывает другую.
3. Задачи без `work_id` продолжают группироваться по прежнему разобранному
   названию, поэтому старые записи не исчезают.
4. Metadata/status/promise для нового контракта находятся по `work_id`, с
   fallback по названию для legacy-данных.
5. В интерфейсе различимы ожидание исполнителя текущим этапом, подготовка
   следующего этапа и queued-состояние отдельной задачи; три случая не имеют
   одинаковой голой подписи «В очереди».
6. Основной экран и навигация называют сущность «Работа», а служебный экран —
   «Исполнители»; голый `work_id` владельцу не показывается.
7. Работа без задач не появляется и не требует нового endpoint, реестра или
   durable storage; критерии применяются только к задачам, уже отданным API.

## Тест-план

В `Work.test.ts` создать пары задач: общий `work_id` при разных stage-title,
разные `work_id` при одинаковом base title и legacy-задачи без `work_id`.
Проверить количество групп, их id/base и новые статусы ожидания.

В `WorkView.test.tsx` отрендерить две одноимённые работы с разными `work_id`,
убедиться, что обе карточки присутствуют, и клик по одной показывает историю
только её task id. Отдельно проверить тексты раздела работ и доски этапов. В
`App.test.tsx` проверить доступные имена «Работа» и «Исполнители».

Обязательная целевая команда:

`npm --prefix web test -- --run src/Work.test.ts src/WorkView.test.tsx src/App.test.tsx`

Дополнительно: `npm --prefix web run typecheck` и `git diff --check`.

## Риски и решения

- Риск: часть старых задач не имеет `work_id`. Решение: явный fallback на
  разобранный title; он не применяется, если provenance присутствует.
- Риск: `works.json` и связанные pilot-файлы переходили с title-ключа на
  `work_id` постепенно. Решение: lookup сначала по id, затем по base.
- Риск: одинаковый base всё ещё нужен resume API. Решение: UI identity и
  callback argument разделены; изменение resume endpoint вынесено за границу.
- Решение: `work_id` остаётся внутренним ключом и не выводится на экран —
  владелец различает карточки по их отдельной истории и состоянию, без голого
  технического идентификатора.
- Осознанное ограничение: pre-task реестр не создаётся. Сейчас работа без задач
  не существует как доступная экрану сущность; расширение требует отдельного
  подтверждения потребности и серверного контракта.
