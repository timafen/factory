# Спецификация: старшая модель перед ответом на административный вопрос

## Цель и влияние на владельца

Административный вопрос, который действительно требует решения владельца,
сначала получает один разбор старшей моделью через строго разрешённый вызов
`fx staging`; владельцу показывается только результат, если модель не может
безопасно решить вопрос сама. Технические вопросы по-прежнему решаются
оркестратором автоматически, а повторные ответы и произвольные shell-команды
не должны расходовать доступы стенда.

Владелец видит человеческое объяснение, причину эскалации и конкретный вопрос;
он не видит сырой argv, секреты, промпт или внутренний хеш как название.

## Текущее поведение и границы

- `pilot/pilot.py:route_question()` вызывает `orchestrator_answer()` для каждого
  обычного вопроса, а затем сразу записывает эскалацию владельцу.
- `pilot/pilot.py:orchestrator_answer()` получает решение через общий `brain()`;
  `brain()` формирует argv отдельных `codex`/`claude`, поэтому специального
  приоритета для административного вопроса нет.
- `pilot/pilot.py:write_question()` и `web/src/Answer.tsx` отвечают за запись и
  показ вопроса; формат вопроса и UI менять не требуется.
- `ops/fx` — единственный мост к стенду и уже использует allowlist. Вызов
  должен быть только фиксированным массивом аргументов, без конкатенации
  пользовательского текста и без `shell=True`.

## Технический подход и реальные файлы

1. Ввести отдельную функцию/маршрутизатор административного разбора в
   `pilot/pilot.py`. Она получает только нормализованные поля
   `stage`, `base`, `situation`, `question` и `prior_result`, ограничивает их
   размер и запускает ровно заданный argv:
   `sudo -n /usr/local/bin/fx staging brain admin-question --model=<senior-model>`.
   Точный подкомандный контракт должен быть согласован с установленным
   `ops/fx` до реализации; до этого нельзя подставлять близкий по смыслу
   `fx staging sandbox` или произвольный verb.
2. Разрешить только senior-модель из конфигурации (`admin_question_model`),
   заданную полностью, без выбора модели из вопроса. Передать текст через
   stdin или отдельный безопасный payload-механизм, если это предусмотрено
   контрактом `fx`; argv остаётся неизменным для каждого вызова.
3. В `route_question()` вызывать новый путь до записи owner-only вопроса только
   для вердикта `escalate`. Ответ `answer` сохранять как
   `answered_by=orchestrator`, `wait` сохранять как машинную паузу; сбой или
   невалидный ответ senior-пути должен безопасно вернуть обычную эскалацию.
4. В `pilot/config.example.json` документировать senior-модель и явный
   enable/disable-флаг с безопасным default. Секреты, пути к сокетам и полный
   текст вопроса в конфиг не добавлять.
5. В `pilot/test_pilot.py` добавить тесты фиксации полного argv, stdin,
   запрета пользовательских argv-фрагментов, приоритета senior-пути и
   fallback при ненулевом коде/невалидном JSON.
6. `ops/fx` изменить только если текущий allowlist не поддерживает ровно этот
   контракт; добавить строгую проверку количества и формы аргументов, без
   расширения доступа к произвольному `manage.py` или shell.

### Данные и API

Новых HTTP endpoint и изменений UI нет. В существующую запись вопроса можно
добавить только технические поля происхождения ответа (`answered_by`,
`model_route`), не сохраняя промпт, секреты или полный stderr. Формат старых
вопросов остаётся читаемым.

## Последовательный план

1. Зафиксировать фактический контракт установленного `fx staging` и имя
   senior-модели; если `brain admin-question` не существует, сначала добавить
   его в allowlist `ops/fx` и покрыть отрицательными argv-тестами.
2. Реализовать изолированный runner с массивом argv, таймаутом, ограничением
   stdin/stdout и разбором только ожидаемого JSON.
3. Подключить runner в ветку административной эскалации `route_question()`;
   сохранить текущие answer/wait/owner-only переходы.
4. Добавить целевые unit-тесты, затем выполнить обязательную проверку.
5. Реальный staging smoke выполнять только после разрешения доступа и только
   точным argv из контракта; production не затрагивать.

## Критерии приёмки

- Для административного `escalate` первым модельным действием является ровно
  senior-вызов через зафиксированный `fx staging` argv.
- Вызов не принимает команду, модель, флаги или shell-синтаксис из текста
  вопроса; неожиданный argv отклоняется до запуска.
- Успешный валидный ответ senior-модели продолжает работу по существующим
  правилам и помечается источником ответа; `wait` действительно оставляет
  pipeline на паузе.
- Ненулевой exit code, timeout, пустой вывод и невалидный JSON не запускают
  следующий этап автоматически и создают понятную owner-эскалацию.
- Обычные вопросы, лимиты brain-chain, UI, production и секреты не меняют
  поведения.

## Тест-план

- `pilot/test_pilot.py`: fake `subprocess.run`/runner проверяет полный список
  argv, stdin и отсутствие shell; senior отвечает, затем вопрос повторяется с
  тем же argv и без второго fallback-вызова.
- Отрицательные случаи: лишний флаг, подмена модели, инъекция через текст,
  timeout, код выхода не 0 и JSON без допустимого `decision`.
- Регрессия: существующий набор `pilot.test_pilot` и `python3 -m py_compile
  pilot/pilot.py`.
- Живая проверка (если доступна): `sudo -n /usr/local/bin/fx staging brain
  admin-question --model=<senior-model>` с безопасным тестовым вопросом; в
  спецификации не считать health/login доказательством результата.

## Риски и решения

- Контракт `brain admin-question` сейчас не найден в checkout: реализация
  блокируется до его подтверждения; подмена на другой `fx staging` verb
  запрещена.
- Senior-вызов может увеличить задержку и стоимость: один вызов на одну
  эскалацию, таймаут и запрет повторов в том же цикле.
- Утечка вопроса в логи: логировать только статус, причину и длительность;
  stdin/stderr не писать целиком.
- Установленный bridge может отличаться от репозитория: тест argv должен
  проверять локальный контракт, а smoke — фактический stderr и exit code.
- Сбой senior-пути не должен скрывать вопрос владельцу: безопасный fallback
  сохраняет текущую owner-only запись.
