# Мониторинг прав Codex проверяет цель ссылки, а не режим симлинка

## Цель и влияние на владельца

Перестать создавать тревогу «OAuth-токены воркеров лежат с правами 777», когда
`auth.json` воркера — обычный Linux-симлинк на защищённый общий файл. Владелец
должен получать предупреждение только при реальном риске: конечный
`auth.json` отсутствует, не является обычным файлом, принадлежит не
`factory:factory` или имеет режим не `600`.

Исходное сообщение этой работы не является новой уязвимостью и закрывается как
дубликат `CARD-0047`: все 11 рабочих путей — ссылки, а общая цель уже проверена
как `regular file 600 factory:factory`. Новая `CARD-0095` относится только к
ложноположительной проверке мониторинга и не меняет provisioning из CARD-0047.

## Технический подход и реальные файлы

В репозитории нет отдельного проверяющего скрипта мониторинга OAuth-прав. Есть
`ops/provision-codex-auth.sh`, который до выпуска уже проверяет общую цель, и
`ops/test-provision-codex-auth.sh`, который доказывает fail-closed provisioning.
Чтобы периодический мониторинг использовал тот же проверяемый контракт, добавить
отдельную read-only команду `ops/check-codex-auth-permissions.sh`:

- обнаруживать только `auth.json`-симлинки непосредственных каталогов
  `$FACTORY_CODEX_DATA_HOME/.codex-*`; не менять ссылки, цели или владельцев;
- сначала явно подтверждать, что путь является симлинком, но не считать
  результат `lstat`/обычного `stat` проверкой доступа к секрету;
- получать тип, режим, владельца и группу конечной цели одной командой
  `stat -Lc '%F %a %U %G' -- "$link"`, то есть с разыменованием ссылки;
- принимать только `regular file 600 factory factory`; dangling-ссылку,
  каталог, неверного владельца/группу и любой другой режим считать тревогой;
- печатать только путь и безопасные метаданные, никогда не читать и не выводить
  содержимое OAuth-файла; возвращать `0`, только если безопасны все найденные
  ссылки, и ненулевой код при любой реальной проблеме;
- отсутствие Codex-воркеров считать штатным состоянием без тревоги, как это
  уже делает provisioner.

Регрессию разместить в `ops/test-check-codex-auth-permissions.sh`, подключить её
к `test-tooling` в `Justfile`, а операторскую команду и смысл `stat -L` описать
в `ops/README.md`. Контекст живой Automation, породившей исходное предупреждение,
обновить через штатное версионируемое API Automations: она должна вызывать этот
checker вместо собственной проверки режима ссылки. Идентификатор, расписание и
исторические Occurrence не менять; секреты в context и результат не записывать.

## Последовательный план

1. Сохранить текущую находку как дубликат CARD-0047 и определить Automation,
   которая выполнила ошибочную проверку, по связанной Occurrence/Task.
2. Добавить read-only checker с настраиваемыми data home, ожидаемыми
   пользователем и группой для изолированного теста.
3. Реализовать проверку конечной цели через `stat -Lc`, явную обработку
   симлинков и единый ненулевой результат при найденных нарушениях.
4. Добавить shell-регрессию на безопасную цель за ссылкой с отображаемым
   режимом `777` и на небезопасные права конечного `auth.json`.
5. Включить тест в `Justfile`, документировать команду, затем новой версией
   Automation заменить ad hoc-проверку на checker без изменения расписания.
6. Выполнить Run now: безопасные рабочие ссылки не создают находку; отдельный
   изолированный fixture с небезопасной целью завершается ненулевым кодом.

## Критерии приёмки

1. Симлинк `.codex-*/auth.json`, чей собственный режим отображается как `777`,
   не вызывает предупреждение, если его конечная цель — обычный файл с режимом
   `600` и ожидаемыми владельцем и группой.
2. Конечный `auth.json` с режимом `644`, `660` или `777` обнаруживается; checker
   возвращает ненулевой код и сообщает путь и метаданные без содержимого файла.
3. Dangling-ссылка, ссылка на каталог, неверный владелец или группа также дают
   ненулевой код; отсутствие каталогов воркеров возвращает `0`.
4. Проверка не выполняет `chmod`, `chown`, замену ссылки или чтение секрета.
5. `test-tooling` запускает новую регрессию, поэтому возврат к `stat` без `-L`
   ломает обязательную проверку.
6. Обновлённая Automation сохраняет прежнее расписание и историю, а Run now на
   фактических 11 безопасных ссылках не создаёт повторную карточку о режиме 777.

## Тест-план

- В `ops/test-check-codex-auth-permissions.sh` создать временный data home,
  обычный `auth.json` режима `600` и ссылку на него. Подтвердить, что обычный
  `stat -c %a` ссылки показывает `777`, после чего checker завершается с `0`.
- Последовательно менять режим именно целевого файла на `644` и `777`; в обоих
  случаях ожидать ненулевой код и безопасную диагностику. Вернуть `600` и
  проверить dangling-ссылку, каталог, владельца/группу через доступные тестовому
  пользователю настройки, а также отсутствие воркеров.
- Добавить маркер-секрет и подтвердить, что он не появляется в stdout/stderr.
- Запустить целевой тест `bash ops/test-check-codex-auth-permissions.sh`, затем
  существующий `just test-tooling` и `git diff --check`.
- После обновления Automation выполнить Run now и сверить связанную Occurrence:
  код checker равен `0`, новой finding/Task про `777` нет; это live-проверка,
  но не основание читать содержимое `/opt/factory-data/.codex/auth.json`.

## Риски и решения

- `stat` без `-L` снова измерит inode ссылки и вернёт типичный режим `777`.
  Решение: регрессия сначала доказывает `777` у ссылки, затем требует успешный
  результат checker; реализация использует именно `stat -Lc`.
- Несколько ссылок ведут на одну цель и могут повторять одну диагностику.
  Это допустимо для кода возврата; вывод можно дедуплицировать по канонической
  цели, не скрывая список затронутых ссылок.
- TOCTOU между обнаружением ссылки и `stat` полностью не устраняется shell-кодом.
  Checker read-only и запускается периодически; исчезновение/подмена цели даёт
  ошибку текущего прогона. Атомарность provisioning остаётся в CARD-0047.
- Изменение только prompt/context без исполнимого checker вновь оставит семантику
  на усмотрение агента. Поэтому Automation должна вызывать версионированную
  команду, а тест — жить в репозитории.
- Исправление режима самого симлинка отклонено: на Linux он не определяет доступ
  к содержимому цели и не устраняет причину ложного предупреждения.
