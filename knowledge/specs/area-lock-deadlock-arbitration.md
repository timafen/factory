# Детерминированный арбитраж замка областей

## Цель и влияние на владельца

Две работы, заявившие один и тот же файл в одном репозитории, не должны
выбирать друг друга владельцем и оставаться в `AREA WAIT` навсегда. Pilot
должен один раз выбрать, кто продолжает, сохранить выбор, а вторую работу
возобновить после освобождения области без ручного ответа и повторного решения
модели.

Для владельца это означает, что пересекающиеся поставки идут последовательно и
предсказуемо: порядок Плана соблюдается, вручную заведённые работы получают
устойчивый порядок, журнал не повторяет одно и то же ожидание каждый цикл.
Экран и схема control plane не меняются.

## Технический подход и реальные файлы

Причина находится в `pilot/pilot.py`: `area_busy()` возвращает первую живую
чужую работу с пересечением, а `review_gate()` отдельно ищет первого соседа по
файлам закреплённого diff. Ни одна проверка не назначает владельца, поэтому для
A и B допустимы одновременно ответы «A ждёт B» и «B ждёт A». Существующий
`state["overlap_wait_decisions"]` сохраняет результат `decide()` для
ожидающего task, но не право на область.

В `pilot/pilot.py` нужен единый арбитр допуска, которым пользуются и обычный
переход стадии, и проверка перед Review:

- единица идентичности работы — `task_work_id(task)`: `work_id` для новых
  задач, а для legacy-задач устойчивый ключ из repository id и базового
  названия;
- единица конфликта — точная пара `(repository_id, path)`. Старые записи
  `areas.json` без репозитория при чтении активной работы дополняются её
  `repository_id`; одинаковые пути разных репозиториев и разные пути одного
  репозитория не конфликтуют;
- при первой конкуренции строится общий детерминированный порядок. Работа из
  Плана получает ключ `(0, order, stable_work_id)`. Ручная работа получает
  ключ `(1, first_assigned_at, stable_work_id)`, где `first_assigned_at`
  берётся из неизменяемого `works.json.at`, с запасным минимумом
  `task.created_at`. Поэтому порядок входного списка задач не влияет на
  результат, а Plan имеет приоритет перед ручным запуском;
- допуск выбирается атомарно для всей заявленной области, а не по одному
  файлу. Уже сохранённые живые владельцы остаются первыми, затем остальные
  кандидаты обходятся по ключу: работа допускается, только если вся её область
  не пересекает уже допущенные. Это не создаёт частичных захватов и разрешает
  одновременно продолжать непересекающиеся работы;
- выбранный `stable_work_id`, repository id, набор путей и источник
  приоритета сохраняются в `STATE_PATH` до запуска следующего task. Запись
  делается до внешнего `create_child_task`, поэтому новый цикл или рестарт не
  меняет победителя. Изменение порядка Плана после выбора не вытесняет живого
  владельца;
- ожидающий task остаётся непроцессированным, а его verdict остаётся в
  `overlap_wait_decisions`. Verdict читается без преждевременного `pop()` и
  удаляется только после успешного перехода либо окончательного закрытия
  работы. После освобождения замка waiter продолжает с тем же verdict и не
  вызывает `decide()` снова;
- владелец освобождается, когда его заявка больше не может продолжаться:
  работа завершена, остановлена или отменена, либо фактический diff после
  `area_replace()` больше не содержит ресурс. Созданная/queued/running стадия
  и сохранённый успешный переход удерживают владение между стадиями. Одно
  отсутствие владельца в ограниченном списке `/tasks?limit=100` не является
  доказательством освобождения: Pilot проверяет сохранённую опорную задачу и
  при недоступности control plane безопасно сохраняет замок;
- для ожидания хранится fingerprint из waiter, владельца, репозитория и путей.
  `AREA WAIT` пишется при первом ожидании и при изменении fingerprint, но не в
  каждом неизменном цикле. После освобождения fingerprint удаляется, чтобы
  новое независимое ожидание снова было видно.

`review_gate()` должен использовать тот же арбитр с файлами свежего
закреплённого diff и вернуть существующий `{"wait": true}` без запуска Review.
Его собственный выбор «первого соседа» удаляется. Проверка обычного перехода
перед созданием следующей стадии передаёт заявленную область тому же арбитру.

Изменяются только:

- `pilot/pilot.py` — общий арбитр, долговечное владение, освобождение и
  дедупликация журнала в обоих местах перехода;
- `pilot/test_pilot.py` — регрессионные сценарии арбитража, рестарта,
  освобождения и изоляции.

## Последовательный план

1. Ввести каноническое представление work id, repository id и path, чтение
   Plan-приоритета и времени первого назначения с legacy fallback.
2. Добавить в состояние Pilot версионированные заявки/владения областями и
   функцию их сверки с активными либо ожидающими продолжения работами.
3. Реализовать атомарный жадный допуск по полному детерминированному порядку,
   сначала сохраняя действующих владельцев, затем выбирая непересекающихся
   победителей.
4. Подключить допуск к обычному переходу стадии и к `review_gate()`, сохранив
   один verdict на всё время ожидания.
5. Добавить освобождение завершённого владельца и fingerprint ожидания;
   неизменный wait не должен повторно логироваться.
6. Закрепить поведение целевыми unit-тестами и проверить компиляцию изменённых
   Python-файлов.

## Критерии приёмки

- При двух работах над одним `repository_id::path` ровно одна получает допуск;
  обе работы не могут ждать друг друга независимо от порядка задач во входном
  снимке.
- Среди работ Плана побеждает меньший `order`; ручные работы сравниваются по
  времени первого назначения, затем по стабильному work id. Выбор не меняется
  после повторного цикла, перестановки входа или перезапуска Pilot.
- Одно правило действует перед обычной следующей стадией и перед Review.
- После завершения/остановки владельца waiter автоматически создаёт следующий
  task, используя сохранённый verdict; `decide()` за всё ожидание вызван один
  раз.
- Работа захватывает всю область либо ничего: встречного или частичного
  ожидания для нескольких пересекающихся файлов нет.
- Одинаковый путь в разных репозиториях и разные пути в одном репозитории
  допускаются одновременно.
- Неизменное ожидание создаёт одну запись `AREA WAIT`; смена владельца или
  набора путей создаёт новую запись, а освобождение очищает дедупликацию.
- Ошибка проверки состояния владельца не освобождает область предположением и
  не запускает конкурирующую работу.
- После выпуска оператор снимает паузу с работы «Провалы запусков
  Автоматизации» и возвращает её в очередь; это rollout-действие, а не часть
  изменения исходников.

## Тест-план

В `pilot/test_pilot.py` добавить отдельный `AreaLockArbitrationTests`:

- взаимный конфликт A/B при прямом и обратном порядке входа: победитель один и
  тот же, проигравший ждёт;
- сериализация состояния и новый вызов `cycle()` с загруженным состоянием:
  победитель сохраняется после рестарта;
- удаление/терминальное состояние владельца: waiter продолжает, создаётся один
  следующий task, `decide()` остаётся вызван один раз;
- одинаковый сценарий через обычный `area_busy`-переход и `review_gate`;
- таблица приоритетов: две Plan-карточки, две ручные работы с одинаковым и
  разным временем, стабильный ID как последний tie-break;
- три работы с областями `{a}`, `{a,b}`, `{b}`: крайние работы допускаются
  вместе, средняя не получает частичный замок;
- одинаковый path в двух repository id и два разных path в одном repository id
  не блокируются;
- два неизменных цикла дают один `AREA WAIT`, изменение blocker/path — второй;
- отсутствие опорной задачи в коротком снимке и ошибка её чтения не снимают
  живое владение.

Обязательная целевая команда запускает весь новый класс. Дополнительно на
этапе реализации выполнить `python3 -m py_compile pilot/pilot.py
pilot/test_pilot.py`; полный набор относится к Verify.

## Риски и решения

- **Старые области не содержат repository id.** Квалифицировать их только по
  репозиторию фактической активной задачи и сохранять миграцию; не переносить
  неуточнённый замок на другой репозиторий.
- **Порядок Плана меняется во время ожидания.** Порядок влияет только на первое
  решение; сохранённого живого владельца не вытеснять.
- **Снимок задач ограничен ста строками.** Не освобождать владельца по
  отсутствию в снимке; проверять сохранённую опорную задачу, а при ошибке
  оставлять замок закрытым.
- **Сбой после допуска и до создания дочерней задачи.** Сначала сохранять
  владение и ожидающий verdict, затем выполнять внешний POST; повтор использует
  прежнее владение и существующую идемпотентность создания task.
- **Несколько файлов дают цикл частичных замков.** Выбирать допуск сразу для
  полного набора путей жадным проходом по общему порядку; частичное владение
  запрещено.
- **Старые записи состояния имеют прежний формат.** Версионировать новый раздел
  состояния, терпимо читать отсутствие полей и покрыть миграцию unit-тестом.
