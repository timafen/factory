# Спецификация: архивные вытесненные попытки не расходуют лимит повторов

## Цель и влияние на владельца

Продолжение текущей работы не должно останавливаться раньше времени из-за её
старых попыток, которые уже вытеснены более новой задачей и сохранены в архиве.
Владелец получает вопрос или остановку только после фактического исчерпания
`max_stage_attempts` в текущем поколении работы, а сохранённая история остаётся
доступной и не удаляется.

## Технический подход и реальные файлы

- В `pilot/pilot.py` изменить расчёт `stage_attempts(tasks, stage, base)`: перед
  подсчётом загрузить `WORKS_PATH`, найти метаданные той же работы с учётом
  `work_id`/`same_task_work` и исключить ID из `archived_attempts`.
- Не менять `cleanup_work_archive`: он уже записывает ID terminal-задачи в
  `works.json.archived_attempts`, когда её вытеснила более новая задача, и
  делает запись идемпотентно.
- В `pilot/test_pilot.py` добавить регрессию на одну архивную вытесненную и
  одну актуальную попытку одного этапа. Отдельно подтвердить, что terminal-
  попытка без архивной квитанции по-прежнему расходует лимит.
- Не менять API, схему БД и UI: исправление находится в локальном учёте Pilot.

## Последовательный план

1. Добавить небольшой способ получить множество архивных task ID для текущей
   работы из `works.json`, безопасно трактуя отсутствующие метаданные как пустые.
2. Отфильтровать эти ID внутри `stage_attempts`, сохранив существующую проверку
   точного этапа и принадлежности задачи работе.
3. Добавить unit-тесты для архивной и обычной истории, а также для двух работ с
   одинаковым заголовком, но разными `work_id`.
4. Запустить целевые тесты Pilot.

## Критерии приёмки

- Вытесненная terminal-попытка, чей `task_id` есть в
  `works.json.archived_attempts` текущей работы, не входит в результат
  `stage_attempts`.
- Текущая и прочие неархивные попытки того же этапа продолжают учитываться.
- Архив другой работы, включая работу с таким же базовым заголовком, не влияет
  на лимит текущей работы.
- При отсутствии карточки работы в `works.json` поведение остаётся прежним.
- Архивная запись и история задачи не удаляются и не переписываются.
- Порог `max_stage_attempts`, диагностика и hard-limit получают исправленное
  число актуальных попыток без изменения их собственной логики.

## Тест-план

- Новый unit-тест создаёт старую failed-задачу, актуальную задачу того же этапа
  и архивную квитанцию для старой; ожидаемый счётчик — `1`, а не `2`.
- Парный сценарий без квитанции ожидает `2` и защищает реальный лимит от
  неограниченных повторов.
- Сценарий одинаковых заголовков с разными `work_id` подтверждает изоляцию
  архивов поколений.
- Обязательная команда: `python3 -m unittest pilot.test_pilot.CorrectionProvenanceStormTests`.

## Риски и решения

- **Смешение одноимённых работ.** Искать архив по устойчивому идентификатору
  работы, а сопоставление задач оставлять на `same_task_work`, не полагаться
  только на текст заголовка.
- **Прощение настоящих сбоев.** Исключать только ID с уже сохранённой архивной
  квитанцией; failed/cancelled без неё считаются как раньше.
- **Повреждённый или старый архив.** Использовать существующий безопасный
  `load(..., {})`; неизвестная структура не должна падать и не должна уменьшать
  счётчик.
- **Расхождение мест применения лимита.** Менять общий `stage_attempts`, который
  уже передаёт `done` и в сравнение с `max_stage_attempts`, и в
  `route_question(attempts_so_far=done)`.
