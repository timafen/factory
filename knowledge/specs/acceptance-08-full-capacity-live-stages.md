# Спецификация: полная нагрузка не делает живой этап просроченным

## Цель и влияние на владельца

Когда все слоты конвейера заняты, сторож должен отложить только действительно
ожидающие переходы. Если работа уже снова имеет живой этап, старая запись о том,
что сторож «сдался», больше не должна держать её в состоянии `stuck` на экране
работ и не должна исчерпывать попытки следующего перехода. Владелец видит
фактическое состояние живой работы, а после завершения этапа получает обычное
новое 450-секундное окно ожидания и две штатные попытки продолжения.

## Технический подход и реальные файлы

В `pilot/pilot.py` функция `pipeline_watch` сейчас при заполненном
`max_parallel_works` использует быстрый выход: она перебирает только `mem`,
сдвигает `since` у неокончательных ожиданий и возвращает управление. Записи с
`why == "give_up"` сознательно пропускаются, а текущий активный снимок
`_active_work_tasks` не сопоставляется с ними. Из-за этого живой `running`,
`queued`, `pending`, `created` или `starting` этап не очищает старую просрочку;
к тому же до выхода не вызывается `work_status_write`, поэтому экран может
оставаться в `stuck`.

Реализация остаётся в быстром пути и читает только уже переданный ограниченный
снимок `_active_work_tasks`, а не параметр `tasks` и не историю задач. Она
выделяет из снимка канонические pipeline-title и `task_work_id` для живых
состояний `PIPELINE_LIVE_STATES`, удаляет соответствующую запись из `STALL_PATH`
включая legacy-запись `give_up`, затем сохраняет память и синхронизирует
`work_status.json`. Для остальных записей fast path сохраняет действующий
контракт: ожидание capacity получает новый `since`, сохраняет `nudges`, не
создаёт задачу и не отправляет уведомление. При следующем цикле после
завершения живого этапа обычная ветвь создаёт новую запись с `since=now`,
`nudges=0` и текущей `stage`; только через `STALL_WAIT` она может сделать
первую попытку.

Затрагиваются только `pilot/pilot.py` и `pilot/test_pilot.py`; пороги,
конфигурация capacity, UI-тексты и обработка обычного handoff не меняются.

## Последовательный план

1. Вынести или добавить малую сверку живых ключей из `_active_work_tasks` для
   fast path, используя существующие title parser, `task_work_id` и
   `PIPELINE_LIVE_STATES`.
2. До capacity deferral удалить записи памяти для найденных живых работ,
   включая `give_up`; не трогать `closed`/`owner` без живого этапа.
3. Сохранить обработанные записи и вызвать `work_status_write(mem)` перед
   ранним возвратом, чтобы старый transient `stuck` исчезал с экрана.
4. Оставить сдвиг `since` и неизменный `nudges` для остальных ожидающих работ;
   не вызывать `work_lifecycle_block`, `create_task` или `notify` в полном
   capacity fast path.
5. Добавить регрессионные тесты полного лимита, живого этапа и legacy
   `give_up`, затем проверить последующее штатное окно и отсутствие дублей.

## Критерии приёмки

1. При заполненном `max_parallel_works`, старом `give_up` в `STALL_PATH` и
   живом этапе той же работы в `_active_work_tasks` запись удаляется, задача не
   создаётся и срочное уведомление не отправляется.
2. После этой очистки `work_status.json` больше не содержит transient-статус
   `stuck` для работы; статус другой записи памяти не стирается.
3. Когда живой этап завершается и слот освобождён, новая переходная запись
   начинается с `since=now`, `nudges=0` и current stage; до 450 секунд нет
   попытки, по границе 450 секунд возможна первая штатная попытка.
4. Другая работа, ожидающая свободного слота, при полном лимите сохраняет
   `nudges`, получает новый `since`, не получает `nudge_failed`/`give_up`, не
   создаёт задачу и не отправляет уведомление.
5. Fast path не обходил `tasks`: тест с большой историей и заглушкой
   `work_lifecycle_block`, бросающей ошибку, завершается успешно.
6. Поддерживаются как legacy-ключ по базовому title, так и durable `work_id`,
   выбранный существующей функцией `task_work_id`; чужая живая работа не может
   очистить запись другой работы.

## Тест-план

- В `PipelineWatchTests` добавить регрессию: limit=1, в `STALL_PATH` лежит
  `give_up` с двумя `nudges`, а единственная работа в `_active_work_tasks`
  имеет тот же ключ и `running`; проверить очистку памяти, отсутствие create/
  notify и очистку status snapshot.
- Продолжить этот сценарий новым снимком завершённого этапа после освобождения
  слота: проверить fresh `since`, нулевые попытки, отсутствие запуска до
  `STALL_WAIT` и ровно одну штатную попытку на границе.
- Расширить тест capacity deferral второй ожидающей работой: её `since`
  обновлён, `nudges` сохранён, её запись не перепутана с очищенной живой.
- Сохранить или уточнить тест с 500 историческими задачами и запретом
  `work_lifecycle_block`, доказывая, что новая сверка читает только active
  snapshot.
- Обязательная команда: `python3 -m unittest -v
  pilot.test_pilot.PipelineWatchTests`; она должна завершиться кодом 0.

## Риски и решения

- У active snapshot может быть только часть общей истории. Это достаточно:
  fast path очищает запись лишь при положительном наблюдении живого этапа, а
  при отсутствии такого наблюдения сохраняет прежнее безопасное ожидание.
- Сопоставление по title может очистить не ту работу. Используется уже принятая
  `task_work_id`: durable `work_id` имеет приоритет, title остаётся только
  legacy fallback.
- Вызов записи статуса на горячем пути добавляет I/O. Он нужен лишь после
  обработки ограниченного снимка и использует существующий writer; обхода
  задач или внешних запросов не добавляется.
- Очистка `give_up` не должна немедленно запустить новый этап. Она происходит
  только при живом этапе; новый таймер создаёт обычная ветвь лишь после его
  terminal-снимка и освобождения capacity.
