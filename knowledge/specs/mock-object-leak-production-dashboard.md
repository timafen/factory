# Спецификация: убрать mock-объект из production dashboard

## Цель и влияние на владельца

Экран «Обзор» сейчас начинает работу с `useState<Dash>({})`. Этот пустой
объект выглядит для рендера как успешный снимок dashboard: при недоступном
`/api/v1/dashboard` владелец видит набор разрозненных «нет данных» вместо
явного сообщения, что production-снимок не получен. Это скрывает сбой
контрольной плоскости и затрудняет решение, ждать ли восстановление или
действовать.

После изменения «Обзор» должен отличать загрузку, недоступный dashboard и
настоящий пустой/неполный ответ сервера. Никакие вымышленные значения не
попадают в production-рендер; прочие независимые данные экрана продолжают
загружаться как сейчас.

## Технический подход и реальные файлы

- `web/src/Overview.tsx`: заменить начальное значение `{}` на явное состояние
  отсутствия снимка (`Dash | null`) и хранить статус запроса dashboard. До
  успешного ответа показывать компактное состояние загрузки; при неуспешном
  HTTP-ответе или ошибке сети — заметное сообщение, что снимок недоступен, с
  кнопкой «Обновить». Не интерпретировать ошибку как объект `Dash` и не
  подставлять тестовые/нулевые метрики. После успешного JSON-ответа оставить
  существующую отрисовку и частичную деградацию полей без изменений.
- `web/src/Overview.test.tsx`: добавить регрессионные сценарии для загрузки,
  HTTP-ошибки и ошибки сети; проверить, что до успешного ответа нет
  содержимого, характерного для ложного dashboard, а повторная загрузка
  восстанавливает настоящий снимок. Существующие тесты успешного ответа
  остаются контрактом совместимости.

Не менять `internal/controlplane/dashboard_http.go`: endpoint уже отдаёт
снимок как есть, а предмет дефекта — клиентский mock-объект, создаваемый до
ответа. Если в ходе реализации окажется, что сервер возвращает 200 с `{}`
при ошибке чтения файла, оформить это отдельной работой: менять HTTP-контракт
в этой задаче нельзя без согласованного поведения для health-check и клиентов.

## Последовательный план

1. Выделить в `Overview` состояние снимка и ошибки, не создавая пустой `Dash`
   как fallback.
2. Ограничить отрисовку dashboard-блоков успешным снимком; в loading/error
   состоянии показать одно понятное сообщение и действие обновления.
3. Сохранить параллельную загрузку задач, works и метрик, чтобы сбой dashboard
   не превращал экран в бесконечную загрузку.
4. Добавить тесты переходов loading → ready, loading → error и error → ready
   после повторной попытки.
5. Запустить целевой Vitest и проверку TypeScript/линтера, если она входит в
   существующую команду теста web.

## Критерии приёмки

- До первого успешного `/api/v1/dashboard` production-экран не рендерит
  пустой объект как dashboard-данные.
- Ответ с не-2xx статусом и ошибка сети дают явный человекочитаемый статус,
  а не набор ложных «нет данных» в карточках.
- Кнопка обновления повторяет загрузку; успешный повторный ответ отображает
  фактические поля снимка.
- Успешный частичный снимок сохраняет нынешнее поведение отдельных блоков,
  где сервер действительно не передал конкретное поле.
- Изменения ограничены `Overview` и его тестом; API, backend и UI-навигация не
  меняются.

## Тест-план

- `npm --prefix web test -- --run src/Overview.test.tsx` — целевой набор:
  loading, не-2xx, ошибка сети, повторная успешная загрузка и текущие
  сценарии dashboard.
- `npm --prefix web run lint` — проверка типов/правил фронтенда, если команда
  определена в `web/package.json`.
- Ручная проверка после выкладки: открыть production «Обзор», временно
  недоступный запрос должен дать статус недоступности, а не пустые карточки;
  после восстановления — реальные данные.

## Риски и решения

- Состояние ошибки может скрыть независимые разделы экрана. Решение: отделить
  оболочку dashboard от уже независимых запросов и не менять их lifecycle.
- Частичный настоящий ответ не равен ошибке. Решение: error задаётся только
  транспортным результатом, а отсутствующие поля успешного JSON остаются
  честно отображёнными как «нет данных».
- Повторные запросы могут обогнать друг друга. Решение: применять результат
  только актуальной попытки либо отменять предыдущую в cleanup эффекта.
- Изменение текста сообщения ломает доступные тесты. Решение: тестировать
  роль/доступное имя статуса и кнопки, а не разметку карточек.
