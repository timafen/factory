# Спецификация: production dashboard не показывает Python `MagicMock` как вопрос

## Цель и влияние на владельца

Владелец не должен видеть внутреннее строковое представление тестового объекта
Python вместо осмысленного вопроса. Фактическая production-запись с заголовком
«Исправить корзину» содержит `<MagicMock name='deep_diagnose().get()' ...>` в
полях `situation` и `question`; экран «Нужен ответ» отображает эти поля как
обычный текст.

После изменения API списка вопросов не отдаёт записи, в чьём владелец-видимом
содержимом обнаружен канонический repr `unittest.mock` (`<MagicMock ...>` или
`<Mock ...>`). Остальные открытые вопросы и история решений остаются доступны.
UI, механизм ответа и production-файл вручную не меняются.

## Технический подход и реальные файлы

Источник отображаемого текста находится до React:

- `pilot/pilot.py`, функция `write_question`, сохраняет `situation`, `question`,
  `options`, `answer` и `escalation_reason` в JSON каталога
  `$FACTORY_DATA_HOME/pilot/questions`;
- `internal/controlplane/questions_http.go`, `listQuestions`, читает эти JSON,
  удаляет только большое поле `prior_result` и без проверки отдаёт остальные
  значения через `GET /api/v1/questions`;
- `web/src/Answer.tsx` выводит `q.situation` и `q.question` и потому не является
  местом возникновения Python repr.

Защитную границу добавить в `internal/controlplane/questions_http.go`: перед
добавлением записи в ответ проверить только владелец-видимые строковые поля
`title`, `situation`, `question`, `options`, `answer` и `escalation_reason`.
Запись целиком пропускается, если отдельное строковое значение имеет форму
Python mock repr: после удаления внешних пробелов начинается с `<MagicMock `
или `<Mock ` и заканчивается `>`. Поиск произвольного слова `MagicMock` не
использовать, чтобы не скрывать настоящий вопрос о тестах. Не удалять и не
перезаписывать файл: endpoint списка остаётся read-only, а аварийная запись
сохраняется для диагностики.

В новом `internal/controlplane/questions_http_test.go` создать временный
`FACTORY_DATA_HOME`, записать загрязнённый JSON «Исправить корзину» и обычный
открытый вопрос, вызвать настоящий `GET /api/v1/questions` через HTTP fixture и
проверить, что ответ содержит только обычную запись и нигде не содержит mock
repr. Второй случай закрепляет узкую сигнатуру: обычный человеческий текст со
словом `MagicMock` не фильтруется. `pilot/pilot.py`, `web/src/Answer.tsx` и
production-данные не входят в реализацию.

## Последовательный план

1. Добавить в `questions_http.go` локальную проверку Python mock repr в
   владелец-видимых полях вопроса, включая строковые элементы `options`.
2. Применить проверку в `listQuestions` после JSON-декодирования и до включения
   записи в API-ответ; повреждённый файл оставить на диске.
3. Добавить HTTP-регрессию с production-формой `deep_diagnose().get()` и
   контрольной нормальной записью.
4. Добавить негативный случай для осмысленного текста, где `MagicMock` — тема
   вопроса, а не Python repr.
5. Запустить целевой Go-тест и `git diff --check`; UI-тесты не менять.

## Критерии приёмки

1. `GET /api/v1/questions` не содержит запись «Исправить корзину», если любое
   из её владелец-видимых значений является Python repr `<MagicMock ...>` или
   `<Mock ...>`.
2. Строковое представление mock не попадает ни в `situation`, ни в `question`,
   ни в другой владелец-видимый участок JSON-ответа.
3. Обычный открытый вопрос из того же каталога по-прежнему возвращается без
   изменения и доступен для ответа.
4. Осмысленный текст, который лишь упоминает слово `MagicMock`, не скрывается.
5. Фильтрация не удаляет и не переписывает production JSON, не меняет статусы,
   endpoint ответа, `Answer.tsx` или другие экраны dashboard.
6. Новый целевой тест воспроизводит загрязнённую production-форму и завершается
   с кодом 0.

## Тест-план

- В `TestListQuestionsHidesPythonMockRepresentations` записать два JSON-файла:
  production-подобный `resolved` с mock repr в `situation` и `question`, а также
  нормальный `open`; проверить единственный нормальный элемент ответа и
  отсутствие подстроки `<MagicMock` в сыром body.
- В отдельном subtest сохранить вопрос «Почему MagicMock попал в тест?» и
  подтвердить, что он возвращается: фильтр распознаёт repr, а не ключевое слово.
- Выполнить обязательную команду
  `go test ./internal/controlplane -run TestListQuestionsHidesPythonMockRepresentations`.
- Выполнить `git diff --check`. Полный набор относится к Verify, не к итерациям
  Implement.

## Риски и решения

- Фильтр может скрыть легитимный вопрос о `MagicMock`. Узкая проверка границ
  `<MagicMock ...>` / `<Mock ...>` сохраняет обычный человеческий текст.
- Утечка может оказаться в массиве `options`. Проверка проходит по всем
  перечисленным видимым полям и строковым элементам массива, но не сканирует
  технические id и `prior_result`.
- Удаление записи из production скрыло бы доказательство причины и добавило бы
  запись в read-only endpoint. Поэтому API только исключает артефакт из ответа.
- Корневая причина была тестовой записью в live data. Commit реализации
  `fc3af293e5e2b2c3802ad9b1d376f7796aa3b067` уже перенаправил Pilot-тесты во
  временный `FACTORY_DATA_HOME`; серверный фильтр нужен для оставшихся данных и
  защиты владельца от аналогичного несерийного содержимого.
- Общая сериализация Go не должна пытаться распознавать произвольные Python
  объекты: scope ограничен API вопросов и точной текстовой сигнатурой.
