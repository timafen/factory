# «Сделано недавно» показывает влитое, даты и подписи по-человечески

## Цель и влияние на владельца

Владелец должен видеть на главном обзоре только фактически влитые в `main`
продуктовые работы, отдельно от неуспешных завершений. Сейчас завершение этапа
само по себе может ошибочно выглядеть как доставка, а короткие ISO-фрагменты
дат и технические слова мешают понять, что и когда произошло.

После реализации блок «Сделано недавно» разделён на «Влито в main» и
«Провалы». У влитой работы есть подтверждённый receipt выпуска; у провала
названы этап и причина. Время отображается как «сегодня ЧЧ:ММ», «вчера ЧЧ:ММ»
либо полной локальной датой. Идентификаторы задач и внутренние статусы на
экран не попадают.

## Технический подход и реальные файлы

В `internal/protocol/types.go` добавить `Task.WorkClass` с JSON-полем
`work_class,omitempty`. Это server-owned признак: клиент не угадывает, является
ли работа продуктовой, автоматизацией или служебной.

В `internal/controlplane/store.go` расширить SQL чтения `Tasks` и `Task`
данными из `automation_occurrences` и `automations`, сгруппировать join по
задаче и передать факты в существующую классификацию. `scanTask` заполняет
`WorkClass`. Пагинационный `WHERE` должен стоять до `GROUP BY`, чтобы первый
запрос и последующие страницы были корректным SQL. Те же поля и группировка
нужны в `internal/controlplane/state.go` для claim-detail и в
`internal/controlplane/work_resume_http.go` для поиска этапов при resume.
Используется фактическое имя колонки `automations.title`, не устаревшее `name`.

В `pilot/pilot.py` `recent_done_block()` принимает только задачи с
`work_class == "product"`. Успешная задача попадает в `merged` только при
наличии delivery receipt; `failed` и `cancelled` образуют отдельную группу.
Для каждой продуктовой работы берётся последний этап, а из последней попытки
добавляется доказательство для влитого результата или причина для провала.
Старый fallback из notification log не используется: он не доказывает
слияние и возвращает служебный шум. Контракт snapshot — объект с массивами
`merged` и `failed`, каждый ограничен `n` элементами.

В `pilot/test_pilot.py` закрепить receipt, классификацию, выбор последнего
этапа, отдельные лимиты групп и причину ошибки.

В `web/src/Overview.tsx` типизировать новый snapshot, показать непустые
группы с человекочитаемыми заголовками и применить `formatRecentDate()` к
recent-done, времени снимка, release train и датам efficiency/capacity.
Форматтер валидирует календарную дату, использует локальное время и возвращает
«дата неизвестна» для пустого, невозможного или неразбираемого значения.
Подпись очереди заменить с p90-жаргона на «обычная длина очереди»; вычисление
метрики не меняется. `web/src/Overview.test.ts` проверяет формат дат, обе
группы, тексты и отсутствие технических статусов.

## Критерии приёмки

1. «Влито в main» содержит только product work с delivery receipt; простой
   `succeeded` без receipt туда не попадает.
2. `failed` и `cancelled` product work показаны только в «Провалы», с этапом
   и причиной либо честным текстом, что причина не указана.
3. Работы automation/schedule/service не появляются в `recent_done`; решение
   о классе приходит с сервера для list, detail, claim и resume чтений.
4. API list с cursor работает при добавленном join: `WHERE` расположен до
   `GROUP BY`, и страница не дублирует задачи.
5. Экран не показывает `merged`, `failed`, task id или сырой ISO-фрагмент;
   даты валидны и форматированы по локальному времени.
6. Пустая группа не имеет пустого заголовка, а существующие соседние метрики
   сохраняют свои расчёты при более понятных подписях.

## Тест-план

В Go добавить/обновить table-driven проверки `Task`/`Tasks` для product,
automation и scheduled задач, а также cursor после SQL join. Проверить
claim-detail и resume, если они читают тот же `scanTask`-контракт.

В Python смоделировать receipt, успешную задачу без receipt, failed/cancelled,
несколько этапов одной работы, automation и независимый лимит двух массивов.
Проверить, что error/result ограничены и fallback notification log не оживляет
неподтверждённую работу.

В React проверить `formatRecentDate()` для сегодня, вчера, старой и
невозможной даты; отрисовать snapshot с обеими группами, проверить названия,
детали и отсутствие сырых статусов. Запустить:

`npm --prefix web test -- --run src/Overview.test.ts`

Дополнительно выполнить целевые Go/Python тесты, `npm --prefix web run
typecheck`, lint и `git diff --check`.

## Риски и решения

- Риск: заголовок задачи похож на продуктовую работу, но создан автоматикой.
  Решение: Pilot не классифицирует по строке, а доверяет только `work_class`.
- Риск: success принимают за merge. Решение: единственное доказательство для
  `merged` — delivery receipt; остальные успехи не показываются как доставка.
- Риск: SQL join размножит строки или сломает cursor. Решение: aggregate
  automation-факты, `GROUP BY` по задаче и `WHERE` до `GROUP BY`.
- Риск: браузер по-разному разбирает повреждённую дату. Решение: до создания
  `Date` проверить календарные компоненты и выводить честное «дата неизвестна».
- Ограничение: UI не восстанавливает старые записи из notify-log, поскольку у
  них нет проверяемого receipt и server-side класса.
