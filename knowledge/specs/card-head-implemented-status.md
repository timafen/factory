# Спецификация: статус `Implemented` в HEAD карточки

## Цель и влияние на владельца

После успешного этапа `Implement + Test` карточка знаний должна явно сообщать
в HEAD, что реализация выполнена: `Status: Implemented`. Владелец видит единый
статус в карточке, а Review и Verify получают проверяемый сигнал, что документ
описывает поставленный код, а не только намерение. Неуспешный, возвращённый или
незавершённый прогон не должен подделывать этот статус.

## Технический подход и реальные файлы

- В `pilot/pilot.py` расширить машинную проверку карточки перед Review: выбрать
  карточку текущей работы, прочитать её содержимое из опубликованной ветки и
  потребовать строку `Status: Implemented` (допустимы Markdown-список и
  регистр, согласованный с существующими карточками).
- В том же месте сохранить независимые ворота полного `Implementation commit`:
  статус не заменяет доказательство предкового code-коммита и не сравнивается
  с меняющимся tip карточки.
- В `pilot/test_pilot.py` добавить изолированные проверки принятого статуса,
  отсутствующего/старого статуса, неверной карточки и сохранения поведения для
  прочих файлов поставки. UI, API и продуктовые исходники не изменяются.

## Последовательный план

1. Уточнить парсер HEAD карточки и единый формат строки статуса.
2. Подключить проверку к существующему `review_gate` после snapshot и проверки
   номера карточки, до создания Review.
3. При отсутствии `Implemented` вернуть работу в Implement с точным сообщением;
   при ошибке GitHub оставить повторяемую инфраструктурную проверку.
4. Добавить целевые тесты для положительного и защитных сценариев.
5. Запустить целевые тесты, проверить diff только из спецификации и карточки.

## Критерии приёмки

- Карточка текущей работы с `Status: Implemented` и валидным implementation
  commit проходит Review gate.
- `Planned`, `In progress`, отсутствующая или чужая карточка не проходит gate;
  Review не создаётся и возвращается понятное действие для Implement.
- Проверка не принимает статус из отчёта агента вместо опубликованного HEAD.
- Существующие проверки SHA, номера карточки, scope и свежей базы не ослаблены.
- Изменения ограничены `pilot/pilot.py`, `pilot/test_pilot.py` и документами.

## Тест-план

- Целевая регрессия: `python3 -m unittest -v pilot.test_pilot.CardHeadStatusTests`.
- Проверить сценарии `Implemented`, старого статуса, отсутствующего статуса,
  чужой карточки и временной ошибки чтения remote.
- Выполнить `git diff --check` и трёхточечную проверку состава поставки.

## Риски и решения

- Разные Markdown-формы статуса: принять только явно определённые формы и
  покрыть их таблицей тестов, не использовать свободный поиск слова.
- Карточка может быть финальным документационным коммитом: проверять статус
  отдельно от стабильного implementation commit.
- Сетевой сбой нельзя трактовать как старый статус: вернуть `BLOCKED`/повтор,
  не создавать ложный Review.
