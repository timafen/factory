# Слияние и выпуск называются подтверждённым результатом

## Цель и влияние на владельца

После Verify владелец должен видеть в названии pull request, выпуска и
уведомления результат поставки, например «Настройки сохраняются безопасно при
сбое записи», а не исходную проблему, служебный статус или номер работы.
Название должно происходить из уже подтверждённого кода и оставаться тем же
после рестарта Pilot и исправления merge conflict. Исходный `base` продолжает
идентифицировать работу, но больше не становится текстом поставки.

## Технический подход и реальные файлы

В `pilot/pilot.py` разделить идентичность работы и её публичное название.
Проверка карточки перед Review уже извлекает `Implementation commit` и
доказывает, что SHA принадлежит опубликованной ветке и меняет не только
карточку. Этот подтверждённый SHA следует сохранить в generation-scoped
delivery artifact. При успешном Verify Pilot получает через GitHub API subject
именно этого коммита (`commit.message`, первая строка), а не subject вершины
ветки, `base`, заголовок задачи или свободный текст отчёта Verify.

Необязательная строка `DELIVERY_TITLE: <название>` в отчёте текущего Verify —
явное переопределение. Допускается ровно одна такая строка; она имеет приоритет
над commit subject. Если override присутствует, но невалиден, fallback
запрещён: Verify должен исправить название. Это делает исключение явным и
аудируемым, не позволяя старому problem title незаметно вернуться.

Единый валидатор принимает одну непустую строку после обрезки краёв и сжатия
внутренних пробелов, длиной не более 72 Unicode-символов. Он отклоняет
переносы строк; служебные вердикты и статусы (`PASS`, `BLOCKED`,
`READY TO SPECIFY`, `REQUEST CHANGES`, `stopped_owner`, `succeeded`,
`failed`, `queued`, `running`); task/card ID (`TASK-…`, `CARD-…`, UUID); SHA
длиной 7–64 hex; stage-обёртки вида `[auto] [2/5 Specification]`; `Merge pull
request` и номера PR вида `#120`. Запрещённый маркер в любой части названия
делает всё название невалидным. Корректный русский текст считается по
Unicode-кодовым точкам и не урезается молча.

При PASS создать `merge_intents[verify_task_id]` только с валидным
`delivery_title`. `recover_merge_intents()` передаёт его в `gh_merge()` без
fallback на `base`. Поле копируется в merge receipt и delivery wait:
release/squash получает его через PR title, а успешные и аварийные уведомления
читают `delivery_title`; `base` во всех этих структурах сохраняется только для
поиска и жизненного цикла работы. Сохранение `state.json` до внешнего merge
обеспечивает рестарт. При conflict исходный intent не теряет title, correction
получает его в контексте, а новый Verify intent наследует его для того же
`work_id`, если текущий Verify не дал новый валидный override.

В `pilot/test_pilot.py` добавить отдельный класс целевых unit-тестов для
получения, валидации, сохранения и использования названия. Другие файлы не
требуются: release scripts уже используют заголовок squash-коммита, созданный
из PR title.

## Последовательный план

1. Изменить проверку карточки/артефакт поставки так, чтобы сохранить точный
   подтверждённый `Implementation commit`, не меняя существующие SHA-gates.
2. Добавить строгий парсер override, чтение subject через GitHub API и единый
   валидатор `delivery_title` с результатом «значение или точная причина».
3. Перед созданием merge intent выбрать override либо subject подтверждённого
   коммита; при ошибке вернуть ту же работу в Verify, не вызывая `gh_merge`.
4. Провести `delivery_title` через intent, recovery, conflict correction,
   receipt, wait и outbox; оставить `base` только идентификатором работы.
5. Передавать в `gh_merge` только сохранённый title и убрать fallback на branch
   или `base` для автоматического PR.
6. Добавить регрессии и выполнить целевые unit-тесты и Python compilation.

## Критерии приёмки

1. Для карточки с подтверждённым implementation commit с subject
   `Настройки сохраняются безопасно при сбое записи` PR создаётся с этим
   точным title; release и уведомление показывают то же название.
2. Строка `DELIVERY_TITLE:` текущего Verify заменяет commit subject только
   после той же валидации; две строки override либо невалидный override
   блокируют PR без fallback.
3. Пустое название, текст наподобие #120 (`stopped_owner`, stage wrapper или
   `Merge pull request #120`), task/card ID, SHA, PR number и строка длиннее 72
   символов не вызывают `gh pr create`; создаётся возврат в Verify с причиной
   и инструкцией дать человеческое название результата.
4. После сохранения intent и рестарта ровно тот же `delivery_title` передаётся
   в повторное recovery. После merge conflict он сохраняется при возврате на
   исправление и в новом intent той же работы; новый валидный override может
   заменить его явно.
5. `base` и `work_id` продолжают связывать этапы, журнал и эпики, но нигде не
   используются как fallback публичного названия.
6. Механика squash merge, release scripts и исторические PR не меняются.

## Тест-план

- В новом `DeliveryTitleTests` замокать GitHub commit API и проверить выбор
  subject подтверждённого карточкой SHA, русский title и явный override.
- Таблично проверить пустую строку, 72/73 символа, служебные статусы,
  `CARD-0164`, task ID/UUID, короткий и полный SHA, stage wrapper, `#120` и
  `Merge pull request #120`.
- Проверить, что невалидное значение возвращает Verify и `gh_merge`/
  `subprocess.run` не вызываются.
- Сериализовать intent в временный `state.json`, восстановить его и доказать,
  что `gh_merge` получает сохранённый title. Отдельно пройти conflict → repair
  → новый Verify intent и сравнить title.
- Проверить успешный и аварийный delivery outbox: уведомление берёт
  `delivery_title`, тогда как receipt сохраняет прежний `base` для identity.
- Выполнить `python3 -m py_compile pilot/pilot.py pilot/test_pilot.py` как
  дополнительную синтаксическую проверку.

## Риски и решения

- GitHub API может не вернуть commit: считать это инфраструктурной ошибкой
  Verify и повторить чтение, не подменять названием задачи.
- Вершина delivery-ветки часто является коммитом карточки: хранить и читать
  только доказанный карточкой implementation SHA.
- Слишком широкий фильтр способен отвергнуть нормальный текст с числами:
  запрещать определённые ID/PR/SHA-маркеры, но не обычные числа и пунктуацию.
- Рестарт между PR и записью состояния способен изменить title: сохранять
  полный intent до внешнего вызова, как уже требует merge state machine.
- Старые intent без `delivery_title` нельзя безопасно домыслить из `base`:
  не создавать для них PR, а вернуть Verify для однократного исправления.
