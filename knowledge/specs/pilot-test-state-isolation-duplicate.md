# Дубликат: тесты Pilot изолируют боевое состояние

## Цель и влияние на владельца

Проблема состояла в том, что тесты, вызывающие настоящий `pilot.cycle()`,
записывали производные от фиксированного `HOME` файлы, включая
`/opt/factory-data/pilot/state.json`. Очередной тест мог затереть `processed`,
`merge_intents` и другие durable-признаки уже выполненных этапов. После этого
живой Pilot видел работу заново и запускал пройденные этапы повторно.

Результат уже поставлен в `main`: тесты работают в одноразовом корне, а
production по-прежнему использует `/opt/factory-data`. Поэтому текущая работа
закрывается как дубликат, без второй реализации и без изменения UI. Источник
Плана отмечен выполненным с причиной и ссылкой на
[PR #152 «Тесты Pilot больше не трогают живое состояние»](https://github.com/timafen/factory/pull/152),
чтобы он не породил новый прогон.

## Технический подход и реальные файлы

Решение в main устроено так:

- `pilot/pilot.py:32-38` читает `FACTORY_DATA_HOME`, оставляя
  `/opt/factory-data` значением по умолчанию, и строит `STATE_PATH`,
  `CONF_PATH`, каталоги эпиков, вопросов и вердиктов от выбранного корня.
- `pilot/test_pilot.py:20-46` создаёт временный `FACTORY_DATA_HOME` до
  импорта Pilot, создаёт нужные подкаталоги, а после набора восстанавливает
  переменную окружения. `TestDataIsolationTests` явно проверяет, что
  `STATE_PATH` не равен боевому пути; дочерние процессы наследуют тот же
  безопасный корень.
- Штатный маршрут закрытия источника уже существует в `intake/plan.py:122-135`:
  действие `done` сохраняет состояние карточки через `pilot.set_idea` и
  закрывает связанную работу через `pilot.close_work`. Код этого маршрута и
  файлы приложения в этой работе не меняются.

Реальные файлы уже поставленного исправления — `pilot/pilot.py` и
`pilot/test_pilot.py`; в текущей ветке меняется только этот документ.

## Последовательный план

1. Сверить свежий `origin/main` и убедиться, что исправление из PR #152 уже
   входит в базу; не переносить удалённую прошлую ветку и не менять исходники.
2. Зафиксировать в этой спецификации фактическую границу: временный корень
   тестов, неизменный production-default и существующий регрессионный тест.
3. Пометить точный источник Плана с этим заголовком как `done`, указав
   дубликат и ссылку на PR #152. Это уже выполнено через штатный маршрут Плана.
4. Запустить целевую проверку из раздела тест-плана.
5. Закоммитить и опубликовать только спецификацию; новую карточку знаний не
   создавать по прямому решению владельца.

## Критерии приёмки

1. `pilot.pilot.HOME` в тестовом процессе указывает на временный каталог, а
   `STATE_PATH` находится внутри него и не совпадает с боевым путём.
2. Тесты, использующие `cycle()` и subprocess-вызовы, сохраняют состояние
   только в тестовом корне; production-default `/opt/factory-data` не меняется.
3. Полный набор из отчёта предыдущей стадии подтверждает 241 пройденную
   проверку и 13 пропущенных, а трассировка не содержит обращений к
   `/opt/factory-data/pilot` и содержит только временные `state.json`.
4. Источник Плана имеет состояние `done`, а причина содержит, что это
   дубликат исправления из PR #152. Повторный автозапуск этой карточки не
   допускается.
5. В поставке этой стадии нет изменений `pilot/`, `intake/`, UI или других
   продуктовых исходников: добавляется только спецификация.

## Тест-план

- Обязательная целевая регрессия:
  `python3 -m unittest pilot.test_pilot.TestDataIsolationTests`.
- Проверить в выводе теста временный `FACTORY_DATA_HOME` и отличие от
  `/opt/factory-data/pilot/state.json`; отдельный полный прогон не нужен на
  стадии Specification, поскольку его результат уже зафиксирован в PR #152
  и отчёте предыдущей стадии.
- Проверить источник Плана чтением его JSON-представления после действия
  `done`: состояние `done`, причина с PR #152, исходный заголовок сохранён.

## Риски и решения

- Риск повторного создания работы из старой карточки Плана. Решение: источник
  закрыт как дубликат и содержит ссылку на PR #152; новый запуск из него не
  разрешён.
- Риск утечки временного пути в production. Решение: переменная окружения
  задаётся только тестовым модулем до импорта, а default в Pilot не меняется.
- Риск ложной уверенности из-за одного теста. Решение: целевой тест проверяет
  саму границу пути, а полный результат и отсутствие боевых обращений уже
  подтверждены в отчёте предыдущей стадии.
- Риск расхождения документа с main. Решение: перед сдачей повторно сверить
  наличие реализации в свежем `origin/main`; продуктовый код не дублировать.
- Новая карточка знаний не заводится: это явно утверждено владельцем для
  закрытия данного дубликата; существующие карточки не изменяются.
