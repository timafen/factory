# Здоровый исполнитель с retained worktree требует эскалации

## Цель и влияние на владельца

Сейчас `factory-janitor` намеренно пропускает online/healthy исполнителя с
`retained_worktrees`: его служба не останавливается и результат не переносится,
но владелец не узнаёт, что удержанный результат продолжает занимать место и
требует решения. После изменения здоровый исполнитель и его worktree останутся
нетронутыми, а владелец получит одну понятную эскалацию на конкретный retained
результат. Повторные циклы и рестарты не должны заспамить канал.

## Технический подход и реальные файлы

Изменить локальный цикл `ops/factory-janitor.sh`, не добавляя остановку healthy
службы в путь очистки:

- оставить `offline + retained` и `online + unhealthy` кандидатами для текущего
  карантина и подтверждения через существующий API;
- выделить `online + healthy + retained` в отдельный поток только уведомления;
- хранить durable ключ эскалации в уже используемом `FACTORY_JANITOR_STATE`
  (имя исполнителя, attempt ID и отпечаток пути/причины), чтобы один и тот же
  снимок уведомлялся один раз, а изменившийся снимок мог быть замечен;
- отправлять уведомление через настраиваемый `FACTORY_JANITOR_ESCALATION_URL`
  с безопасным отсутствующим значением: без URL писать понятную запись в лог,
  не считать это очисткой и не ронять цикл; в production URL — владелический
  канал ntfy;
- сообщение должно назвать исполнителя, attempt ID, репозиторий, путь,
  причину удержания и действие владельца (ручная проверка/cleanup), без
  удаления, `systemctl stop` или POST очистки для healthy-кандидата.

Реальные файлы реализации и проверки: `ops/factory-janitor.sh` и
`ops/test-factory-janitor.sh`. API control plane, схему worker и UI менять не
нужно: состояние уже приходит в `/workers`, а ручная очистка остаётся явной.

## Последовательный план

1. Разделить результат выборки `/workers` на cleanup-кандидатов и healthy
   retained-кандидатов, не меняя условия `active_count` для очистки.
2. Добавить идемпотентную запись/доставку эскалации с атомарным обновлением
   state только после успешного вызова или явно зафиксированного fallback в
   лог; ошибка канала не должна скрыть наличие retained worktree.
3. Ограничить ключ и payload точным снимком записи, чтобы новая регистрация
   после старого обхода не была ошибочно подтверждена.
4. Расширить shell-фикстуру: healthy retained остаётся на месте, не получает
   stop/mv/POST cleanup, получает ровно одну эскалацию; второй запуск не
   дублирует её, а изменённая запись получает новую эскалацию.

## Критерии приёмки

1. Online healthy с retained worktree не останавливается, не перемещается в
   карантин и не попадает в `retained-worktrees/clear`.
2. Для каждого нового точного снимка healthy retained отправляется одна
   эскалация с понятными идентификатором и путём результата.
3. Повторный запуск с тем же снимком не создаёт второе уведомление; изменение
   attempt/path/reason создаёт новую независимую запись.
4. Offline retained и online unhealthy продолжают проходить существующую
   очистку; healthy без retained не создаёт шум.
5. Ошибка HTTP или недоступный канал уведомления не удаляет state/worktree,
   журнал содержит причину, а санитар завершается кодом 0.

## План тестирования

В `ops/test-factory-janitor.sh` добавить мок `curl`, журнал событий stop/mv и
приёмник эскалаций. Проверить первый и повторный обход, изменение снимка,
сохранность healthy worktree и отсутствие POST cleanup. Сохранить текущие
сценарии offline/quarantine, online unhealthy, неперемещённого пути и ошибки
подтверждения. Отдельно проверить неуспешный канал эскалации и код завершения.

Обязательная проверка — целевой shell-тест; полный набор проекта на этапе
спецификации не требуется.

## Риски и решения

- Риск потери результата при агрессивной очистке: healthy исполнитель никогда
  не входит в cleanup-путь; решение владельца остаётся ручным.
- Риск спама: durable ключ снимка хранится в state, а не только в памяти
  процесса; повтор и рестарт идемпотентны.
- Риск гонки регистрации: очистка не вызывается, а уведомление не содержит
  команду без точного пути и attempt ID.
- Риск недоступности ntfy: логировать событие и продолжать обход; не выдавать
  ложное сообщение об успешной доставке.
- Вне области: изменение retention policy, автоматическое повышение уровня
  исполнителя, UI для ручной очистки и новый маршрут control plane.
