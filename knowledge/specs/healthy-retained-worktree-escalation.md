# Эскалация retained worktree здорового исполнителя

## Цель и влияние на владельца

Сейчас `ops/factory-janitor.sh` выбирает для карантина только offline-исполнителя
без активной работы. Запись `online + healthy + retained_worktrees` намеренно не
попадает в разрушительный путь, но отдельного пути уведомления нет. В результате
сохранённая рабочая копия продолжает занимать лимит репозитория, а владелец не
узнаёт, что результат требует ручного решения.

После изменения healthy-исполнитель и его worktree остаются нетронутыми, а
владелец получает одну понятную эскалацию на каждый новый точный snapshot
retained worktree. Повторные циклы и рестарты janitor не дублируют уже
доставленное уведомление. Ошибка канала не выдаётся за успех: результат
сохраняется, причина попадает в журнал, а следующий цикл повторяет доставку.

## Технический подход и реальные файлы

Реализация ограничена локальным janitor и его целевым shell-тестом:

- в `ops/factory-janitor.sh` после одного чтения `GET /api/v1/workers` отделить
  `online + health=healthy + retained_worktrees` от существующих кандидатов на
  карантин;
- не вызывать для healthy-кандидата `systemctl stop`, `mv`, удаление attempts,
  `git worktree prune` или `POST /retained-worktrees/clear`;
- сформировать детерминированный ключ snapshot из подписанных полей worker ID,
  имени исполнителя, attempt ID, repository ID, path и reason; пустые значения
  сохранять в ключе, чтобы разные записи не склеивались;
- хранить доставленные ключи в отдельной секции существующего
  `FACTORY_JANITOR_STATE`, не смешивая их с часовыми счётчиками освобождения;
  обновлять эту секцию через временный файл и атомарную замену, ограничить
  журнал последними 256 ключами;
- отправлять сообщение через `FACTORY_JANITOR_ESCALATION_URL`, production-default
  которого — утверждённый владелический ntfy-канал. Сообщение подписывает имя
  исполнителя, попытку, репозиторий, путь, причину и просит проверить результат
  и выполнить ручной cleanup;
- записывать ключ как доставленный только после успешного HTTP-ответа. При явно
  пустом URL один раз записать тот же текст и предупреждение в локальный журнал
  как durable fallback; при HTTP-ошибке ключ не сохранять, чтобы следующий
  запуск повторил попытку;
- в `ops/test-factory-janitor.sh` расширить мок `curl` и API-фикстуру, сохранив
  существующие сценарии offline cleanup, online unhealthy без retained,
  неперемещённого пути и ошибки подтверждения очистки.

Control-plane API, протокол `RetainedWorktree`, UI и retention policy менять не
нужно: `/workers` уже отдаёт все требуемые поля, а ручная очистка уже существует.

## Последовательный план

1. Получить worker snapshot один раз и независимо сформировать cleanup-кандидатов
   и notification-only кандидатов, сохранив текущие условия очистки.
2. Добавить построение стабильного ключа и чтение отдельной секции state без
   повреждения существующих записей лимита janitor.
3. Добавить доставку понятного уведомления и атомарную фиксацию успешного либо
   локально залогированного fallback-события.
4. Ограничить историю эскалаций и оставить неуспешную HTTP-доставку retryable.
5. Расширить целевую shell-фикстуру первым запуском, повтором, изменённым
   snapshot, отказом канала и проверками отсутствия cleanup-действий.

## Критерии приёмки

1. `online + healthy + retained` не останавливается, не переносится в карантин
   и не попадает в API-подтверждение очистки.
2. Первый обход отправляет ровно одну эскалацию с подписанными именем
   исполнителя, попыткой, репозиторием, путём, причиной и ручным следующим
   действием.
3. Повтор с тем же snapshot, включая запуск новым процессом с тем же state, не
   отправляет уведомление снова.
4. Изменение attempt ID, repository ID, path или reason считается новым
   snapshot и создаёт отдельную эскалацию.
5. HTTP-ошибка эскалации оставляет snapshot неотмеченным, пишет причину в лог,
   сохраняет worktree и позволяет janitor завершиться с кодом 0; следующий
   запуск повторяет доставку.
6. Явно пустой URL создаёт одну локальную эскалацию и durable отметку без спама.
7. Существующая очистка offline retained и сохранность online unhealthy без
   retained продолжают проходить; healthy без retained не создаёт уведомлений.

## Тест-план

В `ops/test-factory-janitor.sh` мок API возвращает offline retained, online
unhealthy, online healthy retained и online healthy без retained. Мок `curl`
разделяет запросы API очистки и владелические уведомления, а мок `systemctl`
фиксирует stop/start.

Целевой тест проверяет первый и повторный обход с общим state, новый reason,
успешный retry после HTTP-ошибки, пустой URL, максимум в 256 сохранённых ключей,
сохранность healthy worktree и отсутствие для него stop/mv/prune/cleanup POST.
Существующие проверки карантина и точного подтверждения offline snapshot
остаются в наборе. Обязательная команда — `bash ops/test-factory-janitor.sh`;
она должна завершаться с кодом 0.

## Риски и решения

- Потеря результата из-за слишком широкой выборки: notification-only поток
  проверяет одновременно `online` и `health=healthy` и не вызывает функции
  очистки.
- Спам после рестарта: доставленный точный ключ хранится в durable state;
  одинаковый snapshot идемпотентен.
- Потеря эскалации при сбое ntfy: ключ фиксируется только после успешной
  доставки, поэтому ошибка остаётся видимой и retryable.
- Рост state-файла: история ограничена 256 последними доставленными ключами и
  записывается атомарно вместе с существующим состоянием.
- Повреждение счётчиков janitor: новая секция имеет отдельное имя, чтение
  сохраняет неизвестные ключи, а тест повторно запускает старый cleanup-путь.
- Ложная уверенность от голых идентификаторов: уведомление всегда даёт
  словесные подписи полям и понятное ручное действие владельца.
