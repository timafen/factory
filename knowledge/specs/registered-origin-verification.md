# Factory проверяет зарегистрированный `origin` во временном Git-репозитории

## Цель и влияние на владельца

Factory создаёт временные репозитории для свежего Review, обновления устаревшей
ветки и пересборки поставки. До начала сетевой Git-операции она должна убедиться,
что имя `origin` действительно привязано к каноническому URL проекта. Это не даст
временной папке с подменённым или ранее сохранённым remote получить данные не того
репозитория, отправить пересобранную ветку не туда либо выдать неверный verdict.
Владельцу остаётся понятная инфраструктурная причина, а не ложное замечание к коду.

## Технический подход и реальные файлы

В `pilot/pilot.py` уже есть `_remote_url()` как источник канонического URL и три
создания временного репозитория с `git remote add origin`: `fresh_branch_snapshot()`,
`refresh_stale_branch()` и `rebuild_clean_branch()`. Добавить общий helper, который
после добавления remote получает `git remote get-url origin`, нормализует только
безопасно сопоставимые представления URL и сравнивает их с URL, который вернул
`_remote_url()`. Несовпадение, отсутствие `origin` или ошибка команды прекращают
операцию до `ls-remote`, `fetch`, `checkout`, `merge`, `diff` и `push`.

Helper возвращает диагностическое сообщение без токенов и не меняет worker-owned
checkout. Call-sites переводят такую ошибку в существующий `state: blocked` либо
в текущий безопасный пустой результат пересборки с журналируемой причиной; старый
успешный путь и существующие remote URL сохраняются.

- `pilot/pilot.py` — helper проверки зарегистрированного remote и его вызовы во
  всех трёх временных Git-потоках.
- `pilot/test_pilot.py` — изолированные unit/regression-тесты совпадения URL,
  подменённого `origin`, ошибки `get-url` и отсутствия последующих сетевых команд.

## Последовательный план

1. Выделить единый контракт канонического URL и зарегистрированного `origin`.
2. Реализовать helper на основе `_git(work, "remote", "get-url", "origin")` с
   безопасной диагностикой и строгим отказом при любой неопределённости.
3. Вызвать helper сразу после `remote add` в snapshot, refresh и rebuild путях.
4. Добавить тесты, проверяющие, что корректный URL сохраняет поведение, а иной URL
   блокирует операцию до `ls-remote`/`fetch`/`push`.
5. Запустить целевой тестовый класс и проверить форматирование diff.

## Критерии приёмки

- Каждый временный Git-репозиторий подтверждает URL `origin` до первой сетевой
  операции или изменения ветки.
- При несовпадении, отсутствующем remote либо сбое чтения URL Review/refresh
  возвращают `blocked`; пересборка не создаёт и не публикует ветку.
- Сообщение объясняет проблему с зарегистрированным `origin`, но не раскрывает
  секреты из URL.
- При совпадающем каноническом URL существующий snapshot/refresh/rebuild поток
  продолжает работать.
- Рабочая ветка исполнителя не переключается и не изменяется.

## Тест-план

Добавить `TemporaryRepositoryOriginTest` в `pilot/test_pilot.py` с mock `_git` и
реальным изолированным bare-remote там, где это необходимо. Покрыть успешное
совпадение URL, подмену `origin` после добавления, ошибку `remote get-url` и
assert порядка вызовов: после отказа нет `ls-remote`, `fetch`, `checkout`, `merge`,
`diff` или `push`. Отдельно подтвердить, что `fresh_branch_snapshot()` сообщает
`blocked`, а `refresh_stale_branch()` и `rebuild_clean_branch()` не публикуют
результат.

## Риски и решения

- Эквивалентные формы одного URL могут различаться синтаксически: нормализовать
  только заранее определённые формы, иначе безопасно блокировать с ясной причиной.
- URL может содержать credential: в логах выводить лишь нейтральное описание
  несовпадения, не исходную строку.
- Неполное покрытие call-site оставит обход: тестом перечислить все три текущих
  временных потока.
- Сбой Git-инфраструктуры не является дефектом поставки: использовать `blocked`,
  не REQUEST CHANGES и не fallback на старый remote.
