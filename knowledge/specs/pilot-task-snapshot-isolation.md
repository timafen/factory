# Спецификация: изоляция снимка `tasks` в подсчёте стадий и handoff

## Цель и влияние на владельца

Пилот должен принимать решения о повторах и приоритете terminal handoff только
по задачам текущего цикла. Владелец не будет получать чужие завершения,
ложные значения числа попыток или пропущенные handoff из-за состояния,
прочитанного вне входного снимка функции.

## Технический подход и реальные файлы

Область реализации ограничить `pilot/pilot.py` и `pilot/test_pilot.py`.
Сохранить функции `stage_attempts(tasks, stage, base)` и
`prioritize_terminal_handoffs(tasks, processed, recovery_ids=())` чистыми по
входу: обходить только `tasks`, не читать глобальный список задач и не добавлять
в него завершения другого work/repository. Все вызовы в `pipeline_watch` и
соседних переходах должны передавать snapshot текущего цикла; если в цикле
создаётся следующая задача, её нормализация в snapshot должна оставаться
явной и локальной.

Добавить регрессионные unit-тесты с двумя независимыми наборами задач:
изменение или terminal-задача во втором наборе не меняет результат первого;
вызов с пустым/ограниченным snapshot не видит задачи из процесса или
предыдущего цикла. Проверять также вызовы, создающие следующий stage, чтобы
новая задача не была скрыта от текущей обработки и одновременно не смешивалась
с чужой работой.

## Последовательный план

1. Зафиксировать текущую семантику двух функций и перечислить все call sites;
   проверить отсутствие скрытого чтения глобального состояния.
2. Уточнить локальный snapshot-контракт в местах формирования цикла, не меняя
   публичные API, хранение задач, UI и формат workflow.
3. Добавить изолированные тесты для подсчёта, terminal-priority и same-cycle
   handoff с задачами разных work/repository.
4. Запустить обязательную целевую проверку и проверить diff только документов
   реализации и карточки.

## Критерии приёмки

1. `stage_attempts` возвращает число только по элементам переданного `tasks`,
   совпадающим по stage и work; глобальный список задач не влияет на результат.
2. `prioritize_terminal_handoffs` переставляет только элементы входного
   snapshot и не добавляет в него terminal-задачи из другого work/repository.
3. Каждый production call site передаёт snapshot текущего цикла; новые задачи
   текущего handoff учитываются только по явно определённому same-cycle правилу.
4. Тесты доказывают изоляцию двух snapshots и отсутствие побочных изменений
   исходных списков.
5. Поведение остальных workflow-переходов, лимит попыток и UI не изменяются.

## Тест-план

Добавить целевые тесты в `pilot/test_pilot.py` рядом с существующими проверками
`stage_attempts` и `prioritize_terminal_handoffs`. Обязательная команда:

`python3 -m unittest -v pilot.test_pilot.TaskSnapshotIsolationTests`

Тесты должны завершаться кодом 0 после реализации и включать: чужую terminal
задачу, чужую попытку того же stage, пустой snapshot, recovery id и проверку
неизменности входного списка. На Verify дополнительно прогнать полный
`python3 -m unittest pilot.test_pilot` ровно один раз.

## Риски и решения

- Риск скрытого call site: перед реализацией инвентаризировать все вызовы
  поиском по имени; новый тест оставить на каждый критичный переход.
- Риск случайно исправить симптом глобальной очисткой: запретить глобальные
  mutable-коллекции и передавать только snapshot, принадлежащий циклу.
- Риск изменения порядка handoff: сохранить текущий порядок `urgent`/`rest`,
  меняя лишь источник задач и assertions изоляции.
- Риск неясного same-cycle поведения: явно документировать, добавляется ли
  созданная задача в локальный snapshot до следующего шага цикла; не расширять
  это правило на другие work.
