# Стоп-кран `route_question()` считает всю историю попыток

## Цель и влияние на владельца

Пилот должен остановить бессмысленный цикл после настроенного числа повторов,
даже если ранние попытки одной работы уже ушли за первую страницу API задач.
Сейчас `cycle()` читает только `/tasks?limit=100`, `stage_attempts()` считает
совпадения в этом усечённом списке, а `route_question()` без проверки использует
переданный `attempts_so_far` для `deep_diag_rounds`, `max_stage_attempts` и
жёсткого `max_work_rounds`. При длинной общей очереди фактические круги могут
быть недосчитаны, поэтому стоп-кран не срабатывает и Фабрика продолжает тратить
вычислительный и денежный лимит.

После изменения пороговые решения будут опираться только на полностью
дочитанную историю конкретной работы. Владельцу не придётся вручную замечать
цикл, скрытый пагинацией; при временной недоступности полной истории Пилот
безопасно отложит маршрутизацию, не выдавая ни продолжение, ни ложную тревогу.

## Технический подход и реальные файлы

Изменение ограничить `pilot/pilot.py` и `pilot/test_pilot.py`; UI, API control
plane, конфигурационные значения и формат сохранённых вопросов не менять.

В `pilot/pilot.py` затронуты существующие точки:

- `all_tasks()` и `_all_tasks_for_diag_repair()` уже обходят страницы задач, но
  реализуют полноту по-разному. Выделить один строгий пагинатор: он идёт до
  пустого `next_cursor`, кодирует cursor, устраняет дубли по `task.id` и явно
  завершает вызов ошибкой при повторе cursor, превышении защитного числа страниц
  или ошибке API. Частичный список не возвращается как полный.
- `stage_attempts(tasks, stage, reference)` оставить единственным правилом
  принадлежности попытки работе. Передавать текущую задачу как `reference`,
  чтобы при наличии `work_id` не смешивать работы с одинаковым заголовком и
  сохранить существующий fallback по заголовку только для legacy-задач.
- `route_question()` больше не должен принимать голое, ничем не подтверждённое
  число из короткого снимка. Передать ему текущую задачу и стадию подсчёта;
  непосредственно перед диагностикой и проверками лимитов получить строгую
  полную историю и вычислить число через `stage_attempts()`. Все сообщения,
  `LOOP_NOTE`, `CAP_NOTE`, `set_loop_baseline()` и уведомления используют одно
  и то же авторитетное значение.
- Если строгий обход не завершён, `route_question()` должен сообщить вызывающему
  коду отдельный технический исход/исключение до вызовов `deep_diagnose()`,
  `orchestrator_answer()`, `pause_pipeline()`, `write_question()` и `notify()`.
  `cycle()` в таком исходе вызывает существующий `retry_terminal_task()`:
  терминальная передача снимается из `processed` и повторяется в следующем
  цикле. Ошибка чтения истории не превращается в вопрос владельцу.
- Короткий список из 100 задач оставить для оперативного планирования цикла.
  Полную историю читать лениво только перед пороговой маршрутизацией; установленный
  `MAX_TERMINAL_TASKS_PER_CYCLE` ограничивает стоимость одним таким обходом за
  цикл. Существующий безопасный полный обход диагностики ремонта перевести на
  тот же строгий пагинатор, не меняя правила отмены и продолжения ремонта.

В `pilot/test_pilot.py` добавить `RouteQuestionCompleteAttemptCountTests` с
постраничным fake API и проверками побочных действий маршрута и состояния
`processed`.

## Последовательный план

1. Объединить полный обход задач в строгий пагинатор с дедупликацией и явным
   отказом от частичного результата.
2. Передать в `route_question()` идентичность текущей работы и стадию, число
   попыток вычислять внутри функции по строгой истории.
3. Во всех вызовах маршрута из `cycle()` убрать расчёт порогов по короткому
   `tasks`; для технических ворот без неудачной попытки явно сохранить нулевой
   режим без применения лимитов.
4. Обработать неполную историю как повторяемую техническую задержку: вернуть
   терминальную задачу в обработку и не создавать вопрос или продолжение.
5. Перевести диагностический ремонт на общий строгий пагинатор и добавить
   целевые регрессии для второй страницы, `work_id`, дубля и сбоя cursor.

## Критерии приёмки

1. Если в первой странице видны менее `max_work_rounds` попыток, но полный
   постраничный список содержит пороговое число попыток той же работы и стадии,
   `route_question()` применяет ветку стоп-крана: дальнейший обычный маршрут не
   выполняется, а зафиксированные число и baseline равны полному счётчику.
2. Порог `max_stage_attempts` и запуск `deep_diagnose()` используют то же полное
   число, поэтому диагностика, ограничение стадии и стоп-кран не расходятся.
3. Задачи с одинаковым названием, но разными `work_id`, не суммируются. Для
   legacy-записей без provenance сохраняется текущее сопоставление по названию.
4. Повтор одной задачи на соседних страницах не увеличивает число попыток.
5. Повторившийся cursor, незавершённая последняя страница или ошибка API не
   разрешают автоответ, паузу, запись вопроса либо уведомление. Терминальная
   задача остаётся доступной следующему циклу через `retry_terminal_task()`.
6. Технические вопросы ворот Review/Verify, для которых текущий код намеренно
   передаёт ноль и не считает неудавшийся запуск стадии, не становятся ложными
   срабатываниями лимита.
7. Существующие сценарии `DiagnosisRepairTests`, включая одноразовый ремонт и
   baseline после настоящей остановки, продолжают проходить.

## Тест-план

В новом `RouteQuestionCompleteAttemptCountTests` собрать минимум 101 задачу:
ранние попытки целевой работы поместить на вторую страницу, а текущую попытку —
на первую. Вызвать маршрут через `cycle()` и подтвердить полный порог,
`pause_pipeline()`/`set_loop_baseline()` и отсутствие обычного продолжения.

Отдельными тестами проверить одинаковый заголовок при разных `work_id`, дубль
ID между страницами, повтор cursor и исключение второй страницы. Для двух
последних случаев проверить отсутствие всех внешних действий маршрута и удаление
ID из `state["processed"]`. Существующие прямые тесты `route_question()` обновить
так, чтобы они подавали полную историю через fake API, а не обходили новый
контракт готовым числом.

Целевая команда этапа реализации:
`python3 -m unittest -v pilot.test_pilot.RouteQuestionCompleteAttemptCountTests pilot.test_pilot.DiagnosisRepairTests`.

## Риски и решения

- Риск: полный обход каждой минуты увеличит нагрузку. Решение: читать его только
  для одной обрабатываемой терминальной передачи, а не заменять короткий снимок
  планировщика.
- Риск: одинаковые названия прежних поколений дадут завышение. Решение:
  `work_id` остаётся приоритетной идентичностью; fallback по названию применяется
  только когда durable provenance отсутствует у обеих сторон, как сейчас.
- Риск: попытка «помочь» при сетевой ошибке снова сожжёт круг. Решение:
  частичная история всегда означает техническое ожидание, а не число ноль и не
  решение владельца.
- Решение: не сохранять отдельный счётчик попыток и не добавлять миграцию. API
  задач остаётся источником истины, а строгая пагинация устраняет расхождение
  без нового состояния.
- Вне области: изменение значений `max_stage_attempts`, `deep_diag_rounds`,
  `max_work_rounds`, правил оркестраторского ответа, UI вопросов и денежного
  сторожа.
