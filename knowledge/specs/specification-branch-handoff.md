# Спецификация сохраняется в ветке до разработки

## Цель и влияние на пользователя

Успешный этап `Specification` сейчас может передать работу в `Implement + Test`,
даже если названная в отчёте ветка не опубликована. Следующий исполнитель тогда
получает только сокращённый текст отчёта, но не сам согласованный документ и не
может надёжно продолжить с того же состояния репозитория.

После изменения Пилот будет запускать разработку только по опубликованной ветке с
непустым отличием от `main`. Если спецификация осталась только в worktree агента,
Пилот один раз вернёт тот же этап с точной инструкцией сохранить и запушить
документ. Для владельца это означает, что принятый план не теряется между
исполнителями и остаётся проверяемой частью поставки.

## Технический подход

Минимальное изменение ограничено `pilot/pilot.py` и `pilot/test_pilot.py`.
В существующем переходе между стадиями, после выбора ветки и до создания задачи
`Implement + Test`, добавить отдельные ворота для завершённой `Specification`:

- выбрать фактически опубликованную ветку через существующие
  `branch_candidates` и `pushed_branch`, как уже делается перед Review;
- проверить её через существующий `branch_report`;
- считать передачу готовой только при состоянии `есть` и непустом списке файлов
  в сравнении `main...branch`;
- при отсутствующей ветке, пустом имени или пустом diff создать повторную задачу
  `Specification` с тем же repository и revision, объяснив, что документ надо
  закоммитить и запушить в текущую назначенную ветку;
- при временной ошибке GitHub не объявлять ветку отсутствующей: снять задачу из
  `processed` и повторить проверку в следующем цикле без создания следующей стадии;
- после успешной проверки передать в контекст разработки именно выбранное
  опубликованное имя ветки.

Новые таблицы, HTTP-маршруты, форматы данных и UI не нужны. Существующие ворота
обещаний `ГОТОВО-КОГДА` остаются независимыми: они проверяют содержание отчёта,
а новые ворота — сохранность артефакта в Git.

## План реализации

1. Вынести или добавить малую проверку опубликованной непустой ветки для
   перехода `Specification → Implement + Test`, используя `branch_report`.
2. До создания следующей стадии вернуть `Specification`, если ветка или её diff
   отсутствуют; ограничить автоматический возврат существующим счётчиком rescue.
3. При недоступном GitHub оставить завершённую задачу на повторную обработку,
   не создавая ни разработку, ни ложный возврат.
4. Передавать разработке подтверждённое имя ветки, даже если в отчёте первой
   упомянута устаревшая ветка, а опубликованная указана отдельно.
5. Добавить изолированные тесты трёх исходов: опубликованная непустая ветка,
   отсутствующая/пустая ветка и недоступная проверка.

## Критерии приёмки

1. Успешная `Specification` с опубликованной веткой и непустым diff создаёт ровно
   одну задачу `Implement + Test`; её контекст содержит подтверждённую ветку.
2. Если ветки нет в origin либо сравнение с `main` не содержит файлов,
   `Implement + Test` не создаётся, а Пилот создаёт повторную `Specification` с
   инструкцией закоммитить и запушить документ.
3. Если имя ветки отсутствует в отчёте и входном контексте, разработка не
   запускается и применяется тот же безопасный возврат спецификации.
4. Сетевая/служебная ошибка проверки GitHub не трактуется как отсутствие ветки:
   ни разработка, ни новая спецификация не создаются, а переход повторяется позже.
5. Ворота не меняют переходы остальных стадий и не ослабляют существующую
   проверку строк `ГОТОВО-КОГДА`.

## План тестирования

В `pilot/test_pilot.py` добавить класс `SpecificationBranchHandoffTests`, который
запускает один цикл с успешной задачей Specification и подменяет только API Factory
и чтение состояния ветки GitHub. Проверки должны фиксировать число, workflow
revision и контекст созданной задачи, а также повторную обработку при сетевой
неопределённости.

Обязательная целевая команда:
`python3 -m unittest -v pilot.test_pilot.SpecificationBranchHandoffTests`.
Новый сценарий отсутствующей ветки должен падать до реализации, потому что текущий
код сразу создаёт `Implement + Test`.

## Риски и решения

- Решение: непустой diff используется как общий для репозиториев признак
  сохранённого артефакта; жёсткий путь `knowledge/specs/` отклонён, поскольку
  подключённые проекты могут хранить спецификации в другом каталоге.
- Решение: временная недоступность GitHub означает ожидание, а не возврат агенту;
  это исключает ложные циклы из-за сети.
- Риск: непустая ветка сама по себе не доказывает качество документа. За качество
  отвечают решение оркестратора и обещания; эти ворота доказывают только сохранность.
- Отклонено: вкладывать полный документ в context следующей задачи. Контекст
  обрезается и не является версионируемым артефактом репозитория.
- Вне области: изменение инструкций workflow, интерфейса Work и ворот перед Review.
