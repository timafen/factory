# Повторная предполётная проверка выпуска при deleted-inode

## Цель и влияние на владельца

Владелец разрешил заново запустить предполётную проверку выпуска Factory. Предыдущая попытка оборвалась сообщением `attempt supervisor output ended unexpectedly`; это сбой доставки вывода, а не доказательство успешного или окончательно неуспешного preflight.

Цель следующего запуска — получить однозначный результат до первой мутации. Если активный process использует удалённый inode, выпуск должен безопасно остановиться, назвать unit и сохранить полный вывод. Если причина устранена, проверка может продолжить штатный release gate. Нельзя объявлять старую попытку PASS, выполнять ручную замену бинаря или отключать fail-closed проверку.

## Технический подход и реальные файлы

- `ops/fx-factory-release` уже пишет бортовой журнал для broker-запуска (`FACTORY_DELIVERY_ID`) и до установки проверяет `MainPID` каждого активного unit через `/proc/<pid>/exe`. Суффикс ` (deleted)` завершает gate с сообщением `процесс <unit> использует deleted-inode` и кодом 4, до создания generation и любой мутации.
- `ops/test-factory-release-systemd.sh` создаёт реальный временный systemd unit, заменяет его executable и доказывает, что `/proc/<pid>/exe` показывает ` (deleted)`. Это проверка ОС-предпосылки, на которой основан gate.
- `ops/test-fx-factory-release.sh` — обязательный изолированный release fixture. Он остаётся местом для сценария, в котором preflight получает deleted executable, отказывает до mutation и печатает диагностическое сообщение.
- `docs/factory-handover-sol.md` задаёт операционное действие после такого отказа: перезапустить затронутый сервис и только затем повторить release. В спецификации не меняются production, systemd units или код выпуска.

## Последовательный план

1. Запустить разрешённый владельцем повторный release/preflight через штатный Factory broker; не подменять команду, release driver или окружение.
2. Привязать запуск к его `FACTORY_DELIVERY_ID` и после окончания прочитать соответствующий voyage-log. Сохранить порядок строк `== ...`, итоговую ошибку и exit code в истории попытки.
3. При `deleted-inode` определить unit из строки отказа, перезапустить только этот service штатной операционной процедурой и повторить preflight один раз. Не выполнять установку до успешного нового gate.
4. При новом обрыве supervisor считать результат неопределённым, а не PASS/FAIL: зафиксировать последний `== <шаг>` и полный доступный вывод voyage-log; передать их в диагностику broker/supervisor.
5. Если fixture не покрывает отказ до mutation и текст ошибки, добавить этот сценарий в `ops/test-fx-factory-release.sh`; если покрывает — продуктовый код не менять и закрыть повтор как операционную проверку.

## Критерии приёмки

1. Повторный запуск имеет отдельный результат и не наследует статус предыдущего обрыва.
2. При deleted inode release прекращается до публикации generation, замены бинарей, миграции или перезапуска сервисов.
3. В диагностике доступны unit, последний именованный шаг, полный вывод и код завершения; отсутствие ответа supervisor не маскирует результат.
4. После штатного restart конкретного unit следующий preflight либо проходит, либо снова выдаёт точную fail-closed причину.
5. Никакая реализация не ослабляет проверку `/proc/<pid>/exe` и не считает заменённый путь доказательством работающего процесса.

## Тест-план

- Выполнить `bash ops/test-fx-factory-release.sh`; он должен завершиться кодом 0 и подтвердить сценарии preflight/rollback без доступа к production.
- Выполнить `bash ops/test-factory-release-systemd.sh` там, где доступен root systemd fixture; ожидать PASS с deleted inode. В локальной среде вне systemd допустим только явный SKIP, не PASS.
- Для повторной живой попытки проверить voyage-log: успешный запуск содержит все шаги до commit, отказ содержит последний `== ...`, строку `!! ...` и ненулевой exit code. При обрыве supervisor приложить полный сохранённый log без сокращения.

## Риски и решения

- **Повторный запуск может перейти от preflight к установке.** Он запускается только по уже данному разрешению владельца; gate остаётся до первой мутации, а при новой неопределённости выпуск не объявляется успешным.
- **Перезапуск не того процесса скрывает проблему.** Использовать только unit из сообщения gate и перепроверить его `MainPID`/`/proc` на следующей попытке.
- **Supervisor снова потеряет stdout.** Бортовой журнал, создаваемый release driver по `FACTORY_DELIVERY_ID`, является источником диагностики; без него статус попытки — неопределённый.
- **Локальный systemd тест недоступен.** Его SKIP не подменяет production-проверку; обязательным остаётся изолированный release fixture.
