# Снимок базы сервера не зависит от домашней папки

## Цель и влияние на владельца

`factory-server -database SOURCE -backup DEST` сейчас вычисляет стандартный путь
базы до разбора флагов. В изолированной среде без `HOME`, `FACTORY_DATA_HOME` и
`FACTORY_V2_DATA_HOME` команда завершается ошибкой `resolve home directory:
$HOME is not defined`, хотя оба нужных пути переданы явно.

После изменения оператор сможет получить согласованный снимок явно указанной
базы в cron, контейнере или минимальном сервисном окружении без фиктивной
домашней папки. Обычный запуск сервера, backup без явного `-database`, restore и
разрешение bootstrap-конфигурации сохраняют текущие правила. Работа является
дубликатом CARD-0124: новое решение не разрабатывается, а уже опубликованный
кандидат проверяется относительно свежего `main` и после PASS передаётся на
squash-слияние. Выкат живой Фабрики не входит в эту работу.

## Технический подход и реальные файлы

Реализация ограничена `cmd/factory-server/main.go` и
`cmd/factory-server/main_test.go`. Готовый кандидат находится в ветке
`factory/7276dbb0-e0b-afc197a8-73b`; его коммит реализации
`3090866634059f02a6fc5ae5d2ada869e1662a97` является исходной точкой, а не
основанием создавать альтернативный патч.

В `run()` до вызова `defaultDatabasePath()` нужно распознать штатным
`flag.FlagSet` только корректную комбинацию непустого `-backup` и явно
посещённого `-database`. Для неё флаги разбираются обычным способом, затем
`runRecoveryMode()` выполняется до чтения домашней папки и bootstrap. Ранний
путь должен поддержать разделённые и `=`-формы с одним или двумя дефисами и
сохранить стандартные ошибки парсера. Все остальные режимы продолжают прежнюю
инициализацию defaults, legacy-проверок, data root и конфигурации.

В `main_test.go` subprocess-тест собирает настоящий `factory-server`, удаляет
из окружения домашние переменные, задаёт отсутствующий bootstrap-файл и
проверяет четыре формы флагов. Проверка подтверждает создание основной базы и
маркера снимка, отсутствие `-wal`/`-shm` у результата и неизменность источника.
Отдельная табличная проверка фиксирует грамматику предварительного распознавания.
Новые UI, API, схема SQLite и release-сценарий не требуются.

## Последовательный план

1. На Review зафиксировать свежие полные SHA remote default branch и ветки
   кандидата, сравнивать только `base...candidate` и убедиться, что кандидат
   содержит ровно заявленные серверный код, тесты и CARD-0124.
2. Проверить в `main.go`, что ранний путь включается только для явного backup,
   использует стандартную грамматику `flag` и возвращается после успешного
   `runRecoveryMode`, не меняя другие режимы запуска.
3. Проверить в `main_test.go` subprocess-сценарий без домашних переменных,
   четыре формы CLI, автономность результата и неизменность исходной базы.
4. На Verify один раз выполнить целевой тест, полный `go test ./...` и
   `go build ./...`; чужую нестабильность полного набора зафиксировать отдельно,
   не подменяя ею результат целевого теста.
5. После PASS перебазировать существующего кандидата на свежий `main`, влить
   его одним squash-коммитом и подтвердить присутствие коммита в remote `main`.
   Живой выкат не выполнять.

## Критерии приёмки

1. При отсутствии `HOME`, `FACTORY_DATA_HOME` и `FACTORY_V2_DATA_HOME` команда
   `factory-server -database SOURCE -backup DEST` завершается с кодом 0 и
   сообщает путь созданного снимка.
2. Поведение одинаково для `-flag value`, `--flag value`, `-flag=value` и
   `--flag=value`.
3. Снимок содержит основную базу и обязательный marker, не требует рядом WAL
   или SHM и открывается независимо от исходной базы.
4. Выполнение backup не изменяет байты исходной базы и её marker.
5. Без явного `-database`, без непустого `-backup`, при неизвестном флаге или
   при режиме restore сервер использует прежний путь и прежние проверки.
6. В поставке используется кандидат CARD-0124; альтернативной реализации и
   живого выката нет.

## Тест-план

Обязательная регрессия — subprocess-тест
`TestBackupCLICreatesSnapshotWithoutHome`: он должен собирать бинарник и
запускать его в очищенном окружении, поскольку прямой вызов helper не выявляет
ошибку порядка инициализации `run()`. Табличный
`TestBackupWithExplicitDatabaseHonorsFlagGrammar` покрывает положительные и
отрицательные формы предварительного разбора.

На Verify выполнить целевой тест без кэша, затем ровно один полный прогон Go и
сборку:

```text
go test -count=1 ./cmd/factory-server -run '^TestBackupCLICreatesSnapshotWithoutHome$'
go test ./...
go build ./...
```

## Риски и решения

- Риск: ручной поиск строк `-database` даст ложные совпадения в значениях.
  Решение: отдельный `flag.FlagSet` с той же грамматикой и проверкой посещённого
  флага.
- Риск: общий ранний recovery-путь незаметно изменит restore или backup с
  default database. Решение: обход home включается только при одновременно
  явном `database` и непустом `backup`; остальные случаи остаются на прежнем
  пути.
- Риск: проверка только наличия файла пропустит несогласованный SQLite-снимок.
  Решение: тест требует marker, отсутствие временных sidecar-файлов и
  неизменность источника; существующие тесты `controlplane.BackupDatabase`
  продолжают проверять механизм копирования.
- Риск: кандидат устареет относительно `main`. Решение: Review и Verify
  повторно фиксируют remote SHA, а слияние разрешено только после rebase и PASS.
- Решение владельца: задача закрывает дубликат через CARD-0124; новый патч и
  production rollout исключены из области.
