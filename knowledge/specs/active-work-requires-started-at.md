# «В работе прямо сейчас» показывает только начатые попытки

## Цель и влияние на владельца

Владелец должен видеть в разделе «В работе прямо сейчас» только работу,
которую исполнитель уже фактически начал. Сейчас `preparing` без
`started_at` преобразуется в API в `running`, поэтому назначенная, но ещё не
запущенная попытка выглядит выполняемой. Это завышает активный счётчик и
скрывает очередь.

После изменения ненулевая дата `attempts.started_at` станет единственным
признаком фактического старта. Подготовленные и ожидающие запуска попытки
останутся в «Ожидают исполнителя»/очереди; начатые — в «В работе прямо
сейчас». Владелец сможет отличить свободную очередь от реально занятой
работы и доверять обоим числам.

## Технический подход и реальные файлы

Сервер должен расширить сводный контракт задачи полем
`started_at?: time.Time`/`started_at?: string` и заполнять его из текущей
попытки. В `internal/controlplane/store.go` запрос `Tasks` должен вернуть
дату попытки без `started_at` как `NULL`; `scanTask` не должен превращать
`preparing` в `running` для этого представления. Деталь задачи и переходы
жизненного цикла не меняются: `StartAttempt` по-прежнему записывает дату.
Состояние очереди и активная классификация должны быть совместимы с
пагинацией и не считать завершённые/отменённые попытки.

В `web/src/types.ts` добавить поле `started_at`. В `web/src/Work.tsx` считать
активной только задачу с `started_at`, а queued/preparing без даты направлять
в queued-статус с подписью «Ждёт исполнителя». Отдельно сохранить историю и
разделение очереди и активных работ; не считать наличие `state === running`
достаточным. В `web/src/Overview.tsx` использовать тот же предикат для
`overviewWork` и отображаемых активных/очередных чисел, чтобы Overview и Work
не расходились.

Серверная регрессия размещается в `internal/controlplane/store_test.go` или
`internal/controlplane/http_test.go`: создать queued/preparing попытку,
проверить отсутствие `started_at` и отсутствие ложного `running`, затем
вызвать старт и проверить дату и `running`. Web-регрессии размещаются в
`web/src/Work.test.ts`, `web/src/WorkView.test.tsx` и
`web/src/Overview.test.ts`; фикстуры должны содержать оба состояния и
проверять активный счётчик.

## Последовательный план

1. Уточнить server/protocol DTO задачи полем `started_at` и убрать
   нормализацию `preparing` в `running` из списка задач.
2. Получать дату только у актуальной попытки, сохранив `NULL` до фактического
   `StartAttempt`; проверить, что detail/терминальные состояния не ломаются.
3. Перевести Work и Overview на общий смысловой предикат «started_at непуст». 
4. Добавить серверную, чистую unit- и component-регрессии; обновить ожидания
   существующих сценариев Work.
5. Запустить целевые проверки, typecheck и проверку пробелов в diff.

## Критерии приёмки

1. `preparing`/`started_at = NULL` не попадает в активный раздел и не
   увеличивает active/running count.
2. `running`/`started_at != NULL` попадает в «В работе прямо сейчас».
3. Очередь и активные работы отображаются раздельно, а queued count включает
   ожидающие старта попытки.
4. API не маскирует неподтверждённый старт преобразованием `preparing` в
   `running`; после `StartAttempt` дата и состояние видны клиенту.
5. Work и Overview используют одинаковую границу активной работы; прежние
   сценарии завершённых, отменённых и повторных попыток не меняются.
6. Есть серверная и UI-регрессии, выражающие оба контракта: до и после
   `started_at`.

## Тест-план

Сервер: через store/HTTP fixture создать задачу с попыткой `preparing` и
`started_at = NULL`, получить список, проверить состояние/дату и счётчики;
затем выполнить старт и проверить `running`, ненулевую дату и активный
результат. Отдельно проверить, что старые terminal attempts не выбираются как
текущая попытка.

Web: в `Work.test.ts` проверить классификацию двух задач; в
`WorkView.test.tsx` проверить видимость queued и active в разных секциях и
число карточек; в `Overview.test.ts` проверить `overviewWork` и нулевой
активный результат для неподтверждённого старта. Сохранить существующие
проверки Work.

Обязательная команда этапа разработки:

`go test ./internal/controlplane/...`

Дополнительно:

`npm --prefix web test -- --run src/Work.test.ts src/WorkView.test.tsx src/Overview.test.ts`

`npm --prefix web run typecheck`

`git diff --check`

## Риски и решения

- Риск: у задачи может быть несколько попыток. Решение: выбирать попытку,
  связанную с текущим execution, либо последнюю актуальную попытку по
  существующему серверному правилу; не брать историческую дату вслепую.
- Риск: обратная совместимость клиентов. Решение: `started_at` сделать
  необязательным JSON-полем, а отсутствие даты трактовать как queued.
- Риск: рассинхрон Work и Overview. Решение: одинаковое условие
  `started_at != null` закрепить отдельными тестами обоих экранов.
- Риск: изменение общего состояния API затронет старые потребители.
  Решение: не менять записи в БД и lifecycle; изменить только честность
  read-модели и добавить серверные проверки.
- Вне области: жизненный цикл попыток, назначение исполнителя, capacity,
  метрики производительности и поведение уже начатых/завершённых работ.
