# Санитар очищает фантомные retained worktree остановленного claude-haiku

## Цель и влияние на пользователя

Когда воркер `claude-haiku` остановлен, встроенный санитар уже переносит его
worktree и manifest в карантин, но control plane продолжает хранить старую запись
`retained_worktrees`. Владелец видит несуществующий результат и не может удалить
связанную terminal-историю: `Store.DeleteTask` намеренно отвечает
`retained_worktree`. После изменения санитар подтвердит в control plane именно
обработанные записи, поэтому карточка воркера и удаление истории снова отражают
реальное состояние диска без ожидания несуществующего heartbeat.

## Технический подход

Добавить в `internal/controlplane/store.go` операцию, которая для конкретного
воркера удаляет из `retained_worktrees_json` только переданный список снимков
retained worktree. Совпадение должно включать `attempt_id` и остальные поля
снимка, а не очищать весь массив: повторный запуск санитара должен быть
идемпотентным, а новая регистрация воркера между чтением и подтверждением не
может потерять новую запись. Не изменять `worker_repositories.retained_count`
и механизм capacity handoff: эти значения принадлежат регистрации воркера и не
являются доказательством физической очистки в данном сценарии.

В `internal/controlplane/http.go` открыть узкий внутренний маршрут подтверждения
санитарной очистки для worker ID и JSON-массива `retained_worktrees`. Он вызывает
новую store-операцию, возвращает актуального воркера и сохраняет обычные ошибки
валидации/`not_found`. Существующий `PUT /api/v1/workers/{worker_id}` остаётся
единственным способом менять здоровье, runtime, репозитории и heartbeat; санитар
не имитирует регистрацию офлайн-воркера.

В `ops/factory-janitor.sh` сохранить из `GET /workers` ID и точный список
retained worktree sick-воркера. После успешного переноса worktree и manifest в
карантин, `git worktree prune` и перед запуском службы санитар отправляет этот
список на новый маршрут. При ошибке HTTP он пишет причину в журнал и не выдаёт
ложного сообщения об освобождении; локальные файлы остаются в карантине, что
сохраняет восстановимость. В обработку не попадут записи, для которых перенос
worktree не состоялся.

Затрагиваемые файлы реализации: `internal/controlplane/store.go`,
`internal/controlplane/http.go`, `internal/controlplane/store_test.go`,
`internal/controlplane/http_test.go`, `ops/factory-janitor.sh` и его целевой
shell-тест `ops/test-factory-janitor.sh`.

## План реализации

1. Выделить в Store транзакционное подтверждение удаления точных retained-снимков
   с проверкой worker ID и сохранением несовпавших/новых записей.
2. Добавить внутренний HTTP-маршрут, декодирование списка и ответ актуальным
   состоянием воркера.
3. Научить санитар получать ID и снимки из `/workers`, собирать только успешно
   перенесённые записи и подтверждать их после локальной очистки.
4. Добавить изолированные Go- и shell-регрессии, включая повторный запуск,
   несовпадающую новую запись и сбой HTTP.

## Критерии приёмки

1. Для остановленного `claude-haiku`, чей worktree санитар успешно перенёс в
   карантин, API воркера больше не возвращает соответствующий `retained_worktree`.
2. После такого подтверждения `DeleteTask` принимает terminal-историю, которую
   прежде блокировала только эта запись.
3. Санитар не удаляет из control plane запись, если её локальный worktree не был
   перенесён в карантин, а при ошибке подтверждения оставляет понятную запись в
   журнале.
4. Подтверждение повторно безопасно; несовпадающие и появившиеся после снимка
   retained worktree сохраняются.
5. Обычная регистрация воркера и её поля (health, heartbeat, runtime,
   repositories и capacity handoff) не меняют семантику.

## План тестирования

В `internal/controlplane/store_test.go` добавить проверку точечного и
идемпотентного снятия retained-снимка, сохранения несовпавшей новой записи и
разблокирования `DeleteTask`. В `internal/controlplane/http_test.go` проверить
маршрут, неверный worker ID и некорректное тело. В новом
`ops/test-factory-janitor.sh` подменить `systemctl`, `curl`/API и файловое дерево:
подтвердить, что санитар отправляет только перемещённые записи, не подтверждает
неперемещённую и журналирует ошибку API.

До реализации основной целевой проверкой служит новый тест
`TestJanitorClearsRetainedWorktreeAfterQuarantine`; он должен падать, пока
санитар не умеет сообщить control plane о карантине.

## Риски и решения

- Решение: не очищать весь список и не посылать санитаром `PUT`-регистрацию.
  Полная регистрация без живого воркера способна подменить heartbeat, health и
  сведения о репозиториях.
- Решение: карантин остаётся источником восстановления. Подтверждение API —
  второй шаг после успешного перемещения, а не замена ему.
- Риск: сервис может зарегистрироваться между снимком и подтверждением. Точное
  сравнение снимка оставляет новую либо изменённую запись нетронутой.
- Риск: внутренний API сейчас не имеет отдельной аутентификации. Новый маршрут
  следует ограничить тем же loopback/сетевым контуром, что и существующий API;
  добавление общей аутентификации — отдельная работа.
- Вне области: автоматическое удаление карантина, изменение лимита трёх попыток
  санитара, ручной CLI cleanup и пересчёт repository retained_count.
