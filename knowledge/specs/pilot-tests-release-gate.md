# Спецификация: тесты Pilot — обязательные ворота выката

## Цель и влияние на владельца

В `main` не должна попасть ревизия, в которой красны проверки мозга Pilot.
Перед сборкой и установкой локальный выкат будет параллельно выполнять полный
набор `pilot.test_pilot`; его отказ отменит остальные ворота, остановит выкат
до изменения установленной генерации и до перезапуска служб. Две регрессии
`AdaptivePollingTests` станут детерминированными относительно уже существующего
контракта часов `run_loop`, без изменения polling-логики.

## Технический подход и реальные файлы

- `pilot/test_pilot.py`: в
  `test_loop_uses_fast_handoff_then_idle_hint_with_fake_clock_and_sleep` и
  `test_network_errors_back_off_and_success_resets_interval` задать столько
  значений fake clock, сколько раз `run_loop` вызывает `clock_fn`: для каждого
  успешного цикла отдельно время live-status и время `record_poll_hint`.
  Ожидания `chosen_at` остаются точными; production-код `pilot/pilot.py` не
  меняется.
- `ops/fx-factory-release`: в `run_parallel_test_gates` добавить третью
  именованную группу «Pilot-проверки», запускающую из `$work/src` доверенным
  `python3` команду `python3 -m unittest pilot.test_pilot`. Группа запускается
  вместе с UI и Go/release группами, участвует в том же `wait -n`, прекращении
  process group, сборе логов и сообщении об ошибке. Обход через переменную
  конфигурации не добавляется.
- `ops/test-fx-factory-release.sh`: расширить изолированную shell-фикстуру
  mock `python3` и журнал ворот. Успешный сценарий докажет старт Python до
  `npx vite build` и установки; сценарий `python-test-fail` докажет ненулевой
  итог выката, отмену соседних ворот и отсутствие изменений установленной
  генерации и служб.

## Последовательный план

1. Уточнить в двух AdaptivePollingTests последовательности fake clock и
   ожидаемые timestamps согласно двум обращениям в успешном цикле.
2. Добавить отдельный Python gate в `run_parallel_test_gates`, не меняя
   production polling или существующие команды ворот.
3. Научить shell-фикстуру записывать Python-команду, блокировать/завершать её
   как соседний gate и имитировать её отказ.
4. Добавить утверждения порядка «Python до сборки/установки», отмены соседей
   при Python-failure, неизменности installation/services и отсутствия
   конфигурационного bypass.
5. Выполнить целевые Python- и shell-проверки, затем один раз полный набор
   проверок этапа Verify.

## Критерии приёмки

1. Обе названные проверки `AdaptivePollingTests` и полный
   `python3 -m unittest pilot.test_pilot` завершаются с кодом 0.
2. Полный Pilot-набор является отдельной именованной параллельной группой
   `run_parallel_test_gates`, а его лог печатается вместе с логами остальных
   ворот.
3. Shell-фикстура подтверждает, что Python-ворота стартуют до сборки и любой
   установки.
4. Искусственный отказ Python-ворот завершает release ошибкой, отменяет
   соседние группы и не меняет бинарники/текущую генерацию или службы.
5. Новый переключатель либо конфигурационная переменная для пропуска
   обязательного Python-набора отсутствует.
6. Не меняются `pilot/pilot.py`, UI, публичные API и остальная release-логика
   вне нужной регистрации ворот и фикстуры.

## Тест-план

- `python3 -m unittest -v pilot.test_pilot.AdaptivePollingTests` — проверяет
  детерминированные часы обеих исправленных регрессий.
- `python3 -m unittest pilot.test_pilot` — обязательная команда нового
  release-gate.
- `bash ops/test-fx-factory-release.sh` — проверяет pre-build запуск,
  Python-failure, отмену параллельных процессов, неизменность installation и
  services, а также отсутствие bypass.
- `go test -timeout 5m ./...` и `git diff --check` — однократно на Verify как
  смежные регрессии и чистота патча.

## Риски и решения

- Полный Pilot-набор увеличит время ворот. Он уже локальный и
  воспроизводимый; отдельная параллельная группа не удлиняет критический путь
  сильнее самой медленной обязательной проверки.
- Фикстура может оставить дочерний Python-процесс. Использовать существующий
  механизм session/PGID и `assert_no_fixture_processes`, а не отдельное
  непроверяемое завершение процесса.
- Лишнее значение времени могло бы ослабить тест. Последовательность часов
  должна документировать оба потребления времени успешным циклом и сохранять
  точную проверку `chosen_at`.
- Переменная отключения сделала бы барьер необязательным. Не добавлять её;
  тест фиксирует неизменный запуск команды в нормальном release-пути.
