# Снятая пауза запускает правильный следующий этап

## Цель и влияние на владельца

Когда владелец удаляет работу из `stopped_pipelines`, уже начавшийся цикл Pilot
должен увидеть durable-настройку и передать застрявшую работу ровно на этап
после последнего успешного. Владелец получает предсказуемое продолжение без
повторного раннего этапа, ручного запуска и параллельных дублей.

Синхронизация уже реализована коммитом
`bd9629268825db1c7e7457fd103b5f49490f6243`: `cycle()` вызывает очистку и
перечитывает `CONF_PATH` до `pipeline_watch()`. Эта работа закрепляет сквозную
приёмку отсутствующим regression-тестом. HTTP-кнопка `/works/resume`, UI,
merge/release и длительность безопасного окна не входят в область.

## Технический подход и реальные файлы

Изменение реализации ограничить `pilot/test_pilot.py`. Добавить в
`OrphanedPausedPipelineCleanupTest` один сквозной unit-сценарий
`test_external_pause_removal_starts_exact_next_stage_in_same_cycle`, который
запускает фактические `cleanup_orphaned_paused_pipelines()` и
`pipeline_watch()` в том же порядке, что и `cycle()`.

Сценарий начинает с устаревшего in-memory
`stopped_pipelines=["Оплата продавцу"]`, тогда как в подменённом durable
`CONF_PATH` паузы уже нет. В снимке задач присутствуют успешные `Triage` и
`Specification` одной работы; запись в `STALL_PATH` уже выдержала
`STALL_WAIT`. Настроен пятиэтапный pipeline, здоровый worker для третьего
`Implement + Test` и repository исходной успешной задачи.

Тест должен перехватить `create_task`/`create_child_task` на границе Factory и
проверить единственное тело новой задачи: заголовок `[auto] [3/5 Implement +
Test] Оплата продавцу`, `workflow_revision_id` следующего workflow,
`worker_id` выбранного worker и исходный `repository_id`. Вызов сторожа второй
раз с созданной живой задачей в том же изменяемом списке не создаёт дубль.

В этом же тесте либо в табличных подслучаях проверить отрицательные условия:
оставшаяся durable-пауза блокирует создание; уже живая задача следующей стадии
блокирует создание; повтор после успешного создания блокируется. Сторож не
должен обходить ожидание: тест заранее старит stall-запись на ровно
`STALL_WAIT`, а отдельная существующая проверка продолжает фиксировать значение
450 и отказ до истечения окна.

`pilot/pilot.py` менять только если новый сценарий сначала выявит фактический
разрыв. Допустима лишь минимальная коррекция порядка синхронизации,
дедупликации или выбора следующего этапа; значение `STALL_WAIT`, API и UI
остаются неизменными.

## Последовательный план

1. Собрать fixture завершённой работы с двумя успешными последовательными
   стадиями, repository и выдержанной stall-записью.
2. Записать в durable config снятую паузу, сохранив устаревшую паузу в `conf`,
   затем вызвать очистку и сторож последовательно в одном тестовом цикле.
3. Проверить ровно одну созданную третью стадию, её title, revision, worker и
   repository, а также обновление текущего снимка созданной живой задачей.
4. Повторить сторож на том же снимке и доказать отсутствие дубля; проверить
   оставшуюся паузу и заранее живую следующую задачу как блокирующие случаи.
5. Если тест падает на текущем `main`, внести минимальную правку только в
   `pilot/pilot.py`, затем выполнить целевые классы и `git diff --check`.

## Критерии приёмки

- Удаление работы из durable `stopped_pipelines` обновляет устаревший `conf`
  до запуска сторожа в том же цикле.
- Для успешных `Triage` и `Specification` создаётся ровно один настроенный
  `Implement + Test`, а не повтор `Triage` или `Specification`.
- Заголовок и `workflow_revision_id` соответствуют следующей стадии;
  `worker_id` выбран для неё с учётом repository, а `repository_id` взят у
  последней успешной стадии.
- Оставшаяся durable-пауза, живая задача следующего этапа, добавленная после
  создания живая задача и повторный вызов сторожа не создают задач.
- Создание разрешается только после `STALL_WAIT=450`; при меньшем возрасте
  существующая защита продолжает удерживать переход.
- Регрессия проходит без обращения к сети, реальному Factory API и рабочему
  `/opt/factory-data/pilot/config.json`.

## Тест-план

- `python3 -m unittest -v pilot.test_pilot.OrphanedPausedPipelineCleanupTest pilot.test_pilot.PipelineWatchTests`
  — новый сквозной сценарий и существующие контракты синхронизации, выбора
  следующей стадии, окна ожидания и дедупликации.
- `python3 -m unittest -v pilot.test_pilot` — один полный Pilot-набор на этапе
  Verify, не на каждой итерации реализации.
- `git diff --check` — корректность документации и будущего тестового diff.

## Риски и решения

- Ложноположительный тест может напрямую обнулить `conf` и не проверить чтение
  с диска. Решение: до очистки память обязательно содержит паузу, а
  `CONF_PATH` — уже снятую паузу; проверяется результат фактического helper.
- Тест отдельных helper-ов может разойтись с production-порядком. Решение:
  сохранить порядок `cycle()` — cleanup после supersede и до handle/watch — и
  явно назвать сценарий проверкой одного цикла.
- Немедленное создание замаскирует обход safety-window. Решение: не мокать
  константу и старить stall-запись ровно на 450 секунд; границу меньше 450
  оставляет существующий `PipelineWatchTests`.
- Повтор может выглядеть безопасным лишь из-за stall-memory. Решение: проверить,
  что созданная задача добавлена в переданный список со state `created`, и
  именно живая задача подавляет повтор.
- Реализация синхронизации уже находится в `main`; повторно переписывать её без
  красного regression-теста запрещено.
