# Спецификация: идемпотентный handoff после записи `processed`

## Цель и влияние на владельца

Устранить риск, при котором Pilot уже записал завершённую задачу в
`state["processed"]`, но процесс остановился до создания следующей стадии.
Нужно также исключить повторное создание продолжения, если другой Pilot успел
выполнить handoff по устаревшему снимку. Для владельца это означает, что
завершение стадии не теряет хвост и не разветвляет одну работу на дубли.

Это повторная работа: утверждённое владельцем исправление уже вошло в `main`
через PR #220, implementation commit
`c648f4a4adaa65faefaa6d1806ca1a3090b0afca`. На текущем этапе новый продуктовый
код, UI, выкат и дополнительная реализация не требуются.

## Технический подход и реальные файлы

Фактическая реализация и регрессии находятся в следующих файлах:

1. `pilot/pilot.py` — при обработке terminal-задачи ID попадает в
   `state["processed"]` до handoff, но `retry_terminal_task()` удаляет его при
   повторяемом отказе. `continuation_request_key()` строит стабильный ключ из
   родительской задачи и revision следующей стадии, поэтому конкурентные или
   повторные запросы становятся одной атомарной операцией control plane.
2. `pilot/pilot.py` — после всех долгих decision/delivery gates вызывается
   последняя `live_or_done_at()` непосредственно перед `create_child_task()`.
   Успешно созданный child добавляется в текущий снимок `tasks`, чтобы
   последующие handoff этого цикла видели его без нового API-запроса.
3. `pilot/pilot.py` — `run_loop()` сохраняет watermark, а startup recovery
   проверяет только ограниченное множество недавних `processed` IDs. Detail
   загружается отдельно для задачи за пределами первой страницы; recovery
   создаёт отсутствующий хвост только если завершение новее watermark и
   `live_or_done_at()` не находит уже живую или успешную следующую стадию.
4. `pilot/test_pilot.py` — `AdaptivePollingTests` проверяет пропущенный handoff
   после рестарта, отсутствие дубля при повторном процессе, повтор временного
   отказа создания, ожидание занятости области и ограниченность recovery.

`ops/*`, UI и общий журнал `knowledge/cards/CARD-0030*` к этой работе не
относятся и не должны изменяться. Текущий результат — документационная
фиксация уже принятого duplicate/no-op решения.

## Критерии приёмки

- Завершённая terminal-задача не считается безвозвратно обработанной, если
  создание продолжения не состоялось из-за повторяемого отказа: её ID удалён
  из `processed` и доступен для следующего цикла.
- Handoff одной пары «родительская задача — revision следующей стадии» имеет
  стабильный request key и не создаёт второй child при конкурентном повторе.
- `live_or_done_at()` вызывается непосредственно перед внешним созданием
  continuation, после всех потенциально долгих ворот; уже созданный child
  добавляется в локальный снимок.
- После рестарта Pilot проверяет только недавние завершения новее watermark,
  восстанавливает отсутствующий хвост, не дублирует существующий live/done
  child и повторяет временный отказ на следующем цикле.
- `python3 -m unittest pilot.test_pilot.AdaptivePollingTests` завершается с
  кодом 0 и сообщает 24/24 успешных теста.
- В этой Specification-поставке нет изменений продуктового кода, UI или
  выкатов; документ ссылается на уже влитый PR #220, а карточка текущей работы
  отделена от общего `CARD-0030`.

## Тест-план

- Обязательная целевая проверка: `python3 -m unittest
  pilot.test_pilot.AdaptivePollingTests`.
- В наборе должны быть покрыты: recovery `processed` после рестарта с
  отсутствующим next-stage, recovery ID за пределами первой страницы,
  атомарный стабильный request key для двух Pilot, временный
  `ParallelWorkLimit`, повтор после area wait и bounded startup recovery.
- Успешный результат текущей проверки зафиксирован как 24/24; live/browser
  проверка не нужна, потому что изменение невидимое и уже поставлено в `main`.

## Риски и решения

| Риск | Решение |
| --- | --- |
| Между ранней проверкой и API-create появляется новый child | Финальная проверка `live_or_done_at()` выполняется после ворот; стабильный request key дополнительно делает повтор атомарным. |
| Процесс падает после записи `processed` | Watermark и ограниченный startup recovery находят завершение; повторяемый отказ снимает ID через `retry_terminal_task()`. |
| Старая задача скрыта за первой страницей `/tasks` | Recovery запрашивает detail по сохранённому ID и применяет тот же duplicate guard. |
| Повторное исправление может разойтись с уже принятым PR | Источник истины — полный commit PR #220 в `main`; в текущей ветке меняются только документы. |
| Ref прошлой рабочей ветки из контекста недоступен на `origin` | Использован фактический `main`, где присутствует указанный commit; отсутствие старого ref отмечено как инфраструктурная находка, без попытки переключить ветку. |
