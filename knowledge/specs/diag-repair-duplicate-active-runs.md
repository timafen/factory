# Автопочинка не считает один запуск дважды

## Цель и влияние на пользователя

Автопочинка застрявшей работы должна начинаться, когда курсорный список задач
вернул один и тот же активный запуск на соседних страницах. Владелец больше не
получает ложное сообщение «найдено активных запусков — 2» и не чинит вручную
технический цикл, для которого цель отмены уже однозначно определена.

Защитный контракт не меняется: если найдены два разных активных ID одной работы,
Фабрика ничего не отменяет автоматически.

## Технический подход

В `pilot/pilot.py` при проверке всех страниц для `begin_diag_repair()` считать
активные запуски по уникальному `task.id`, а не по количеству строк в склеенном
ответе `/tasks`. Повтор одной задачи с тем же ID не создаёт неоднозначности;
разные ID по-прежнему блокируют ремонт. Запись без ID не должна сливаться с
другой записью без ID и тем самым ослаблять предохранитель.

В `pilot/test_pilot.py` добавить регрессионный сценарий с одним `running`-запуском,
который повторяется на двух страницах: ремонт должен выбрать сохранённый ID и
запросить его отмену ровно один раз. Существующие сценарии с двумя разными ID,
включая второй запуск за первой страницей, остаются зелёными.

Новых API, форматов сохранённого ремонта и миграций данных нет.

## План

1. Дедуплицировать результаты курсорного обхода задач по непустому `task.id`,
   сохраняя отдельными потенциально опасные записи без ID.
2. Добавить регрессионный тест дубликата одного активного ID на соседних страницах.
3. Запустить целевой класс `DiagnosisRepairTests` и проверить чистоту diff.

## Критерии приёмки

1. Один активный запуск, дважды встреченный в страницах `/tasks`, считается одним
   и запускает прежний безопасный путь отмены по его ID.
2. Для повторившегося ID выполняется ровно один запрос отмены.
3. Два разных активных ID той же работы всё ещё дают отказ без отмены любого из них.
4. Активный запуск с другим ID на следующей странице всё ещё блокирует ремонт.
5. Ошибка или повтор курсора сохраняет прежнее безопасное завершение ремонта с
   уведомлением владельца.

## План проверки

- Добавить в `DiagnosisRepairTests` тест, который до реализации падает на ложном
  количестве активных запусков, а после неё подтверждает единственную отмену.
- Выполнить `python3 -m unittest pilot.test_pilot.DiagnosisRepairTests`.
- Выполнить `git diff --check`.

## Риски и решения

- Дедупликация только по ID не скрывает реально параллельные запуски и потому не
  ослабляет запрет на неоднозначную отмену.
- Записи без ID нельзя объединять: это могло бы ошибочно разрешить необратимое
  действие при неполном ответе API.
- Альтернатива отменять все совпавшие задачи отклонена как расширение области и
  нарушение действующего контракта безопасности.
- Если API способен переиспользовать один ID для разных задач, требуется отдельный
  контракт control plane; подтверждений такого поведения в текущем коде нет.
