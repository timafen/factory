# Спецификация: новый проект подключается по безопасному шаблону

## Цель и влияние на пользователя

Владелец подключает новый проект одним понятным шаблоном вместо отдельного
включения managed-репозитория и не связанных с ним настроек. До запуска задач
Factory проверяет, что репозиторий и основная ветка доступны, выбранный
исполнитель готов, объявлены все нужные секреты, а на одном фиксированном SHA
успешно прошли secret-scan, статическая/типовая проверка, тесты и сборка.

Шаблон делает staging обязательным. Production можно описать заранее, но он
изначально заблокирован и требует отдельного подтверждения владельца. Выпуск и
откат доступны только через именованный серверный адаптер из allowlist; UI и
репозиторий не могут передать произвольную shell-команду. Значения секретов не
попадают ни в БД Factory, ни в API, UI или логи.

## Технический подход

### Модель и хранение

Вместо расширения `protocol.ManagedRepository` создать отдельный проектный
контракт, связанный один-к-одному с managed-репозиторием. Это сохраняет
`internal/controlplane/store.go` и существующий `POST /api/v1/repositories`
обратносуместимыми: старый API продолжает регистрировать только репозиторий, но
не создаёт пригодный для работы безопасный проект.

Новая миграция в `migrations/` добавит проекты, среды, обязательные проверки,
операции выпуска и требуемые имена секретов. `Project` содержит: стабильный ID,
человекочитаемое имя, нормализованный `repository_id`, основную ветку, тип
проекта и состояние. Среда содержит имя (`staging` либо `production`), HTTPS URL,
health-check и блокировку. Запись production создаётся только с
`blocked=true`; staging обязателен и не может быть удалён или заблокирован при
активном проекте. Операции хранят только идентификаторы именованного адаптера
release/rollback, а не команды. Точный allowlist web-хостов хранится как список
FQDN; wildcard, IP-адрес, URL с путём и пустой список отклоняются.

Тела API в `internal/protocol/types.go` вводят `CreateProjectRequest`, проект,
среды, readiness и безопасные статусы операций. `POST /api/v1/projects` в
`internal/controlplane/http.go` принимает только полный шаблон и создаёт
репозиторий/проект транзакционно. Повтор одного нормализованного репозитория
должен быть идемпотентным только при идентичном контракте, иначе вернуть
конфликт. Отдельные read endpoints отдают лишь имена секретов и `present`;
значения отсутствуют в типах и JSON. `Store` валидирует все инварианты до записи.

### Готовность к запуску

Новая `ProjectReadiness` объединяет существующую маршрутизационную готовность
`ManagedRepositoryReadiness` (доступ GitHub, cache/advertised, состояние worker)
с четырьмя новыми закрывающими воротами: доступ к основной ветке, готовность
исполнителя, наличие каждого именованного секрета и успешный набор проверок на
одном commit SHA. SHA передаётся как неизменяемый кандидат проверки; результаты
от разных SHA, просроченные или отсутствующие результаты не разрешают запуск.

Адаптеры являются серверной реализацией интерфейса в
`internal/controlplane/`, зарегистрированной по фиксированному ID и типу
проекта. Адаптер получает структурированные аргументы (project, environment,
SHA, секреты) и исполняет фиксированную операцию без shell. Он также проверяет,
что браузерная сеть ограничена точным allowlist проекта. Неизвестный ID,
несоответствие типа, неразрешённый хост или неполная health-конфигурация — отказ
до запуска процесса.

Секретный resolver читает только
`/etc/factory/projects/<project>/<environment>.env`; путь строится из
валидированного ID, а не из пользовательской строки. Файл обязан быть regular
file, принадлежать `root:<executor-group>` и иметь `0640`; он проверяется на
наличие всех объявленных имён. Резолвер возвращает значения только процессу
разрешённой адаптерной операции, а наружу — имена и наличие. Репозиторий,
SQLite и диагностика не получают значения или содержимое файла.

### Выпуск и UI

`POST /api/v1/projects/{project_id}/environments/{environment}/release` и
`.../rollback` принимают подтверждённый SHA/операционный запрос, а не command.
Выпуск разрешён только при полной readiness и разрешённой среде. Production
дополнительно требует одноразовое подтверждение владельца; этот факт записывается
в операцию, не заменяется флагом клиента. Сервер выполняет адаптер
транзакционно: начинает операцию, запускает выпуск, делает health-check и при
ошибке здоровья вызывает именованный rollback-адаптер; финальный статус отражает
выпуск, health и автоматический откат.

`web/src/Repositories.tsx` остаётся каталогом прежних репозиториев. Новый экран
`web/src/Projects.tsx` и API-клиент создают/показывают только шаблонные поля,
готовность ворот и состояния операций. Поля команды, значения секретов и любой
редактор allowlist адаптеров в UI не добавляются. Навигация в `web/src/App.tsx`,
типы в `web/src/types.ts`, запросы в `web/src/api.ts` получают новый проектный
раздел.

Затрагиваемые файлы реализации: `migrations/021_projects.sql`,
`migrations/embed.go`, `internal/protocol/types.go`,
`internal/controlplane/store.go`, `internal/controlplane/http.go`,
`internal/controlplane/projects.go`, `internal/controlplane/project_secrets.go`,
`internal/controlplane/project_adapters.go`, соответствующие Go-тесты,
`web/src/api.ts`, `web/src/types.ts`, `web/src/App.tsx`, `web/src/Projects.tsx`,
`web/src/Projects.test.tsx` и минимальные стили в `web/src/index.css`.

## План

1. Добавить миграцию и строгие protocol-типы проекта, сред, проверок, секретных
   имён, адаптерных операций и readiness; покрыть в Store транзакционное создание
   и инварианты v1.
2. Добавить HTTP endpoints проекта и тесты отрицательных контрактов: неполный
   шаблон, запрещённый хост, неименованный адаптер, production без блокировки и
   конфликт повторного подключения.
3. Реализовать secret resolver с проверкой пути/владельца/режима, отображающий
   только имена и наличие; подключить его к readiness и адаптерным операциям.
4. Реализовать registry именованных серверных адаптеров, запуск без shell,
   неизменяемый SHA-контекст, health-check и автоматический rollback.
5. Закрыть запуск задач проверкой сводной readiness и проверочных результатов на
   одном SHA; добавить запись статусов secret-scan, static/typecheck, tests и build.
6. Добавить экран Projects и тесты создания, отображения блокировок, ворот и
   безопасных состояний release/rollback; не менять поток старых repositories.

## Критерии приёмки

1. Новый проект создаётся только с именем, репозиторием, основной веткой, типом,
   staging URL/health-check, обязательными проверками, ID release/rollback,
   именами секретов и точным web-host allowlist; отсутствующее поле отклоняется.
2. Production при создании либо отсутствует, либо имеет URL/health-check и
   `blocked=true`; выпуск в production без отдельного подтверждения владельца
   невозможен.
3. До полного прохождения branch access, executor readiness, наличия секретов и
   всех четырёх проверок на одном SHA задача не маршрутизируется и выпуск не
   запускается; причина каждого отказа видна без секрета.
4. API/UI/логи никогда не содержат значения секретов; проверяется только наличие
   объявленных имён в root-owned `0640` env-файле нужной среды.
5. Неизвестный адаптер, тип или хост, а также любой command-подобный ввод,
   отклоняются сервером. Адаптер не вызывает shell и не может расширить allowlist.
6. Неудачный выпуск или health-check автоматически вызывает именованный rollback
   и сохраняет понятный статус операции; успешный выпуск подтверждён health-check.

## План проверки

- `internal/controlplane/store_test.go` и новые `projects_test.go`: миграция,
  полный шаблон, инварианты staging/production, конфликты и блокировка задач.
- `internal/controlplane/http_test.go`: JSON-контракт, скрытие значений секретов,
  отклонение команд/неизвестных ID/host allowlist и owner-confirmation production.
- `internal/controlplane/project_secrets_test.go` и `project_adapters_test.go`:
  права/владелец/имена env-файла, один SHA всех результатов, отсутствие shell,
  health и автоматический rollback.
- `web/src/Projects.test.tsx`: полный ввод шаблона, отображение readiness,
  production-lock и безопасные ошибки.
- Обязательная целевая команда: `go test ./internal/controlplane -run
  'Project|Secret|Adapter' -count=1 && npm --prefix web test -- --run
  src/Projects.test.tsx`.

## Риски и решения

- Нужна явная таблица v1 именованных адаптеров по типу проекта: владелец утвердил
  сам механизм allowlist, но не конкретные ID/реализации. Реализация не должна
  добавлять адаптер по свободному тексту. Это единственное содержательное
  согласование перед включением первого реального проекта.
- Проверка владельца группы executor зависит от OS-группы конкретного worker.
  В v1 проект должен хранить ожидаемое имя группы как серверную конфигурацию,
  а не принимать его в API; иначе клиент сможет ослабить доступ к секретам.
- Точная семантика "статической проверки/проверки типов" различается по типу
  проекта. Контракт хранит обязательный ID gate, а тип адаптера выбирает
  фиксированную реализацию; произвольные команды и CI-интеграция вне scope.
- История выпусков, редактирование секретных файлов, автоматическое создание
  DNS/стендов и произвольные провайдеры — scope creep, не входят в v1.
