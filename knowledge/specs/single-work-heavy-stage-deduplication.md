# Спецификация: одна работа не запускает одну тяжёлую стадию дважды

## Goal and user impact

Одна работа не должна одновременно занимать два воркера одинаковой следующей
стадией, если в одном цикле Пилот увидел несколько успешно завершённых попыток её
предыдущей стадии. Владелец получает один Review или Verify вместо двух, а Factory
не тратит вычислительное время и бюджет на параллельную повторную проверку одного
и того же результата.

Сейчас `pilot.cycle()` один раз загружает `tasks`, затем последовательно разбирает
терминальные задачи. Защита `live_or_done_at()` проверяет только этот исходный
снимок. После успешного `create_task()` созданная стадия в снимок не добавляется,
поэтому следующий завершённый дубль той же работы тоже проходит защиту и создаёт
ещё одну стадию в пределах того же цикла.

## Technical approach

Минимальное изменение ограничено оркестрацией Пилота:

- В `pilot/pilot.py` после успешного обычного перехода между стадиями извлечь
  созданную задачу из ответа `create_task()` и сразу добавить её в локальный
  список `tasks`, который использует `live_or_done_at()` в этом же цикле.
- Добавлять только реально возвращённую сервером задачу. При ошибке создания или
  некорректном ответе не придумывать локальное состояние: существующий механизм
  снимает predecessor с `processed` и повторяет переход в следующем цикле.
- Не вводить глобальную блокировку и не запрещать параллельность разных работ:
  уже существующий ключ дедупликации — базовый заголовок работы и номер стадии —
  должен увидеть свежее серверное состояние.
- В `pilot/test_pilot.py` добавить регрессию одного `cycle`: два успешных
  predecessor одной работы присутствуют в исходном снимке, следующая стадия
  тяжёлая (Verify), а `/tasks` получает ровно один запрос создания. Сохранить
  существующий сценарий четырёх разных работ, каждая из которых продвигается один
  раз в том же цикле.

Публичные API, схема БД, конфигурация, формат задач и правила межциклового
возобновления не меняются.

## Plan

1. Добавить в `AdaptivePollingTests` сценарий двух терминальных попыток одной
   работы, которые обе готовы перейти на Verify в одном вызове `cycle()`.
2. Зафиксировать в тесте единственный вызов создания Verify и отсутствие второго
   параллельного task при сохранении обработки обоих terminal task.
3. После успешного `create_task()` обычного handoff добавлять возвращённый task в
   локальный `tasks`, чтобы последующие итерации использовали обновлённый снимок.
4. Прогнать новую регрессию и соседний тест четырёх независимых handoff; полный
   набор `pilot.test_pilot` оставить единственному прогону стадии Verify.

## Acceptance criteria

1. Если один снимок содержит две успешные попытки одной работы на одной стадии,
   Пилот создаёт для неё ровно одну следующую Verify-задачу.
2. Вторая попытка в том же цикле видит уже созданную задачу через
   `live_or_done_at()` и не запускает параллельный дубль.
3. Четыре разные работы в одном цикле по-прежнему создают четыре независимые
   следующие стадии: защита не превращается в глобальный mutex.
4. Ошибка `create_task()` не оставляет вымышленную задачу в памяти и сохраняет
   существующий повтор перехода в следующем цикле.
5. Поведение API, хранилища, worker capacity и названия стадий не меняется.

## Risks and decisions

- Добавление серверного ответа в локальный снимок предпочтительнее отдельного
  множества `advanced_bases`: оно переиспользует существующие правила
  `live_or_done_at()` для номера стадии, времени и состояния без второго источника
  истины.
- Глобальная блокировка всех Verify отклонена: разные работы должны продолжать
  проверяться параллельно на свободных воркерах.
- Идемпотентный `request_key` не решает гонку: текущий код создаёт новый UUID для
  каждого predecessor. Менять контракт control plane ради локальной гонки — лишний
  scope.
- Спецификация не расширяет задачу на историческую очистку уже созданных дублей;
  это отдельная восстановительная политика. Согласование человека перед
  реализацией не требуется.
