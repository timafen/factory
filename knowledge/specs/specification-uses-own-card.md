# Спецификация публикует карточку своей работы

## Цель и влияние на владельца

Каждая параллельная работа получит собственную карточку знаний уже на этапе
`Specification`. Владелец больше не увидит, как две несвязанные поставки
пытаются изменить одну и ту же карточку `CARD-0074`: история, доказательства и
следующий этап будут привязаны к своей работе и своей опубликованной ветке.

Если карточка уже была назначена в контексте, она останется назначенной. Если
её не было, Pilot до запуска Specification безопасно выделит новый свободный
номер; агенту не придётся угадывать номер и создавать конфликтующую карточку.

## Технический подход и реальные файлы

В `migrations/024_specification_uses_own_card.sql` добавить следующую
неизменяемую revision только для включённых workflow с title `Specification`.
Она заменит текст revision 023, но не изменит её историю и не затронет
отключённые workflow. Новый prompt не содержит фиксированной строки
`CARD-0074`: он требует использовать точный путь из строки контекста
`Card: knowledge/cards/CARD-NNNN-<slug>.md`, создать только эту карточку и
собственную спецификацию, не менять карточки других работ, в том числе
`CARD-0074` и `CARD-0075`.

В `pilot/pilot.py` добавить разрешение карточки до вызова API из `create_task`
для каждой автоматической задачи стадии `Specification`.

- Сначала извлечь из исходного context явную строку `Card:`; для совместимости
  принять также единственный путь `knowledge/cards/CARD-*.md`. Валидный
  назначенный путь сохранить дословно и передать дальше, не создавая новый
  номер.
- При отсутствии пути под межпроцессной блокировкой Pilot обновляет durable
  registry резервов в `/opt/factory-data/pilot/`, повторно использует резерв
  той же работы при retry и выделяет минимальный свободный номер. Имя имеет
  вид `knowledge/cards/CARD-NNNN-<slug-текущей-работы>.md`, где slug
  детерминированно получен из `base_title` и безопасен для пути.
- Пока удерживается блокировка, получить свежий список карточек из
  `origin/main` и всех опубликованных веток данного repository через GitHub
  API; заняты также номера и полные пути из registry. Номер можно записать в
  registry только после этой проверки. Так два одновременных вызова не могут
  получить одинаковую карточку даже до первого push.
- Дописать в context одну каноническую строку `Card: <путь>` до блока правил
  агента. Повторные возвраты Specification, handoff и выбор опубликованной
  ветки сохраняют эту строку без переназначения.
- Дополнить specification branch gate: после `branch_report` принять ровно
  одну спецификацию в `knowledge/specs/` и ровно назначенную карточку; любые
  другие файлы, другая карточка или изменение `CARD-0074`/`CARD-0075` вернуть
  на Specification. Сообщение возврата должно называть допустимые пути, а не
  предлагать фиксированный номер.

В `internal/controlplane/store_test.go` расширить upgrade-тест legacy базы:
после применения всех миграций проверить новую revision 024, её номер,
`request_key`, exact instructions, сохранённую revision 023 и неизменность
disabled workflow. Проверка отдельно запрещает строку `CARD-0074` в новой
инструкции.

В `pilot/test_pilot.py` добавить тесты resolver и handoff. Они подменяют
GitHub-список веток/деревьев и registry во временный каталог, поэтому не
зависят от реальной сети или карточек рабочей машины.

## Последовательный план

1. Добавить migration 024 с детерминированными id/request key, следующей
   revision для включённой Specification и prompt, использующим только
   назначенную в context карточку.
2. Реализовать в Pilot разбор `Card:`, нормализацию slug, durable registry и
   критическую секцию резервирования; ошибку чтения origin/GitHub не заменять
   догадкой и не запускать задачу до следующего цикла.
3. Встроить resolved `Card:` в context перед созданием новой и возвращаемой
   Specification, сохранив уже указанную карточку и ветку.
4. Ужесточить branch gate для Specification до её собственной спецификации и
   назначенной карточки; сохранить существующие проверки push, непустого diff
   и повторной попытки при временной ошибке GitHub.
5. Добавить Go upgrade-regression и Python тесты явной карточки, уникального
   конкурентного резерва, разных опубликованных веток и состава поставки.

## Критерии приёмки

1. Установленная revision Specification больше не содержит фиксированный
   путь или номер `CARD-0074`; revision 023 остаётся исторической записью.
2. Context с `Card:` передаёт в Specification именно этот путь при первой
   попытке, retry и handoff, без запроса нового номера.
3. Две одновременные Specification без Card получают разные `CARD-NNNN` и
   разные paths, а их опубликованные ветки не смешивают назначение.
4. Перед резервом номер и полный path отсутствуют в свежем `origin/main`,
   всех опубликованных ветках и durable registry; недоступный источник
   останавливает создание задачи, а не выдаёт потенциально занятый номер.
5. Ветка Specification содержит только её один файл `knowledge/specs/` и
   назначенную карточку. Изменения `CARD-0074`, `CARD-0075`, чужой карточки
   либо любого исходника не передаются в Implement.
6. Существующие правила commit/push, `BRANCH`/полного `HEAD`/`PUSHED: yes`,
   непустого diff и безопасного возврата при отсутствии ветки не регрессируют.

## Тест-план

- Выполнить `go test ./internal/controlplane -run
  TestSpecificationPublishesDocumentsMigrationInstallsExactRevision -count=1`:
  legacy upgrade устанавливает revision 024 с точной новой инструкцией и не
  меняет disabled workflow.
- Добавить и выполнить
  `python3 -m unittest -v pilot.test_pilot.SpecificationCardReservationTests`:
  два параллельных вызова получают разные card paths и branches; занятые
  `CARD-0074`/`CARD-0075` не меняются, а исходная `Card:` сохраняется.
- В том же классе проверить, что branch gate принимает только назначенную
  карточку и собственную спецификацию, а чужой файл/карточку возвращает на
  Specification.
- Сохранить регрессии `SpecificationBranchHandoffTests` и выполнить
  `git diff --check` перед передачей в Verify.

## Риски и решения

- Сканирование всех опубликованных веток может быть медленнее обычного
  создания задачи. Оно выполняется лишь при первом отсутствии Card под
  короткой блокировкой; готовый резерв переиспользуется на retry.
- Локальная atomic-запись без блокировки дала бы двум потокам один номер.
  Durable registry обновляется только внутри критической секции; ошибка
  блокировки, записи или GitHub — безопасная пауза, а не fallback к 0074.
- Старый context может содержать путь без строки `Card:`. Совместимый разбор
  принимает ровно один валидный card path; несколько разных значений —
  диагностическая ошибка, чтобы не выбрать карточку произвольно.
- Не расширять задачу до UI, общего журнала карточек, схемы API handoff либо
  изменения существующих `CARD-0074`/`CARD-0075`: это отдельные работы.
