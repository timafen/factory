# Санитар снимает уже отсутствующий retained worktree

## Цель и влияние на пользователя

После завершения работы `claude-haiku` control plane может продолжать показывать
`retained_worktree`, хотя каталога результата уже нет. Встроенный санитар сейчас
подтверждает только каталоги, которые сам перенёс в карантин, поэтому такой фантом
переживает повторные обходы, продолжает занимать retained-capacity и блокирует
удаление terminal-истории ошибкой `retained_worktree`.

После изменения санитар будет снимать и точный снимок уже отсутствующего результата,
когда отсутствие проверено при остановленной службе после очистки Git-регистрации.
Реальные сохранённые результаты по-прежнему сначала попадут в карантин.

## Технический подход

Изменить только локальное согласование в `ops/factory-janitor.sh`. Санитар уже
останавливает worker-службу, переносит существующие каталоги и manifests, затем
выполняет `git worktree prune` во всех локальных репозиториях. После этих шагов он
должен построить подтверждение из исходного снимка `retained_worktrees`:

- включить запись, если её точный `path` успешно перемещён в карантин;
- также включить запись, если после остановки службы и prune её `path` отсутствует;
- не включать существующий путь, который не удалось переместить;
- отправить неизменённый полный снимок записи, чтобы существующий
  `Store.ClearRetainedWorktrees` сохранил защиту от новой или изменённой регистрации.

Новый маршрут, схема БД и формат API не нужны: `POST
/api/v1/workers/{worker_id}/retained-worktrees/clear` уже удаляет только точные
совпадения и идемпотентен. `ops/test-factory-janitor.sh` следует расширить
регрессией для отсутствующего до запуска пути и сохранить сценарии успешного
карантина и ошибки подтверждения.

## План реализации

1. При формировании `confirmed` различать перемещённый, уже отсутствующий и
   существующий неперемещённый путь из исходного снимка воркера.
2. Подтверждать перемещённые и уже отсутствующие точные снимки одним существующим
   запросом после `git worktree prune`.
3. Обновить shell-фикстуру: отсутствующий `attempt-missing` должен войти в payload,
   а отдельный неперемещённый существующий путь должен остаться неподтверждённым.
4. Сохранить проверку журналирования HTTP-сбоя и сохранности карантина.

## Критерии приёмки

1. Уже отсутствующий путь из `retained_worktrees` снимается при очередном обходе
   остановленного санитаром `claude-haiku`.
2. Успешно перемещённый результат снимается только после появления в карантине.
3. Существующий путь, который не удалось переместить, остаётся в control plane.
4. Новая или изменённая запись, не совпадающая с исходным снимком, не удаляется;
   повторное подтверждение безопасно.
5. При недоступности API санитар пишет ошибку, не теряет карантин и завершает
   локальный цикл без ложного сообщения об успешном подтверждении.

## План тестирования

В `ops/test-factory-janitor.sh` изменить целевой сценарий так, чтобы мок API
возвращал три записи: успешно перемещаемую, уже отсутствующую и существующую,
для которой `mv` завершается ошибкой. Payload обязан содержать первые две точные
записи и не содержать третью. Отдельно сохранить второй запуск с ошибкой `curl`
и проверки журнала/карантина.

Обязательная целевая команда: `bash ops/test-factory-janitor.sh`. Обновлённая
проверка отсутствующего пути должна падать до реализации и завершаться с кодом 0
после неё. Go-тесты не требуются, поскольку контракт существующего точечного
маршрута и `Store.ClearRetainedWorktrees` не меняется.

## Риски и решения

- Решение: отсутствие считается доказанным только после остановки службы и
  `git worktree prune`; проверка до остановки могла бы состязаться с воркером.
- Решение: существующий неперемещённый путь не подтверждается, чтобы не потерять
  ссылку на результат, который не попал в карантин.
- Риск: путь может исчезнуть из-за внешнего вмешательства. В этом случае запись
  уже не ведёт к восстанавливаемому результату, поэтому удаление фантома отражает
  фактическое состояние и является предпочтительным поведением.
- Отклонено: tombstone/версия регистрации в БД. Это потребовало бы нового
  состояния и протокола ради случая, который санитар может доказать локально.
- Вне области: срок хранения карантина, лимит трёх запусков в час, ручная команда
  cleanup и изменение семантики `retained_count`.
