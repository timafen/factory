# Спецификация: расходовать возврат этапа только после запуска повторной задачи

## Goal and user impact

Лимит автоматического возврата этапа должен означать фактически запущенную
повторную задачу, а не попытку её создать. Если `create_task` временно не может
создать задачу (например, нет подходящего исполнителя или недоступен control
plane), следующий цикл должен повторить возврат. После успешного запуска лимит
расходуется ровно один раз, уведомление и запись в историю описывают только
реально созданную задачу.

Это сохраняет защиту от бесконечных возвратов и общие лимиты, но устраняет окно,
в котором единичный сбой инфраструктуры навсегда блокирует полезное продолжение
конвейера.

## Technical approach

Изменение ограничить `pilot/pilot.py` и `pilot/test_pilot.py`; публичные API,
схемы данных, выбор исполнителя, общие лимиты и circuit breaker не менять.

- Ввести единый узкий способ завершать возврат: сначала выполнить
  `create_task`, затем зафиксировать `note_cap_rescue(base, stage)`. При
  исключении создание считается неуспешным, исходная задача удаляется из
  `state["processed"]`, а счётчик не меняется; следующий цикл получает тот же
  шанс. Если реализация сохранит предварительную запись для совместимости,
  она обязана атомарно восстановить прежнее значение при любом исключении.
- Для прямых возвратов в `cycle` применить порядок к `INFRA`, `MERGE`,
  `SPEC_BRANCH` и `SPEC`: сохранить проверку лимита до запуска, но перенести
  фиксацию счётчика и `notify` после успешного `create_task`.
- Для `review_gate` изменить результат `GATE`/`DIRT` так, чтобы проверка
  возвращала отложенный маркер возврата, а `cycle` фиксировал его только после
  успешного создания задачи. Сетевые ошибки и успешная автоматическая
  пересборка ветки не должны сами по себе расходовать return-cap.
- Провести аудит `LOOP`, `DIAG` и `ESCNOTE`. Они не являются отложенным
  созданием повторной задачи: `LOOP` записывается после принятого ответа,
  `DIAG` — при начале разрешённого одноразового разбора, `ESCNOTE` — при
  фактическом повышении исполнителя. Оставить их текущую семантику и явно не
  привязывать к транзакции `create_task`.
- Сохранить существующее удаление `processed` при ошибке создания и сделать
  его частью проверяемого контракта для каждого возврата, чтобы повторный цикл
  действительно увидел исходную завершённую задачу.

История и уведомление для возврата должны выполняться в том же успешном пути,
что и фиксация счётчика. Идентификатор созданной задачи следует использовать в
ссылке уведомления, где он уже доступен; при ошибке не писать сообщение о
возврате и не оставлять ложный cap marker.

## Plan

1. Добавить в `pilot.py` маленький внутренний примитив/паттерн фиксации
   return-cap после успешного `create_task` и определить его контракт для
   исключения и отсутствующего результата.
2. Перестроить прямые ветки `INFRA`, `MERGE`, `SPEC_BRANCH` и `SPEC`, не меняя
   тексты контекста, критерии лимитов и выбор worker/workflow.
3. Передать отложенный marker из `review_gate` для `GATE` и `DIRT`; зафиксировать
   его в `cycle` только после создания возвратной задачи. Убедиться, что
   `LOOP`, `DIAG`, `ESCNOTE` не затронуты.
4. Добавить регрессионные тесты на отказ `create_task`, повторный цикл,
   успешный запуск после рестарта и отсутствие уведомления/истории при отказе.
5. Запустить целевые тесты, компиляцию и проверку diff; затем полный
   `pilot.test_pilot` как регрессию поведения остальных переходов.

## Acceptance criteria

1. При ошибке `create_task` для возврата `SPEC_BRANCH` или `SPEC` значение
   `cap_rescues(base, stage)` не увеличивается, возвратное уведомление и запись
   истории не появляются, а `state["processed"]` освобождает исходную задачу.
2. Следующий цикл с тем же завершённым этапом снова пытается создать возвратную
   задачу; после успеха счётчик увеличивается ровно на один, создаётся ровно
   одна повторная задача и публикуется одно уведомление.
3. После перезапуска процесса/сброса in-memory state неудачный `create_task` не
   превращается в использованный rescue: следующий запуск повторяет возврат.
4. Успешный `create_task` для всех возвратов `SPEC_BRANCH`, `SPEC`, `GATE`,
   `DIRT`, `INFRA` и `MERGE` расходует соответствующий cap ровно один раз; при
   повторной обработке лимит блокирует второй возврат согласно прежним порогам.
5. Регрессия `no_eligible_worker` → следующий цикл → опубликованная ветка
   Specification создаёт `Implement + Test` с опубликованной веткой и не
   расходует return-cap из-за одной неудачной попытки запуска.
6. `LOOP`, `DIAG` и `ESCNOTE` сохраняют прежнюю семантику и не получают
   искусственной зависимости от создания задачи; общие лимиты, circuit breaker,
   API-контракты и логика выбора исполнителя не изменяются.

## Test plan

- Расширить `SpecificationBranchHandoffTests` проверками отказа `create_task`
  для возврата и последующего успешного цикла; проверять cap storage,
  `processed`, количество задач, уведомлений и записей истории.
- Добавить отдельный сценарий с тем же durable cap-файлом и новым `state`,
  моделирующий рестарт между неудачным и успешным циклом.
- Добавить параметризованный/табличный тест для прямых веток `INFRA`, `MERGE`,
  `SPEC_BRANCH`, `SPEC` и для отложенных `GATE`/`DIRT`: ошибка создания не
  меняет счётчик, успех меняет его один раз.
- Сохранить существующие 8 тестов `SpecificationBranchHandoffTests` и добавить
  сценарий `no_eligible_worker` с последующим опубликованным branch handoff.
- Обязательные команды:
  `python3 -m unittest -v pilot.test_pilot.SpecificationBranchHandoffTests`
  `python3 -m py_compile pilot/pilot.py pilot/test_pilot.py`
  `git diff --check`
- Для регрессии остальных переходов выполнить:
  `python3 -m unittest -v pilot.test_pilot`

## Risks and decisions

- Между внешним `create_task` и локальным JSON-счётчиком нет общей транзакции.
  Предпочтён порядок «создать, затем отметить»; fallback с откатом допустим
  только если он восстанавливает точное прежнее значение при исключении.
- Перенос `note_cap_rescue` из `review_gate` в вызывающий `cycle` необходим,
  иначе `GATE`/`DIRT` продолжают расходовать лимит до запуска. Изменение
  структуры внутреннего результата gate допустимо, публичного API нет.
- Не следует менять общий `max_cap_rescues`, `max_work_rounds` или критерии
  `no_eligible_worker`: задача исправляет момент учёта, а не ослабляет защиту.
- Не следует делать повторную задачу идемпотентной через новый API или схему:
  существующий `request_key`, `processed` и текущая проверка дублей остаются
  источниками поведения.
