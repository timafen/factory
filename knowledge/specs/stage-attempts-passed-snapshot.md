# Спецификация: `stage_attempts()` считает только переданный снимок задач

## Цель и влияние на владельца

Лимит повторов этапа должен рассчитываться по тому набору задач, который Pilot
уже получил в начале прохода. Новая задача, появившаяся после получения этого
снимка, не должна изменить решение текущего прохода: не вызвать преждевременную
эскалацию, не заблокировать повтор и не повлиять на выбор исполнителя. Для
владельца это означает предсказуемое число попыток: изменения очереди будут
учтены следующим проходом, а не задним числом в уже начатом.

## Технический подход и реальные файлы

1. В `pilot/pilot.py` закрепить контракт `stage_attempts(tasks, stage, base)`:
   функция читает только аргумент `tasks` и не получает задачи из API, файлов,
   глобального состояния или нового обхода очереди.
2. Передавать в неё неизменяемый снимок, сформированный в `cycle()` из ответа
   `/tasks`; все существующие вызовы при диагностике, обработке ошибки и
   возврате из Review/Verify используют именно этот снимок текущего цикла.
3. В `pilot/test_pilot.py` добавить регрессионный сценарий: после создания
   снимка в изменяемую исходную коллекцию добавляется ещё одна задача той же
   работы и стадии; подсчёт для уже переданного снимка остаётся прежним, а для
   следующего снимка увеличивается. Сценарий также сохраняет различение работ
   через `same_task_work` и `work_id`.
4. Не менять UI, API-контракт, настройку `max_stage_attempts` и правила
   `same_task_work`: задача ограничена границей времени, в которой читаются
   попытки, а не определением самой работы.

## Последовательный план

1. Найти место получения списка `tasks` в `cycle()` и сделать его явным
   снимком на один проход.
2. Убедиться, что `stage_attempts()` и её вызывающие ветви используют только
   этот объект, без повторного чтения очереди.
3. Добавить регрессионный тест со старым и следующим снимком.
4. Запустить новый целевой тест и соседние тесты подсчёта попыток.

## Критерии приёмки

- При неизменном переданном снимке `stage_attempts()` выдаёт одно и то же число
  попыток, даже если после его формирования в очереди появилась подходящая
  задача.
- Следующий снимок, содержащий новую задачу, учитывает её ровно один раз.
- Учитываются только задачи нужных стадии и работы; одноимённая работа с другим
  `work_id` в подсчёт не попадает.
- Вызовы из одного `cycle()` не смешивают его решение с более свежим состоянием
  очереди.
- Изменения ограничены `pilot/pilot.py` и `pilot/test_pilot.py`.

## Тест-план

- Новый целевой тест снимка: `python3 -m unittest pilot.test_pilot.SameTitlePlanEpicBudgetIsolationTests.test_stage_attempts_uses_passed_task_snapshot`.
- Смежный тест идентичностей: `python3 -m unittest pilot.test_pilot.SameTitlePlanEpicBudgetIsolationTests.test_identical_titles_with_distinct_work_ids_remain_distinct`.
- После реализации допускается объединить оба сценария в один целевой запуск
  класса, но полный набор на этом этапе не запускается.

## Риски и решения

- Риск пропустить задачу, созданную параллельно: принять это как осознанную
  границу консистентности; следующий polling-цикл получит новый снимок.
- Риск случайно разделить задачи одной работы: сохранить `same_task_work` как
  единственный предикат принадлежности работе.
- Риск изменения поведения старых записей без `work_id`: покрыть сценарий
  существующим fallback по заголовку и не менять его в этой работе.
- Риск скрытого повторного чтения: тестировать разницу между уже переданным и
  заново сформированным снимками, а не только конечное число.
