# Спецификация: полный визуальный аудит Factory на компьютере и телефоне

## Goal and user impact

Владелец получает проверенный целиком интерфейс Factory: каждый рабочий экран
можно открыть на компьютере и телефоне без горизонтального переполнения,
обрезанных действий, перекрытий и ошибок браузера. Скриншоты всех состояний
останутся артефактами целевого browser-теста, поэтому последующие изменения UI
можно сверять не по памяти, а с воспроизводимым эталоном аудита.

## Текущее поведение и граница задачи

- `web/src/App.tsx` объявляет 16 основных маршрутов, detail-экраны task, worker,
  repository, workflow и automation, общую модаль `Delegate task`, боковую
  навигацию и её мобильное состояние.
- `web/src/styles.css` содержит общий responsive breakpoint 760 px и локальные
  breakpoints компонентов. Это подходящее место для найденных исправлений
  компоновки без изменения продуктовой логики.
- `web/playwright.config.ts` запускает только Desktop Chrome 1440×1000.
  Существующий тест `supports narrow grouped layouts...` вручную переходит на
  390×844, но проверяет лишь overview, work, workers, task detail и модаль.
- `web/e2e/control-plane.spec.ts` уже создаёт детерминированные данные, умеет
  фиксировать console/network failures и сохранять screenshots. Аудит следует
  расширить здесь, не вводя второй fixture-server и параллельный набор данных.
- Серверные страницы `/intake/plan` и `/intake/alerts`, API, тексты, редизайн и
  новые функции не входят в задачу. Найденные там либо требующие React-разметки
  продуктовые проблемы оформляются отдельными находками, а не расширяют diff.

## Technical approach

Добавить в `web/e2e/control-plane.spec.ts` один именованный, воспроизводимый
визуальный аудит с таблицей экранов и двумя viewport: desktop 1440×1000 и phone
390×844. В таблицу входят все маршруты `App`, пять detail-состояний и открытая
модаль постановки задачи. Тест сам подготавливает необходимые workflow и
automation через существующий HTTP/UI-контракт, чтобы отдельный запуск через
`--grep` не зависел от порядка других тестов.

Для каждого состояния тест:

1. открывает маршрут и ждёт его смысловой heading/region/dialog;
2. проверяет отсутствие горизонтального overflow у документа и `main`, а также
   нахождение topbar и основных действий в пределах viewport;
3. на телефоне открывает и закрывает меню, проверяя sidebar, scrim и возврат
   фокуса/доступность основной страницы;
4. сохраняет полноэкранный screenshot с устойчивым именем
   `<screen>-desktop.png` или `<screen>-phone.png`;
5. в конце требует отсутствие console errors, failed requests и неожиданного
   realtime transport через существующий `observeBrowser`.

Обнаруженные воспроизводимым тестом дефекты исправить минимальными responsive
правилами в `web/src/styles.css`, сохраняя desktop-компоновку выше breakpoint.
Pixel-perfect snapshot comparison не вводится: динамические task-данные делают
его хрупким; артефакты предназначены для человеческого просмотра, а машинные
ворота проверяют геометрию, доступность состояния и ошибки браузера.

### Affected modules/files

- `web/e2e/control-plane.spec.ts` — полный маршрутный аудит, подготовка fixture
  состояний, геометрические assertions и screenshots.
- `web/src/styles.css` — только подтверждённые аудитом desktop/mobile layout fixes.

Изменений данных, backend API и TypeScript-моделей нет.

## Plan

1. Зафиксировать таблицу всех маршрутов из `App.tsx`, detail-состояний и модали,
   а также ожидаемый смысловой элемент каждого экрана.
2. Добавить самодостаточную подготовку данных и helper проверки viewport,
   overflow, browser errors и сохранения screenshots.
3. Прогнать аудит сначала на desktop, затем на phone; для мобильного shell
   отдельно проверить открытие/закрытие навигации и доступность действий.
4. Исправить только подтверждённые проблемы компоновки в `styles.css`, повторяя
   целевой тест после каждого связанного набора исправлений.
5. Просмотреть полученные screenshots попарно и выполнить финальный целевой
   browser-тест вместе с `git diff --check`.

## Acceptance criteria

### Полнота аудита

- Автоматизированный список содержит каждый route из `readRoute`/`routePath`,
  существующие detail-экраны и `Delegate task`; пропуск маршрута требует явного
  комментария с причиной.
- Каждый экран сохранён в desktop- и phone-варианте с однозначным именем;
  тест можно запустить отдельно, без предварительного исполнения иных e2e tests.
- На каждом screenshot виден смысловой контент, а не loading, login, health или
  пустая служебная заглушка.

### Компьютер

- При 1440×1000 sidebar, topbar, основной контент и доступные основные действия
  не перекрываются, не обрезаются и не создают горизонтальную прокрутку страницы.
- Списки, карточки, detail-экраны и модаль сохраняют текущую desktop-иерархию.

### Телефон

- При 390×844 основной контент не шире viewport; длинные названия и технические
  значения переносятся либо прокручиваются только внутри предназначенного блока.
- Навигация открывается поверх страницы, закрывается кнопкой и scrim, а основные
  кнопки и поля формы остаются видимыми и достижимыми.
- Ни один проверяемый экран не вызывает console error или failed request.

## Test plan

- Новый Playwright-сценарий в `web/e2e/control-plane.spec.ts` с точным названием
  `audits every Factory screen on desktop and phone` должен падать до реализации
  как отсутствующий при запуске через `--grep` и после реализации выдавать все
  screenshots и exit code 0.
- Обязательная целевая команда:
  `npm --prefix web run test:browser -- --grep "audits every Factory screen on desktop and phone" && git diff --check`.
- На Implement-стейдже запускать только эту команду; полный suite остаётся для
  Verify согласно правилам конвейера.

## Risks and decisions

- Полный аудит длиннее нынешнего narrow smoke. Один последовательный сценарий и
  два viewport дают полноту без удвоения всего Playwright project matrix.
- Геометрическая проверка не оценивает вкус и визуальную иерархию; поэтому ручной
  просмотр пар screenshots остаётся обязательной частью приёмки.
- Динамические анимации и polling могут менять снимок. Тест ждёт смысловой элемент
  и делает screenshots после стабилизации, но не сравнивает пиксели.
- Исправление текстов, бизнес-состояний, intake-страниц либо backend-контрактов —
  scope creep и требует отдельной задачи. Перед реализацией дополнительного
  файла, кроме двух заявленных, нужно согласование владельца.
