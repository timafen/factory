# Спецификация: честная цена дублей, отмен и незавершённых конвейеров

## Цель и влияние на владельца

Владелец видит не абстрактный «потраченный бюджет», а сколько долларов за
последние 24 часа ушло на три вида работы без результата: повторные стадии,
отменённые задачи и конвейеры, которые остановились до слияния. Разбивка
позволяет отличить дорогую полезную работу от потерь и выбрать, что исправлять
сначала. Сумма категорий совпадает с показанным итогом; неизвестная стоимость
не превращается в ноль и явно снижает покрытие метрики.

## Технический подход и реальные файлы

Сейчас `pilot/pilot.py::write_dashboard` перебирает только первые 60 задач,
относит весь `task_cost_usd` к окну по `created_at` задачи и записывает в
`spend.wasted_usd` лишь `failed`/`cancelled`. Поэтому повторная успешная стадия
не считается потерей, незавершённый хвост без merge не считается вовсе, а
расход попытки за границей окна может попасть внутрь. `web/src/Overview.tsx`
показывает только общий `wasted_usd` без определения и покрытия.

Реализация сохраняет `spend.wasted_usd` для обратной совместимости и добавляет
`spend.waste` со значениями `duplicate_usd`, `cancelled_usd`,
`unfinished_usd`, `total_usd`, `priced_attempts`, `unpriced_attempts`,
`window_started_at` и `generated_at`. Стоимость считается из usage-событий
Claude/Codex, timestamp которых попал в полуоткрытое окно
`[window_started_at, generated_at)`; лимит `tasks[:60]` для этой метрики
убирается. Повреждённый журнал или неизвестная модель увеличивают
`unpriced_attempts`, а соответствующая категория отображается как минимум
известной стоимости, не как полная цена.

Классификация работает только для product-задач с каноническим заголовком
`[auto] [N/M Stage] <base>` и merge receipts из `pilot/merges.jsonl`:

1. Попытка отменённой задачи относится в `cancelled_usd`.
2. Из остальных задач более ранняя задача той же пары `(repository, base,
   stage)`, после которой создана ещё одна задача этой стадии, относится в
   `duplicate_usd`; последняя задача стадии дублем не считается.
3. Остальные попытки относятся в `unfinished_usd`, если для `(repository,
   base)` нет merge receipt, нет живой задачи и последняя задача terminal не
   менялась 10 минут. Пока продолжение живо или действует grace, цена не
   объявляется потерей.
4. Приоритет правил делает категории непересекающимися; одна попытка входит
   максимум в одну категорию, `total_usd` равен их сумме. Служебные patrol,
   scheduled, helper и неклассифицируемые задачи не попадают в разбивку.

В `web/src/Overview.tsx` карточка расходов показывает итог и три русские строки
с суммой, определением, окном и покрытием `priced / (priced + unpriced)`.
При неполном покрытии текст прямо говорит «известно не меньше», а при отсутствии
нового объекта используется прежний `wasted_usd` с подписью «без разбивки».
`web/src/Overview.test.ts` фиксирует владелецкий текст и обратную совместимость;
стили остаются локальными inline, поэтому `styles.css` менять не требуется.

## Последовательный план

1. В `pilot/pilot.py` вынести чтение usage с event timestamp и ценой модели;
   вернуть стоимость окна и признак неизвестной/повреждённой цены без изменения
   существующих budget helpers.
2. Построить индекс product-задач по repository/base/stage, прочитать merge
   receipts с дедупликацией и классифицировать попытки по приоритетным правилам.
3. Сформировать `spend.waste`, вычислить совместимый `wasted_usd = total_usd` и
   удалить искусственный предел 60 задач только из расчёта waste.
4. Обновить типы и карточку расходов в `web/src/Overview.tsx`: разбивка,
   честная подпись покрытия, окно и legacy fallback.
5. Добавить целевые Python и React regression-тесты и выполнить обязательную
   команду, затем `git diff --check`.

## Критерии приёмки

1. Usage до начала окна не входит, usage на начале входит, usage на правой
   границе не входит; возраст задачи не меняет результат.
2. Отменённая задача, после которой повторили ту же стадию, целиком учитывается
   только в `cancelled_usd`, а не одновременно в дублях.
3. Ранняя succeeded/failed задача повторённой стадии учитывается в
   `duplicate_usd`; последняя задача стадии и единственная стадия — нет.
4. Terminal-хвост без merge и живого продолжения после 10 минут учитывается в
   `unfinished_usd`; merge receipt, queued/preparing/running продолжение или
   grace исключают его из потерь.
5. `total_usd` с точностью округления равен сумме трёх непересекающихся
   категорий, одна attempt ID не считается дважды, повторный merge receipt не
   меняет результат.
6. Все product-задачи окна рассматриваются независимо от позиции в списке;
   patrol, scheduled, helper и неканонические задачи исключены.
7. Неизвестная модель/битая usage-строка отражается в `unpriced_attempts`; UI
   говорит «известно не меньше» и не выдаёт неполную сумму за точную.
8. Overview показывает итог, три понятные владельцу причины, границы 24-часового
   окна и покрытие; старый dashboard JSON продолжает отображаться без ошибки.

## Риски и решения

- Категории могут пересекаться. Фиксированный приоритет cancellation → duplicate
  → unfinished и set учтённых attempt ID обеспечивают одно зачисление.
- Исторические usage-строки могут не иметь timestamp/model. Они не оцениваются
  догадкой: увеличивают uncovered count, UI маркирует сумму как нижнюю границу.
- Незавершённая, но ещё живая работа может выглядеть потерей. Live-state и
  10-минутный grace совпадают с существующим правилом `FinalDeadEnds`.
- Одинаковые заголовки в разных репозиториях могут склеиться. Ключ обязательно
  включает repository identity; receipts связываются по task ID, а не по title.
- Полный обход задач и журналов дороже текущих 60. За один snapshot кэшировать
  detail/attempt и один раз сканировать каждый session JSONL; не менять частоту
  dashboard refresh в рамках этой работы.
