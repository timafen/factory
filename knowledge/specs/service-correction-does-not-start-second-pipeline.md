# Спецификация: служебная коррекция ветки не запускает второй конвейер

## Цель и влияние на владельца

Когда Пилот возвращает задачу на исправление из-за ветки, инфраструктуры или
проверки, такая задача сейчас получает обычный `[auto]`-заголовок и при
следующем опросе может быть принята за новую самостоятельную работу. Владелец
видит лишний второй конвейер, дублирующие этапы и расходование исполнителей.

После изменения служебная коррекция будет явно связана с исходной задачей:
`parent_task_id` хранит её родителя, а `correction_kind` — причину/вид
коррекции. Пилот не начнёт по такой записи отдельный Pipeline. Старые задачи с
двумя пустыми полями остаются обычными и проходят без изменения поведения.

## Технический подход и реальные файлы

- Добавить миграцию `migrations/024_task_corrections.sql`: nullable
  `tasks.parent_task_id` с внешней ссылкой на `tasks(id)`, nullable
  `tasks.correction_kind`, индекс по непустому виду коррекции для выборки
  метрики. Поля не имеют значений по умолчанию, поэтому исторические строки
  совместимы как обычные задачи.
- В `internal/protocol/types.go` добавить оба поля в `CreateTaskRequest` и
  `Task` с JSON-именами `parent_task_id` и `correction_kind`. Перед вставкой
  нормализовать оба значения; разрешать их только парой: родитель должен
  существовать, не совпадать с создаваемой задачей, а вид — быть короткой
  машинной строкой `cap_rescue:<stage>` из разрешённого набора возвратов.
  `request_key` сохранить для идемпотентности HTTP-повтора, но не использовать
  как признак служебности.
- В `internal/controlplane/store.go` передать значения в INSERT, список задач,
  `Task` и `TaskDetail`; replay по прежнему `request_key` возвращает уже
  сохранённую связь. Добавить в `internal/controlplane/metrics.go` и
  `MetricsSummary` число `correction_kind IS NOT NULL` за выбранное окно как
  `duplicate_pipeline_starts_prevented`: каждая созданная служебная коррекция
  означает один запуск самостоятельного конвейера, который Пилот пропустил.
  HTTP `/api/v1/metrics/summary` публикует это поле вместе с остальными
  метриками.
- В `pilot/pilot.py` расширить `create_cap_rescue` и все его вызовы из
  `cycle`: передавать ID завершаемой исходной задачи как `parent_task_id` и
  стабильный `correction_kind` для `INFRA`, `MERGE`, `SPEC_BRANCH`, `SPEC`,
  `GATE` и `DIRT`. Сохраняется существующий порядок: задача создана, затем
  расходуется cap. При разборе `/tasks` до определения базовой работы рано
  пропускать запись с непустым `correction_kind`, записывая диагностический
  счётчик/лог «предотвращён второй конвейер»; не добавлять её в новую работу,
  не строить stages и не создавать новую задачу.
- Добавить регрессии в `internal/controlplane/store_test.go`,
  `internal/controlplane/metrics_test.go`, `internal/controlplane/http_test.go`
  и `pilot/test_pilot.py`: миграция и API, прежние пустые поля, replay,
  метрика, payload коррекции и пропуск Пилотом дочерней задачи.

Не менять заголовки работ, правила выбора worker, лимиты rescue, существующую
семантику `LOOP`/`DIAG`/`ESCNOTE`, UI и контракты обычных задач.

2. Валидировать пару полей и существование родителя при создании; покрыть
   создание, HTTP, повтор `request_key` и обратную совместимость.
3. Прокинуть parent/kind только из возвратных ветвей `create_cap_rescue` и
   научить основной опрос Пилота пропускать уже маркированные коррекции.
4. Добавить агрегат `duplicate_pipeline_starts_prevented` в summary-метрику и
   его оконные тесты.
5. Запустить целевые Go- и Python-тесты, затем проверить форматирование и
   состав diff.

## Критерии приёмки

1. API создания и чтения задачи сохраняет и возвращает nullable
   `parent_task_id` и `correction_kind`; невалидная одиночная или неизвестная
   связь отклоняется понятной ошибкой.
2. Все шесть возвратов cap (`INFRA`, `MERGE`, `SPEC_BRANCH`, `SPEC`, `GATE`,
   `DIRT`) создают дочернюю задачу с ID текущей исходной задачи и своим
   `cap_rescue:<stage>`; `request_key` остаётся дополнительной защитой повтора.
3. Пилот, получив задачу с непустым `correction_kind`, не создаёт для неё новый
   Pipeline и не запускает следующую стадию; журнал фиксирует предотвращение.
4. Задача без обоих полей работает как до миграции, включая ручные и старые
   `[auto]`-задачи.
5. `/api/v1/metrics/summary` для каждого окна возвращает
   `duplicate_pipeline_starts_prevented`, равный числу созданных служебных
   коррекций в окне; он не считает обычные задачи.
6. Ошибка создания коррекции по-прежнему не расходует cap и освобождает
   исходную задачу для следующего цикла.

## Риски и решения

- Самоподобная ссылка или произвольный `correction_kind` сделают контракт
  нечитаемым. Решение — серверная проверка пары, существования parent и
  ограниченного перечисления видов.
- Миграция SQLite с self-FK не должна переписывать существующие записи.
  Решение — только nullable ADD COLUMN и индекс; не backfill-ить по заголовку
  или request key, так как это недостоверно.
- Метрика «предотвращено» является счётчиком созданных маркированных
  коррекций, а не попыток `create_task`: только созданная запись могла быть
  ошибочно поднята опросом Пилота. Явно документировать это значение в API.
- Пересечение с уже работающим cap-return не расширяет задачу: он отвечает за
  момент расходования лимита, а эта поставка — за идентичность дочерней работы.
