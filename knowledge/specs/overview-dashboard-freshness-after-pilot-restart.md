# Свежесть dashboard.json после рестарта factory-pilot

## Цель и влияние на владельца

После рестарта `factory-pilot` владелец должен видеть на «Обзоре» текущий
снимок состояния, а не данные, оставшиеся почти на шесть часов. Если новый
снимок временно не собран, экран обязан явно показать возраст и состояние
данных; устаревший снимок не должен выглядеть свежим или молча заменяться
пустым.

## Технический подход и реальные файлы

Источник истины — `pilot/pilot.py`: `cycle()` вызывает `write_dashboard()`, а
`dashboard_slow()` отдельно кэширует дорогой блок проектов на 300 секунд.
Сервер `internal/controlplane/dashboard_http.go` должен остаться dumb-reader:
он отдаёт один атомарно записанный JSON и не вычисляет данные на запрос.
Клиентские изменения нужны только для явного отображения времени/признака
устаревания, если текущий контракт этого не делает: `web/src/Overview.tsx`,
`web/src/Overview.test.ts`.

Реализация должна разделить два понятия: время формирования всего снимка
(`updated_at`) и время обновления медленного блока (новое поле, например
`sections.projects.updated_at`, если оно действительно требуется). На каждом
успешном цикле пилот пишет новый снимок через временный файл в том же каталоге,
`fsync` файла и `os.replace`; ошибка сборки сохраняет последний валидный файл,
но записывает диагностируемую причину в журнал. После старта процесса кэш
медленного блока сбрасывается и не может блокировать первый снимок после
рестарта. Интервал в 300 секунд сохраняется только для дорогостоящего блока,
не для всего dashboard.

API `GET /api/v1/dashboard` сохраняет совместимость: при отсутствии файла
возвращается JSON-объект, а при наличии — последняя полностью записанная
версия. Не следует делать запросы к пилоту из HTTP-обработчика или запускать
тяжёлые проверки на открытие «Обзора».

## Последовательный план

1. Добавить тестируемые часы/метаданные снимка и атомарный writer в
   `pilot/pilot.py`; определить поведение при исключении и после рестарта.
2. Обновить `dashboard_slow()` так, чтобы старт процесса принудительно
   публиковал свежий baseline, а последующие циклы кэшировали только его
   медленный раздел.
3. Проверить чтение и сериализацию снимка в
   `internal/controlplane/dashboard_http.go` и его тесте, не добавляя сетевых
   вычислений.
4. В `web/src/Overview.tsx` показать время снимка и понятное предупреждение,
   когда возраст превышает согласованный порог; не скрывать содержимое при
   диагностической ошибке.
5. Добавить целевые unit/API/UI тесты, затем выполнить обязательную проверку
   и `git diff --check`.

## Критерии приёмки

1. После запуска нового процесса первый успешный цикл меняет `updated_at` и
   публикует полный, валидный `dashboard.json`, даже если старый кэш был
   создан до рестарта.
2. Два последовательных успешных цикла дают монотонно обновляемое время
   снимка; пятиминутный кэш проектов не удерживает весь JSON неизменным.
3. Чтение во время записи никогда не получает обрезанный JSON или смесь
   старой и новой версий; при ошибке остаётся последний валидный снимок.
4. Ошибка сборки видна в диагностике пилота и не маскируется как свежий
   результат или пустой dashboard.
5. «Обзор» показывает время снимка и предупреждение для устаревших данных;
   свежий снимок не показывает это предупреждение.
6. Существующий API-контракт и прочие разделы dashboard не меняют смысл
   данных, а HTTP-обработчик не выполняет внешних команд.

## Тест-план

- `pilot/test_pilot.py`: первый цикл после рестарта, повторная запись, ошибка
  сборки с сохранением последнего файла, атомарность и независимость общего
  `updated_at` от пятиминутного project-cache.
- `internal/controlplane/http_test.go`: чтение полного снимка, отсутствие
  файла и отсутствие наблюдения промежуточного JSON.
- `web/src/Overview.test.ts`: свежий/устаревший timestamp, предупреждение и
  сохранение данных при ошибке обновления.
- Обязательная проверка после реализации: `python3 -m unittest pilot.test_pilot
  && go test ./internal/controlplane -run 'Dashboard' && npm --prefix web test
  -- --run src/Overview.test.ts && git diff --check`.

## Риски и решения

- Атомарная замена не исправит постоянный сбой сбора; поэтому UI обязан
  показывать возраст, а лог — причину, сохраняя последний полезный снимок.
- `fsync` каталога может отличаться по платформам; использовать безопасную
  best-effort синхронизацию с тестом на Linux и не удалять старый файл до
  успешной замены.
- Слишком короткий порог устаревания создаст шум при штатном медленном цикле;
  порог должен быть конфигурируемым или явно равняться нескольким ожидаемым
  интервалам, с тестом граничного значения.
- В область не входят изменение UI-компоновки, новые метрики проектов,
  исправление unrelated ошибок пилота и миграция формата всех старых файлов.
