# Спецификация: отдельная страница «Решения» со всеми вопросами

## Цель и влияние на владельца

В меню должна появиться самостоятельная страница «Решения», на которой владелец
видит историю всех доступных вопросов конвейера, а не только текущую очередь с
кнопками «Делаем» и «Не делаем». Это даёт один обзор: что спрашивали, на каком
этапе, когда, в каком статусе и какой ответ был сохранён.

Пункт «Нужен ответ» остаётся операционной очередью. Он по-прежнему показывает
только открытые вопросы и содержит голосовой/текстовый ответ и быстрые решения.
Страница «Решения» не дублирует эти действия: она только читает и объясняет
историю, поэтому случайное повторное решение из двух экранов невозможно.

## Технический подход и реальные файлы

### Что уже есть

- `web/src/App.tsx` знает route `/answer`, пункт меню «Нужен ответ», счётчик
  открытых вопросов и подключение `AnswerView`, но route `/solutions` отсутствует.
- `web/src/Answer.tsx` получает `GET /api/v1/questions`, отбирает `status ===
  "open"` и отправляет решения. Это контракт очереди действий, его поведение
  нельзя расширять историей.
- `internal/controlplane/questions_http.go` уже возвращает все корректные JSON-
  записи вопросов из `pilot/questions`, не ограничивая их статусом и не делая
  `slice`; сервер удаляет только большой `prior_result` и загрязнённые Python
  mock-представления.
- `internal/controlplane/questions_http_test.go` фиксирует, что обычные записи
  проходят API, а mock-записи не показываются. Этот серверный контракт остаётся
  без нового endpoint и миграции.

### Что будет сделано

1. В `web/src/App.tsx` добавить route `solutions`, путь `/solutions`, отдельный
   пункт «Решения», заголовок страницы и подключение `SolutionsView`. Пункт
   «Нужен ответ» и его badge открытых вопросов не переименовывать и не сливать
   с новым пунктом.
2. Создать `web/src/Solutions.tsx` как read-only страницу с тем же
   `GET /api/v1/questions` и query key `questions`. Рендерить каждую запись из
   ответа ровно один раз, без фильтра по статусу и без ограничения количества.
   Строка/карточка должна показывать идентификаторный контекст без технического
   шума: название, этап, дату вопроса, статус, полный текст ситуации и вопроса;
   если есть `answer`, `answered_by` или `answered_at`, показать и эти сведения.
   Для неизвестного статуса оставить безопасный raw fallback, не скрывать запись.
3. Вынести общий тип записи владельческого вопроса в `web/src/types.ts` и
   использовать его в `web/src/Answer.tsx` и `Solutions.tsx`, чтобы два экрана
   не разошлись по полям API. Это только типовой рефакторинг: отправка ответа,
   удаление вопроса и фильтр очереди не меняются.
4. Не добавлять на `/solutions` кнопки «Делаем», «Не делаем», «Отправить и
   продолжить», голосовую запись, подсказку оркестратора или DELETE/POST.
   Допустима только навигационная ссылка обратно к «Нужен ответ» и обычное
   обновление списка.
5. Добавить целевую регрессию в `web/src/Solutions.test.tsx` с открытым,
   отвеченным, решённым и устаревшим вопросами. Отдельно проверить wiring
   меню/route в `web/src/App.test.tsx`; существующий `Answer.test.tsx` должен
   продолжить проверять быстрый ответ.

Новый backend-файл и новый API не нужны: «все вопросы» означает все валидные
записи, возвращённые существующим endpoint (включая статусы, отличные от
`open`), а не записи, намеренно отфильтрованные серверной санитаризацией.

## Последовательный план

1. Зафиксировать в тестовых данных смешанные статусы и ожидаемое отображение
   полной истории без кнопок изменения.
2. Вынести тип вопроса и добавить `SolutionsView` с состояниями loading, error,
   empty и list; сохранить обновление только при видимой вкладке.
3. Подключить `/solutions` к чтению маршрута, `routePath`, меню, заголовку и
   мобильной навигации; проверить активность только этого пункта.
4. Прогнать целевые Vitest-тесты Solutions, App и Answer, затем typecheck/lint
   затронутой web-области. Исправления API или данных не входят в эту работу.
5. На ручной проверке открыть `/solutions` с несколькими статусами и убедиться,
   что решения отправляются только с `/answer`, а переходы браузера и меню не
   теряют route.

## Критерии приёмки

1. В основном и мобильном меню есть отдельный пункт «Решения», ведущий на
   `/solutions`; при его открытии заголовок и `aria-current` соответствуют
   странице, а «Нужен ответ» остаётся отдельным пунктом.
2. `/solutions` запрашивает существующий `GET /api/v1/questions` и отображает
   все полученные валидные записи: открытые, отвеченные, решённые, устаревшие и
   неизвестные статусы — без фильтра `open`, лимита 5/12 или потери дубликатов с
   разными `id`.
3. Для каждой записи видны название, этап, статус, дата вопроса и полный текст
   вопроса/ситуации; при наличии ответа видны ответ и кто/когда его дал.
4. На странице «Решения» нет кнопок быстрых решений и нет запросов
   `POST /api/v1/questions/{id}/answer` или `DELETE /api/v1/questions/{id}`.
   Действия владельца по-прежнему доступны на `/answer` и не регрессировали.
5. Loading, API error и пустой список имеют явное состояние; refresh не меняет
   данные и не создаёт вторую запись.
6. Серверный фильтр Python mock, удаление `prior_result` и существующий endpoint
   не изменены; продуктовый diff последующего Implement не меняет другие
   разделы панели.

## Тест-план

- `web/src/Solutions.test.tsx`: смешанный fixture из минимум четырёх статусов;
  проверить наличие всех заголовков/вопросов/ответов, отсутствие decision
  buttons и отсутствие mutation-запросов.
- `web/src/App.test.tsx`: открыть `/solutions`, увидеть заголовок, активный
  пункт и вызов `GET /api/v1/questions`; перейти в «Нужен ответ» и проверить,
  что активность и очередь не подменяются новой страницей.
- `web/src/Answer.test.tsx`: существующая проверка «Делаем» и точного POST;
  она является регрессией единственного места, где разрешена мутация.
- `web/src/types.ts`: TypeScript typecheck подтверждает единый контракт без
  обхода `any` для полей вопроса.
- Проверки Implement: `cd web && npm test -- --run src/Solutions.test.tsx
  src/App.test.tsx src/Answer.test.tsx`, затем `npm run typecheck` и `npm run
  lint` в `web`.

## Риски и решения

- История уже содержит записи, которые нельзя показать владельцу из-за серверной
  mock-санитаризации. Решение: не ослаблять фильтр и считать «всеми» все записи
  из публичного API, а не сырые повреждённые JSON.
- `/answer` и `/solutions` могут по-разному трактовать статус. Решение: общий
  тип, явная карта человекочитаемых статусов и raw fallback; фильтр `open`
  остаётся только в AnswerView.
- Большой архив может сделать страницу тяжёлой, потому что текущий endpoint не
  пагинирует. Решение для этой работы — не скрывать и не обрезать данные; если
  объём станет проблемой, пагинация оформляется отдельной спецификацией API.
- Пользователь может принять одно решение дважды из-за двух экранов. Решение:
  SolutionsView не имеет POST/DELETE и decision-кнопок; действия остаются на
  `/answer`.
- Ошибка маршрутизации может пометить два пункта active. Решение: отдельный
  literal route и тест на `aria-current` для `/solutions`.
