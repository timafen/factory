# Отчёт патруля не блокирует подписку Claude

## Цель и влияние на владельца

Сохранить доступной всю подписку Claude, когда успешный патруль лишь упоминает
`rate limit`, `quota exceeded` или другую сигнатуру лимита в своём отчёте. Для
владельца это означает, что описание найденной проблемы больше не выключает
всех Claude-исполнителей и не переводит работы на запасного провайдера без
реального исчерпания подписки.

Сейчас `pilot/pilot.py:detect_limits()` просматривает успешные, неуспешные и
отменённые задачи, объединяет системное `attempt.error` с произвольным
`attempt.result` и передаёт совпадение `LIMIT_SIGNS` в `note_limit()`. Защита по
свежему проценту не помогает, если снимок отсутствует, устарел или показывает
80% и выше. Поэтому текст отчёта патруля становится ложным доказательством и
создаёт provider-wide блокировку Claude в `limits.json`.

## Технический подход и реальные файлы

- `pilot/pilot.py` — сузить `detect_limits()` до доверенной границы отказа:
  рассматривать только задачу в состоянии `failed`, только её действительно
  неуспешную попытку и только непустое поле `attempt.error`. Поле
  `attempt.result` не участвует ни в поиске `LIMIT_SIGNS`, ни в извлечении
  `RESET_AT`, независимо от свежести и значения реального счётчика.
- `pilot/pilot.py` — сохранить существующий порядок классификации доверенной
  ошибки: сначала `LIMIT_SIGNS`, затем исключение `INFRA_SIGNS`, после этого
  `RESET_AT` и `note_limit()`. Ручной `manual_off`, время жизни блока и формат
  `limits.json` не менять.
- `pilot/pilot.py:provider_limits_tick()` оставить независимым авторитетным
  путём: настоящий общий счётчик Claude по-прежнему может заранее заблокировать
  провайдера при 95%. Прямой отказ CLI в `brain()` также остаётся отдельным
  сигналом; лимит одной модели продолжает обрабатываться через `engine_down`.
- `pilot/test_pilot.py` — добавить изолированный класс
  `ProviderLimitDetectionTests` с моками task detail, `note_limit()` и снимка
  процентов. Главная регрессия воспроизводит успешный Claude-патруль, в отчёте
  которого есть точная сигнатура лимита, при отсутствующем или устаревшем
  снимке подписки.

Контракт worker уже поддерживает эту границу: terminal error Claude Code
попадает в `attempt.error`, а stdout/stderr неуспешного runtime сохраняется как
ошибка попытки. Поэтому для распознавания настоящего отказа читать свободный
текст успешного отчёта не требуется. Изменения worker, control-plane, UI,
миграций и формата API не нужны.

## Последовательный план

1. Добавить красную регрессию: успешная задача Claude с отчётом патруля,
   содержащим `rate limit reached`, не вызывает `note_limit()` даже без свежих
   процентов подписки.
2. Добавить парные сценарии для `failed`: сигнатура только в `result` не
   блокирует провайдера, а та же сигнатура в `error` вызывает `note_limit()` с
   провайдером Claude и извлечённым временем сброса.
3. Проверить отменённую задачу и историческую успешную попытку внутри упавшей
   задачи: их отчёты и ошибки не становятся доказательством текущего лимита.
4. Переписать `detect_limits()` на выбор последней неуспешной попытки и её
   `error`; удалить зависимость этого пути от `result` и защитного процента.
5. Проверить исключение инфраструктурной ошибки, существующий реальный опрос
   лимитов и полный целевой набор Pilot.

## Критерии приёмки

- Успешный или отменённый Claude-патруль с любой сигнатурой `LIMIT_SIGNS` в
  `attempt.result` не вызывает `note_limit()` и не меняет доступность Claude.
- Упавшая задача, у которой сигнатура встречается только в отчёте, также не
  блокирует подписку; свежесть и процент реального снимка на это не влияют.
- Только `attempt.error` последней неуспешной попытки упавшей задачи может
  служить текстовым доказательством лимита; время сброса извлекается из той же
  ошибки.
- Ошибка с `INFRA_SIGNS` не считается лимитом даже при совпадении
  `LIMIT_SIGNS`.
- `provider_limits_tick()` сохраняет provider-wide блокировку по настоящему
  общему счётчику Claude при 95%, а `manual_off` остаётся без изменений.
- Изменение не затрагивает worker, control-plane, UI, API, миграции и формат
  сохранённого состояния.

## Тест-план

В `ProviderLimitDetectionTests` создать task/attempt fixtures и проверить:

1. `succeeded` Claude patrol + `result="... rate limit reached ..."` + пустой,
   устаревший и высокий снимок — ноль вызовов `note_limit()`;
2. `failed` + сигнатура только в `result` — ноль вызовов;
3. `failed` + последняя failed attempt с
   `error="usage limit reached; resets at 2026-08-13T08:00:00Z"` — один вызов
   для `claude` с тем же доказательством и точным `resets_at`;
4. историческая failed attempt перед успешной последней попыткой, cancelled
   task и ошибка с `INFRA_SIGNS` — ноль ложных вызовов;
5. существующий путь настоящего процента в `provider_limits_tick()` по-прежнему
   вызывает `note_limit()` на пороге 95%.

Обязательная проверка — новый точечный класс. После неё выполнить весь
`python3 -m unittest pilot.test_pilot`, чтобы проверить соседние переходы,
автоподбор исполнителей и fallback мозга.

## Риски и решения

- Runtime может изменить формат terminal error. Решение: опираться на
  нормализованное поле `attempt.error` контракта worker; если доверенной ошибки
  нет, не гасить провайдера по свободному тексту, а дождаться авторитетного
  `provider_limits_tick()`.
- Старая task detail может не содержать состояние попытки. Решение: fail-open
  именно для автоматической provider-wide блокировки; не угадывать отказ по
  `result`.
- Широкая `LIMIT_SIGNS` может совпасть с инфраструктурной ошибкой. Решение:
  сохранить приоритет `INFRA_SIGNS` и закрепить его регрессией.
- Сужение источника сигнала может позже заметить настоящий лимит. Решение:
  terminal runtime error и реальный 95%-счётчик остаются двумя независимыми
  доверенными путями; потеря мощности безопаснее ложного отключения всей
  подписки по пользовательскому отчёту.
- Исправление не очищает ранее записанный ложный блок. Решение: текущий TTL и
  успешный вызов `brain()` уже снимают автоматический блок; миграция состояния
  не нужна и не входит в эту работу.
