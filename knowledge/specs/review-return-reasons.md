# Повторяющиеся причины возвратов Review

## Цель и влияние на пользователя

Владелец на экране «Главное» сможет видеть, какие причины чаще всего возвращают
работу с Review на доработку, за те же периоды 24 часа и 7 дней, что и текущая
метрика первого прохождения Review. Это превращает число «Review с первого раза»
в понятный сигнал, куда улучшать процесс: требования, реализацию, тесты,
интерфейс и понятность, безопасность, документацию или процесс либо прочее.

Причина возврата будет обязательной категорией из фиксированного списка. Для
«прочее» Review обязан дать короткое пояснение. Полный свободный текст отчёта
остаётся обычным результатом попытки и не используется для угадывания категории.
Исторические возвраты не переписываются: когда они попадают в расчёт, они видны
как «Не классифицировано».

## Технический подход

Существующий конвейер в `pilot/pilot.py` уже принимает решение `APPROVE` либо
`REQUEST CHANGES` после успешного Review и сам создаёт вопрос/возврат. В него
добавляется строгий контракт отчёта только для Review с `REQUEST CHANGES`:

```
ПРИЧИНА ВОЗВРАТА: <одна фиксированная категория>
ПОЯСНЕНИЕ ПРИЧИНЫ: <обязательно только для «прочее», кратко>
```

Допустимы ровно: `требования`, `ошибка реализации`, `тесты`, `интерфейс и
понятность`, `безопасность`, `документация или процесс`, `прочее`. Оркестратор
не выводит категорию из других фраз: он принимает только точную строку. При
`REQUEST CHANGES` без корректной категории (или без пояснения для «прочее») он
однократно возвращает задачу на тот же этап Review с точным замечанием о формате;
некорректный отчёт не создаёт запись причины и не возвращает работу в разработку.

После корректного `REQUEST CHANGES` `pilot/pilot.py` дописывает идемпотентную
запись по `task_id` в `pilot/review-returns.jsonl`: категория, короткое
пояснение, время и идентификатор Review-задачи. Это отдельный журнал наблюдений,
аналогичный уже читаемому `merges.jsonl`; исходный свободный отчёт по-прежнему
хранится у попытки в control plane. Запись создаётся до передачи работы назад,
поэтому перезапуск пилота не теряет уже признанную причину и не удваивает её.

`internal/controlplane/efficiency.go` читает этот журнал вместе с данными задач
и слияний, добавляет в `EfficiencyPeriod` упорядоченный массив счётчиков причин
возврата Review. В знаменатель входят только фактические возвраты Review работ,
вошедших в период по времени слияния; категория `не классифицировано` собирает
возвраты без журнальной записи, то есть историю до внедрения. Строки отчёта не
разбираются для ретроклассификации. Контракт `GET /api/v1/metrics/efficiency`
расширяется только новым полем, поэтому старые клиенты его безопасно игнорируют.

`web/src/Overview.tsx` получает новый тип и в раскрываемой части «Эффективности
Factory» показывает «Причины возврата Review»: категории с числом возвратов и
долей от всех возвратов, включая ясное пустое состояние. Новый блок использует
выбранное окно и не меняет существующий расчёт `Review с первого раза`.

Затрагиваемые файлы реализации:

- `pilot/pilot.py`
- `pilot/test_pilot.py`
- `internal/controlplane/efficiency.go`
- `internal/controlplane/efficiency_test.go`
- `web/src/Overview.tsx`
- `web/src/Overview.test.ts`

## План

1. Ввести в пилоте константы категорий и чистый разборщик строгих строк отчёта
   Review; добавить текст контракта в контекст запуска Review.
2. Перед маршрутизацией `REQUEST CHANGES` валидировать категорию: корректный
   возврат записывать идемпотентно в журнал, некорректный один раз отправлять на
   повторный Review с объяснением формата.
3. Расширить расчёт эффективности чтением журнала и агрегированием фиксированных
   категорий; определить старые фактические возвраты как «не классифицировано».
4. Расширить JSON-тип и блок деталей «Главного» таблицей/списком причин для
   выбранного периода, с пустым состоянием и понятной подписью знаменателя.
5. Добавить целевые регрессии пилота, control plane и интерфейса.

## Критерии приёмки

1. Новый Review с `REQUEST CHANGES` принимает ровно одну из семи утверждённых
   категорий; для «прочее» без краткого пояснения возврат в разработку не создаётся.
2. Корректный возврат сохраняет выбранную категорию и свободный текст отчёта;
   повторный цикл пилота не создаёт второй записи для той же Review-задачи.
3. Категория не извлекается из произвольного текста: отсутствующая или неверная
   строка вызывает один повтор Review с указанием нужного формата.
4. `/api/v1/metrics/efficiency` для 24 часов и 7 дней отдаёт счётчики причин и
   их общий знаменатель только для фактических возвратов Review соответствующих
   влитых работ.
5. Возврат, созданный до журнала или не имеющий записи категории, показан как
   «Не классифицировано», без попытки угадать его из старого отчёта.
6. В «Главном» после раскрытия деталей владелец видит причины, число и долю;
   при нуле возвратов показано понятное пустое состояние.

## План проверки

- `pilot/test_pilot.py`: все семь категорий, обязательное пояснение «прочее»,
  отказ от свободного текста, однократный повтор Review и идемпотентный журнал.
- `internal/controlplane/efficiency_test.go`: агрегирование в обоих окнах,
  знаменатель, порядок категорий и старый возврат как «не классифицировано».
- `web/src/Overview.test.ts`: отображение причин, долей, выбранного периода и
  пустого состояния.
- Обязательная команда: `python3 -m unittest pilot.test_pilot && go test
  ./internal/controlplane -run 'Efficiency' && npm --prefix web test -- --run
  src/Overview.test.ts`.

## Риски и решения

- Решение: категории фиксированы утверждённым владельцем; свободный текст —
  детализация, а не источник классификации. Автоматическое извлечение отвергнуто
  как нестабильное и неаудируемое.
- Решение: журнал JSONL выбирается вместо миграции таблицы, потому что пилот уже
  владеет решением о возврате, а control plane уже безопасно читает аналогичные
  журналы метрик. Это минимизирует изменение API и схемы БД.
- Риск: агент может ошибиться в формате. Однократный повтор Review исправляет
  это без ложной статистики и без лишнего круга разработки. Если повтор также
  неверен, текущая маршрутизация остановки попросит решение владельца.
- Вне области: изменение исторических результатов, редактирование существующих
  workflow-инструкций и разрезы по репозиторию/исполнителю. Их можно добавить
  отдельной задачей после появления достоверных категорий.
