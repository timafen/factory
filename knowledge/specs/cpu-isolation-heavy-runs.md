# Изоляция по процессору: тяжёлые прогоны не душат панель и мозг

## Цель и влияние на владельца

Тяжёлый `Implement + Test` или `Verify` не должен занимать весь CPU так, чтобы
панель переставала отвечать, а Factory Brain начинал ждать или ошибаться.
Владелец видит актуальные работы и может принять решение даже во время
длинного прогона; очередь тяжёлых работ при этом ограничивается фактической
ёмкостью исполнителей.

## Технический подход и реальные файлы

Изменить политику допуска в `pilot/pilot.py`: учитывать CPU-порог и занятые
слоты до запуска тяжёлого этапа, резервировать слот по `work_id`, а лёгкие
операции оркестрации (опрос, ответы владельца, публикацию состояния) оставлять
доступными. Нельзя использовать имя работы как ключ: одноимённые работы
должны изолироваться по идентификатору.

Сохранить диагностический снимок нагрузки в существующем контракте health и
передавать его в `web/src/Overview.tsx`, чтобы панель объясняла задержку числом
активных работ и занятых мест, а не скрывала её. Проверки добавить в
`pilot/test_pilot.py` и `web/src/Overview.test.ts`. Форматы задач и публичные
API менять только при необходимости совместимого поля состояния.

## Последовательный план

1. Зафиксировать текущие источники CPU, активных работ и слотов в пилоте.
2. Ввести единое решение допуска тяжёлого запуска с резервированием по
   `work_id`; отказ не должен останавливать цикл обслуживания.
3. Применить решение ко всем путям запуска и восстановления тяжёлых этапов.
4. Вывести причину ограничения в обзоре и покрыть её тестами.
5. Прогнать целевые тесты, затем один полный набор перед Verify.

## Критерии приёмки

- При CPU выше порога второй тяжёлый запуск не начинается, пока первый
  `work_id` занимает разрешённую ёмкость.
- Две одноимённые работы не делят блокировку: решения принимаются по
  независимым `work_id`.
- Панель и Brain продолжают обслуживаться при отложенном тяжёлом запуске.
- В обзоре видны состояние CPU, число активных работ и занятые слоты; при
  отсутствии слотов UI честно сообщает об отсутствии данных.
- После освобождения ресурса отложенная работа запускается без ручного
  вмешательства, а обычная нагрузка сохраняет прежнее поведение.

## Тест-план

- `pilot/test_pilot.py`: табличные проверки порога, резервирования,
  освобождения, одинаковых названий с разными `work_id` и продолжения цикла.
- `web/src/Overview.test.ts`: тексты причины CPU с реальными слотами и без них.
- Обязательная целевая команда после реализации:
  `python3 -m unittest pilot.test_pilot.HostLoadAdmissionTests`

## Риски и решения

- Слишком низкий порог ухудшит пропускную способность: использовать текущую
  политику host load и измеряемые слоты, без нового пользовательского лимита.
- Потеря освобождения создаст вечную очередь: резерв делать идемпотентным и
  проверять cleanup в `finally`.
- Health может быть старым: показывать время снимка и не выдавать устаревшее
  состояние за текущий факт.
