# Production dashboard не принимает Mock-объекты

## Цель и влияние на владельца

Production dashboard не должен показывать технические строки вида `MagicMock` и
не должен изменяться от запуска модульных тестов. После реализации владелец будет
видеть либо последний корректный снимок Factory, либо штатное отсутствие данных,
но не внутреннее представление тестового объекта.

Сейчас снимок собирается в `pilot/pilot.py`: `write_dashboard` объединяет данные
API, вычислений и глобального кэша `_dash_slow`, после чего `save(DASH_PATH, data)`
атомарно заменяет `/opt/factory-data/pilot/dashboard.json`. Обработчик
`internal/controlplane/dashboard_http.go` только читает этот JSON и отдаёт его без
преобразований, а `web/src/Overview.tsx` отображает полученные строки. Поэтому
маскировка дефекта в Go или UI оставила бы загрязнённый production-артефакт.

## Технический подход и реальные файлы

Изменение ограничить `pilot/pilot.py` и `pilot/test_pilot.py`.

В `pilot/pilot.py` сделать путь назначения явной границей `write_dashboard`: по
умолчанию остаётся `DASH_PATH`, а тест может передать временный путь. Перед
`save` рекурсивно проверить готовый снимок: разрешены только JSON-совместимые
словари со строковыми ключами, списки, строки, числа, boolean и `null`; значения
из `unittest.mock` и их диагностические строковые представления не считаются
данными dashboard. Проверка не должна импортировать тестовую библиотеку в
production-код: достаточно структурного контракта и узкого распознавания
Python mock-repr на выходной границе.

Невалидный новый снимок не заменяет последний корректный файл. Pilot пишет в лог
безопасную причину с путём поля, но не полный объект. Это сохраняет уже имеющуюся
атомарность `save` и делает отказ заметным оператору. Go API и React остаются без
изменений: они получают только проверенный JSON.

В `pilot/test_pilot.py` добавить `DashboardSnapshotIsolationTests`. Каждый тест,
который реально вызывает writer, обязан использовать `TemporaryDirectory`; новый
регрессионный сценарий подставляет `MagicMock` в одну из отображаемых ветвей
снимка, подтверждает отказ публикации и сохранность заранее записанного хорошего
снимка. Отдельная проверка подтверждает успешную публикацию обычных данных.

## Последовательный план

1. Добавить параметр пути в `write_dashboard`, сохранив production-значение по
   умолчанию и существующий формат JSON.
2. Добавить малую рекурсивную проверку итогового снимка с путём до ошибочного поля.
3. Проверять снимок до вызова `save`; при отказе логировать причину и оставлять
   предыдущий dashboard без изменений.
4. Изолировать реальные записи dashboard в тестах временным каталогом.
5. Добавить целевые тесты хорошего снимка и Mock-загрязнения, включая строковое
   представление, которое иначе является формально валидным JSON.

## Критерии приёмки

1. Обычный вызов `write_dashboard` публикует тот же контракт dashboard и по
   умолчанию пишет только в `DASH_PATH`.
2. Прямой Mock либо строка его диагностического представления в любом вложенном
   поле не попадает в опубликованный JSON.
3. При невалидном снимке существующий корректный dashboard остаётся побайтно
   неизменным; временный файл не становится новым production-снимком.
4. В логе есть имя проблемного поля, но нет полного `repr` объекта и случайных
   данных из него.
5. Тестовый сценарий записи использует только временный путь и не может изменить
   `/opt/factory-data/pilot/dashboard.json`.
6. `internal/controlplane/dashboard_http.go` и `web/src/Overview.tsx` не меняются:
   источник дефекта закрыт до границы публикации.

## Тест-план

В `DashboardSnapshotIsolationTests` использовать минимальные корректные `tasks`,
`workers`, usage snapshot и подмены тяжёлых источников. Проверить:

- корректный снимок сохраняется и читается стандартным `json.load`;
- вложенный `MagicMock` отклоняется, а ранее сохранённый sentinel остаётся;
- строковый mock-repr отклоняется по тому же правилу;
- сообщение лога содержит JSON-путь и не содержит полный mock-repr;
- переданный временный путь использован вместо глобального `DASH_PATH`.

Обязательная команда: `python3 -m unittest -v pilot.test_pilot.DashboardSnapshotIsolationTests`.
До реализации сценарий строкового mock-repr должен падать: текущая `save` считает
такую строку допустимым JSON и не отделяет тестовый путь от production-пути.

## Риски и решения

- Риск ложного совпадения с пользовательским текстом. Решение: распознавать
  только полный технический формат Python mock-repr, а не слово `mock` внутри
  обычного заголовка (включая название этой работы).
- Риск потери всего dashboard из-за одного источника. Решение: сохранять
  последний хороший файл и логировать точный путь поля для исправления источника.
- Риск расхождения формата. Решение: валидатор не переписывает значения и не
  вводит новый DTO; успешный снимок проходит без изменений.
- Риск тест снова использует production default. Решение: тестовая fixture
  передаёт временный путь явно, а регрессионный тест проверяет этот контракт.
- Отклонено: фильтрация в React или Go handler, потому что она скрывает уже
  испорченный общий артефакт и оставляет других потребителей незащищёнными.
