# Спецификация: ворота выката запускают локальные тесты

## Goal and user impact

Перед установкой новых бинарей и перезапуском служб выкат Фабрики будет
останавливаться на любой локальной детерминированной регрессии. Оператор не сможет
поставить ревизию, в которой не проходят UI unit-тесты, Go-тесты или сценарий
отката выката; действующая пара бинарей и работающие службы останутся нетронутыми.

## Technical approach

Минимальное изменение ограничено release-скриптом и его изолированной shell-
регрессией:

- В `ops/fx-factory-release` после `npm ci` и до создания/сохранения кандидатов
  добавить три последовательные ворота: `npm test` в `web`, `go test ./...` из
  корня репозитория и `bash ops/test-fx-factory-release.sh` из корня. Существующие
  TypeScript-проверка, Vite-сборка и две Go-сборки остаются без изменения.
- Каждая из трёх команд исполняется тем же непривилегированным пользователем,
  что и сборка, и при ненулевом коде завершает выкат с существующим кодом ошибки
  сборки (`5`), вызывает `cleanup` и не доходит до `cp`, `install_binary` либо
  `systemctl`.
- В `ops/test-fx-factory-release.sh` расширить фикстуру: записывать выполнение
  новых ворот и моделировать отдельный сбой UI-, Go- и release-regression-проверки.
  Для последней фикстурный `bash` перехватывает только вызов
  `ops/test-fx-factory-release.sh`; все остальные shell-вызовы передаёт `/bin/bash`.
  Это проверяет вызов ворот без рекурсивного запуска release-скрипта из его же
  регрессионного теста.

Публичных API, схем данных и конфигурационных контрактов не меняется.

## Plan

1. Вставить в `ops/fx-factory-release` UI unit-, Go- и release-regression-ворота
   после установки web-зависимостей и перед существующими сборками; дать ясные
   русские сообщения каждому отказу.
2. Дополнить тестовую фикстуру mock-командами и журналом, чтобы она различала
   успех и каждый новый отказ.
3. Добавить случаи отказа: прежние серверный и воркерный бинарь сохранены,
   журнал служб пуст, а последующие сборка и установка не выполнялись.
4. Запустить целевую shell-регрессию; на Verify один раз выполнить все команды
   из test plan в чистой копии зависимостей.

## Acceptance criteria

1. При нормальном выкате до установки бинарей выполняются UI unit-тесты,
   `go test ./...` и `bash ops/test-fx-factory-release.sh`, а также существующие
   проверка типов и обе сборки.
2. Отказ любого из трёх новых ворот завершает выкат с ошибкой до изменения
   файлов `FACTORY_SERVER_BIN` и `FACTORY_WORKER_BIN` и до любого перезапуска
   `factory-server.service` или `factory-worker.service`.
3. Изолированная регрессия доказывает успешный путь и все три новых отказа,
   не рекурсируя при проверке самого release-regression-ворота.
4. Внешние интеграционные, браузерные и ручные проверки в эти ворота не входят.

## Test plan

- Добавить в `bash ops/test-fx-factory-release.sh` проверки порядка новых ворот
  и трёх соответствующих отказов с неизменными бинарями и пустым журналом служб.
- Локально при реализации: `bash ops/test-fx-factory-release.sh`.
- На Verify: после `npm ci` в `web` выполнить `npm test`, `npx tsc -p
  tsconfig.app.json --noEmit`, `npx vite build`; из корня — `go test ./...` и
  `bash ops/test-fx-factory-release.sh`.

## Risks and decisions

- Решение владельца: обязательны только воспроизводимые локальные UI unit,
  Go и release-regression проверки; Playwright, внешние интеграции и ручные
  действия сознательно исключены.
- Release-regression заметно увеличивает длительность выката, но он уже
  детерминирован, автономен и проверяет критичный откат — это принятый барьер
  перед установкой.
- Не добавлять переменную окружения для отключения ворот: она позволила бы
  обойти утверждённое правило. Перехват shell-команды существует только внутри
  временной фикстуры регрессионного теста.
- Человеческое согласование перед реализацией не требуется: состав ворот
  утверждён владельцем.
