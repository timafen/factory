# Спецификация: GitHub CLI берёт репозиторий из `origin`

## Цель и влияние на владельца

Устранить неверный выбор репозитория в автоматизации Factory: на свежем
`origin/main` команда `gh repo view --json nameWithOwner`, запущенная без
`--repo`, возвращает `owainlewis/factory` из контекста GitHub CLI, хотя remote
рабочей копии — `github.com/timafen/factory`. Из-за этого Pilot может читать,
сравнивать или публиковать артефакт не в том репозитории.

После изменения источник репозитория будет однозначным: фактический `origin`
рабочей копии. Владельцу не потребуется исправлять локальный контекст `gh`, а
при расхождении или нераспознаваемом remote конвейер остановится с понятной
диагностикой до внешнего действия.

## Технический подход и реальные файлы

- `pilot/pilot.py` — выделить проверяемый resolver GitHub-репозитория: прочитать
  `git -C <worktree> remote get-url origin`, нормализовать HTTPS/SSH формы в
  `owner/repo`, отвергнуть пустой, локальный и не-GitHub remote; передавать
  полученное значение во все GitHub CLI/API вызовы явно (`--repo owner/repo` или
  endpoint `repos/owner/repo`). Не использовать bare `gh repo view` как
  источник истины. Если диагностический ответ `gh` всё же запрашивается,
  сверять `nameWithOwner` с resolver и не продолжать при несовпадении.
- `pilot/test_pilot.py` — добавить регрессии для fresh worktree с
  `origin=github.com/timafen/factory` и подменённым bare-ответом
  `owainlewis/factory`; проверить, что вызов получает явный правильный repo,
  чужой ответ не используется и ошибка resolver/расхождение даёт блокировку.
- `pilot/context.md` — уточнить только при необходимости, что контекст CLI не
  является идентичностью задачи; фактический remote уже остаётся источником
  истины. Не менять UI, конфигурацию доступа или схему control plane.

## Последовательный план

1. Найти все пути Pilot, где `gh` получает репозиторий неявно либо может
   использовать результат `repo view` без `--repo`.
2. Реализовать один resolver из `origin` и нормализацию допустимых SSH/HTTPS
   URL, не меняя рабочую ветку или remote.
3. Прокинуть результат resolver в CLI/API аргументы; bare-вызов удалить либо
   оставить только как проверяемую диагностику с обязательным совпадением.
4. Сделать ошибки origin, неподдерживаемого host и mismatch безопасной
   блокировкой с human-readable причиной и без запроса к чужому репозиторию.
5. Добавить изолированные unit-регрессии для воспроизведения, успешного
   explicit-repo пути и всех отказов.

## Критерии приёмки

- При `origin` на `github.com/timafen/factory` любой GitHub CLI/API путь Pilot
  адресует `timafen/factory`, независимо от текущего контекста `gh`.
- Ответ bare `gh repo view` с `owainlewis/factory` не может переопределить
  `origin` и не приводит к чтению, сравнению, PR или публикации в чужом repo.
- SSH и HTTPS варианты GitHub remote приводятся к одному `owner/repo`; пустой,
  локальный или иной host не допускаются к GitHub-действию.
- Ошибка чтения `origin` либо mismatch завершает конкретный путь до внешней
  мутации с диагностикой, а не fallback на конфигурацию CLI.
- Регрессия воспроизводит ошибочный bare ответ и завершается с кодом 0 после
  исправления.

## Тест-план

- Новый целевой тест в `pilot.test_pilot`: fixture `origin` указывает на
  `timafen/factory`, mock bare `gh repo view` возвращает `owainlewis/factory`;
  assert, что действие использует только `--repo timafen/factory`.
- Отдельные тесты для `git@github.com:timafen/factory.git`, HTTPS URL,
  malformed/local origin и mismatch; последние не должны создавать внешних
  запросов/мутаций.
- Обязательная команда: `python3 -m unittest pilot.test_pilot`.

## Риски и решения

- У разных worktree SSH и HTTPS формы remote: нормализация и таблица тестов
  исключают зависимость от записи URL.
- `gh` авторизован в другом аккаунте или хранит другой default repo: всегда
  передавать `--repo`, не полагаться на его текущий каталог/конфиг.
- Некорректный origin: безопасно остановить путь до GitHub-команды; оператор
  видит причину вместо скрытой операции над чужими данными.
- Замена всех вызовов может затронуть служебные diagnostics: инвентаризация
  вызовов и целевые mocks фиксируют только GitHub-операции, не меняя UI.
