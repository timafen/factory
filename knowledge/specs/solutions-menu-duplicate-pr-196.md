# Спецификация: предложение «Решения» закрывается как дубликат PR #196

## Цель и влияние на владельца

Не создавать вторую реализацию уже поставленного экрана решений владельца.
Владелец продолжает видеть все открытые вопросы в одном месте по пункту меню
«Нужен ответ», замечает их количество и принимает бинарное решение кнопками
«Делаем» и «Не делаем». Название точнее сообщает, что от владельца требуется
действие, поэтому переименование пункта в «Решения» не входит в работу.

Результат Specification — проверяемо закрыть текущее предложение как дубликат
PR #196. Продуктовый код, UI, API и данные менять не требуется.

## Технический подход и реальные файлы

Фактический `origin/main` уже содержит commit
`e43462307fcd7c25003eecfe693fd21a9dfe8ba7` из PR #196:

- `web/src/App.tsx` ведёт из основного меню на route `/answer` под подписью
  «Нужен ответ» и показывает счётчик открытых вопросов;
- `web/src/Answer.tsx` получает вопросы через `GET /api/v1/questions`, собирает
  все записи со статусом `open`, показывает вопрос одной строкой и отправляет
  «Делаем» либо «Не делаем» в действующий endpoint ответа;
- `web/src/Answer.test.tsx` подтверждает однострочное представление, обе кнопки
  и payload выбранного решения.

Свёрнутый блок решений оркестратора в `Answer.tsx` не мешает основному сценарию
и остаётся без изменений. Отдельная страница `/solutions`, новый route, новый
API, удаление истории и миграция данных не нужны.

## Последовательный план

1. Зафиксировать решение владельца: текущее предложение является дубликатом
   поставки PR #196 и не порождает этап реализации.
2. Сопоставить формулировку предложения с меню, route, фильтром открытых
   вопросов, быстрыми действиями и существующей регрессией в `origin/main`.
3. Сохранить название «Нужен ответ» и свёрнутую историю без изменений.
4. На последующих этапах проверить целевой Vitest. Если поведение PR #196
   регрессировало, исправлять регрессию отдельной работой, не расширяя этот
   дубликат.
5. Закрыть карточку текущей работы со ссылкой на поставленный commit и эту
   спецификацию; продуктовый diff не создавать.

## Критерии приёмки

1. В основном меню есть пункт «Нужен ответ», ведущий на `/answer`; при наличии
   открытых вопросов рядом показан их счётчик.
2. `/answer` выводит все полученные вопросы со статусом `open` в одном списке,
   а текст каждого вопроса визуально ограничен одной строкой с ellipsis.
3. Для открытого вопроса доступны «Делаем» и «Не делаем»; нажатие отправляет
   выбранную строку в `POST /api/v1/questions/{id}/answer`.
4. Пункт меню не переименован в «Решения», новый экран не добавлен, свёрнутая
   история решений оркестратора не удалена.
5. Diff текущей работы содержит только эту спецификацию и отдельную карточку;
   исходники приложения отсутствуют в diff.

## Тест-план

  наличие обоих быстрых действий и точный POST payload «Делаем».
- Статически проверить в `web/src/App.tsx` подпись «Нужен ответ», переход на

- Проверить `git diff --name-only origin/main...HEAD`: только два документа
  текущей Specification.
- Ручная UI-проверка не обязательна: работа не меняет уже поставленный экран.

## Риски и решения

- Название задачи «Решения» расходится с фактическим пунктом меню. Решение
  владельца приоритетно: «Нужен ответ» сохраняется, потому что яснее обозначает
  требуемое действие; отдельное предложение о переименовании не создаётся.
- Свёрнутая история может восприниматься как лишняя. Она не блокирует список
  открытых вопросов и сама по себе не обосновывает новую работу; остаётся вне
  scope.
- Повторная реализация могла бы породить второй route и расходящиеся ответы.
  Риск снимается закрытием дубликата и опорой на один существующий `/answer`.
- Целевой тест зависит от установленных npm-зависимостей. Обязательная команда
  должна завершиться с кодом 0 на этапе реализации/проверки; отсутствие
  зависимостей является проблемой окружения, а не основанием менять продукт.
