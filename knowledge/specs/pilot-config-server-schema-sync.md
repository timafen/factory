# Синхронизация `config.json` со схемой сервера

## Цель и влияние на пользователя

Поле `respect_host_load` уже читается пилотом из `config.json`, но отсутствует в
серверной схеме `protocol.PilotSettings`. Если владелец явно добавляет это поле в
боевой конфиг, строгий декодер `PilotConfigStore` отклоняет весь файл, и экран
«Настройки» перестаёт загружаться. После изменения сервер принимает, показывает и
сохраняет этот флаг, в том числе значение `false`.

Дополнительно автоматическая проверка связывает эталонный
`pilot/config.example.json` со строгой схемой сервера. Новое поле конфигурации,
добавленное в эталон без одновременного обновления схемы, сразу ломает целевой тест,
а не обнаруживается на работающем сервере.

## Технический подход

- В `internal/protocol/types.go` добавить в `PilotSettings` булево поле
  `RespectHostLoad` с JSON-именем `respect_host_load` без `omitempty`, чтобы
  явное `false` не исчезало при сохранении через API.
- В `internal/controlplane/pilot_config.go` применить совместимое значение `true`,
  когда ключ отсутствует в старом конфиге. Это сохраняет действующее поведение
  `pilot.py`, где используется `conf.get("respect_host_load", True)`.
- В `pilot/config.example.json` объявить `respect_host_load: true` как часть
  репозиторного образца конфигурации.
- В `internal/controlplane/pilot_config_test.go` добавить регрессионную проверку:
  загрузить реальный `pilot/config.example.json` строгим серверным декодером,
  проверить наличие/значение флага и round-trip значения `false` через
  `PilotConfigStore.Write`/`Read`.

API-маршруты не меняются. В ответах `GET /api/v1/settings/pilot` и запросах
`PUT /api/v1/settings/pilot` появляется поле `settings.respect_host_load` типа
boolean. Миграция файла не нужна: отсутствующий ключ получает старое значение
`true` при чтении и будет записан при следующем сохранении.

## План

1. Расширить `protocol.PilotSettings` и совместимое чтение старого файла.
2. Добавить `respect_host_load` в эталонный конфиг.
3. Добавить целевой тест соответствия эталона строгой серверной схеме и сохранения
   обоих булевых значений.
4. Запустить целевой тест пакета controlplane.

## Критерии приёмки

1. Старый `config.json` без `respect_host_load` по-прежнему читается, а API
   возвращает для него `respect_host_load: true`.
2. Конфиг с `respect_host_load: false` принимается сервером; чтение, сохранение и
   повторное чтение сохраняют `false`.
3. `pilot/config.example.json` целиком принимается тем же строгим декодером,
   который обслуживает настройки сервера.
4. Неизвестные поля по-прежнему отклоняются: защита от опечаток не ослабляется.
5. Если в эталонный конфиг добавить поле без JSON-тега в `PilotSettings`, целевой
   тест падает с ошибкой строгой схемы.

## План проверки

- Добавить тест `TestPilotConfigExampleMatchesServerSchema` в
  `internal/controlplane/pilot_config_test.go`.
- В тесте использовать репозиторный `pilot/config.example.json`, а не сокращённую
  копию, и отдельно проверить round-trip явного `false`.
- Обязательная команда реализации:
  `go test ./internal/controlplane -run TestPilotConfigExampleMatchesServerSchema`.
- На этапе Verify один раз выполнить полный набор проверок проекта согласно
  принятому процессу; это не расширяет область реализации.

## Риски и решения

- Тест защищает поля, внесённые в репозиторный эталон; непроверяемый ручной ключ
  только в боевом файле CI увидеть не может. Решение: считать одновременное
  обновление `pilot/config.example.json` обязательной частью добавления поля.
- Автоматическое извлечение всех вызовов `conf.get` из Python отвергнуто: там есть
  внутренние и временные ключи, а статический разбор был бы хрупким и расширил бы
  задачу.
- Разрешение произвольных полей на сервере отвергнуто: оно скрыло бы опечатки и
  при сохранении могло бы потерять данные.
- Изменения UI не входят в поставку: общий сериализатор уже передаёт серверную
  модель, а отдельный визуальный элемент для флага является самостоятельным
  продуктовым решением.
