# Сторож продолжает работу с настоящей ветки реализации

## Цель и влияние на пользователя

После успешной `Implement + Test` конвейер может остановиться на замке области
(`AREA WAIT`). Когда ожидание снимает Watch, он создаёт `Review` только с
названием работы и предыдущей стадией. Новый исполнитель не получает ветку с
реальной реализацией и может начать с собственной пустой служебной ветки.
Одновременно отменённая служебная попытка из старого снимка задач не видит
созданный Watch `Review` и запускает лишний `Implement + Test`.

После изменения успешная реализация оставит долговечный факт о своей ветке и её
вершине. Watch, Review, Verify, автоматический ответ и возобновление будут
передавать именно этот факт. Владельцу это даёт продолжение проверки по
существующему коду вместо пустого повторного круга и исключает лишние запуски
исполнителей.

## Технический подход

Изменение ограничивается `pilot/pilot.py` и `pilot/test_pilot.py`. UI, worker,
controlplane и карточки `CARD-0069`/`CARD-0058` не меняются.

В существующей долговечной записи работы `WORKS_PATH` (`~/pilot/works.json`) для
ключа `base_title` появится вложенный артефакт успешной реализации:

```json
"implementation_artifact": {
  "branch": "factory/...",
  "head": "40-символьная вершина origin",
  "task_id": "успешная Implement + Test",
  "recorded_at": "UTC RFC3339"
}
```

Его записывает только успешная `Implement + Test`, до решения о переходе к
следующей стадии. Кандидат выбирается из её результата/контекста через
существующие `branch_candidates` и `pushed_branch`, затем подтверждается в
origin: ветка опубликована, её diff относительно `main` непустой, а вершина
читается как полный SHA. Непустая опубликованная реализация — единственный
случай замены артефакта. Нет имени, ветка отсутствует, diff пуст, SHA не
прочитан или задача относится к служебной работе — запись не меняется.

Добавляется малый единый helper чтения этого артефакта. Он отдаёт `branch` и
`head` только для текущего поколения работы; при явном `reopen_work` старый
артефакт очищается. Для совместимости с уже идущими работами, у которых записи
ещё нет, helper может безопасно восстановить факт только из успешной
`Implement + Test` с теми же проверками origin. Поиск произвольного первого
упоминания ветки (`branch_from_history`) остаётся последним fallback для старых
диагностических путей, но не может перезаписать сохранённый артефакт.

Все исходящие контексты после реализации получают строки `Branch` и
`Implementation head` из артефакта. Он имеет приоритет над веткой, случайно
упомянутой в отчёте Review/Verify или в вопросе. Это касается:

- Watch при создании потерянной следующей стадии;
- обычного перехода `Implement + Test → Review` и `Review → Verify`, включая
  выбор ветки для `review_gate` и auto-merge;
- `route_question`/`write_question`, автоматического ответа и
  `handle_answers` при повторном запуске этапа;
- возврата после непрошедшего Verify и конфликта merge.

Ветка, которую `review_gate` временно пересобирает для поставки, передаётся
только в контексте данного Review/Verify, как сейчас; она не заменяет артефакт
успешной реализации. Таким образом пустая рабочая ветка Review, helper/debug и
любой непроверенный service-branch не становятся источником продолжения.

При успешном `create_task` Watch добавит нормализованную созданную задачу в
текущий список `tasks` (как уже делает обычный handoff). В записи должны быть
как минимум title, repository_id, состояние `created` и время создания, чтобы
`live_or_done_at` увидел её в этом же цикле. Дедупликация отменённой/упавшей
стадии будет считать задачу той же работы на более позднем Review или Verify
живой уже в состояниях `created`, `queued`, `preparing` и `running`; тогда она
не создаёт ни INFRA retry, ни вопрос/возобновление `Implement + Test`.

Новых HTTP-маршрутов, таблиц и пользовательских API нет. Формат `works.json`
расширяется обратно-совместимым необязательным полем.

## План реализации

1. Добавить в `pilot/pilot.py` проверку и запись canonical implementation
   artifact: полная ветка, head, task id и время; очистить его при новом
   поколении работы.
2. Записывать артефакт для успешной `Implement + Test` до `decide()` и не
   заменять сохранённое значение пустой, несуществующей или служебной веткой.
3. Вынести выбор рабочей ветки в helper с приоритетом артефакта и применить его
   в Watch, обычном handoff, маршрутизации вопросов, resume, возврате Verify и
   auto-merge; контекстам добавить сохранённый head.
4. После Watch `create_task` дополнить текущий `tasks` нормализованной записью
   созданного Review/Verify, чтобы последующая отменённая задача того же цикла
   увидела более позднюю живую стадию.
5. Добавить сквозной регрессионный тест: успешный Implement сохраняет ветку и
   head; `AREA WAIT` удерживает переход; Watch создаёт Review с этой веткой;
   отменённый service retry того же цикла подавляется; Review/Verify и
   auto-answer/resume сохраняют тот же branch/head.
6. Добавить узкие тесты отказа: пустой/неопубликованный candidate и ветка
   служебной задачи не перезаписывают ранее сохранённый артефакт; новое
   поколение не наследует старый факт.

## Критерии приёмки

1. Успешная `Implement + Test` с опубликованным непустым diff сохраняет в
   `works.json` branch, полный head, id задачи и время; сохранённый branch/head
   присутствует в контексте созданного Review.
2. После `AREA WAIT` Watch создаёт потерянный Review по branch/head последней
   настоящей успешной реализации, а не по пустой ветке исполнителя Review.
3. Review, Verify, auto-answer и ручное/автоматическое resume используют тот
   же branch/head, пока новая успешная `Implement + Test` не подтвердила другой.
4. Пустой diff, отсутствующая ветка, нечитаемый head, service run или новое
   поколение не заменяют и не наследуют canonical implementation artifact.
5. Если Watch создал более поздний Review/Verify в текущем цикле, отменённый
   retry более ранней стадии не создаёт `Implement + Test`, даже если исходный
   снимок был загружен до Review.
6. Существующая защита от дублей, AREA WAIT и отправка контекстов остаются
   работоспособны для работ без нового поля `implementation_artifact`.

## План тестирования

В `pilot/test_pilot.py` расширить `PipelineWatchTests` проверкой, что Watch
передаёт сохранённые `Branch` и `Implementation head` в созданный Review и
добавляет его в текущий список задач. Добавить отдельный класс, например
`CanonicalImplementationBranchTests`, с подменёнными Factory/GitHub API и
временным `WORKS_PATH` для записи, очистки поколения, приоритетов и отказов.

Сквозной тест запускает `cycle()` с успешным Implement, решением `advance`,
искусственным `AREA WAIT`, следующим Watch-циклом и отменённой служебной
задачей. Он фиксирует ровно один Review, отсутствие повторного Implement и
непрерывность branch/head через Review, Verify и обработанный auto-answer.
Этот тест должен падать до реализации, потому что Watch не записывает branch в
context и не обновляет снимок после `create_task`.

Обязательные команды после реализации:

`python3 -m unittest -v pilot.test_pilot.PipelineWatchTests pilot.test_pilot.CanonicalImplementationBranchTests`

`python3 -m unittest -v pilot.test_pilot`

`git diff --check`

## Риски и решения

- Решение: `works.json` выбран вместо нового файла, так как уже является
  долговечной записью поколения работы; отдельное хранилище добавило бы вторую
  несогласуемую точку состояния.
- Решение: branch и head записываются только после проверки origin. Доверие
  одному тексту отчёта отвергнуто: это и позволило пустой служебной ветке стать
  следующей рабочей.
- Решение: результат `review_gate` не повышается до implementation artifact.
  Это сохраняет происхождение реализации; Review/Verify всё ещё получают
  пересобранную ветку через свой контекст. Если product требует считать такую
  пересборку новой canonical-реализацией, это отдельное изменение контракта.
- Риск: у уже начатой до релиза работы может не быть артефакта. Ограниченный
  fallback только к подтверждённой успешной Implement сохраняет совместимость,
  но не будет угадывать ветку из отменённой service task.
- Вне области: UI Work, worker/controlplane, схема API, существующие карточки
  `CARD-0069` и `CARD-0058`, а также изменение логики самого `review_gate`.
