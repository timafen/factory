# Спецификация: безопасная ежедневная уборка диска Factory

## Цель и влияние на владельца

Тестовые прогоны не должны снова занять десятки гигабайт и остановить конвейер.
Factory ежедневно освобождает устаревшие тестовые кэши, браузерные артефакты,
карантин и старые успешные выпуски, сохраняя активные работы и результаты,
которые ещё могут понадобиться владельцу. Первый проход только показывает точный
список кандидатов, а удаление происходит лишь при неизменном втором снимке.

Владелец получает предсказуемую политику: обычный кэш и Playwright старше трёх
дней удаляются, карантин хранится семь дней, а среди успешных выпусков остаются
две последние версии и цели ссылок `current`/`previous`. Ошибка API или
неизвестный путь активного worker останавливает широкую уборку, а не рискует
рабочим прогоном.

## Технический подход и реальные файлы

- `ops/factory-janitor.sh` расширить ежедневной фазой с неблокирующим `flock`,
  настраиваемыми корнями/сроками, ротацией собственного журнала и JSON-манифестом
  кандидатов. Корни обязаны быть абсолютными, не `/` и не symlink.
- Активность брать из `GET /api/v1/workers`, а фактический `data_directory` — из
  TOML, найденного через соответствующий systemd unit. Защищать всю рабочую
  область активного worker. При недоступном API или невозможном сопоставлении
  завершаться ненулевым кодом до отбора и удаления.
- Сканировать только непосредственных детей разрешённых корней. Не переходить по
  symlink. Playwright учитывать отдельной категорией, не дублируя через общий
  cache. Для выпусков удалять только каталоги с `.successful`, кроме двух самых
  свежих и фактических целей `current`/`previous`; неуспешные выпуски не трогать.
- Первый снимок атомарно записывать в
  `/var/lib/factory-janitor/cleanup-candidates.json` и логировать как `DRY-RUN`.
  Только полностью совпавший следующий снимок разрешает удаление; после успеха
  манифест удаляется. Изменение политики или состава кандидатов снова даёт dry-run.
- `ops/systemd/factory-janitor.service` запускать как root, потому что janitor
  управляет worker units и файлами разных владельцев, но оставить
  `ProtectSystem=strict`, `NoNewPrivileges=true` и ограничить `ReadWritePaths`
  рабочими данными, состоянием, журналом и lock-файлом.
- `ops/systemd/factory-janitor.timer` запускать oneshot через 15 минут после
  загрузки и затем раз в сутки с `Persistent=true`.
- `ops/test-factory-janitor.sh` расширить изолированными сценариями двухфазной
  уборки, retention выпусков, защиты активного пути, lock, отказа API,
  неизвестного worker и ограниченных прав service.

## Последовательный план

1. Добавить безопасные настройки корней, lock и построение карты worker → unit и
   `data_directory`, не меняя существующее освобождение retained worktree.
2. Получить снимок активных worker; при любой неопределённости завершить
   ежедневную фазу fail-closed.
3. Встроенным Python собрать детерминированный список кандидатов с категорией,
   путём, mtime, размером и сроком хранения; записать его атомарно.
4. На идентичном втором запуске повторно проверить каждый путь и удалить только
   разрешённые кандидаты, оставив аудит в журнале.
5. Добавить systemd service/timer с минимально необходимой областью записи.
6. Расширить целевой shell-тест всеми положительными и аварийными сценариями;
   полный набор проекта оставить единственному этапу Verify.

## Критерии приёмки

1. Первый запуск не удаляет старые cache, Playwright, quarantine или release,
   фиксирует каждого кандидата и сохраняет манифест; неизменный второй запуск
   удаляет их и завершается кодом 0.
2. Кэш моложе трёх дней, карантин моложе семи дней, рабочая область активного
   worker, неуспешный выпуск, две последние успешные версии и цели
   `current`/`previous` сохраняются.
3. Недоступный `/workers` или активный worker без достоверного `data_directory`
   завершают janitor ненулевым кодом до удаления любого ежедневного кандидата.
4. Параллельный запуск из-за занятого lock безопасно пропускается с кодом 0 и
   заметной записью в журнале.
5. Небезопасный корень, symlink-кандидат или кандидат, ставший защищённым между
   снимками, не удаляется; выполнение завершается ошибкой.
6. Существующая карантинизация retained worktree и подтверждение через API
   сохраняют прежнее поведение.
7. Timer запускает service ежедневно и догоняет пропущенный запуск после
   выключения; service имеет права управлять worker, но не произвольную запись
   по файловой системе.

## Тест-план

- `bash -n ops/factory-janitor.sh ops/test-factory-janitor.sh` проверяет синтаксис.
- `bash ops/test-factory-janitor.sh` в отдельном временном дереве и с локальным
  HTTP-сервером проверяет восемь сценариев: прежний retained cleanup, выбор
  offline worker, пропуск online worker, dry-run/cleanup, lock и API failure,
  неизвестный активный путь и права service.
- В регрессии создать старые и свежие cache/quarantine, Playwright, четыре
  успешных и один неуспешный release; после двух запусков проверить точный набор
  оставшихся путей.
- Отдельно оборвать тестовый API и убрать TOML-сопоставление активного worker;
  оба запуска обязаны вернуть ненулевой код и оставить кандидат на месте.
- На Verify один раз выполнить полный набор репозитория по принятому workflow.

## Риски и решения

- Ошибочное широкое удаление опаснее переполнения диска. Поэтому неизвестное
  состояние трактуется как запрет уборки, корни валидируются, symlink исключены,
  а удалению предшествуют два одинаковых снимка.
- `/workers` не сообщает путь worktree. Не угадывать его из имени: источник
  истины — `data_directory` сопоставленного worker TOML; отсутствие соответствия
  останавливает фазу.
- Размер каталога из `lstat` не равен освобождённым байтам. Поле `size` служит
  аудитной подсказкой, но критерий выбора основан на возрасте и категории;
  обещание точного подсчёта освобождённого места не входит в scope.
- Запуск от root нужен для systemd и владельцев файлов. Риск ограничивается
  hardening service и точным `ReadWritePaths`; запуск непривилегированным
  пользователем отклонён как неработоспособный.
- Два совпавших ежедневных запуска означают, что фактическое удаление может
  произойти на следующий день. Это намеренный обмен скорости на проверяемость;
  ручной немедленный destructive mode не добавляется.
