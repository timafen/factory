# Спецификация: параллельные финальные проверки используют разные браузерные порты

## Цель и влияние на пользователя

Две независимые финальные проверки смогут одновременно запустить браузерную
регрессию Factory. Сейчас обе пытаются занять `127.0.0.1:17437`: второй запуск
падает до проверки интерфейса, хотя его ветка и тестовые данные независимы.

После изменения каждый запуск `npm run test:browser` получает собственный
свободный loopback-порт, а Playwright, сервер Factory, worker-конфигурация и
fixture legacy poller используют один и тот же адрес. Параллельная проверка
станет достоверным сигналом о продукте, а не о случайном занятии порта.

## Технический подход

Минимальное изменение ограничено браузерной fixture в `web`:

- В `web/playwright.config.ts` ввести один экспортируемый адрес E2E-сервера,
  составленный из `127.0.0.1` и порта, переданного в окружении запуска. Если
  значение не задано, конфигурация выбирает свободный порт до старта `webServer`;
  значение валидируется как TCP-порт, чтобы не запускать fixture с разными или
  недопустимыми адресами.
- `baseURL` и URL health-check `webServer` будут производными от этого адреса.
  Команда `webServer.command` передаст выбранный порт дочернему `e2e/server.mjs`.
- В `web/e2e/server.mjs` заменить все три жёсткие ссылки на `17437` (listen,
  `worker.toml` и legacy `poller.toml`) адресом из переданного окружения. Сервер
  продолжит слушать только loopback; публичная конфигурация, API и production
  runtime не меняются.
- В `web/src/playwrightConfig.test.ts` добавить проверку: явно заданный порт
  даёт согласованные URL и command env, а два независимо созданных значения не
  совпадают и каждый пригоден для loopback TCP. Тест не будет запускать Chromium.

Выбор делается в Node-конфигурации до создания `webServer`, а не внутри
`server.mjs`: Playwright должен знать точный URL, по которому ждать health-check
и к которому направлять браузер. Отдельный внешний allocator, фиксированный набор
портов и выключение параллельности отклонены: они добавляют координацию между
worktree либо сохраняют коллизию при большем числе проверок.

## План реализации

1. Вынести в Playwright-конфигурацию создание и валидацию адреса E2E, включая
   override через переменную окружения для воспроизводимого локального запуска.
2. Подключить этот адрес к `baseURL`, `webServer.url` и окружению команды fixture.
3. Прочитать адрес в `e2e/server.mjs`, передать его `factory-server -listen` и
   записать его в обе временные TOML-конфигурации, которые обращаются к серверу.
4. Добавить unit-регрессию, фиксирующую единый адрес всех потребителей и разные
   порты для двух независимых конфигураций.
5. Выполнить целевой Vitest-тест и затем два одновременных `test:browser` в
   отдельных временных каталогах; оба процесса обязаны завершиться с кодом 0.

## Критерии приёмки

1. Один `npm run test:browser` сохраняет текущий сценарий: Playwright ждёт
   health-check, браузер получает рабочий `baseURL`, а реальный worker и legacy
   poller обращаются к тому же fixture server.
2. Два одновременных запуска `npm run test:browser` не используют общий TCP-порт
   и оба завершаются с кодом 0; в их выводе нет ошибки bind/address already in use.
3. Явно переданный валидный порт используется всеми потребителями одного запуска,
   что позволяет локально воспроизвести проблему и диагностику.
4. Некорректный порт из окружения завершает конфигурацию понятной ошибкой до
   запуска серверов; он не приводит к fallback на чужой фиксированный порт.
5. Изменение не затрагивает production listener, публичные HTTP API, базу данных,
   параметры sandbox-браузера или последовательный режим тестового сценария.

## План тестирования

- Добавить проверки helper-а адреса в `web/src/playwrightConfig.test.ts`: valid
  explicit port, invalid override и два различных автоматически выделенных порта.
- Целевая команда разработки:
  `cd web && npx vitest run src/playwrightConfig.test.ts --reporter=dot`.
- Проверка сути исправления на Verify: из двух отдельных временных рабочих
  каталогов одновременно выполнить `cd web && npm run test:browser`, дождаться
  обоих кодов завершения и проверить, что каждый равен 0. Вывод сохранить как
  артефакт проверки, не добавляя test-results в Git.
- После изменения конфигурации также выполнить `cd web && npm run typecheck`;
  полный набор проекта остаётся единственным запуском стадии Verify.

## Риски и решения

- Автоматический выбор свободного порта имеет обычную TOCTOU-гонку между поиском
  и bind. Риск практически устраняется независимым случайным ephemeral port и
  должен быть пойман обязательной параллельной browser-регрессией; сложный
  предварительно открытый socket нельзя передать Playwright и Go server без
  расширения scope.
- Переменная окружения должна называться отдельно для E2E (например,
  `FACTORY_E2E_PORT`) и не может менять production `factory-server`.
- Не менять `fullyParallel: false` и `workers: 1`: они защищают общий сценарий
  внутри одного E2E-прогона и не решают столкновение отдельных финальных работ.
- Не менять browser sandbox launcher: он отвечает за изоляцию Chromium, тогда как
  эта задача только про адрес тестового control plane.
- Человеческое утверждение до реализации не требуется, если scope остаётся в
  трёх перечисленных файлах и обязательная параллельная проверка проходит.
