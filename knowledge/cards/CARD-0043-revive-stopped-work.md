## Goal and user impact

На карточке работы, которую пилот пометил как остановленную владельцем или окончательно застрявшую, владелец видит кнопку «Оживить» и может продолжить именно этот конвейер, не переходя в настройки и не редактируя список `stopped_pipelines` вручную. После успешного действия карточка перестаёт обещать, что работа всё ещё на паузе; при ошибке причина остаётся видимой и пользователь получает понятное сообщение.

## Technical approach

Самое малое связное изменение — отдельная команда уровня работы, а не повтор последней Task через уже существующий `POST /api/v1/executions/{id}/retry`: Task retry допустим только для `failed`/`cancelled` execution и не снимает паузу конвейера.

- В `internal/controlplane/http.go` зарегистрировать `POST /api/v1/works/{work}/revive`.
- В `internal/controlplane/pilot_config_http.go` принять название работы из path, вызвать атомарное изменение конфигурации и вернуть актуальный статус либо структурированную ошибку.
- В `internal/controlplane/pilot_config.go` под существующей блокировкой чтения/записи удалить только точное название из `stopped_pipelines`. Идемпотентно разрешить `stuck`, которого в списке пауз нет: пилот уже умеет снова пробовать переход после сброса его состояния. Не давать клиенту пересылать всю конфигурацию и не допускать потери параллельных настроек.
- В `pilot/pilot.py` добавить безопасный для повторов сигнал возобновления: убрать для этой работы запись `give_up` из `pipeline_stalls.json`, чтобы следующий `pipeline_watch` снова получил полный лимит попыток и запустил следующий незавершённый этап. Контрольная плоскость не создаёт Task сама — выбор этапа, workflow, worker и branch остаётся у существующего `pipeline_watch`.
- В `web/src/api.ts` добавить типизированный вызов команды.
- В `web/src/Work.tsx` показывать «Оживить» только у групп со статусом `stopped_owner` или `stuck`; остановить всплытие клика карточки, блокировать повторный клик во время запроса, после успеха перечитать данные, а ошибку показать рядом с кнопкой.
- В `web/src/WorkHistory.test.tsx`, `internal/controlplane/pilot_config_test.go` и `pilot/test_pilot.py` закрепить видимость кнопки и сквозные гарантии снятия паузы/сброса исчерпанных попыток.

Новых таблиц и миграций нет. Формат `GET /api/v1/work-status` сохраняется; новая команда адресует работу URL-кодированным каноническим заголовком.

## Plan

1. Добавить атомарную серверную операцию revive и HTTP-маршрут с проверками неизвестной/пустой работы и повторного запроса.
2. На стороне пилота обработать сигнал, очистить только состояние выбранной работы и оставить запуск следующего этапа `pipeline_watch`.
3. Добавить вызов API и состояние мутации в карточку работы.
4. Показывать кнопку только для двух реально остановленных состояний; после ответа обновлять статусы, ошибки оставлять на карточке.
5. Добавить целевые backend, pilot и UI-тесты и выполнить обязательную команду.

## Acceptance criteria

1. Для `stopped_owner` карточка показывает «Оживить»; нажатие удаляет точное название только этой работы из `stopped_pipelines` и разрешает пилоту продолжить со следующего незавершённого этапа.
2. Для `stuck` кнопка сбрасывает исчерпанные попытки патруля этой работы; следующий цикл снова пытается продолжить конвейер, не начиная его с Разбора.
3. У живых, завершённых, архивных и просто failed/cancelled задач без остановленного конвейера кнопки нет.
4. Двойное нажатие не создаёт две команды; повтор запроса после уже успешного revive безопасен.
5. При ошибке API карточка остаётся остановленной, кнопка снова доступна, а рядом показано понятное сообщение.
6. Операция не меняет настройки и stall-состояния других работ и не создаёт Task в control plane напрямую.

## Risks and decisions

- Решение: отдельная команда работы предпочтительнее общего `PUT /settings/pilot`, потому что исключает lost update и не раскрывает UI всю конфигурацию ради удаления одного элемента.
- Решение: control plane только фиксирует намерение оживить; непосредственный переход делает `pipeline_watch`, чтобы не дублировать правила выбора следующей стадии и ветки.
- Риск: между ответом API и циклом пилота будет короткое состояние «возобновляется». UI должен показывать его нейтрально и перечитывать `/work-status`, а не заявлять, что этап уже запущен.
- Риск: заголовок работы является текущим идентификатором в `stopped_pipelines` и stall-файле. Ввод отдельного стабильного work ID — полезное, но отклонённое расширение области: оно требует изменения форматов и миграции данных.
- Человеческого решения до реализации не требуется; текст кнопки «Оживить» задан задачей.
