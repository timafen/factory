# CARD-0060 — Завершённая задача видна на экране Work

## HEAD

- Status: Specified — awaiting implementation.
- Branch: `factory/f182d387-c20-d5d17c5a-d01`.
- Scope: завершённая обычная задача без pipeline-вердикта должна остаться в активной группе «Сделано» на экране Work.
- Evidence: полный `just test-browser` дошёл до сценария `renders grouped work and saves the desktop Work view`: 4 сценария прошли, затем Playwright не нашёл `Prove the complete local workflow`; 13 последующих сценариев не запущены.
- Previous related card: `knowledge/cards/CARD-0057-reduced-pipeline-handoff-wait.md` зафиксировала этот внешний блокер, но не является карточкой этой самостоятельной работы.

## Goal and user impact

После успешного выполнения обычной задачи владелец видит её в группе «Сделано» на странице `/work`, не открывая «Архив». Сейчас `build` в `web/src/Work.tsx` считает работу принятой только при `verdict.final_pass === true`; у вручную делегированной завершённой задачи такого вердикта нет, поэтому она выглядит исторической. Это ломает живой сценарий, в котором задача `Prove the complete local workflow` успешно выполнилась, но исчезла из активной группы Work.

## Technical approach

Минимальное изменение — в `build` отличить конечную одиночную успешную задачу без pipeline-вердикта от архивной записи: если в группе нет активной задачи, нет возврата на доработку, задача не отменена и последняя попытка имеет `state === "succeeded"`, присвоить группе статус `done`. Существующее правило для pipeline-работ сохраняется: `final_pass === false` остаётся ошибочным этапом, а положительный финальный вердикт по-прежнему показывает «работа принята».

Изменяются только:

- `web/src/Work.tsx` — правило классификации успешно завершённой работы.
- `web/src/Work.test.ts` — unit-регрессия на одиночную `succeeded` задачу без вердикта и защита архивных отменённых/ошибочных задач.
- `web/e2e/control-plane.spec.ts` — существующий сценарий Work остаётся сквозным доказательством: созданная ранее реальная завершённая задача видна до раскрытия архива.

Данных, HTTP API, миграций и новых экранов не требуется. `GET /api/v1/tasks?limit=200` уже доставляет задачу в `App.tsx`; проблема возникает исключительно при классификации сгруппированного списка в браузере.

## Plan

1. В `build` выделить проверяемый факт успешного завершения последней задачи и добавить его к существующему условию `passed` для статуса `done`.
2. Добавить в `Work.test.ts` красный до изменения сценарий: одиночная задача `succeeded` без `verdicts` имеет `status.kind === "done"` и `sectionOf(group) === "done"`; сохранить проверки `cancelled`, `failed` и возвращённой на доработку работы в архиве.
3. Уточнить e2e-ожидание Work, чтобы оно проверяло заголовок задачи в разделе «Сделано» до клика по «Архив», затем выполнить целевой Vitest и этот Playwright-сценарий.

## Acceptance criteria

1. Обычная задача со статусом `succeeded` и без записи в `/api/v1/verdicts` отображается в разделе «Сделано» на `/work`.
2. Задача с `final_pass: false`, отменённая задача и последняя неуспешная попытка не становятся «Сделано».
3. Pipeline-работа с `final_pass: true` сохраняет подпись «работа принята».
4. Сквозной сценарий реального worker/worktree проходит: после успешного выполнения `Prove the complete local workflow` страница Work находит задачу до раскрытия архива.

## Test plan

- Новый/обновлённый unit: `cd web && npm test -- --run src/Work.test.ts`.
- Целевой Chromium: `cd web && npx playwright test e2e/control-plane.spec.ts --grep 'renders grouped work and saves the desktop Work view'`.
- На Verify, один раз для поставки: `just test-browser`.

## Risks and decisions

- Решение: успешная последняя задача без pipeline-вердикта — завершённая работа, а не архив. Это соответствует экранному контракту и реальному worker-сценарию.
- Не расширять scope до изменения пагинации или API: текущая задача уже создаётся и успешно видна на странице детали; наблюдаемая ошибка следует из ветки `passed` в `Work.tsx`.
- При необходимости различать вручную закрытые исторические задачи в будущем потребуется отдельный серверный признак; текущий контракт такого признака не содержит, поэтому это не часть исправления.
