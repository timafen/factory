# CARD-0057 — «Сделано недавно» только после финального этапа

- Status: Specification — согласована по содержанию, дополнена проверяемым контрактом.
- Branch: `factory/ea308d28-fca-7e8ab710-a41`.
- Implementation commit: предстоит на стадии Implement — промежуточный успешный этап перестанет считаться завершённой работой.
- What changes: успешный Triage и другие промежуточные этапы не попадают в
  «Сделано недавно»; результат появляется после успешного последнего этапа,

- Evidence target: отдельная регрессия `RecentDoneTest` воспроизводит успешный
  Triage `[1/5]` и подтверждает отсутствие работы в итоговом блоке.

## Goal and user impact

Владелец не должен видеть работу в блоке «Сделано недавно», пока конвейер
закончил только промежуточный Triage. Блок снова будет означать законченный
результат, а не успешную передачу между этапами, поэтому состояние работы не
будет создавать ложного ощущения поставки.

## Technical approach

Минимальное изменение остаётся в серверном формировании dashboard:

- в `pilot/pilot.py`, внутри `recent_done_block`, учитывать номер этапа и общее
  число этапов из уже принятого заголовка `[auto] [N/M Stage]`;
- успешную задачу включать только при `N == M`; промежуточный `succeeded`, в
  частности Triage `[1/5]`, пропускать;
- существующее отображение `failed`/`cancelled`, подтверждение merge по
  `MERGES_PATH`, доказательство из последней попытки и legacy-fallback не менять;
- в `pilot/test_pilot.py` добавить узкую регрессию рядом с `RecentDoneTest`.

Формат `recent_done` и компоненты `web/src/Overview.tsx` не меняются. Новых
полей данных, миграций и API нет. Проверка по `N/M`, а не по имени `Verify`,
сохраняет поддержку конвейеров с иным названием последнего этапа.

## Plan

1. Дополнить разбор pipeline-заголовка признаком последнего этапа, не меняя
   текущий owner-facing title и stage.
2. Отфильтровать успешные промежуточные задачи до формирования `recent_done`.
3. Добавить тест: успешный Triage `[1/5]` отсутствует, успешный финал `[5/5]`
   остаётся, а промежуточный провал по-прежнему виден честно.
4. Запустить целевой тестовый метод и затем весь класс `RecentDoneTest`.

## Acceptance criteria

1. При единственной задаче `[auto] [1/5 Triage] Работа` в состоянии `succeeded`
   «Работа» отсутствует в `recent_done`.
2. Успешная задача с номером последнего этапа (`N == M`) остаётся кандидатом в
   `recent_done` и сохраняет текущие статусы `merged`/`passed`.
3. `failed` или `cancelled` промежуточного этапа продолжает показываться как
   неудачный результат с пояснением, что работа не влита в `main`.
4. Ответ dashboard и UI-контракт `RecentDone` не меняются.

## Risks and decisions

- Решение: финальность определяется структурными числами `N/M`, а не строкой
  `Verify`; это уменьшает связанность с названиями workflow.
- Решение: не скрывать промежуточные провалы — они уже явно помечены как
  невлитые и нужны владельцу как результат остановившегося конвейера.
- Риск: некорректный заголовок без `N/M` и раньше не участвовал в
  `recent_done`, поэтому отдельный fallback не добавляется.
- Отклонено как scope creep: изменения UI, API-схемы, merge-журнала и общей
  модели жизненного цикла работ.
- Дополнительного решения человека перед Implement не требуется.
